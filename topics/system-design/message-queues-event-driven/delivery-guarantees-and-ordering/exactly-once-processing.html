Exactly-Once Processing

🎯 The Hook & ELI5

A librarian stamps a request card and writes the matching loan in one indivisible notebook update. If the update fails, neither mark remains; if it succeeds, repeating the same card finds the existing loan. But that notebook cannot magically control a courier outside the library. The promise works only inside the boundary actually updated together.

Exactly-once processing describes a defined observable result for a defined input identity and failure model, not the absence of retries. Inputs may be delivered or executed more than once internally while one committed logical effect becomes visible. Specify input identity, state, output, progress, isolation, retention and recovery before using the term.

Two useful examples have different boundaries: a local database transaction can coordinate a deduplication marker and a ledger change; a configured Kafka transaction can coordinate Kafka output records and consumed positions. Neither automatically commits an unrelated payment provider. Producer deduplication alone addresses a still narrower repeated-publication problem.

🗺️ High-Level Big Picture

The two local writes share one real atomic boundary. The external arrow deliberately crosses it; a stronger claim needs a separate verified protocol at that provider.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the actual actor, communication, acknowledgment and recovery boundary.

1. Write down the observable promise

For each stable award ID, the local loyalty ledger should contain one credit after successful recovery, assuming the database remains durable and valid work is retried. Separate safety, no extra committed credit, from liveness, eventually obtaining the credit. Permanent invalid input or permanent outage can prevent completion without violating the safety property.

Define whether repeated identity with different content is an error and how long identity remains meaningful. A transport-generated attempt ID is usually insufficient when upstream retries create new messages for the same award. Exactly once for one Kafka offset is not automatically exactly once for one business order.

2. Coordinate local identity and effect atomically

This executable model targets Python 3.10 with its bundled SQLite library and an in-memory database. It demonstrates rollback and duplicate suppression in one local transaction only. It is not a distributed benchmark or proof of production concurrent behavior; error handling for real database contention requires the chosen engine’s contract.

import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE seen (intent TEXT PRIMARY KEY);
CREATE TABLE ledger (intent TEXT PRIMARY KEY, points INTEGER NOT NULL);
""")

def apply(intent, points, fail=False):
    with db:
        prior = db.execute(
            "SELECT points FROM ledger WHERE intent = ?", (intent,)
        ).fetchone()
        if prior is not None:
            if prior[0] != points:
                raise ValueError("conflicting intent payload")
            return "duplicate"
        db.execute("INSERT INTO seen VALUES (?)", (intent,))
        db.execute("INSERT INTO ledger VALUES (?, ?)", (intent, points))
        if fail:
            raise RuntimeError("simulated crash before commit")
    return "applied"

try:
    apply("award-1", 10, fail=True)
except RuntimeError:
    pass
assert db.execute("SELECT count(*) FROM seen").fetchone()[0] == 0
assert db.execute("SELECT count(*) FROM ledger").fetchone()[0] == 0
assert apply("award-1", 10) == "applied"
assert apply("award-1", 10) == "duplicate"
assert db.execute("SELECT sum(points) FROM ledger").fetchone()[0] == 10
try:
    apply("award-1", 11)
except ValueError:
    pass
else:
    raise AssertionError("conflicting payload accepted")
print("local transaction model: passed")

The unique keys are the final database constraint, not the preliminary lookup. A crash after commit but before acknowledgment can repeat delivery; the retained identity/outcome prevents another local credit. A crash before commit leaves neither marker nor credit in this model.

3. Scope Kafka transactions precisely

The Kafka example is explicitly Kafka 4.1 with Java 4.1.2 APIs. A supported consume-transform-produce transaction can include produced Kafka records and consumed offsets, while downstream consumers use read_committed to hide aborted transactional results. Configure transactional identity, producer initialization/fencing and group-offset coordination according to those APIs.

Idempotent production protects defined retry cases within producer semantics; it does not alone atomically commit consumed positions, local SQL and remote effects. Kafka Streams has its own documented processing-mode contract and state/changelog recovery obligations. Name the actual configured mode instead of assuming every stream application provides it.

4. Trace failure and recovery on both sides of commit

Before a transaction commits, recovery can retry while aborted/uncommitted outputs remain invisible under the promised isolation. After commit but before the worker sees success, recovery must recognize committed progress/effects instead of independently repeating the business operation. An unknown response requires protocol resolution, not guessing.

Transactions need limits and ownership: a long-running batch can exceed timeouts, a stale producer may be fenced and readers may wait behind open transactions. Observe aborts, retries, age and lag. The local model tests rollback/duplicates; no Kafka cluster or Java client is executed in this lesson.

5. Cross external boundaries without exaggerating the promise

A database outbox atomically records a state change and an intent for later delivery. The relay can repeat that intent, so a payment/email endpoint still needs a supported idempotency identity, queryable outcome or explicit reconciliation. Recording sent=true locally before a remote call can lose work; recording it afterward can duplicate it.

If a provider cannot participate in a shared transaction and cannot deduplicate or reveal an uncertain result, universal exactly-once external effects are not established. Use an explicit pending/manual policy or redesign the business interaction. A saga organizes compensating steps, and those steps have their own failure windows.

6. Keep the guarantee valid through retention and replay

Document the deduplication horizon, event identity migration, backup consistency and manual redrive rules. Expiring the sole protection while old input can return changes the guarantee. A projection rebuild should not accidentally invoke live external effects using a fresh identity namespace.

Test duplicate identity with matching/conflicting payload, crash before/after commit, concurrent contenders under the real store, expired identity and external timeout. Compare effects and progress, not only delivered record counts. A correct claim names exactly which of those cases are covered and which require another protocol.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Idempotent producer still double-charges

Symptom: One business request becomes repeated external effects.

Root Cause: Publication retry protection was mistaken for sink atomicity.

Fix/Prevention: Protect the actual business identity and provider outcome boundary.

Marker suppresses missing effect

Symptom: The system reports done but no ledger entry exists.

Root Cause: Deduplication and effect used different commits.

Fix/Prevention: Use a supported atomic transaction and verify recovery states.

Historical replay escapes protection

Symptom: Old input is treated as a fresh operation.

Root Cause: Identity expired or replay generated a new business key.

Fix/Prevention: Align retention and isolate replay/live-effect ownership.

Name the boundary and retain the identity that makes recovery safe. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Does exactly-once processing mean code never runs twice?

No. Retries can occur internally while the defined committed result becomes visible once.

What must an exactly-once claim name?

Input identity, state/output/progress atomicity, isolation, failure assumptions, retention and recovery/liveness conditions.

What does a Kafka transaction not automatically include?

An unrelated SQL database, arbitrary HTTP endpoint or external provider effect.

Does an outbox alone make a remote effect exactly once?

No. It preserves delivery intent locally, but relay retries still need a supported remote identity/outcome contract.

Tricky & Most-Asked Interview Scenarios

A worker dies after a SQL credit but before acknowledgment. What makes recovery safe?

The Scenario & Constraint

The marker and credit can reside in one transactional database. What will you do and why?

The Direct Answer & Architectural Decision

Commit the scoped unique intent and credit atomically, retain the outcome, then acknowledge. Redelivery verifies the existing identity/content rather than issuing another credit.

Key Trade-Offs & Follow-Up Traps

Transactions and identity storage cost resources. Separate marker/effect stores require a different protocol; a preliminary lookup cannot prevent a concurrent duplicate.

A Kafka transform needs one visible output per input position. What configuration boundary matters?

The Scenario & Constraint

Outputs and consumed positions are both Kafka-managed and aborted results must not be visible. What will you do and why?

The Direct Answer & Architectural Decision

Use the supported 4.1 transactional consume-transform-produce API or documented Streams processing mode, coordinate consumed offsets in the transaction and configure downstream read_committed behavior.

Key Trade-Offs & Follow-Up Traps

Transactions add abort/timeout/ownership overhead. Producer idempotence alone does not coordinate input progress, and external sinks remain outside this boundary.

The broker claims exactly-once but a card charge times out. What do you trust?

The Scenario & Constraint

The provider is outside the broker transaction and may have accepted the charge. What will you do and why?

The Direct Answer & Architectural Decision

Keep the intent pending, reuse a supported provider identity, discover/reconcile its outcome and retry under the actual provider contract.

Key Trade-Offs & Follow-Up Traps

Without deduplication/discovery, automatic certainty is unavailable. A saga can define compensation but does not retroactively make an unknown charge atomic with a broker commit.

A producer sends one order twice under different message IDs. Is offset-level safety enough?

The Scenario & Constraint

Both records are valid transport inputs but represent one business action. What will you do and why?

The Direct Answer & Architectural Decision

Define stable business-intent identity upstream and enforce it at the effect boundary, with conflict checks so different legitimate actions remain distinct.

Key Trade-Offs & Follow-Up Traps

Identity coordination and retention add cost. One effect per input offset is a narrower promise and can correctly yield two effects for these two records.

A six-month replay exceeds stored deduplication history. How do you protect effects?

The Scenario & Constraint

Only one month of identity records remains and old work can be redriven. What will you do and why?

The Direct Answer & Architectural Decision

Extend durable protection or enforce an authoritative invariant for that horizon, and route historical reconstruction away from live-effect execution until reconciled.

Key Trade-Offs & Follow-Up Traps

Longer retention costs resources. Explicitly limiting supported replay is possible, but it changes the recovery promise and must be agreed before deleting protection.

Long transformations keep Kafka transactions open and readers lag. What changes?

The Scenario & Constraint

The work includes slow remote calls and frequently exceeds the configured transaction budget. What will you do and why?

The Direct Answer & Architectural Decision

Measure the open-transaction/timeout path, bound transaction work and separate remote workflows from the Kafka atomic boundary using durable intent and independent outcome recovery.

Key Trade-Offs & Follow-Up Traps

Smaller batches add overhead; tuning timeouts can trade recovery delay for longer work but does not bring a remote provider into the transaction.
