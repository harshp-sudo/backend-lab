CQRS

🎯 The Hook & ELI5

A restaurant takes orders through a waiter and shows available dishes on a menu board. The waiter checks whether an order is allowed; the board helps people read quickly. They can work from the same kitchen notebook. If someone updates a separate board later, a newly sold-out dish might briefly remain visible.

Command Query Responsibility Segregation (CQRS) separates the responsibility for changing state from the responsibility for reading it. A command validates an intention and changes the authoritative model; a query returns a view without causing a business change. Different logical models can share a physical database. Separate databases, asynchronous messages and event sourcing are possible additions rather than the definition.

Imagine booking a concert seat while thousands of readers browse availability. The booking command must enforce the no-double-booking invariant; the browsing view can be optimized for search and tolerate explicitly bounded staleness. The design earns its complexity when those needs diverge enough to justify synchronization, failure recovery and honest user-facing completion states.

This diagram chooses an asynchronous separate-view variant. A simpler CQRS implementation can keep both responsibilities in one transactional database and avoid this synchronization boundary.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the actual actor, communication, acknowledgment and recovery boundary.

1. Begin with the invariant and two responsibilities

The write model owns whether seat A12 can be reserved. It must reject an invalid command using supported transactional or conditional concurrency control; a stale search result is not authorization to book. The read model answers availability queries using a representation convenient for readers.

Separate code paths and models where that clarifies intent. Do not add a broker or second database automatically. If one transactional model satisfies both needs with acceptable performance and clarity, ordinary CRUD or a modest logical separation may be the better design.

2. Choose synchronous or asynchronous synchronization

A shared-database implementation can update required state and views under a supported local transaction. A separate asynchronous projection decouples read storage and load but introduces lag and a delivery/recovery contract. State which variant the service actually uses.

For a committed write that must later be projected, atomically record the change and its delivery intent using a supported outbox/change-feed mechanism. Publishing after a database commit without a recoverable bridge can lose the update during a crash; publishing before commit can advertise a change that never became true.

3. Make projection progress duplicate-safe and observable

A projector transforms a change into a read-model update, then advances progress according to its durability boundary. Duplicate delivery or a crash after an update must not corrupt counts or apply the same reservation twice. Use stable identity, conditional versions or transactional progress/effect handling appropriate to the store.

Track last applied version/checkpoint, oldest unprocessed age and reconciliation mismatches. A healthy queue connection does not prove the view is current. If an event cannot be applied, isolate and diagnose it while exposing the affected view’s freshness rather than silently declaring success.

4. Give read-your-writes a concrete contract

A successful reservation response can return an authoritative result and a version token. A subsequent read may wait until the projection has reached that token within a bounded deadline, return an explicit pending state, or use a narrow authoritative read when appropriate. Choose the option the product can support.

A fixed sleep is not proof of projection visibility. A version token must identify the relevant stream/scope; independent partitions cannot be compared as one universal integer without a defined ordering scheme. Do not route all browsing to the write store merely to hide a small subset of consistency-sensitive interactions.

5. Rebuild a view without losing live changes

Create a new projection generation from an authoritative snapshot/history, capture its position consistently and catch up changes before switching queries. Verify counts, invariants and freshness. Keep the old view available until the replacement meets the cutover contract.

Not every CQRS system retains events for full replay. If the source only has current rows, plan a consistent snapshot plus change capture or another supported reconciliation path. A rebuilt view cannot recover history that no component retained. State the source and handoff explicitly.

6. Scope complexity to the demanding domain

Measure command contention, query cost, lag and operational burden. Introduce specialized read models for a justified workload rather than applying CQRS to every administrative screen. Maintain access control and privacy rules on derived views; authorization is not inherited automatically from the write API.

These are architectural traces verified against the named patterns, not a deployed database or broker benchmark. Test the chosen implementation’s crash points and cutover behavior before making strong consistency/availability claims. A separate model is useful only if its promised behavior is understandable to its users and operators.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Seat shown available is double-booked

Symptom: Two commands trust the browsing projection.

Root Cause: The read view was treated as the concurrency authority.

Fix/Prevention: Enforce booking invariants against authoritative state on every command.

Committed bookings disappear from search

Symptom: A worker crash lost the only publication.

Root Cause: Database change and message handoff were unrelated writes.

Fix/Prevention: Use a supported atomic delivery-intent bridge and reconciliation.

Refresh still shows old data

Symptom: A fixed delay expired before a slow projector caught up.

Root Cause: Time elapsed was mistaken for causal visibility.

Fix/Prevention: Use a scoped version/freshness contract with bounded waiting or explicit pending state.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Separate decisions that change state from views that help people read, then choose only the synchronization boundary the workload warrants. Make authority, lag, read-your-writes and recovery visible. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Must CQRS use two databases?

No. It separates command and query responsibilities/models; physical separation is optional.

Must CQRS use event sourcing?

No. Authoritative current rows and projection synchronization can support CQRS without authoritative event history.

Which model decides whether a reservation is valid?

The authoritative command/write boundary with real concurrency protection, not a potentially stale browsing view.

How can the caller know its write is visible?

Use a defined authoritative response, scoped version token and freshness check, bounded wait or explicit pending/fallback contract.

Tricky & Most-Asked Interview Scenarios

The read model says a sold seat is free. Can booking still be safe?

The Scenario & Constraint

Browsing may lag by seconds but double-booking is forbidden. What will you do and why?

The Direct Answer & Architectural Decision

Validate and commit the reservation against authoritative state with atomic concurrency control, return rejection if already reserved, and expose browsing freshness honestly.

Key Trade-Offs & Follow-Up Traps

The user may see a failed booking after a stale offer. Synchronous reads reduce that surprise at greater coupling/cost; they still do not replace concurrency control on the command.

A customer refreshes after booking and sees no reservation. What do you return?

The Scenario & Constraint

Reservation commit succeeded but the asynchronous projection is behind; the response budget is finite. What will you do and why?

The Direct Answer & Architectural Decision

Return the authoritative booking result/version, wait for a bounded scoped freshness check on subsequent reads, then show pending or use a justified narrow authoritative fallback.

Key Trade-Offs & Follow-Up Traps

Waiting adds latency and fallback adds write-store load. A fixed sleep or global offset guess cannot establish that this customer’s update is visible.

A database commit succeeds just before the process dies. How does the view recover?

The Scenario & Constraint

The projection relies on a message that the process had not yet published. What will you do and why?

The Direct Answer & Architectural Decision

Record the state change and delivery intent atomically using the chosen database’s supported outbox/change-feed pattern; relay and apply updates with duplicate-safe progress and reconciliation.

Key Trade-Offs & Follow-Up Traps

The relay adds operating work and duplicates remain possible. A shared local transactional view is simpler when independent read storage is unnecessary.

A redelivered reservation increases occupancy twice. How do you fix the projection?

The Scenario & Constraint

The worker committed its update before losing the progress acknowledgment. What will you do and why?

The Direct Answer & Architectural Decision

Use stable event identity or a correct per-entity version rule and atomically coordinate projection effect/progress where supported. Repair/rebuild corrupted counts from authoritative data.

Key Trade-Offs & Follow-Up Traps

Deduplication requires retention/state and version skipping can hide missing events. Recomputing a view is an alternative only when authoritative reconstruction input actually exists.

A new search schema needs a rebuild without an outage. How do you cut over?

The Scenario & Constraint

The old view must serve traffic while new reservations continue arriving. What will you do and why?

The Direct Answer & Architectural Decision

Build a new generation from a consistent authoritative snapshot/history and matching change position, catch up, verify freshness/content, then switch readers with rollback ownership.

Key Trade-Offs & Follow-Up Traps

Parallel storage and catch-up consume capacity. If no replay history exists, use a supported snapshot/change-capture boundary rather than assuming CQRS provides an event log.

Should an internal ten-user CRUD tool get separate read infrastructure?

The Scenario & Constraint

No divergent performance or history requirement exists and the team has limited operational capacity. What will you do and why?

The Direct Answer & Architectural Decision

Keep a simple transactional design, optionally separate command/query code for clarity, and measure a concrete bottleneck before introducing asynchronous stores.

Key Trade-Offs & Follow-Up Traps

Future scaling can require redesign. Separate storage is justified when workload needs outweigh lag/recovery cost, not by the pattern’s popularity.
