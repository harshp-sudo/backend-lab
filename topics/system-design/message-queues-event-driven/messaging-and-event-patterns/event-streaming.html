Event Streaming

🎯 The Hook & ELI5

A weather station keeps a numbered recording of observations. A forecaster and a historian can listen at different speeds and return to earlier entries while the recording survives. Listening later does not change when the rain actually fell, and the recording does not make two distant stations share one perfect clock.

Event streaming treats events as continuing sequences that can feed independent computations over time. In a retained-log example, readers track positions and can replay available records. Stateful processing adds checkpoints, joins/windows and recovery boundaries beyond simply receiving messages.

Use regional sensor observations to build a live dashboard and an hourly aggregate. This lesson uses Kafka 4.1/Kafka Streams concepts where a concrete platform is needed, while marking event-time/completeness policy as an explicit processing contract. A streaming HTTP connection such as SSE is a transport surface; it does not itself supply retained history, replay positions or transactional projections.

🗺️ High-Level Big Picture

Retention supplies available input history; positions and processing state describe each computation. The meaning of an hourly result depends on timestamps, late data and its completion policy.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the actual actor, communication, acknowledgment and recovery boundary.

1. Define the event and stream boundary

A sensor record should identify the source, observation, timestamp semantics and stable event identity where repeats matter. Event time describes when the observed occurrence happened under the source’s clock/definition; ingestion and processing time describe later stages. None should be silently substituted for the others.

Choose a partition/key model that preserves the needed local order and scales the workload. Distinct sensors can have concurrent observations without one global total order. The stream’s schema/units and correction events must remain interpretable through the required replay lifetime.

2. Separate retained input from processing progress

A retained log can serve a live dashboard, aggregate and new application from independent positions. One consumer advancing does not necessarily delete records. Retention/compaction policy, however, limits what a future reader can reconstruct.

State whether history is complete, compacted by key, sampled or expired. A compacted latest-state stream can be useful for bootstrap but may not preserve every historical observation needed for an hourly recomputation. Detect position gaps rather than silently claiming a full aggregate from incomplete input.

3. Give state and checkpoints a joint recovery contract

An aggregate combines inputs into state and may publish output. If state updates and recorded progress drift apart during a crash, restart can skip required input or double-apply it. Use the chosen engine’s supported checkpoint/transaction/state restoration model, or an explicitly atomic/deduplicating sink design.

A saved process memory object is not durable state recovery. A transaction within Kafka has a specific included-state/output/progress scope; an unrelated dashboard database/provider may require its own cooperation. The Exactly-Once Processing lesson names those boundaries in detail.

4. Choose windows and late-event behavior

Define what one hour means, which timestamp drives it, and how late/out-of-order observations are treated. A processing framework’s progress/watermark/stream-time mechanism is an estimate or defined policy surface, not proof every possible source has delivered everything. Verify the actual selected engine’s terminology and behavior.

The dashboard may revise an earlier count, publish a correction, hold a result provisional or discard data outside a documented lateness bound. Each choice affects state retention, user expectations and recovery. Clock skew or a silent partition can make a naive “time has passed” completeness claim wrong.

5. Replay without confusing reconstruction and new effects

A bug fix or new view may need historical replay into a separate projection generation. Isolate its state/progress and bound read/write load so it does not starve the live path. Validate output before switching readers to the rebuilt generation.

Keep materialization distinct from irreversible notifications or commands. Replaying a sensor alert history should not automatically send every historical alarm to users. Use explicit replay/effect policy and stable identities, and preserve original event meaning rather than querying today’s context and pretending it was historical truth.

6. Operate end-to-end lag and recovery

Measure event age at useful output as well as partition position lag; variable traffic and record sizes make offset counts alone incomplete. Track state restoration time, late-data rates, checkpoint failures, retention headroom and downstream capacity. A faster input reader can still leave the view stale if its sink is blocked.

Test producer delay/skew, source silence, out-of-order delivery, crash around state/progress updates, restart from retained history and history expiry. The diagrams are explanatory; no Kafka Streams application or external sensor deployment is executed here.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Old events enter the wrong hour

Symptom: Delayed observations are counted by arrival time unexpectedly.

Root Cause: Event-time and processing-time semantics were not defined.

Fix/Prevention: Choose timestamps/window/late-data policy explicitly and test delayed input.

Replay doubles the aggregate

Symptom: State survived but progress restarted earlier without duplicate protection.

Root Cause: State and recovery position were not coordinated.

Fix/Prevention: Use the supported state/checkpoint boundary or a verified atomic sink protocol.

History cannot rebuild the promise

Symptom: Required observations expired or were compacted away.

Root Cause: Retention was chosen separately from reconstruction needs.

Fix/Prevention: Set a supported history/bootstrap plan and detect gaps before publishing completeness.

🧠 Active Recall & Mastery Check

Summarize this in your own words: A streaming result needs a clear input history, time/late-data meaning, coordinated state/progress recovery and a safe boundary between replay and new effects. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

How do event time and processing time differ?

They describe the occurrence under its source semantics and the time computation handles it respectively; delay/skew can separate them.

Does replay mean unlimited permanent history?

No. Available history depends on retention, compaction and the source/rebuild contract.

Why coordinate state with progress?

A crash between them can skip input or repeat an effect on restart.

Does an SSE connection alone provide a replayable event platform?

No. It transports updates; durable history, positions, state and replay need separate mechanisms.

Tricky & Most-Asked Interview Scenarios

Yesterday’s observation arrives today. Which hour owns it?

The Scenario & Constraint

The aggregate is intended to represent observation time, not arrival time. What will you do and why?

The Direct Answer & Architectural Decision

Use the defined source event-time semantics and an explicit late-data/correction policy, checking clock quality and supported state retention before revising historical output.

Key Trade-Offs & Follow-Up Traps

Late corrections need retained state or recomputation. Dropping late data simplifies operations but changes the result contract and must be disclosed.

The count increments but progress does not commit. What must recovery do?

The Scenario & Constraint

Restart can reread the same observation and add it again. What will you do and why?

The Direct Answer & Architectural Decision

Use the engine’s supported coordinated state/progress/output mechanism or a sink-local atomic identity/state design, then test crashes on both sides of the commit.

Key Trade-Offs & Follow-Up Traps

Transactions/checkpoints cost resources and have limited scope. A broker acknowledgment by itself does not establish that an external aggregate was updated exactly once.

A rebuild overwhelms the live dashboard sink. What changes?

The Scenario & Constraint

Historical and live processing share the same resources with no admission policy. What will you do and why?

The Direct Answer & Architectural Decision

Separate rebuild state/generation, bound replay read/write concurrency and reserve live capacity; validate a catch-up/handoff before switching the view.

Key Trade-Offs & Follow-Up Traps

Rebuild takes longer and temporary duplicate storage costs money. Increasing input consumption alone can worsen sink saturation.

A new annual view needs events older than retention. What can you promise?

The Scenario & Constraint

The current stream no longer contains the full required input. What will you do and why?

The Direct Answer & Architectural Decision

Find a supported archive/snapshot/source-of-truth bootstrap with compatible semantics, or state the missing interval and revise completeness honestly.

Key Trade-Offs & Follow-Up Traps

Archival and bootstrap add costs. Resetting to latest is suitable for a future-only view but does not reconstruct the requested year.

A partition is silent. Is the hour complete?

The Scenario & Constraint

Other sources have advanced, but this source may be delayed rather than finished. What will you do and why?

The Direct Answer & Architectural Decision

Apply an explicit progress/idle-source/lateness policy matched to the chosen engine and product, marking provisional output or correcting it when late facts arrive.

Key Trade-Offs & Follow-Up Traps

Waiting improves completeness under assumptions but increases latency/state. Treating silence as proof can silently discard valid late observations.

A replay sends thousands of historical alarms. How do you prevent it?

The Scenario & Constraint

A projection rebuild reused an effectful live alert handler. What will you do and why?

The Direct Answer & Architectural Decision

Separate deterministic reconstruction from new external effects, use an explicit replay mode/output generation and stable intent where legitimate delayed effects must be reconciled.

Key Trade-Offs & Follow-Up Traps

Separate paths require compatibility tests. Disabling every effect blindly can also skip genuinely pending live work, so define the replay boundary and cutover.
