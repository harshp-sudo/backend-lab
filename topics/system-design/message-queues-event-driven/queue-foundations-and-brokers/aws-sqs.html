AWS SQS

🎯 The Hook & ELI5

A managed ticket desk keeps work slips for your team. Picking up a slip hides it for a while, but does not remove it. If you disappear, the slip can become available again. You must return the correct receipt after completing the work, and a tidy ticket desk still cannot prove an outside payment happened only once.

Amazon SQS is a managed queue service with different Standard and FIFO contracts. This lesson uses the official service/API documentation checked on 2026-11-17, not an assumed SDK wrapper or universal default. The running example is a background fulfillment task whose durable business intent is separate from a receive attempt.

Standard/FIFO choice, message-group identity, producer deduplication, visibility, deletion, retention and redrive all affect behavior. Managed infrastructure removes some broker operations but leaves application correctness, configuration, observability and recovery ownership with the application team. No AWS queue or billable resource is created by this lesson.

🗺️ High-Level Big Picture

Visibility changes delivery eligibility; deletion uses a receipt handle from receiving. Neither step atomically includes an arbitrary business database or provider.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the actual actor, communication, acknowledgment and recovery boundary.

1. Choose Standard or FIFO from the operation contract

Use the verified Standard or FIFO semantics required by the workload. Standard is not a strict per-business-key ordered application workflow. FIFO introduces ordering/deduplication rules with message groups and producer configuration that must be understood in their documented scope. Do not turn these into universal speed or price rankings.

For independent fulfillment tasks, strict cross-task order may be unnecessary. For updates to one shipment, choose the required group/sequence policy and define how the application processes returned batches. A service delivery-order promise does not automatically serialize asynchronous effects inside your worker.

2. Preserve business intent and publication outcomes

Give a task a stable identity independent of receipt handles. If a send times out, distinguish retrying the same intended task from creating another one. FIFO SendMessage deduplication has a documented five-minute interval and identity/body rules; it is not an unlimited business deduplication ledger.

If a database change and send must agree, retain local publication intent under a supported transaction/outbox. A managed send call does not atomically join an arbitrary application database. Keep accepted task status and completed fulfillment status separate.

3. Receive with a processing/visibility plan

ReceiveMessage returns the message and a receipt handle while the message becomes temporarily invisible under the service rules. Choose a visibility plan based on real processing duration, failure recovery and supported extension behavior. If work outlasts visibility, another attempt can become eligible while the original process still runs.

Visibility is not a correctness lock over your external resource. Long timeouts can delay retry after a failed worker; short ones can increase concurrent duplicates. Bound in-flight work and handle renewal uncertainty explicitly rather than assuming receiving transferred permanent exclusive ownership.

4. Delete with the correct receipt after the effect boundary

DeleteMessage uses the current applicable receipt handle, not the producer MessageId. The API documentation warns that an older handle can yield a successful request without deleting the message, and Standard queues retain rare redelivery caveats even after deletion.

Keep the consumer’s effect duplicate-safe or reconcilable using business identity. A crash after effect commit but before deletion is a normal failure window. Deleting first avoids that window by accepting lost unfinished work instead; it does not meet the same fulfillment contract.

5. Inspect batch results and group concurrency

A batch request can return overall HTTP success with per-entry failures. Track each entry’s success, failure and uncertain outcome rather than marking the whole list sent. Retrying already successful entries without the appropriate identity policy can create extra work.

For FIFO, respect per-group delivery/processing constraints and separate unrelated groups when their business order allows it. A hot group is still an ordered path; more consumers cannot safely parallelize a single invariant merely by running the same message handler concurrently. Different groups and consumer capacity still share downstream limits.

6. Operate retention, dead letters and redrive

Choose retention and retry/redrive policy from the task’s useful life, diagnosis time and recovery capacity. Monitor age, available/in-flight work, receive/delete errors, completion and dead-letter growth. DLQ movement is failure routing, not proof the business operation was undone or never partly executed.

The documented Standard and FIFO dead-letter retention timestamp behavior differs, and moving a blocking FIFO item aside can change the intended operation order. Repair the cause, reconcile existing effects and redrive within a measured capacity budget. Service quotas and permissions should be checked for the real deployment; no numerical sizing promise is inferred from these examples.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

MessageId used for delete

Symptom: Tasks reappear despite a supposedly successful completion handler.

Root Cause: Business/message identity and receive receipt were confused.

Fix/Prevention: Track the receipt for transport deletion and stable intent for effect reconciliation.

FIFO treated as unlimited exactly once

Symptom: A replay repeats an external action after the deduplication window.

Root Cause: Send deduplication was mistaken for permanent sink effect atomicity.

Fix/Prevention: Scope the promise and retain the effect/progress identity where the action occurs.

Batch success hides failures

Symptom: Some fulfillment commands never arrive.

Root Cause: The application checked only the HTTP status.

Fix/Prevention: Inspect and reconcile each batch entry under its own identity/outcome.

Summarize this in your own words: Treat SQS send, receive/visibility, effect commit and delete as separate boundaries; choose the queue mode and recovery policy without extending its guarantee to unrelated effects. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

What does visibility timeout change?

It changes when a message can be delivered again under the queue contract; it is not deletion or an external-resource lock.

Which identity does DeleteMessage use?

A receive receipt handle under the API rules, distinct from MessageId or the business intent.

What is the scope of FIFO send deduplication here?

The documented five-minute send deduplication interval and configured identity rules, not perpetual exactly-once business effects.

Does HTTP success mean every batch entry succeeded?

No. Inspect per-entry successes/failures and uncertain outcomes.

Tricky & Most-Asked Interview Scenarios

A ten-minute task becomes visible while its worker still runs. What changes?

The Scenario & Constraint

The configured visibility period is shorter than actual processing and two attempts can act on the same fulfillment intent. What will you do and why?

The Direct Answer & Architectural Decision

Use a supported bounded visibility/extension plan and duplicate-safe effect ownership, monitor uncertainty and keep task identity stable across receipts.

Key Trade-Offs & Follow-Up Traps

Long visibility delays recovery of abandoned work; extensions can fail. Neither timeout choice physically stops the original worker, so sink correctness still needs its own mechanism.

Delete returned success but the message appears again. What do you inspect?

The Scenario & Constraint

The handler reused a receipt handle from an earlier receive. What will you do and why?

The Direct Answer & Architectural Decision

Follow the DeleteMessage receipt rules, track the relevant receive attempt and reconcile repeated business intent safely. Inspect Standard redelivery and transport outcomes rather than assuming the effect should run again.

Key Trade-Offs & Follow-Up Traps

More receipt/state tracking is needed. Even a correct delete is not a cross-system atomic commit or permission to remove effect deduplication.

A FIFO message triggers a payment twice after replay. Did FIFO fail?

The Scenario & Constraint

The application replayed outside producer deduplication scope and did not protect the provider effect. What will you do and why?

The Direct Answer & Architectural Decision

Use stable provider-supported intent/status semantics or a sink-local atomic effect/progress boundary, and define retention covering the supported replay window.

Key Trade-Offs & Follow-Up Traps

Additional state/coordination is required. FIFO send deduplication is a narrower service guarantee and cannot atomically include a nonparticipating payment provider.

A successful batch response contains failed entries. Resend all?

The Scenario & Constraint

Some fulfillment messages succeeded and others failed or remain uncertain. What will you do and why?

The Direct Answer & Architectural Decision

Record per-entry outcomes, retry only eligible unresolved work under its stable identity and classify permanent failures separately.

Key Trade-Offs & Follow-Up Traps

Per-entry tracking is more work than a batch flag. Blind full resend can duplicate successful tasks, while treating HTTP success as complete loses failed tasks.

More consumers do not clear one busy FIFO group. What can change?

The Scenario & Constraint

Per-shipment order matters, but all unrelated shipments were assigned one group. What will you do and why?

The Direct Answer & Architectural Decision

Choose independent business groups where invariants permit, bound worker concurrency and measure skew/sink capacity. Keep each required ordered sequence intact, including processing within received batches.

Key Trade-Offs & Follow-Up Traps

More groups improve potential parallelism but change order scope. If the entire workload truly needs one total order, scaling out consumers cannot remove that serialized boundary.

Skipping a failed FIFO item changes later business meaning. What do you do?

The Scenario & Constraint

Later commands assume the missing earlier transition completed. What will you do and why?

The Direct Answer & Architectural Decision

Define a per-entity failure/gap policy before redrive: pause/reconcile the sequence or explicitly change the business contract, with diagnosed repair and controlled replay.

Key Trade-Offs & Follow-Up Traps

Blocking preserves order but delays valid later work. Moving to a DLQ can improve progress while breaking the original strict operation sequence; it is not invisible recovery.
