Apache Kafka

🎯 The Hook & ELI5

A newsroom writes numbered entries into several long notebooks. Each department keeps its own bookmark and can reread older entries while they remain in the notebooks. Adding reporters helps only if work can be divided among those notebooks without breaking the story’s required order.

Apache Kafka is a partitioned retained-log platform, not simply a work item that disappears when one worker receives it. This lesson targets Apache Kafka 4.1 documentation and the documented Java client 4.1.2 model, using ordinary topic subscriptions and the classic consumer-group protocol. It does not claim these are the latest versions or cover every newer consumption mode.

Use shipment events keyed by shipment ID. Fulfillment and analytics are independent applications with independent group progress. Within one classic group, partition assignment distributes work; offsets identify positions in a partition, not one total ordering across the entire topic. Configure retention, replication and acknowledgments around an explicit business contract.

🗺️ High-Level Big Picture

Each group can consume the retained history independently. A group assignment and an offset are separate from whether an external effect committed safely.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the actual actor, communication, acknowledgment and recovery boundary.

1. Choose keys and the partition contract

Route related shipment events using a stable key/partitioning contract when per-shipment log order matters. A topic with several partitions does not define one global order. More partitions can permit more parallel work, but changing the mapping can move future records for the same key while old records remain elsewhere.

Identify the producer that orders a shipment’s facts and how concurrent upstream writers establish valid business order. Broker append order cannot reconstruct a causal order the producer never defined. A hot shipment or tenant can still saturate one ordered processing path.

2. Set publication safety explicitly

For the chosen 4.1 producer, verify acks, retries, idempotence and in-flight settings together. acks=all waits under the in-sync replica rules; the topic’s replication/minimum in-sync settings and failure assumptions determine whether publication can proceed and what survives. Merely having several configured replicas is not the same as requiring enough eligible copies at acknowledgment.

A timeout after send can hide an appended record. Producer idempotence addresses supported producer retry duplication under its documented identity/sequence model; it does not merge separately created business intents or atomically update an unrelated database.

3. Separate fetched position, completed work and committed offset

The Java consumer has a current fetched/read position and a committed position used for recovery. Application work may be between them. Saving progress ahead of durable processing risks skipped work; saving after effects leaves a crash window where work can repeat.

In a simple per-partition serial handler, commit the next position after the completed prefix. With asynchronous workers, a later completion must not advance the committed frontier past unfinished earlier records. Keep per-partition completion tracking and the consumer’s documented thread-safety rules explicit.

4. Handle membership and ownership changes

The classic group coordinates which member owns each subscribed partition for consumption. Joins, loss and subscription/partition changes can require reassignment. Long processing, missed polls or process pauses can interact with membership timeouts; the right response includes workload/batch/concurrency design, not just larger timeout numbers.

When ownership changes, stop/reconcile old work and protect external effects from stale attempts. A new assignment does not physically terminate the old worker. Use supported rebalance/progress protocols and duplicate-safe sinks; explain which member may commit what progress.

5. Treat retention and replay as a data lifecycle

Consumption does not delete a topic record merely because one group advanced. Retention/compaction policies determine what history remains. A lagging consumer can fall behind the available start and need a defined reset, snapshot/bootstrap or failure procedure. Do not silently reset an authoritative projection to the newest event and call it complete.

Replay can rebuild analytics only if required history, schemas and processing logic remain interpretable. A compacted stream has different historical meaning from an unabridged event history. Keep replay effects scoped so rebuilding a view does not reship physical goods.

6. Scope transactions and operations honestly

Kafka can coordinate consumed offsets and produced Kafka outputs in a supported transaction, with downstream visibility chosen appropriately such as read_committed. This is a defined Kafka processing boundary, not a promise that arbitrary email, SQL or payment calls join it. The Exactly-Once Processing lesson traces the external-sink case.

Monitor per-partition lag/age, ISR/under-replication, publish errors, group churn and sink completion, and test broker/member loss plus reply loss around commits. The description and configuration choices were source-checked; no live Kafka cluster or Java client is executed by these explanatory traces.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Committed frontier skips unfinished work

Symptom: A worker crashes and an older shipment event is never retried.

Root Cause: A later async completion committed past an unfinished earlier offset.

Fix/Prevention: Track a safe completed prefix and commit the next position only when valid.

Producer idempotence mistaken for business dedup

Symptom: A retried API call creates another shipment event with a new intent.

Root Cause: Two logical sends were treated as one producer retry sequence.

Fix/Prevention: Preserve business identity and enforce duplicate-safe decisions at the effect owner.

History expires during catch-up

Symptom: A new projection cannot reconstruct old shipments.

Root Cause: Retention/compaction was chosen independently of rebuild requirements.

Fix/Prevention: Define required history, bootstrap and lag alerts before accepting replay promises.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Model Kafka as retained partition logs plus explicitly managed publication, group progress and sink boundaries; configure and test each guarantee at its actual scope. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

What scope does a partition offset order?

Positions within that partition; it is not a global topic order or automatic order of external effects.

How does current position differ from committed position?

Fetching can advance current position before application work completes; committed progress defines a recovery point.

Why can more classic-group members stop adding throughput?

Partition ownership and hot partitions can limit useful parallelism, as can downstream capacity.

What must be named for an exactly-once Kafka claim?

The included inputs/state/outputs/progress, transaction/isolation configuration and effects outside that boundary.

Tricky & Most-Asked Interview Scenarios

Three replicas are configured. Can one surviving copy always accept a safe write?

The Scenario & Constraint

The business requires a specified replicated acknowledgment, but minimum ISR and election settings are not stated. What will you do and why?

The Direct Answer & Architectural Decision

Set and verify producer/topic durability requirements together, trace publication with reduced ISR and choose explicit unavailable behavior when the promised acknowledgment cannot be met.

Key Trade-Offs & Follow-Up Traps

Stronger acceptance can reject writes during failures. Replica count alone cannot settle the trade-off; weakening requirements changes the durability/availability contract.

Offset 12 finishes before 11. Commit 13 now?

The Scenario & Constraint

The same partition is processed concurrently and recovery from 13 would skip 11. What will you do and why?

The Direct Answer & Architectural Decision

Maintain a contiguous completed frontier per partition and commit only progress that does not skip unfinished required work; bound concurrency and handle failures/revocation.

Key Trade-Offs & Follow-Up Traps

Tracking increases complexity and waiting can limit throughput. Serial per-partition processing is simpler when the order/latency requirement permits it.

A new consumer starts while the old worker still calls a provider. What now?

The Scenario & Constraint

Partition reassignment happened during a slow external shipment operation. What will you do and why?

The Direct Answer & Architectural Decision

Stop/reconcile revoked work under the supported group lifecycle and make the provider intent/effect duplicate-safe; do not rely on assignment change to cancel an old request.

Key Trade-Offs & Follow-Up Traps

Extra sink state or fencing/cooperation may be required. Faster rebalancing does not alone make external effects exclusive or exactly once.

A stopped analytics group returns after its history expired. Reset to latest?

The Scenario & Constraint

Its contract requires a complete projection, not only future updates. What will you do and why?

The Direct Answer & Architectural Decision

Detect the gap and rebuild/bootstrap from a supported snapshot or retained authority, then resume at the matching position. Expose incomplete status until validated.

Key Trade-Offs & Follow-Up Traps

Longer retention costs storage; bootstrap adds time and source load. Latest-only restart is valid only under an explicitly different future-events contract.

Adding partitions changes per-shipment processing order. What do you plan?

The Scenario & Constraint

Existing key-based routing may map new shipment records differently after expansion. What will you do and why?

The Direct Answer & Architectural Decision

Use a planned key/ownership migration or another supported ordering transition, account for old in-flight records and verify consumer effect sequencing across the handoff.

Key Trade-Offs & Follow-Up Traps

Migration adds coordination and delay. More partitions improve potential parallelism but do not automatically preserve one key’s complete historical processing path.

Kafka output is transactional but a SQL counter still doubles. Why?

The Scenario & Constraint

A consumer commits the SQL update and crashes before its consumed progress is durably coordinated. What will you do and why?

The Direct Answer & Architectural Decision

Put the sink effect and its dedup/progress record in a supported sink-local atomic boundary or use a connector/protocol with the required sink cooperation. Reconcile repeats using stable identity.

Key Trade-Offs & Follow-Up Traps

Sink state/retention and concurrency rules add work. Kafka output transactions alone do not enlist an arbitrary SQL transaction; a different output topology may reduce the boundary.
