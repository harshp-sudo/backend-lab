Memcached

🎯 The Hook & ELI5

A shared coat-check counter holds labeled parcels for quick retrieval. It knows a label, the parcel’s bytes and when it should stop keeping it; it does not know who owns the original purchase or how to rebuild it. Memcached provides a similar shared item-cache interface, leaving application meaning and recovery to the caller.

Memcached is commonly used as a shared item cache. In this lesson, its values are rebuildable product views and the database remains authoritative. Client routing, lifetime, item size, memory and failure behavior matter as much as a successful get/set demonstration.

Examples target the Memcached 1.6 basic text protocol with CAS enabled and a volatile cache deployment. They are documentation-reviewed protocol exchanges, not an executed server installation. Verify actual server/client/configuration and any managed service or extension rather than assuming every deployment exposes identical features or persistence.

🗺️ High-Level Big Picture

The basic item API does not make the selected server the authoritative database. All clients must agree on key format, value representation and routing behavior.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the copy, authoritative owner, acknowledgment and recovery boundary.

1. Define keys, bytes and lifetime explicitly

For the basic text protocol, keys are bounded byte strings with restrictions such as no spaces/newlines in ASCII mode. Store a clear serialized representation with a schema/version policy; flags are application/client metadata, not automatic business meaning. Key/value size limits and client encodings must be verified.

Do not assume Python/Java string character count equals encoded byte count. A UTF-8 value can use several bytes per character. Namespacing by tenant and representation reduces collisions, but authorization and permission changes remain application responsibilities.

2. Read a complete text-protocol exchange

The following annotated client/server exchange stores eight ASCII bytes, reads them, obtains an opaque CAS token and conditionally replaces them with seven bytes. C and S labels are explanatory, not bytes sent on the wire; real protocol lines use CRLF.

C: set demo:product:7 0 60 8
C: Notebook
S: STORED
C: gets demo:product:7
S: VALUE demo:product:7 0 8 12345
S: Notebook
S: END
C: cas demo:product:7 0 60 7 12345
C: Journal
S: STORED

The sample token 12345 represents the token returned by that particular gets, not a fixed value clients should invent. A conflicting item update changes the token and the conditional write is rejected. A missing item and a changed existing item need distinct recovery handling.

3. Treat expiration encoding as a protocol contract

In this basic protocol, zero means no time-based expiry, not guaranteed residency. Expiration values up to thirty days are relative seconds; larger values are interpreted as Unix timestamps. Passing a thirty-one-day duration as if every integer were relative can therefore expire data unexpectedly.

Choose the intended lifetime and convert long deadlines correctly through the actual client. Normal item replacement and application refresh must preserve/reset lifetime deliberately. An unexpired item can still be evicted under memory pressure or lost with the selected volatile server lifecycle.

4. Measure memory allocation and admission

Memory use includes item/key/metadata overhead and allocation behavior. Examine configured item limits, size distribution, evictions, expired items, failed storage, connection behavior and latency. A large value can be rejected even when someone looking only at aggregate memory thinks there is space.

Use the actual server’s allocation/slab diagnostics and tuning capabilities rather than treating every free byte as interchangeable space for every item. Bound large result admission and compare a smaller reusable unit. A failed cache store must not be mistaken for successful authoritative persistence.

5. Keep clients, concurrency and recovery coherent

Clients commonly choose which server owns a key according to a routing policy. Inconsistent server sets/hash settings can create low hit rates and apparent stale/missing data. Membership changes can make keys cold; coordinate rollout and protect origin load instead of assuming adding a node only adds capacity.

CAS coordinates a conditional update against the currently observed item, not an external database transaction or permanent distributed lock. Handle missing/changed items and routing/server restart explicitly. Reuse client connection objects appropriately, set bounded timeouts and avoid accidental flush_all during routine invalidation.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

A thirty-one-day TTL expires immediately

Symptom: A long-lived key cannot be read after storing.

Root Cause: A duration above the basic protocol threshold was interpreted as an absolute timestamp.

Fix/Prevention: Convert explicitly and verify the client API’s expiration semantics.

Unicode corrupts a text exchange

Symptom: Following commands are misparsed or values truncate.

Root Cause: The bytes field counted characters rather than encoded value bytes.

Fix/Prevention: Use a correct client library/byte calculation and test multibyte values.

A new node lowers hit rate sharply

Symptom: Origin traffic spikes after expansion.

Root Cause: Client routing changed item placement without a recovery budget.

Fix/Prevention: Coordinate topology and warm/admit misses within origin capacity.

Does expiration zero guarantee an item stays forever?

No. It disables time-based expiration in this protocol, but eviction, deletion or server loss can still remove the item under the chosen deployment.

What changes above thirty days in the basic text expiration field?

It is interpreted as an absolute Unix timestamp rather than a relative duration. Verify any client-side conversion.

What does a CAS token prove?

It identifies the version of the currently observed cache item for a conditional update. It is not an authoritative database version or a permanent lease.

Why must clients count encoded bytes?

The basic protocol length describes the value bytes. Character counts can differ for multibyte encodings and break framing.

Tricky & Most-Asked Interview Scenarios

A key stored with 31 days of seconds vanishes. What do you inspect?

The Scenario & Constraint

The application passes 2,678,400 as an expiration duration to a basic text-protocol path. Reads miss immediately. What will you do?

The Direct Answer & Architectural Decision

Check the client and protocol expiration encoding: above the relative threshold that number is a Unix timestamp, not thirty-one days from now. Supply a correctly converted absolute deadline or a suitable supported relative lifetime, then test boundary values and the actual client.

Key Trade-Offs & Follow-Up Traps

Long lifetimes improve reuse but increase stale-data/invalidation responsibility; shorter bounded reuse can be simpler. Zero does not promise permanent residency. Do not fix the symptom by disabling expiration without reviewing memory and freshness.

Two clients edit the same cached item. What does gets/cas buy you?

The Scenario & Constraint

A read/modify/write operation loses one update under plain get/set. The cache is a derived view, not the authoritative account record. What will you change?

The Direct Answer & Architectural Decision

Use gets and the returned opaque CAS identifier for a conditional item replacement where that cache-level operation is appropriate. On conflict/miss, re-read or rebuild under a bounded retry policy. Keep actual account invariants in the authoritative owner.

Key Trade-Offs & Follow-Up Traps

CAS retries cost work under contention; rebuilding an immutable derived view may be simpler. CAS does not atomically include an external database write and cannot preserve a token through arbitrary eviction/routing changes.

ASCII examples work, but accented values break the connection stream. Why?

The Scenario & Constraint

A handcrafted client computes the value length from character count. UTF-8 product names now corrupt subsequent responses. What will you do?

The Direct Answer & Architectural Decision

Serialize to bytes first, use the encoded byte length and correct CRLF framing, and prefer a tested client implementation. Add representative multibyte and size-boundary cases. Distinguish protocol parse errors from normal cache misses so failures are not hidden as absence.

Key Trade-Offs & Follow-Up Traps

A client library adds a dependency but avoids fragile framing logic; handwritten code needs full protocol coverage. Retrying malformed exchanges endlessly can create connection churn. Compression/encryption also changes the bytes that length must describe.

Storage fails while a dashboard shows unused memory. What do you measure?

The Scenario & Constraint

Some large items fail and evictions rise for specific workloads. Aggregate memory alone looks acceptable. What will you inspect?

The Direct Answer & Architectural Decision

Check item-size/configuration limits, encoded key/value sizes, allocator/slab metrics, evictions and failed stores for the actual server version. Reduce or reject low-value oversized entries and test the workload distribution before tuning memory. Preserve the authoritative result even if optional cache population fails.

Key Trade-Offs & Follow-Up Traps

Smaller cached units add lookups/assembly; more cache memory may help some distributions. Available memory does not imply every item shape is admissible, and storing a value successfully is not durable origin commit.

Two application versions use different server rings and see different values. What is the rollout?

The Scenario & Constraint

One client includes a new Memcached server while another still hashes over the old set. Origin load and stale-looking results rise. What will you do?

The Direct Answer & Architectural Decision

Align canonical keying and topology/hash configuration across supported clients, stage membership changes and plan cold-key recovery with bounded origin admission. Treat item placement changes as a lifecycle event and invalidate/version representations as needed.

Key Trade-Offs & Follow-Up Traps

Coordinated rollout adds operational work; a routing abstraction can centralize it at another cost. Merely adding servers does not migrate every old item or authorize stale copies. Hot keys can remain concentrated despite a larger fleet.

An invalidation job calls flush_all for one product edit. What changes?

The Scenario & Constraint

Every edit makes the whole cache cold and the origin repeatedly overloads. What policy will you implement?

The Direct Answer & Architectural Decision

Use precise dependency/key invalidation or a deliberately scoped version namespace, review all callers of global flush and monitor its counter. Bound fallback/warm-up while repairing the invalidation path. Preserve multi-tenant separation instead of using a fleet-wide reset for ordinary edits.

Key Trade-Offs & Follow-Up Traps

Fine-grained dependencies require metadata and repair; coarse version invalidation can be reasonable for rare full rebuilds with capacity planning. A flush acknowledgment does not mean the origin can absorb the resulting load.
