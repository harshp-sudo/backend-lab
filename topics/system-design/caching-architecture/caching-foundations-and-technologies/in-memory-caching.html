In-Memory Caching

🎯 The Hook & ELI5

A cook keeps a few frequently used recipes on the counter. Reading one is quick, but every cook has a separate counter, old papers take space and a spilled drink can remove the whole collection. Local in-memory caching trades trips to another system for memory and lifecycle responsibilities inside one process.

This lesson focuses on request-local and process-local application caches. A remote Redis server can also store data in memory, but reaching it crosses another process/network boundary. Locality is useful only when the copy’s scope, memory budget and allowed staleness match the task.

We use immutable string values and a Python 3.12 teaching model to explain capacity, expiry and recency. It is deliberately single-threaded and bounds entry count rather than bytes. It is not a production concurrent cache, a distributed coherence mechanism or persistent storage.

🗺️ High-Level Big Picture

A process restart discards its ordinary heap cache. Multiple processes need a deliberate freshness/invalidation policy even when every local lookup is fast.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the copy, authoritative owner, acknowledgment and recovery boundary.

1. Choose lifetime and key scope

A request cache should be created for one trusted operation and released afterwards. A process cache lives across requests until eviction, expiry or process exit. Include tenant, parameters and representation context needed for safe reuse, and avoid retaining whole request/session objects as accidental key/value references.

Request-scoped DataLoader is a useful related example for batching/memoization under one identity. Promoting it to a global cache changes authorization, invalidation and memory requirements. A function result cached forever can also keep object graphs alive long after their useful request ends.

2. See capacity and expiry in a runnable model

The following complete Python 3.12 example uses an injected clock so expiry is deterministic. A hit refreshes recency; expiration uses time since insertion and does not automatically extend on reads. Values in this example are immutable strings.

from collections import OrderedDict
from time import monotonic

MISSING = object()

class LocalCache:
    def __init__(self, capacity, clock=monotonic):
        if capacity < 1:
            raise ValueError("capacity must be positive")
        self.capacity, self.clock = capacity, clock
        self.data = OrderedDict()

    def get(self, key):
        entry = self.data.pop(key, None)
        if entry is None:
            return MISSING
        value, deadline = entry
        if self.clock() >= deadline:
            return MISSING
        self.data[key] = entry
        return value

    def put(self, key, value, ttl):
        self.data.pop(key, None)
        if ttl <= 0:
            return
        while len(self.data) >= self.capacity:
            self.data.popitem(last=False)
        self.data[key] = (value, self.clock() + ttl)

now = [0.0]
cache = LocalCache(2, clock=lambda: now[0])
cache.put("a", "one", 5)
cache.put("b", "two", 5)
assert cache.get("a") == "one"
cache.put("c", "three", 5)
assert cache.get("b") is MISSING
now[0] = 5.0
assert cache.get("a") is MISSING
print("capacity, recency and expiry checks passed")

Expired entries not accessed can remain until another insertion evicts them; the count remains bounded. A production library needs appropriate cleanup, byte accounting, concurrency and observability rather than blindly extending this demonstration.

3. Budget actual memory and object behavior

Entry count is not memory size. Keys, values, index/expiry metadata and referenced objects all occupy memory; a few large results may dominate. Multiply the budget by worker count and leave headroom for normal application work, serialization and garbage collection. Observe retained bytes and pause/allocation behavior in the actual runtime.

If callers receive a mutable object reference, one caller can alter what later callers observe without any origin write. Use immutable representations or a deliberate copy/ownership policy. Copies can cost CPU/memory; measure them rather than claiming every local hit is free.

4. Handle concurrent misses and updates explicitly

A thread-safe mapping does not automatically make “miss, load, put” one operation. Concurrent misses can still repeat expensive work, and an old in-flight load can repopulate after invalidation. Use a suitable cache library, per-key coalescing and a version/update policy according to required guarantees.

Do not hold a broad global lock across every slow origin read; unrelated keys would wait behind one request. Bound refresh concurrency and waiters. Synchronization inside one process does not coordinate another worker or survive a restart.

5. Define multi-worker freshness and restart recovery

Choose bounded lifetime, tracked invalidations/version checks or bypass for reads that cannot accept local staleness. If an invalidation connection is lost, a local cache needs an explicit recovery policy rather than pretending no updates occurred. Refresh authoritative state or discard affected local copies as appropriate.

A deploy can simultaneously cold-start all workers. Protect origin capacity and warm selectively; a process cache should not make application startup depend on eagerly loading an unbounded dataset. Test that local eviction/restart affects performance only where the product explicitly permits it.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

A cached object changes without a write

Symptom: One user edits an object and another sees it.

Root Cause: Callers share a mutable reference.

Fix/Prevention: Use immutable values or explicit copies and keep origin writes in the owner.

A dictionary grows forever

Symptom: Memory stays high after requests finish.

Root Cause: Keys/values retain data with no bounded admission or lifecycle.

Fix/Prevention: Set measured capacity/cleanup and inspect retained references.

A local lock is called distributed consistency

Symptom: Other workers still serve stale data.

Root Cause: Process synchronization was mistaken for a fleet protocol.

Fix/Prevention: Define cross-worker freshness/invalidation or avoid local reuse for that requirement.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Local memory saves remote work only when object ownership, scope, capacity, concurrency and fleet freshness are explicit; treat restart and multi-worker divergence as normal cases. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

What changes when a cache moves from request to process scope?

It begins sharing across requests/identities and retaining memory longer. Authorization, invalidation and capacity requirements change.

Why is an entry limit not a byte budget?

Keys, values, metadata and referenced object graphs vary in size. Worker count and runtime overhead also matter.

Does a thread-safe map guarantee only one origin load per key?

No. The compound miss/load/store sequence needs its own coordination, and local coordination does not cover other processes.

How can a cache hit unexpectedly change future results?

Returning a mutable shared object lets the caller alter the cached instance. Immutable views or explicit ownership/copy rules prevent that path.

Tricky & Most-Asked Interview Scenarios

A local cache has only ten thousand entries but exhausts memory. What do you measure?

The Scenario & Constraint

A few values contain huge lists and every worker holds a separate copy. What will you do?

The Direct Answer & Architectural Decision

Inspect retained bytes/key/value distributions, object references and aggregate worker memory. Bound size/admission and avoid caching oversized or low-reuse objects; reserve headroom for normal work. Compare a shared cache or smaller derived unit against actual lookup/serialization costs.

Key Trade-Offs & Follow-Up Traps

Byte-aware bounds and estimates add overhead; entry limits may suffice for uniformly small immutable values. Increasing worker count can multiply copies. Garbage collection cannot reclaim objects still strongly referenced by a live cache.

One caller changes a cached dictionary and another sees the edit. What is the fix?

The Scenario & Constraint

The origin was not updated, yet the process cache now exposes a modified value across requests. What will you change?

The Direct Answer & Architectural Decision

Define immutable cached representations or copy-on-read/write with explicit ownership. Route real changes through the authoritative operation, and invalidate/update copies according to its version policy. Test nested mutable structures, not just a shallow outer copy.

Key Trade-Offs & Follow-Up Traps

Copying costs allocation and CPU; immutable serialized values can simplify ownership but add decode work. Locking dictionary access does not prevent a caller mutating an object after it was returned.

A request-scoped memo is promoted to a global singleton. What can go wrong?

The Scenario & Constraint

The original loader assumed one tenant/permission context. Reuse now spans users and long-lived requests. What will you do?

The Direct Answer & Architectural Decision

Restore request-scoped lifetime or deliberately redesign shared keys, authorization, invalidation and memory bounds. Keep loader context trusted and review every value whose visibility changes by user. Measure batching benefit separately from long-term cache reuse.

Key Trade-Offs & Follow-Up Traps

Request scope sacrifices cross-request hits; a reviewed shared data layer can be an alternative. Globally unique object IDs do not authorize access, and a global cache can retain stale permission-dependent values.

One hundred threads miss the same local entry. Is a concurrent map enough?

The Scenario & Constraint

The origin operation is expensive and each thread starts its own load. What will you add?

The Direct Answer & Architectural Decision

Coalesce in-flight loads per safely scoped key with bounded wait/deadline behavior, then populate a usable result once. Use a suitable concurrency primitive/library and control origin admission. Keep failure distinct from an absent value.

Key Trade-Offs & Follow-Up Traps

Coalescing introduces waiters and cancellation ownership; small inexpensive loads may not need it. A process-wide lock around all remote work blocks unrelated keys, and one process’s coalescer does not cover the fleet.

After a write, half the fleet serves old values. How do you provide read-your-write?

The Scenario & Constraint

Process-local entries live for a minute and requests can move between workers. The product requires the editing user to observe its acknowledged version immediately. What will you choose?

The Direct Answer & Architectural Decision

Carry the committed version/receipt and route or verify subsequent reads against an authoritative or version-aware path that can satisfy it. Invalidate/update local copies under a documented protocol, or bypass local caching for this read. Test worker changes and delayed invalidations.

Key Trade-Offs & Follow-Up Traps

Version checks add work; bounded stale display may be acceptable under a different requirement. Sticky routing is not a correctness protocol through failover. A short TTL still permits a period of violating an immediate promise.

A deploy empties every local cache and overloads the origin. What changes?

The Scenario & Constraint

Each new worker eagerly reloads thousands of entries while production traffic also misses. What will you do?

The Direct Answer & Architectural Decision

Stage worker rollout, warm only valuable bounded keys and enforce shared origin concurrency/rate budgets. Coalesce where appropriate and use an explicit degraded response for excess work. Measure startup and recovery load together.

Key Trade-Offs & Follow-Up Traps

Slower rollout/warming extends recovery; origin overprovisioning is another cost choice. Warming an unbounded dataset can be worse than on-demand misses. Local coordination alone cannot cap aggregate origin work across many workers.
