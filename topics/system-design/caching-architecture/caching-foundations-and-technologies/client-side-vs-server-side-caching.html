Client-Side vs Server-Side Caching

🎯 The Hook & ELI5

You can keep a timetable in your pocket, on your team’s desk or on a public station board. Pocket copies work without another trip, while a shared board helps many people. But a private appointment list belongs on neither a public board nor a previous user’s pocket app after they log out.

Client-side and server-side describe where reuse occurs relative to an application boundary, not one universal pair of technologies. Browser HTTP caches, script-managed Cache API storage, per-request memoization, process-local objects, shared cache services and CDNs have different lifetimes and rules. Draw the actual boundaries rather than calling every nearby copy “the client cache.”

Our example serves public catalog text and authenticated account details. Catalog text can tolerate bounded staleness; account information must respect current user/tenant permissions. This lesson chooses scope and responsibility. The existing REST/API Gateway lessons explain their API policies, and CDN Caching later covers edge configuration in depth.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the copy, authoritative owner, acknowledgment and recovery boundary.

1. Name the consumer and sharing scope

A request-local memo can reuse a value during one operation without serving the next user. A process-local cache spans requests within that worker. A shared service can span workers, while a browser/edge may store a completed HTTP representation. Decide which repeated work each copy avoids.

Place copies around actual latency/capacity needs. A local process hit avoids a shared-cache round trip but duplicates memory and update responsibilities. An edge hit avoids application work but may lack the application context needed for private representations. More tiers increase opportunities for reuse and for stale/incorrect answers.

2. Use HTTP cache policy for HTTP storage

Response policy must match the representation. These two independent examples show a reusable public localized catalog response and a sensitive account response. They are illustrative header blocks, not complete server implementations.

HTTP/1.1 200 OK
Cache-Control: public, max-age=60
Vary: Accept-Language
Content-Type: application/json

{"title":"Public catalog"}

HTTP/1.1 200 OK
Cache-Control: no-store
Content-Type: application/json

{"accountId":"a-7","balanceCents":1200}

A private response directive excludes shared storage under HTTP rules; no-cache requires validation before reuse rather than forbidding storage. The actual CDN/gateway can add provider policy, so test through it. A cookie on a request/response is not a universal instruction that every intermediary must treat the content as private.

3. Distinguish browser HTTP caching from application storage

The Cache API is script-managed Request/Response storage. Its entries do not automatically become fresh or expire according to an application TTL; the application must manage updates/deletion and match the intended semantics. Browser storage can also be evicted under resource/lifecycle policy, so offline availability needs a deliberate product contract.

An HTTP Cache-Control policy does not replace reviewing explicit script storage. Keep offline data selection, versioning, user partitioning and logout cleanup explicit. Do not let an offline fallback for a public catalog accidentally serve a previous user’s private account view.

4. Propagate updates across actual tiers

A server invalidating a shared data key does not automatically remove a browser response already stored or a process-local copy. Track each tier’s key, lifetime and invalidation/validation owner. Use validators/versioned resources for suitable representations, and bounded lifetime or explicit notifications where their failure semantics fit.

For personalized state, a client may need an authoritative refresh after login, role change or mutation. Consistency requirements can justify bypassing a tier or returning a new version token. State what the user sees during disconnected/offline use instead of silently treating old data as current.

5. Evaluate privacy, recovery and total cost

Measure avoided work per tier alongside memory duplication, serialization and invalidation complexity. Test two identities on one device, multiple workers, cache outage, stale edge entries and a cold browser. Apply current authorization before returning protected objects; a cache key is not a credential.

Prefer the smallest useful set of tiers. A public static asset can use broad shared reuse; a sensitive action may require an authoritative online decision. Document what is allowed to remain on the device and what is only a potentially stale display, with a clear refresh/expiry path.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Logout leaves a private offline view

Symptom: The next user sees account data on the same device.

Root Cause: Script storage was not partitioned/cleared with the session lifecycle.

Fix/Prevention: Review application storage independently, minimize sensitive copies and enforce cleanup/access policy.

A central delete does not refresh the UI

Symptom: The server is current but a browser serves an old representation.

Root Cause: Different tiers have independent keys/lifetimes.

Fix/Prevention: Map every tier and define validation/version/change behavior.

Every worker repeats the same memory

Symptom: Memory rises linearly with worker count.

Root Cause: Per-process state was budgeted as one shared cache.

Fix/Prevention: Budget aggregate copies and compare local benefit with a shared or request-scoped alternative.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Choose cache placement by the work avoided and the scope of safe reuse; map every tier’s identity, lifetime, update owner and recovery behavior. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Why is “in memory” not a complete placement description?

Memory can belong to one request, a process, another service or a client. Sharing, lifetime, trust and failure differ across those scopes.

Does browser HTTP cache policy manage all script caches?

No. Explicit Cache API/application storage has its own managed lifecycle. Review its selection, update and deletion behavior separately.

How do no-cache and no-store differ?

Under HTTP semantics, no-cache allows storage with validation before reuse; no-store directs caches not to store the response. Neither replaces application authorization.

Does deleting a server key invalidate every downstream copy?

No. Browser, edge and local-process copies have separate ownership and policies. Design the whole path.

Tricky & Most-Asked Interview Scenarios

A second user sees the first user’s cached account screen. What changes?

The Scenario & Constraint

A browser app stores account responses for offline use and reuses the same cache after logout/login. What will you do?

The Direct Answer & Architectural Decision

Stop unsafe reuse, remove/partition sensitive application storage according to a session/user policy and fetch an authorized current view for the new user. Review HTTP policy and explicit script storage separately, with tests for account switching and revoked access.

Key Trade-Offs & Follow-Up Traps

Removing offline copies reduces offline capability; a carefully scoped encrypted/offline data product needs a different explicit lifecycle. Server authorization cannot retract bytes already handed to an uncontrolled offline view. A URL-only key or a cookie is not sufficient isolation.

One worker shows a new price while another shows the old one. Where is the boundary?

The Scenario & Constraint

Every application process has a local cache; only the process handling the edit updates its copy. Readers can land anywhere. What will you choose?

The Direct Answer & Architectural Decision

Define a bounded local lifetime, reliable-enough invalidation/version check for the required promise, or remove that tier for sensitive reads. Keep authoritative purchase validation independent of a possibly stale display. Compare shared caching and request-local reuse against the actual workload.

Key Trade-Offs & Follow-Up Traps

A shared cache adds network/failure cost; local copies can be fine with accepted staleness. Updating one worker is not a fleet-wide invalidation. If the product promises immediate read-your-write, carry/verify an appropriate version or route to authority rather than hoping routing stays sticky.

A French catalog request receives cached English text. What did the key miss?

The Scenario & Constraint

The public representation varies by language, but an edge reuses only by URL. What will you fix?

The Direct Answer & Architectural Decision

Include language selection in the reviewed HTTP/edge variation contract, use appropriate Vary/actual provider key configuration and purge incompatible entries. Test language variants through cache hits, not only against the origin. Keep variant cardinality bounded.

Key Trade-Offs & Follow-Up Traps

More variants reduce hit rate; explicit locale-specific URLs are an alternative. Adding Vary at origin may not configure every custom gateway cache automatically. Private fields must remain outside a public representation even when localization is correctly keyed.

An offline app shows an outdated policy as current. How should it behave?

The Scenario & Constraint

A public policy document is stored in the Cache API and never explicitly updated or expired. Users need to know when they are seeing old data. What will you do?

The Direct Answer & Architectural Decision

Define a script-managed version/lifetime and refresh strategy, display truthful freshness/offline status and remove/revalidate old entries as the product requires. Separate acceptable offline display from actions that need an online authoritative decision. Test storage eviction and failed refresh.

Key Trade-Offs & Follow-Up Traps

Stricter freshness can make offline access unavailable; retaining a clearly labeled older copy may fit a different requirement. Cache API storage is not automatically governed by an app-level TTL merely because a response once carried HTTP headers.

Browser, edge, process and Redis each cache the same private object. Is this always faster?

The Scenario & Constraint

Invalidation incidents grow and the measured latency gain is unclear. The team wants another layer. What will you do?

The Direct Answer & Architectural Decision

Map the work avoided and policy owner at each tier, measure end-to-end hit/miss paths and remove redundant or unsafe copies. Keep only tiers whose benefit exceeds their memory, network and update costs. Verify protected responses under the resulting access policy.

Key Trade-Offs & Follow-Up Traps

Fewer tiers can increase some origin work but simplify correctness; a public derived representation may be broadly cacheable. The number of caches is not a performance metric. If the bottleneck is serialization after a hit, another data lookup cache may not help.

A permission is revoked but a valid-looking cache entry remains. Does its key authorize delivery?

The Scenario & Constraint

A shared cache key includes tenant and user ID, yet the user no longer has access to the object. The TTL has not expired. What will you do?

The Direct Answer & Architectural Decision

Enforce the current permission contract at delivery or use a reviewed permission-version/invalidation strategy that meets its bounded revocation requirement. Bypass or delete unsafe representations while containing the gap. Keep authentication and object authorization explicit at the owner.

Key Trade-Offs & Follow-Up Traps

Current checks cost work and bounded revocation can permit a documented exposure interval; cache avoidance may be simpler for highly sensitive views. Adding user ID to a key separates identities but does not freeze their permissions forever.
