Redis

🎯 The Hook & ELI5

A shared fast-access cabinet lets many workers retrieve labeled boxes without walking to the records room. Some boxes are strings, others contain structured collections, and the cabinet can remove old or less useful boxes when space is tight. Redis can play this role, but the labels and removal rules must match what the application is allowed to lose.

Redis is a data server with typed values and operations; caching is one use, not its entire identity. For this lesson the product database is authoritative and Redis contains rebuildable product views. Mixing those views with irreplaceable business state changes the storage promise.

The command examples use a Redis 8.0-compatible core command subset and redis-cli; they do not require newer conditional SET additions. Deployment details such as standalone, replication and Redis Cluster have different boundaries. Commands are illustrative and documentation-checked; no Redis server or client package was installed/executed for this static lesson.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the copy, authoritative owner, acknowledgment and recovery boundary.

1. Model keys and values around the reusable view

Choose a canonical key such as demo:tenant:42:product:7:v1 containing the tenant, identity and representation version. Include locale/visibility where the view varies. Decide whether the value is a whole immutable view or a smaller typed structure with explicit update rules.

Redis supports several data types, but a cache hit is useful only if the consuming application agrees on schema, freshness and permission. Reusing one key for incompatible types/schema versions can fail at runtime or return misleading data. Version and invalidate deliberately rather than relying on a convenient string name.

2. Set value and lifetime in one command

These independent redis-cli calls assume a controlled local Redis endpoint on the usual default port. The key is an illustrative public product view; examples do not configure a production deployment.

redis-cli SET demo:tenant:42:product:7:v1 '{"name":"Notebook","version":3}' EX 60
redis-cli GET demo:tenant:42:product:7:v1
redis-cli TTL demo:tenant:42:product:7:v1
redis-cli DEL demo:tenant:42:product:7:v1

SET with EX attaches the initial lifetime in the same operation, avoiding a process crash between a value write and a separate expiry command. A normal replacing SET without an expiry option can remove an existing TTL; choose replacement/KEEPTTL behavior intentionally and verify the actual command version. Expiry is still different from memory-pressure eviction.

3. Distinguish atomic commands from compound workflows

A command such as an appropriate conditional update has its own Redis operation semantics. A client GET followed later by SET is not automatically one atomic read/modify/write. Use a verified transaction/script/conditional mechanism when that key-level operation needs it, and state the exact scope.

Pipelining can reduce network round trips but is not by itself an atomic transaction. In Redis Cluster, multi-key operations also have placement constraints; clients must understand the selected topology. None of these mechanisms makes a separate SQL write and Redis update a single distributed commit.

4. Budget memory and eviction for the role

Set an explicit memory/policy budget and observe used memory, key sizes, hits/misses, evictions, latency and application errors. An allkeys policy can evict eligible cache values; volatile policies consider keys with expiry and can behave like noeviction if none are eligible. noeviction can reject memory-growing writes rather than create more space.

Leave room for operational/runtime buffers and recovery; maxmemory is not a promise that total process RSS equals that number. Do not put durable deduplication or accepted work into the same indiscriminately evictable keyspace and then call it disposable. Isolate responsibilities or provide an actual durable recovery contract.

5. Design persistence, replication and hot-key recovery

RDB snapshots and AOF policies have different durability, recovery and operational costs. Replication/failover behavior depends on configuration and can lose acknowledged writes under stated failures; a replica is not a universal no-loss guarantee. For a rebuildable cache, define bounded cold-start fallback instead of requiring every key to survive.

A hot key, large result, slow client or long-running operation can dominate latency even when average throughput looks good. Measure by command/key class and bound values/work. Redis Cluster distributes keys by slots; it does not automatically split one hot key into many independent owners. Reconnect, timeout and stale-client routing behavior also belong to the operational design.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

An update removes expiration

Symptom: A refreshed product stays cached indefinitely.

Root Cause: Replacing SET omitted its intended lifetime.

Fix/Prevention: Set lifetime atomically or intentionally preserve it with supported semantics; observe TTL behavior.

A pipeline is called a transaction

Symptom: Concurrent edits lose a computed value.

Root Cause: Separate GET/SET calls were batched but not made atomic.

Fix/Prevention: Use a verified atomic operation/transaction/script in its actual scope.

A replica promises too much

Symptom: Failover loses an acknowledged key.

Root Cause: Asynchronous replication was treated as synchronous durable commit.

Fix/Prevention: State the failure model and reconcile/rebuild or use a suitable authoritative boundary.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Use Redis through explicit key, operation, memory and failure contracts; product capabilities do not remove origin ownership or make every deployment equally durable and consistent. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Is Redis always a disposable cache?

No. That is an application role. If Redis holds authoritative state, its durability, eviction and recovery must satisfy that role explicitly.

Why combine a new value with EX?

The value and initial lifetime are applied together instead of leaving a crash gap before a separate expiration call.

Does pipelining alone make GET then SET atomic?

No. It changes request transport/round trips, not the business concurrency boundary of that compound workflow.

Does adding cluster nodes split one hot key automatically?

No. Key placement distributes keys; one key can remain a bottleneck. Measure and redesign that access pattern where appropriate.

Tricky & Most-Asked Interview Scenarios

Keys stop expiring after refresh. What command behavior do you inspect?

The Scenario & Constraint

A product key initially has a sixty-second TTL. A background refresh uses plain SET, and memory/staleness grow. What will you do?

The Direct Answer & Architectural Decision

Inspect the actual replacing command and TTL after refresh. Set an explicit expiry atomically with each replacement or intentionally retain lifetime using supported semantics. Add operational checks for unexpectedly persistent cache keys and verify refresh timing against the freshness policy.

Key Trade-Offs & Follow-Up Traps

Retaining an old deadline can expire a freshly computed value sooner; resetting it can extend staleness if fills are stale. A separate EXPIRE after SET leaves a crash gap. TTL is not proof that the source value used for the fill was current.

Redis rejects writes even though an eviction policy is configured. Why?

The Scenario & Constraint

The instance uses a volatile policy, but almost every key has no expiry. Memory-growing writes now fail. What will you investigate?

The Direct Answer & Architectural Decision

Check maxmemory, actual policy and eviction eligibility, inspect keys/TTLs and memory overhead, then choose a policy appropriate to the role. For disposable cache data, make lifetime/admission deliberate and keep irreplaceable records out of an unsafe eviction design. Protect the origin if writes cannot populate.

Key Trade-Offs & Follow-Up Traps

An allkeys policy may restore cache admission but can remove any eligible cached item; noeviction preserves keys at the cost of write failure. Raising memory without understanding growth/eligibility only postpones the problem.

Two callers read 10 and each stores 11. Did Redis lose an atomic update?

The Scenario & Constraint

Application code performs separate GET and SET operations for a shared value, possibly pipelined. What will you change?

The Direct Answer & Architectural Decision

Use an operation whose semantics match the desired atomic change or a verified conditional/transaction/script mechanism, and test concurrent callers in the selected topology. Keep source-of-truth invariants in their owning boundary rather than updating a cache as if it were the database.

Key Trade-Offs & Follow-Up Traps

Atomic mechanisms can add contention or placement constraints; avoiding cached mutable counters may be simpler. Pipelining alone is not synchronization, and key-level Redis atomicity does not make an external database transaction part of the same commit.

An acknowledged dedup key disappears on failover and a payment repeats. What was wrong?

The Scenario & Constraint

The service relied on a Redis replica setup as proof that accepted operation identity could never be lost. What will you do?

The Direct Answer & Architectural Decision

Treat deduplication as authoritative business state, review actual persistence/replication/failure guarantees and move or engineer the durable outcome boundary accordingly. Reconcile uncertain external effects before new execution; keep a rebuildable Redis lookup only where losing it cannot violate the promise.

Key Trade-Offs & Follow-Up Traps

Stronger durability/coordination costs latency and operations; a disposable cache can instead rebuild safely if it owns no durable promise. A replica or long TTL does not eliminate every acknowledged-write loss window.

Adding shards does not reduce latency for one hot key. Why?

The Scenario & Constraint

A massive catalog aggregate is read repeatedly from one key and dominates network/CPU. What will you choose?

The Direct Answer & Architectural Decision

Measure key size, serialization and command latency, then shrink or split the reusable unit where semantics permit, use safe local/edge replication of an immutable view, or reduce read demand. Confirm client routing and capacity before adding nodes.

Key Trade-Offs & Follow-Up Traps

Splitting adds assembly and version-coherence work; a single bounded aggregate can still be simpler at moderate load. Redis Cluster placement does not automatically partition one key’s operation. More shards do not reduce bytes sent for each unchanged giant result.

Eviction removes business records mixed with product copies. What is the architecture decision?

The Scenario & Constraint

A shared Redis instance uses allkeys eviction for product caching and also holds the only accepted background work records. What will you do?

The Direct Answer & Architectural Decision

Separate rebuildable cache admission from authoritative work durability, with explicit storage, retention and recovery for accepted jobs. Choose eviction/noeviction and persistence by the actual role, then test memory pressure and restart. Do not hide ownership behind a generic Redis service name.

Key Trade-Offs & Follow-Up Traps

Separate stores/instances cost operations; a carefully engineered common system can work only if its guarantees satisfy both roles. Turning off eviction can replace data loss with admission failure, which the service must still handle honestly.
