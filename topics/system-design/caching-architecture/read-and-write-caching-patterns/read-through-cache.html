Read-Through Cache

🎯 The Hook & ELI5

At a library desk you ask for a book once. If the nearby shelf is empty, the librarian fetches it from the archive for you. You do not write the fetching routine at every table. Read-through caching moves miss-loading behind a cache abstraction, while the fetching rules and archive still need a clear owner.

A read-through cache invokes a configured loader when a usable mapping is absent and returns/populates according to that abstraction’s contract. In cache-aside, the calling application coordinates those steps directly. Both can use similar storage; the distinction is ownership and interface, not whether a particular server has a magic read-through switch.

Ehcache 3.11 CacheLoaderWriter is the concrete reference: load/loadAll supply the read path, while write/delete behavior must be chosen deliberately. General examples describe an authorized product-view loader. Provider-specific coalescing, errors, expiry, bulk behavior and deployment guarantees must be verified rather than inferred from the pattern name.

🗺️ High-Level Big Picture

The caller has one entry point, but a miss can still perform network/storage work. Expose that cost and failure behavior in the abstraction’s contract.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the copy, authoritative owner, acknowledgment and recovery boundary.

1. Define the loader boundary and authority

Choose the cache abstraction and loader owner. Establish the authoritative source, canonical key/schema and permission scope. The caller should know whether get can block, fail or return absence; hiding an origin call must not hide its budget or correctness meaning.

Ehcache 3.11’s unified CacheLoaderWriter makes read and mutation behavior explicit. A read-only application facade should reject unsupported writes rather than silently accepting a put that never reaches the authority. A no-op writer is an implementation choice with consequences, not automatic durable persistence.

2. Specify hit, absence and failure independently

A loader needs more than a value-or-null convention. Use the selected provider’s actual representation and make these meanings explicit in the application boundary.

For provider examples verify how null/missing mappings and loader exceptions are handled. A timeout cannot prove an item is absent, and caching an error as a successful value can suppress recovery.

3. Bound and observe hidden miss work

Propagate caller deadlines to the loader and underlying client, bound origin concurrency and decide what cancellation means for shared in-flight work. One departing waiter need not cancel a refresh still serving others, but work must not run without any limit.

Measure loader invocations, latency, waiters, failures and source freshness separately from cache get latency. Coalescing must be verified for the selected operation, instance and deployment. A read-through interface by itself does not promise one origin call across the whole fleet.

4. Batch deliberately without weakening scope

Use an actual bulk loader when several requested keys can be fetched efficiently together. Confirm missing-key and partial-failure handling, result-to-key alignment, maximum batch size and tenant/permission context. A getAll interface can still internally issue one origin call per key if configured that way.

Keep unrelated tenant work from sharing a cached authorization-dependent result. Include relevant trusted identity in the key/context or load only a safely shared internal representation and authorize the returned view separately. Avoid a singleton loader capturing the first request’s mutable session context.

5. Plan updates and loader dependencies

A loader fetches a missing value; it does not automatically learn that an already cached value changed. Pair it with the required invalidation/version/lifetime policy, and inspect late fills during concurrent writes just as with cache-aside. Writes that bypass the configured owner can leave the cache stale.

Keep loader dependencies acyclic or explicitly managed. A loader that calls its own cache for the same missing key can wait on itself or recurse without bound. Test cold start, source failure, concurrent get, bulk paths and read-only mutation behavior in the actual provider.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

A cache get surprises the timeout budget

Symptom: A seemingly local lookup stalls on origin I/O.

Root Cause: Miss-loading cost was hidden from callers.

Fix/Prevention: Document blocking/failure semantics and propagate bounded budgets.

A null masks an outage

Symptom: Missing screens appear during a database timeout.

Root Cause: Loader exceptions were converted to cached absence.

Fix/Prevention: Keep confirmed absence distinct from failed retrieval.

A loader loads itself

Symptom: A cold key deadlocks or recurses indefinitely.

Root Cause: The loader calls the same cache/key instead of an independent authority.

Fix/Prevention: Review dependency paths and use bounded nonrecursive origin access.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Read-through centralizes loading, not correctness by magic: expose hidden cost, define absence/errors and mutation behavior, and verify provider and deployment boundaries. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

What makes this read-through rather than cache-aside?

The cache abstraction owns invoking the configured loader and population policy; callers do not repeat the miss/load/store orchestration.

Does read-through automatically coalesce fleet-wide loads?

No. Verify method/provider/instance scope. Distributed origin admission and duplicate load suppression remain explicit decisions.

Why should an origin timeout not be returned as absent?

It did not establish whether the object exists. The caller needs honest failure/retry behavior, not a misleading negative result.

Why define write behavior for a read-focused abstraction?

A cache put can diverge from the authority if mutations are accepted but ignored. Reject, route or implement writes deliberately under the chosen contract.

Tricky & Most-Asked Interview Scenarios

A read-through cache still issues a hundred origin reads for one key. What do you inspect?

The Scenario & Constraint

Callers assumed the loader guaranteed global single-flight, but requests span many instances. What will you do?

The Direct Answer & Architectural Decision

Verify actual load-coalescing scope and operation behavior, then add suitable per-key coordination where useful and a shared origin capacity budget. Bound waiters/timeouts and measure loader invocations per logical key. Keep correctness independent of an unreliable refresh lease.

Key Trade-Offs & Follow-Up Traps

Local coalescing is simpler but leaves one load per instance; distributed refresh ownership costs coordination and recovery. A single interface name does not establish cross-instance semantics. Distinct-key cold load still needs admission control.

Database timeouts become cached nulls. How do you repair the contract?

The Scenario & Constraint

A loader catches every exception and returns “not found,” so real products disappear during outages. What will you change?

The Direct Answer & Architectural Decision

Preserve loader failure separately from authoritative absence, purge misleading negatives and apply bounded retry/degradation policy. Verify the selected provider’s missing/exception behavior and use an explicit negative representation only for confirmed absent data under a valid lifetime.

Key Trade-Offs & Follow-Up Traps

Richer result handling adds caller cases; a read-through facade can centralize it. Negative caching is useful for nonexistent keys but must not conceal a failing source. Restoring database availability will not help until incorrectly retained negatives expire or are repaired.

A caller puts a new value into a read-through cache, but the origin stays old. Was the save successful?

The Scenario & Constraint

The abstraction uses a no-op writer. A new caller treats put as a durable save. What will you do?

The Direct Answer & Architectural Decision

Reject unsupported mutations in a read-only facade or route them through an explicitly implemented authoritative write path. Define the acknowledgment contract and add misuse cases to review. Correct or invalidate the divergent cache copy.

Key Trade-Offs & Follow-Up Traps

A separate command path is more explicit but adds an interface; a configured write-through path is another option with its own failure contract. A cache update cannot honestly acknowledge an origin write that never occurred.

getAll still performs one database call per key. What must be implemented?

The Scenario & Constraint

A page needs fifty product views, but the loader only implements repeated single-key retrieval. What will you do?

The Direct Answer & Architectural Decision

Inspect the provider’s bulk path and implement a bounded batch origin lookup where it actually helps. Preserve key-to-result mapping, missing/error handling and tenant context; compare round trips, rows and latency with representative batches.

Key Trade-Offs & Follow-Up Traps

Bulk loading adds partial-failure and size controls; independent lookups can be simpler for a few keys. A large batch may still scan too much data or exceed deadlines. Do not combine users’ private representations solely to maximize batch size.

A singleton loader remembers the first tenant’s session. Where should context live?

The Scenario & Constraint

All later callers use that loader and can receive permission-dependent data from the first context. What will you change?

The Direct Answer & Architectural Decision

Remove mutable request/session capture, define trusted scope in the access/key policy and authorize every protected view. Use request-scoped loaders where needed or a shared internal representation that is safe to reuse before view authorization. Invalidate exposed entries and test multiple identities.

Key Trade-Offs & Follow-Up Traps

Request scope reduces cross-request reuse; a carefully designed shared loader needs more key/invalidation policy. Even a correct type/schema does not authorize another tenant’s result. Provider caching cannot infer business permission dimensions you omit.

A loader calls the same cache and hangs on a cold key. What is the fix?

The Scenario & Constraint

To reuse code, the loader invokes a repository that itself calls cache.get for the same key. What will you do?

The Direct Answer & Architectural Decision

Separate authoritative retrieval from cached access and make loader dependencies explicit and bounded. Detect or prevent same-key recursive cycles, and test cold rather than only warm paths. Propagate deadlines so a dependency error cannot hold resources indefinitely.

Key Trade-Offs & Follow-Up Traps

A separate uncached origin interface adds structure but clarifies ownership; a general dependency framework may be excessive for a small cache. Warm-cache tests can hide the cycle. Increasing timeout only prolongs a logically circular wait.
