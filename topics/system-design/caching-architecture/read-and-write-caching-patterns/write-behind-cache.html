Write-Behind Cache

🎯 The Hook & ELI5

A busy receptionist writes an address change on a tray card and says it is accepted before updating the official file. This can keep the line moving, but a lost tray can lose accepted changes. Write-behind is that timing choice: the later write still needs an owner, a durable promise and a recovery plan.

Write-behind defers writes to a backing store, often allowing batching/coalescing. A caller can return before that store commits. Until propagation completes, the newest accepted state may exist only in a cache or queue; it cannot automatically be treated as a safely disposable copy.

Ehcache 3.11’s asynchronous CacheLoaderWriter wrapper is the concrete reference for queue, batching and coalescing concepts. Its wrapper does not supply automatic retry of failed writes; application writer/recovery logic must define that behavior. This lesson distinguishes an in-process volatile queue from a deliberately durable acceptance log rather than assigning the same durability to both.

🗺️ High-Level Big Picture

The gap between the acknowledgment and the backing-store commit is a real ownership boundary. Queue placement/durability and worker recovery determine what the system can promise.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the copy, authoritative owner, acknowledgment and recovery boundary.

1. Define acceptance before optimizing latency

State whether the caller received best-effort volatile acceptance, durable queued acceptance or confirmed backing-store completion. These are different product promises. If accepted work must survive process/power failure, use a mechanism that actually meets that failure model before acknowledging.

A memory queue, a replicated cache and a durable event log are not interchangeable guarantees. If the queue owns accepted updates during lag, engineer its retention, replication, admission and recovery as business state. A cache miss must not rebuild an older backing-store value over a newer pending change.

2. Record identity, ordering and state meaning

This illustrative record describes setting one key to a versioned state. It is not a deployment recipe or proof that an in-memory queue is durable.

{
  "operationId": "change-31",
  "key": "tenant-42:display-counter",
  "keyVersion": 7,
  "kind": "set-state",
  "value": 120
}

Choose a real per-key ordering/version owner and carry identity through retries. A set-state sequence may permit replacing intermediate pending versions with the newest one. Independent deltas/events cannot generally be collapsed by keeping only the last record, because each can carry a required effect.

3. Bound batching, coalescing and concurrency

Batching amortizes store calls; coalescing can reduce repeated updates to one key when intermediate states are truly replaceable. Concurrency can help independent keys but may reorder one key unless its application path prevents it. Verify the actual provider configuration, including whether clustered deployment honors the same settings.

Ehcache 3.11 documents queue size, concurrency, batching and maximum batch delay. A configured batch delay is not an end-to-end persistence deadline during backlog or store outage. Track oldest pending age, accepted versus committed versions and effective flush throughput.

4. Make retries and partial failures duplicate-aware

A batch can partially commit or commit before its reply is lost. Use idempotent/operation-aware application at the backing owner and version guards that prevent an old retry overwriting newer accepted state. Distinguish retryable failures from poison input and provide bounded retry/dead-letter or operator repair as appropriate.

Do not assume a framework wrapper retries for you: the selected Ehcache wrapper explicitly leaves failed-write retry to the application. Dequeuing/acknowledging pending work before its required commit can lose it; committing before completion bookkeeping can repeat it. State which mechanism closes or tolerates that gap.

5. Apply backpressure and a coherent read policy

If accepted rate exceeds flush capacity, the queue grows unless admission slows or work is safely coalesced. Bound memory/storage, wait time and concurrent batches; reject/defer truthfully when the acceptance promise cannot be met. Keep shutdown draining useful but do not treat graceful shutdown as crash durability.

Readers must know whether they observe latest accepted front state or lagging backing state. Eviction, restarts and direct-store writes complicate that policy. Test process death after acceptance, partial batch failure, reordered retry, prolonged outage and misses while writes remain pending. Prefer synchronous authority when deferred loss/lag cannot be accepted or engineered safely.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

A tray is mistaken for a durable ledger

Symptom: Acknowledged updates disappear after a crash.

Root Cause: Acceptance occurred only in volatile memory.

Fix/Prevention: Match acknowledgment to real durable state or label best-effort loss honestly.

An old batch wins

Symptom: Backing data goes backward after recovery.

Root Cause: Retries applied out of order without version/identity policy.

Fix/Prevention: Enforce appropriate per-key order and guarded duplicate-safe application.

A counter loses increments

Symptom: Many accepted events become one final delta.

Root Cause: Coalescing independent effects was treated like replacing state.

Fix/Prevention: Preserve events or aggregate them with a mathematically valid durable rule.

What separates write-behind from write-through?

The backing-store write occurs later, after the front-path acknowledgment under the chosen contract, rather than being completed synchronously by that writer path.

Can pending accepted updates be called disposable cache data?

Not if they are the only record of promised work. During lag they need an ownership/durability contract that matches the acknowledgment.

When is keeping only the last pending value reasonable?

When it represents replaceable complete state and intermediate transitions have no required effect. Independent deltas/events need different handling.

Does the referenced Ehcache wrapper retry failed writes automatically?

No. Its documented write-behind wrapper leaves appropriate retry behavior to the application writer/recovery design.

Tricky & Most-Asked Interview Scenarios

A process crashes after “saved” but before flushing. What was actually promised?

The Scenario & Constraint

Users expect accepted profile edits to survive restarts, but pending writes existed only in a local queue. What will you do?

The Direct Answer & Architectural Decision

Define a truthful acceptance contract and put required durable pending state in place before acknowledgment, or use synchronous authoritative writes. Recover/replay accepted work with stable identity and expose pending versus completed state clearly. Test hard failure, not only graceful shutdown.

Key Trade-Offs & Follow-Up Traps

Durable acceptance costs latency/storage and recovery machinery; best-effort loss may be acceptable for replaceable telemetry. Calling a memory enqueue “saved” does not create durability, and flush-on-exit cannot protect sudden process/power loss.

Version 8 commits before a delayed retry of version 7. How do you avoid regression?

The Scenario & Constraint

Several workers flush updates and a timed-out old batch is retried later. What will you implement?

The Direct Answer & Architectural Decision

Assign versions through a real per-key owner/order, apply changes with a suitable guard at the backing store and make duplicates/out-of-order work explicit. Retain enough completion/recovery state to resolve unknown outcomes. Partition processing where it simplifies per-key order.

Key Trade-Offs & Follow-Up Traps

Ordering can limit concurrency on hot keys; complete immutable events are another design with a projection owner. A number in the message is not a guard unless the destination enforces it. Blind last-arrival-wins can overwrite the newest accepted value.

Ten queued increments become one increment. Why is coalescing unsafe here?

The Scenario & Constraint

A queue keeps only the latest update per key, but every update means “add one” rather than “set count.” What will you change?

The Direct Answer & Architectural Decision

Preserve required events with duplicate-safe application or aggregate deltas under a durable mathematically valid identity/order policy. Use last-state coalescing only when the value truly replaces prior states and lost transitions have no independent meaning.

Key Trade-Offs & Follow-Up Traps

Keeping all events costs queue/store work; a trusted state owner can emit a complete latest count instead. Coalescing price snapshots can be reasonable while coalescing audit events is not. Retried increments still need duplicate handling.

The backing store is down and the queue is full. Should writes continue succeeding?

The Scenario & Constraint

The application has no remaining safe space for accepted work. Dropping it would violate the product contract. What will you do?

The Direct Answer & Architectural Decision

Apply bounded backpressure or reject/defer before acceptance when the promise cannot be met. Preserve already accepted work, expose pending status and prioritize controlled recovery. Monitor oldest age/capacity and keep retry load within the recovering store’s budget.

Key Trade-Offs & Follow-Up Traps

Availability may fall; a larger durable queue buys time but not infinite capacity. Unbounded memory growth eventually fails more broadly. Do not silently drop oldest business writes just to keep front-end success rates high.

Half a batch commits before timeout. How does retry avoid repeating effects?

The Scenario & Constraint

The framework does not automatically resolve failed write-behind batches. The worker cannot tell which effects reached the store. What will you do?

The Direct Answer & Architectural Decision

Use operation identity/idempotent versioned application at the destination and reconcile batch/item outcomes. Retry only within an explicit bounded policy, preserving pending work until the required commit is established. Separate invalid poison records for visible repair rather than endless replay.

Key Trade-Offs & Follow-Up Traps

Per-item receipts and guards add storage/logic; idempotent full-state writes can simplify some workloads. The referenced Ehcache wrapper leaves retry design to the application. Replaying non-idempotent effects with new identities can duplicate them.

A dirty cached entry is evicted before flush and a read reloads old store data. What is the owner?

The Scenario & Constraint

The newest accepted value has not reached the backing store, but the cache was treated as entirely rebuildable. What will you change?

The Direct Answer & Architectural Decision

Preserve the accepted pending state independently of disposable entries and define reads against that state/order where required. Prevent a miss fill from overriding newer pending work, or choose a synchronous authoritative model if the extra ownership is unjustified. Test eviction and restart during lag.

Key Trade-Offs & Follow-Up Traps

A pending-state overlay adds read/recovery complexity; weaker stale reads may fit explicitly best-effort data. Simply extending TTL cannot protect against capacity eviction or process loss. Backing-store lag is part of the chosen write contract, not merely a cache hit-rate issue.
