Cache-Aside Pattern

🎯 The Hook & ELI5

You check your desk for a recipe. If it is missing, you walk to the cookbook, copy the recipe and leave it on the desk for next time. You own that extra trip and the job of throwing away obsolete copies. Cache-aside puts this responsibility in the application rather than hiding it inside the cache service.

With cache-aside, application code consults a cache, loads from the authoritative store on a miss and decides whether/how to populate. Writes normally go through the authoritative owner, followed by a deliberate cache maintenance policy. The cache is a reusable copy, not an automatic transaction participant.

Our product-view example permits a bounded stale display but requires the purchase operation to validate authoritative price/stock. We separate ordinary invalidation order from concurrent stale-fill races: committing before deleting avoids one race, but does not make every overlapping reader safe.

🗺️ High-Level Big Picture

Loading and population are application decisions. A failed cache lookup, an absent origin row and a failed origin read must not be collapsed into one meaning.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the copy, authoritative owner, acknowledgment and recovery boundary.

1. Define the read result and the reusable key

Create a canonical key for tenant, object, parameters and representation version as needed. Treat a usable cache hit as a policy decision, not merely a non-null value. Define a separate representation of confirmed absence if negative caching is allowed.

Set cache and origin time budgets and control aggregate origin admission. A cache outage should not silently turn every application instance into an unlimited database client. Decide whether optional cache population failure still permits returning a successfully read authoritative value.

2. See ownership in a complete small model

This executable Python example models a single-threaded authoritative dictionary and immutable tuple views. It demonstrates application ownership and one stale-fill interleaving; it intentionally supplies no production concurrency or TTL guarantee.

origin = {"p-7": ("Notebook", 1)}
cache = {}

def read_product(key):
    if key in cache:
        return cache[key]
    value = origin.get(key)
    if value is not None:
        cache[key] = value
    return value

def update_product(key, value):
    origin[key] = value
    cache.pop(key, None)

assert read_product("p-7") == ("Notebook", 1)
old_reader_snapshot = origin["p-7"]
update_product("p-7", ("Notebook revised", 2))
cache["p-7"] = old_reader_snapshot
assert read_product("p-7") == ("Notebook", 1)
print("late reader can repopulate an obsolete view")

The last fill represents a reader that fetched before the write but completed afterwards. A correct simulation of the bug is not a recommended implementation. Use the following ordering/freshness decisions to decide whether such a stale result is permitted and how it is prevented or repaired.

3. Trace commit, delete and the late reader

Deleting before committing permits a miss to reload the still-old origin. Committing then deleting avoids that particular window, but an already running old load can still fill afterwards. Trace the actors rather than declaring one ordering universally consistent.

Options include an allowed short stale window, immutable/version-addressed views with a trustworthy current-version check, a guarded fill against retained version metadata, or bypassing caching for the required read. Any guard must survive the failures in the promise; a missing/evicted version marker cannot automatically authorize an old fill.

4. Handle absence, retries and invalidation failure

A confirmed missing item can be cached briefly where delayed visibility of creation is acceptable. An origin exception is not absence. Bound repeated failed loads with admission/backoff or a documented stale response instead of negative-caching every error.

If the origin commits but cache deletion fails, record retry/repair intent durably where the freshness promise requires it. Event-based invalidation needs actual delivery/order/replay handling. TTL can be a safety net, but the lifetime of a newly filled old value depends on when that fill occurred and which source it read.

5. Operate misses as a capacity path

Measure hit/miss reasons, origin/fill latency, duplicate loads, invalidation lag and stale-version observations. Coalesce overlapping loads by safe key and cap distinct-key origin work. Keep lease/timeout failure behavior explicit; a slow expired refresh owner may still finish later.

Test cold start, cache store failure, delayed reader fill, dropped invalidation and source replica lag. Correctness-sensitive actions should reach an owner capable of the required invariant. Cache-aside is often a useful simple pattern, but its application-owned recovery work is real.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Delete-before-commit reloads old data

Symptom: The cache is stale immediately after a write.

Root Cause: A miss read the old origin before the new value committed.

Fix/Prevention: Choose commit/invalidation ordering deliberately and still inspect in-flight readers.

Commit-delete is called race-free

Symptom: An old value returns after deletion succeeded.

Root Cause: A reader fetched an earlier snapshot and filled late.

Fix/Prevention: Use a justified stale window, guarded/versioned fill or authoritative path.

Cache failure is a database stampede

Symptom: Every request falls through at once.

Root Cause: Fallback had no shared capacity budget.

Fix/Prevention: Bound origin admission and coalesce duplicate loads separately.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Cache-aside makes loading explicit; correctness comes from source ownership, race-aware population, invalidation recovery and bounded miss traffic, not from the happy-path snippet. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Who loads the origin on a cache-aside miss?

The application does and decides how to populate, handle failure and maintain the copy.

Does commit then delete solve every stale-fill race?

No. It avoids reloading before commit in one ordering, but an old in-flight reader can fill after the deletion.

Why keep not-found and origin failure separate?

One is an authoritative result eligible for a scoped negative policy; the other does not establish whether data exists.

What assumption matters for a version guard?

Its version/ownership metadata must remain trustworthy under the failure model. Missing or lost guard state cannot silently validate an old result.

Tricky & Most-Asked Interview Scenarios

Deletion succeeds after a write, then an old value reappears. What is the interleaving?

The Scenario & Constraint

A reader fetched version 1 before version 2 committed and populated after the writer deleted the key. What will you do?

The Direct Answer & Architectural Decision

Reproduce the ordering, define the allowed stale window and choose a mechanism that meets it: guarded/version-addressed fills with trustworthy version state, or authoritative bypass for strict reads. Preserve a repair/expiry policy for stale displays and test delayed readers explicitly.

Key Trade-Offs & Follow-Up Traps

Guard/version discovery adds state and work; a bounded stale view is simpler if acceptable. Repeating delete after an arbitrary sleep does not prove every earlier reader finished. A lost/evicted version marker must not make obsolete fills valid.

The database committed but cache deletion timed out. What does success mean?

The Scenario & Constraint

The API must acknowledge the real durable change while readers may still find an old copy. What recovery will you implement?

The Direct Answer & Architectural Decision

Keep the authoritative outcome truthful and arrange invalidation retry/repair through a durable mechanism if the freshness promise needs it. Expose the committed version or bypass for read-your-write clients where appropriate. Monitor invalidation age and reconcile missed changes.

Key Trade-Offs & Follow-Up Traps

Repair infrastructure costs operations; a short explicitly accepted stale window can need less. A local transaction rollback cannot undo a committed external cache/origin sequence, and a timeout does not prove deletion never happened.

Redis is unavailable. Should every read go straight to SQL?

The Scenario & Constraint

Normal cache hits hide most load and the database cannot absorb full request volume. What will you do?

The Direct Answer & Architectural Decision

Apply bounded origin concurrency/rate admission, coalesce safe same-key work and use documented degradation or allowed stale responses. Set fast bounded cache timeouts and monitor aggregate fallback work rather than letting every worker bypass without a budget.

Key Trade-Offs & Follow-Up Traps

Some reads fail or wait; provisioning the origin for full uncached load is another cost choice. Coalescing does not reduce distinct-key misses, and retries can amplify the outage.

A newly created product stays invisible because not-found was cached. How do you recover?

The Scenario & Constraint

Negative entries live for ten minutes, but the product team needs new catalog items visible promptly. What will you change?

The Direct Answer & Architectural Decision

Align negative lifetime/invalidation with creation visibility: invalidate the scoped negative entry on creation, use an appropriately shorter policy or verify authoritative existence for the required path. Keep origin failure separate from genuine absence and test create-after-miss races.

Key Trade-Offs & Follow-Up Traps

Shorter negative reuse increases origin work for nonexistent keys; existence/version metadata is another coordination cost. A broad deletion may still race with a late negative fill, so apply the same ordering reasoning as positive values.

A miss reads a lagging replica and caches an old value with a new TTL. Is the TTL enough?

The Scenario & Constraint

The writer invalidated correctly, but the selected source replica is behind. What policy will you choose?

The Direct Answer & Architectural Decision

Define source freshness for cache fills. Use a primary/version-qualified read or a session minimum version where required, or accept and label bounded staleness under a justified model. Avoid refreshing old values indefinitely from an unconstrained source; monitor source/version lag.

Key Trade-Offs & Follow-Up Traps

Fresher source reads may cost latency/capacity; ordinary stale display can be acceptable. TTL measures cache lifetime, not the age of a source snapshot, so resetting it cannot establish a strict origin-freshness bound alone.

Different services implement inconsistent miss and invalidation logic. Should cache-aside remain scattered?

The Scenario & Constraint

One caller caches errors, another omits tenant scope and a third never expires entries. What will you do?

The Direct Answer & Architectural Decision

Centralize the application policy in a reviewed reusable access layer or adopt a verified read-through abstraction where appropriate. Define key/absence/error/lifetime contracts and keep domain authorization explicit. Test the same cases across all access paths.

Key Trade-Offs & Follow-Up Traps

Centralization introduces a shared dependency and may hide costs; cache-aside can remain explicit when a few call sites are disciplined. Merely moving code into a loader does not create a freshness or distributed-transaction guarantee.
