Cache Consistency

🎯 The Hook & ELI5

Two classroom noticeboards can show different timetables. “Both will eventually be updated,” “you will see the change you just made,” and “everyone immediately follows one ordered timetable” are different promises. Cache consistency is choosing which promise a reader receives and implementing the path that can keep it.

Cache consistency concerns the relationship between cached answers, authoritative changes and observations across reads. It is not the same as memory safety, successful replication or database transaction isolation. A valid unexpired entry can still violate a specific reader’s required version.

Our example commits a versioned profile change and returns a receipt identifying that object/version. Ordinary public views can be eventually refreshed, while the editing session needs at least its acknowledged version. The primary session reference defines useful concepts in a database product; this lesson does not transfer that product’s guarantees to Redis, Memcached or a custom cache automatically.

🗺️ High-Level Big Picture

A version token is useful only if it refers to a trustworthy ordered identity and the server actually enforces it. Failure to obtain the required version must not silently become a stale success.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the copy, authoritative owner, acknowledgment and recovery boundary.

1. State a reader-visible guarantee precisely

Describe what the application may observe before selecting a mechanism. These are conceptual choices, not default guarantees of the products used elsewhere.

Different guarantees require different evidence
PromiseReader expectationMechanism obligation
Eventual convergenceCopies converge when updates/repair complete under stated assumptionsReliable enough propagation/repair and no perpetual obsolete refill
Bounded source stalenessAnswer age stays within a defined boundTrustworthy age/version and all-tier enforcement

Monotonic readsA session does not go backward after observing a versionRetain/enforce a meaningful observation floor
Real-time ordered object readsA later read respects a completed earlier write under the stated modelAn end-to-end protocol/authority that supplies that ordering

Do not say merely “strong consistency” without defining the object/operation and failure scope. A promise for one object is not a multi-object serializable transaction.

2. Bind versions to the actual owner and identity

Generate versions/order through the authoritative object owner or another justified protocol, not arbitrary client wall-clock guesses. Bind the version to object generation, tenant and representation where needed. A recreated object or a different tenant must not reuse a token as if it referred to the same history.

A session can carry a minimum observed/committed version for relevant objects and require the read facade to return a satisfying view or use an appropriate origin path. Bound token/state lifecycle and reauthorize access; the token is a consistency condition, not a permission credential.

3. Follow every tier and every writer

A process cache, shared cache, database replica, CDN and browser response can each preserve an older view. Enforcing a minimum only at Redis is insufficient if a browser returns an old response without consulting the read facade. Map keys, versions, cache policy and bypass behavior for the entire path.

Audit direct database writers, background jobs and asynchronous projections. A cached aggregate built from several independently read records can mix versions even if each object is individually acceptable. If a decision requires an atomic multi-object view, obtain one from the authoritative transaction/snapshot boundary or a deliberately versioned projection.

4. Prevent regression and repair unknown state

Old fills and reordered updates can overwrite newer cache content unless publication is guarded within its actual coherence boundary. Immutable version-addressed payloads prevent overwriting the same version key but still require trustworthy current/minimum-version discovery. Missing or evicted metadata is not evidence of freshness.

Consumer gaps, replica lag and cache failover can make the newest safe version unknown. Choose an authoritative read, conservative invalidation/rebuild or truthful failure rather than claiming a local lease proves global currentness. Record repair/backlog signals and test the failure cases the guarantee includes.

5. Spend coordination only where the product needs it

A public catalog display may accept temporary staleness while checkout validates current stock/price. A profile editor can use read-your-write without requiring every unrelated user’s next read to see the change immediately. These narrower promises can reduce cost while remaining honest.

Measure stale-version observations, session fallbacks, origin latency and unavailable-required-version cases. Test write/read routing changes, slow replicas, disconnected invalidation, clock/version mistakes and concurrent updates. Availability and latency costs belong in the decision, not in a hidden fallback that violates the promise.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

A TTL is called read-your-write

Symptom: The user immediately sees an older profile.

Root Cause: The read path accepted any unexpired value.

Fix/Prevention: Enforce the session’s actual committed version or a capable authority.

One tier is fresh but the page is old

Symptom: The API returns version 2 while the browser reuses version 1.

Root Cause: Only one segment of the path enforced freshness.

Fix/Prevention: Map the full representation/tier policy and test real cache hits.

An object promise becomes a transaction promise

Symptom: A cached transfer view mixes debit/credit versions.

Root Cause: Independent object reads were assumed to form one atomic snapshot.

Fix/Prevention: Use the proper transaction/snapshot or versioned aggregate contract.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Name the exact reader promise and enforce it across the real path; versions, TTLs and cache labels are mechanisms whose assumptions must be proven, not substitutes for that promise. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Does read-your-write require all users to see the write immediately?

No. It is a session-specific observation promise. Stronger cross-session real-time ordering requires additional mechanisms.

Does a minimum-version token authorize access?

No. It is a consistency condition scoped to an identity/history; current object/action permission still must be enforced.

Do immutable versioned keys identify the current version by themselves?

No. They protect payload identity but need a trustworthy current/minimum-version discovery path.

Is cache freshness equivalent to database transaction isolation?

No. One concerns reused reader observations; the other governs concurrent authoritative transactions and their visible effects under a specific isolation model.

Tricky & Most-Asked Interview Scenarios

A user saves version 2 and immediately sees cached version 1. What promise can you enforce?

The Scenario & Constraint

The edit is committed but invalidation is asynchronous and requests can land on any worker. What will you do?

The Direct Answer & Architectural Decision

Return an authoritative version/receipt and enforce a minimum-version read for that workflow, falling back to an owner capable of satisfying it or returning honest failure. Audit downstream caches so they cannot bypass the condition. Keep permission checks independent.

Key Trade-Offs & Follow-Up Traps

Version/fallback work costs capacity; a documented eventually refreshed display may suffice for other users. Short TTL or sticky routing does not prove immediate read-your-write through failure.

A session sees version 5, then version 3 after routing changes. How do you stop regression?

The Scenario & Constraint

Different replicas/cache tiers have different lag, but the user must not move backward through one object’s history. What will you implement?

The Direct Answer & Architectural Decision

Track/enforce a meaningful minimum observed version for the relevant session/object and route or read accordingly. Bind tokens to identity/generation and handle required-version unavailability explicitly. Review cache hits at every tier, not only the origin client.

Key Trade-Offs & Follow-Up Traps

Session state adds lifecycle and potentially more authoritative reads; unconstrained eventual reads are cheaper under a weaker contract. A later wall-clock response is not necessarily a newer version. Token data cannot be trusted as authorization.

A ten-second TTL is advertised as a ten-second authoritative-staleness guarantee. What must be true?

The Scenario & Constraint

Fills come from a lagging replica and each tier can reset its own lifetime. What will you change?

The Direct Answer & Architectural Decision

Define the actual source-age/version bound, verify upstream freshness and all-tier behavior, and enforce a suitable version/authority check where the promise requires it. If those conditions cannot be established, describe bounded reuse rather than the stronger unsupported claim.

Key Trade-Offs & Follow-Up Traps

Tracking source age and strict reads costs work; a weaker stale display can be acceptable. Resetting TTL at fill time does not erase source lag or a late old snapshot, and jitter must fit the full bound.

Two individually fresh cached objects form an impossible account total. Is the cache strongly consistent enough?

The Scenario & Constraint

A business decision combines balances that must belong to one atomic view. Separate reads race a transfer. What will you do?

The Direct Answer & Architectural Decision

Obtain the decision from an authoritative transaction/snapshot boundary or an explicitly versioned consistent aggregate. Keep cached independent objects for suitable display work rather than infer multi-object atomicity from their individual versions. Document the decision’s actual concurrency requirement.

Key Trade-Offs & Follow-Up Traps

Snapshots/transactions or projection generation cost resources and coordination; approximate dashboards may accept a weaker view. An object-level read-your-write token does not automatically define a consistent cut across unrelated objects.

Failover loses the cache’s version guard. Can an old fill proceed?

The Scenario & Constraint

The payload and metadata were treated as disposable, yet callers rely on the guard to reject obsolete results. What will you do?

The Direct Answer & Architectural Decision

Treat missing guard state as uncertainty and recover a trustworthy owner/version boundary before accepting guarded publication, or bypass the cache. Engineer metadata retention/failure semantics to match the reader promise and test late fills during recovery.

Key Trade-Offs & Follow-Up Traps

Recovery reduces availability or adds origin work; a weaker stale policy may avoid strict coordination if honestly chosen. A lease or replica label does not prove the newest version survived. A guard absent because of eviction must not mean every historical version is safe.

The shared cache is current but a browser serves a revoked private response. Where is consistency enforced?

The Scenario & Constraint

Only the server cache participates in invalidation; the product requires prompt permission changes at access. What will you change?

The Direct Answer & Architectural Decision

Review the full HTTP/application-storage path, restrict unsafe reuse and enforce the required current authorization/freshness boundary. Separate public reusable fields from protected state when useful. Test warm browser/edge/process copies, not only direct owner reads.

Key Trade-Offs & Follow-Up Traps

Stricter access checks and limited offline storage reduce reuse; a documented bounded revocation window is another product promise. Current database/cache values cannot retract an already uncontrolled offline copy, so scope the guarantee explicitly.
