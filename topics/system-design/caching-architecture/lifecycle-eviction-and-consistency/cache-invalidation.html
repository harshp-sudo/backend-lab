Cache Invalidation

🎯 The Hook & ELI5

A restaurant changes its menu and removes the old printed copies. A waiter returning from the printer can still put an old menu back on a table. Invalidation is not just throwing away one sheet: it is identifying every obsolete copy and preventing or repairing the ways it can return.

Cache invalidation makes a cached result unusable because its source or interpretation changed. It can delete a key, advance a version namespace or notify a client/tier. Expiry removes reuse by age; eviction removes data for capacity. Those mechanisms can help recovery but are not the same update contract.

Our example caches a product page derived from product, category and visibility facts. The owner publishes monotonically meaningful versions under an explicit scheme. We examine invalidation dependencies and races, while related Cache Consistency states the reader-visible promise. The original NSDI 2013 Memcache paper informs race reasoning; its lease extensions are not presented as automatic stock Memcached behavior.

🗺️ High-Level Big Picture

The publication/repair path is part of the design. Sending one best-effort message is not proof that every cached copy became unusable.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the copy, authoritative owner, acknowledgment and recovery boundary.

1. Map facts to derived cache entries

Record which product detail, category list, search fragment and personalized view depend on a changed fact. A cache key that contains only the product ID cannot by itself identify all aggregate pages affected by a category move or permission change.

Choose precise dependency metadata, a coarser namespace/version boundary or short explicitly accepted lifetimes according to cost. Exact reverse indexes need maintenance; coarse invalidation creates more misses. Define responsibility when derived keys are created so the dependency map does not silently omit new view types.

2. Couple change knowledge to the authoritative write

If freshness requires recovery after crashes, produce durable change/invalidation intent with the authoritative change in its real boundary or use an appropriate source change mechanism. Consumers must know how to resume, reconcile and detect gaps.

Redis Pub/Sub delivers at most once; a disconnected listener can miss an update. It can be a useful notification path but not the only retained record when every change must eventually be repaired. Track versions/positions and make reconnect behavior explicit, including discarding local copies whose coherence is unknown.

3. Guard against stale and reordered fills

This complete single-threaded Python model preserves a minimum known version and refuses unknown guard state. It illustrates one local atomic-decision invariant, not a distributed protocol or proof that every new origin version has already arrived.

floor, cache = {}, {}

def invalidate(key, version):
    floor[key] = max(floor.get(key, 0), version)
    if key in cache and cache[key][0] < floor[key]:
        del cache[key]

def fill(key, version, value):
    if key not in floor or version < floor[key]:
        return False
    floor[key] = max(floor[key], version)
    cache[key] = (version, value)
    return True

invalidate("p-7", 2)
assert not fill("p-7", 1, "old")
assert fill("p-7", 2, "new")
invalidate("p-7", 1)
assert cache["p-7"] == (2, "new")
del floor["p-7"]
assert not fill("p-7", 1, "late")
print("known-version and unknown-guard checks passed")

In a real implementation, guard check/update/publication must be coordinated atomically within the chosen coherence boundary, and guard retention/recovery must satisfy the promise. An invalidation that has not arrived cannot protect a reader yet. Missing guard state requires an authoritative/version recovery path, not unconditional acceptance.

4. Handle deletion, recreation and identity changes

An old positive fill can resurrect a deleted object’s view; an old negative fill can hide a newly created object. Preserve meaningful deletion/version state or use an identity generation so an old value cannot masquerade as a recreated object. Retention must cover the old requests that can still complete.

Permission changes can invalidate views even when the underlying product text is unchanged. Do not assume a short TTL is an adequate immediate-revocation policy. Reauthorize or use a reviewed permission-version path where the required promise demands it.

5. Operate invalidation as a bounded pipeline

Measure commit-to-invalidation age, consumer lag, retries, stale-version observations and origin misses caused by invalidation. Make duplicates/order changes safe and ensure repair work cannot regress versions. Test dependency fan-out, consumer restarts, missed messages and late fills.

For large changes, batch/coarsen deliberately and control refill traffic. A global flush can remove uncertainty at one tier while overwhelming the origin and leaving other tiers untouched. Audit the full browser/edge/process/shared path; deletion in one cache is not a universal purge.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

One key is deleted but aggregate pages stay old

Symptom: Category/search views disagree with product detail.

Root Cause: Dependency tracking covered only the direct object key.

Fix/Prevention: Map derived views or use a justified version boundary with refill control.

A missed message lasts indefinitely

Symptom: One worker never learns about a change.

Root Cause: Best-effort notification was the only change record.

Fix/Prevention: Add replay/reconciliation or discard uncertain local state on reconnect.

An older invalidation regresses metadata

Symptom: A delayed event makes an obsolete fill appear valid.

Root Cause: Version handling used arrival order rather than the authoritative order.

Fix/Prevention: Use monotonic meaningful versions and explicit unknown-state recovery.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Invalidation is a change-and-repair protocol over dependent views: know which copies changed, preserve ordering, reject unsafe late fills and recover lost coherence explicitly. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

How is invalidation different from expiry?

Invalidation reacts to changed meaning/source state; expiry ends reuse by age. Capacity eviction is a third cause of removal.

Why can a product edit affect many keys?

Derived lists, aggregates, languages and permission-specific views can all depend on that fact. Key naming alone does not maintain a reverse dependency graph.

Can a disconnected Pub/Sub consumer replay every missed invalidation?

Not from Pub/Sub alone under its at-most-once contract. Retained change state, reconciliation or conservative cache reset must cover the requirement.

Why does the model reject a fill with no known guard?

Absence of metadata is uncertainty, not evidence that an old result is safe. Recover a trustworthy version boundary first.

Tricky & Most-Asked Interview Scenarios

One worker misses an invalidation while disconnected. What happens on reconnect?

The Scenario & Constraint

Local copies have no useful expiry and updates were sent only over Pub/Sub. What will you do?

The Direct Answer & Architectural Decision

Treat the coherence gap explicitly: discard affected local state or reconcile/replay from retained authoritative change/version information. Add a recovery mechanism matching the freshness promise and monitor listener gaps/lag. Keep Pub/Sub as a hint where appropriate.

Key Trade-Offs & Follow-Up Traps

Rebuilds cost origin capacity; durable change streams add retention/consumer management. A successful publish does not establish every subscriber processed the change. Reconnecting alone cannot replay messages the selected Pub/Sub contract never retained.

An invalidation arrives before an old load completes. What must a fill check?

The Scenario & Constraint

Version 2 is known obsolete-to-replace, but an earlier reader still holds version 1 and tries to populate. What will you implement?

The Direct Answer & Architectural Decision

Use a coordinated version/lease guard that can reject the old fill under an explicit retained metadata protocol, or route strict reads to authority. Test the guard check and publication as one intended atomic decision and handle missing/recovered metadata conservatively.

Key Trade-Offs & Follow-Up Traps

Guarding adds coordination; accepting a bounded stale display is simpler under a different requirement. A random lock or delayed second delete is not proof all old readers are fenced. The cited Memcache lease design is an engineered extension, not a default feature of every cache.

A category rename leaves thousands of cached pages with the old name. How do you choose invalidation scope?

The Scenario & Constraint

Precise reverse dependencies are incomplete and a fleet-wide flush would overwhelm the origin. What will you do?

The Direct Answer & Architectural Decision

Choose a reviewed dependency/version boundary for that category or representation family, repair dependency registration and stage controlled refill. Keep unrelated keys usable where possible and measure fan-out and origin admission. Use authoritative lookup for paths that cannot tolerate the transition.

Key Trade-Offs & Follow-Up Traps

Precise tracking costs metadata; a coarser version costs misses and cleanup. A namespace advance does not instantly reclaim old bytes or update a browser copy. State which tier and reader promise the operation actually covers.

Invalidation version 9 arrives after version 10. Should it replace the current marker?

The Scenario & Constraint

Consumers retry and messages can reorder. A newer cached view must not be made obsolete under an older identity. What will you do?

The Direct Answer & Architectural Decision

Use meaningful authoritative version/order information and monotonic application of invalidation metadata. Make duplicate events safe and prevent an old fill from replacing a newer known view. Record/repair gaps instead of assuming arrival order is business order.

Key Trade-Offs & Follow-Up Traps

Version state needs ownership and retention; an ordered per-key log can simplify some pipelines. A timestamp from unsynchronized clients may not be an adequate order. Losing metadata requires recovery rather than resetting the minimum to an unsafe value.

A deleted object is recreated under the same key and an old fill resurrects its former view. What changes?

The Scenario & Constraint

Readers from before deletion can complete after the new object exists. What identity rule will you choose?

The Direct Answer & Architectural Decision

Use a version/generation that distinguishes the recreated entity and preserve deletion/guard information for the required in-flight horizon. Bind new cache entries to that generation and reject old fills; recover authoritative identity if metadata is missing.

Key Trade-Offs & Follow-Up Traps

Generations/tombstones cost retention and lookup work; never reusing object identity can be simpler. A TTL on payloads alone does not stop an older load from beginning a new lifetime after deletion.

A user loses access but its cached view still exists. Is deleting the product key sufficient?

The Scenario & Constraint

Visibility depends on membership as well as product contents, and several tiers hold derived responses. What will you do?

The Direct Answer & Architectural Decision

Include permission dependencies in the invalidation/access policy and enforce the current required authorization boundary at delivery. Remove/bypass unsafe views, map affected tiers and use a trustworthy permission-version mechanism where chosen. Test revocation with warm caches and disconnected clients.

Key Trade-Offs & Follow-Up Traps

Immediate revocation can cost current checks or broader invalidation; a documented bounded exposure policy is a different promise. Public content and private fields may be separated to simplify reuse. Product-version changes alone do not represent every permission change.
