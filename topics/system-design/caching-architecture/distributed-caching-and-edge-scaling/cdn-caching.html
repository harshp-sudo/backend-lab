CDN Caching

🎯 The Hook & ELI5

A chain of local newsstands keeps copies of a newspaper near readers. Public copies can be shared, but a sealed personal letter cannot go on the same shelf. When an edition changes, the publisher must decide whether to replace copies, validate them or publish a clearly new edition address. CDN caching applies those reuse decisions at HTTP edges.

A content delivery network can serve eligible HTTP representations from edge locations before requests reach the origin. The relevant contract includes cache eligibility, key/variation, freshness/validation, private content, purge and failure behavior. A CDN is not automatically a cache for every method, status or content type.

We use RFC 9111 HTTP semantics and Cloudflare’s official cache-key/default-behavior/purge documentation as a named provider example checked for this lesson. Plan, settings and rules can affect actual behavior; examples do not configure a live CDN. The linked REST API Design and API Gateway lessons retain their API-contract/policy focus.

🗺️ High-Level Big Picture

Test the actual rule and cache key through the edge. A correct origin response alone does not prove a personalized or varied representation is safe to share.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the copy, authoritative owner, acknowledgment and recovery boundary.

1. Decide what is eligible and public

Inventory methods, status codes, path/content types, response directives and provider rules. Public static assets are different from authenticated account responses. Default eligibility is provider-specific; an illustrative JSON response is not proof a selected CDN caches JSON without configuration.

Never treat “request has a cookie” as a complete private-content policy. Choose safe private/no-store behavior and deliberate bypass for protected responses where appropriate. If personalized sharing is contemplated, review all identity/permission dimensions and access on cache hits; bypass is often the clearer starting point for sensitive views.

2. Define representation variation and freshness

This illustrative public response permits a one-minute private-cache freshness and a five-minute shared-cache freshness under HTTP rules. It assumes that the public catalog’s product policy permits the longer shared reuse; a provider still must be configured to honor the intended behavior.

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: public, max-age=60, s-maxage=300
Vary: Accept-Language
ETag: "catalog-en-v7"

{"edition":7,"language":"en","title":"Public catalog"}

Include inputs that affect the representation in a safe cache-key/variation policy: locale, selected query parameters, representation version and any other legitimate dimensions. Keep cardinality and untrusted input bounded. Removing a query parameter from the key is safe only if it truly cannot change the selected representation or security behavior.

3. Use validators and versioned resource identities deliberately

A validator such as an ETag lets an origin confirm whether a selected representation changed. A 304 response reuses a stored body under the relevant updated policy; it is not an instruction to invent an empty successful body. Validators must reflect the actual varied representation.

Content-addressed/versioned asset URLs can make immutable asset deployment easier: publish new assets, switch referencing HTML deliberately and retain needed old assets for supported old pages. HTML and API data need their own freshness/update policy. A new filename does not purge old HTML that still points to old assets.

4. Purge the intended key space and verify the scope

A purge operation is provider-specific. Identify URL/custom-key variation, tags/prefix/host options supported by the selected service and any rate/plan constraints before using them. Cloudflare’s documented purge 200 indicates request receipt, not proof the targeted content was previously stored or globally removed.

Check representative URLs/variants and observed edge status/age/version after a purge, and be honest about the regions/paths tested. Use versioned publication where it reduces correctness dependence on purge timing. Old browser/application copies may not be controlled by a provider-side purge.

5. Bound stale serving and origin recovery

stale-while-revalidate and stale-if-error express bounded stale behavior where implemented and allowed. Do not apply stale display rules to current authorization or business decisions without a suitable product contract. A failed refresh must not turn a bounded allowance into infinite reuse.

Expiry/purge can cause many edge locations to contact the origin. Verify request collapsing/revalidation scope rather than assuming one global refresh; protect aggregate origin work. Test cold edges, authentication, language/query variants, changed rules, validation, purge and an unavailable origin through the real provider path.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

A private response becomes public

Symptom: One customer receives another customer’s data.

Root Cause: Eligibility/key policy ignored identity and object permission.

Fix/Prevention: Contain/purge exposure and bypass until a reviewed safe contract exists.

Purge misses a variant

Symptom: Some languages or query views stay old.

Root Cause: The targeted purge did not match the actual key dimensions.

Fix/Prevention: Map variants and verify the selected provider operation with representative requests.

The UI references deleted old assets

Symptom: A previously cached HTML page fails after deployment.

Root Cause: Old asset versions were removed before supported pages stopped referencing them.

Fix/Prevention: Coordinate HTML freshness, version publication and retention.

🧠 Active Recall & Mastery Check

Summarize this in your own words: An edge cache is a representation-reuse contract: verify eligibility, variation, freshness, purge scope and protected-content behavior through the actual provider path. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

How do eligibility and key variation differ?

Eligibility decides whether a response may be cached at all; the key/variation decides which requests can reuse the stored representation.

What does the example s-maxage control?

Its HTTP shared-cache freshness policy, distinct from max-age for private caches. Actual provider/rule behavior still must be checked.

Does a successful purge response prove global content removal?

Not under the cited Cloudflare receipt contract. Verify intended variants/observations and state the scope of that evidence.

Do versioned assets eliminate HTML freshness work?

No. Old HTML can still refer to old assets, which need a deliberate retention/deployment policy.

Tricky & Most-Asked Interview Scenarios

An authenticated response is cached by URL and leaks across customers. What comes first?

The Scenario & Constraint

The origin checks access, but a shared hit bypasses the intended per-caller view policy. What will you do?

The Direct Answer & Architectural Decision

Disable unsafe shared reuse, purge affected variants and review cache eligibility, key dimensions and authorization on hits. Separate public fields from private representations or keep protected content on a bypass path. Test two identities and permission changes through the real edge.

Key Trade-Offs & Follow-Up Traps

Bypass increases origin work; a carefully reviewed isolated representation cache is more complex. Adding a tenant dimension is insufficient when roles/users within it differ. A cookie does not automatically make every configured CDN rule private.

A query parameter is omitted from the cache key but changes output. What is the correction?

The Scenario & Constraint

One variant requests an expanded or localized response and another receives it under the same key. What will you do?

The Direct Answer & Architectural Decision

Make representation-affecting inputs part of a canonical reviewed key or remove their ability to change the cached output. Purge incompatible entries, bound cardinality and test both origin and actual edge behavior. Reject ambiguous inputs where layers disagree.

Key Trade-Offs & Follow-Up Traps

More variation lowers reuse; explicit version/locale paths can simplify the contract. Dropping arbitrary parameters to improve hit rate can change correctness or security. A parameter is safely ignored only after its full routing/rendering effect is understood.

The purge API returned 200, but a user still reports old content. What do you verify?

The Scenario & Constraint

The provider receipt is being treated as proof that every edge, variant and browser was refreshed. What will you inspect?

The Direct Answer & Architectural Decision

Check actual targeted key/URL dimensions, provider operation/rule scope, observed response version/age/status and which cache tier served the user. Test representative variants/locations and distinguish provider removal from browser/app reuse. Record what was verified instead of claiming a global result from the receipt.

Key Trade-Offs & Follow-Up Traps

Broader purge increases miss load and can still leave client copies; versioned publication may reduce purge dependence. The cited Cloudflare response acknowledges receipt, not proof the content existed or was evicted.

New HTML deploys while old cached HTML still points to removed assets. What sequence works?

The Scenario & Constraint

A release deletes every previous asset filename immediately. Some clients break until their HTML refreshes. What will you change?

The Direct Answer & Architectural Decision

Publish new versioned assets before references, update HTML under a deliberate freshness/validation policy and retain old assets for the supported old-reference window. Roll back by restoring valid references/assets where needed. Test cold and warm clients across the deployment.

Key Trade-Offs & Follow-Up Traps

Retention costs storage; very short HTML reuse can reduce but not automatically eliminate old references/offline clients. Asset hashing prevents bytes changing under one URL but does not instantly update every HTML consumer.

Can stale-if-error serve an outdated private entitlement response during an outage?

The Scenario & Constraint

The proposed fallback treats public catalog staleness and current permission checks identically. What will you decide?

The Direct Answer & Architectural Decision

Separate product contracts: permit bounded stale public display only where allowed, and use a capable current authorization path or truthful refusal for strict entitlement decisions. Verify provider implementation and end-to-end expiry/access behavior rather than applying one broad stale rule.

Key Trade-Offs & Follow-Up Traps

Strict checks reduce availability when the owner is unreachable; a documented bounded revocation window is a different explicit promise. Stale HTTP extensions do not redefine business authorization, and failure must not extend stale reuse indefinitely.

A purge makes many edges refresh at once. Does one local request collapse protect the origin?

The Scenario & Constraint

The origin is sized for normal cached traffic, but simultaneous regional misses exceed capacity. What will you implement?

The Direct Answer & Architectural Decision

Verify the scope of provider collapsing/shielding where available, add aggregate origin admission and stage publication/warming/purge where useful. Coalesce safe duplicate work at the appropriate layer and provide bounded stale/degraded behavior under the product policy.

Key Trade-Offs & Follow-Up Traps

Shielding/coordination adds latency and another dependency; origin headroom is another cost choice. Coalescing inside one process or edge does not prove only one load across all locations. Distinct cold keys still consume origin capacity.
