Cache Stampede

🎯 The Hook & ELI5

A popular recipe disappears from the kitchen counter and every cook runs to the archive to copy it at once. One trip would have been enough, but the crowd slows the archive and makes even more cooks join. A cache stampede is this duplicated miss work turning a useful cache into an overload trigger.

A stampede occurs when many requests regenerate the same unavailable value concurrently. Simultaneous expiry of many different keys or a full cache outage can produce related but different origin-load problems. The remedy must identify which work is duplicated, which is necessary and which can be refused or delayed.

Our example has fifty requests/second for one view whose origin computation takes two seconds. Without coordination, roughly one hundred arrivals can start overlapping work during that fill interval under a simple steady-arrival model. Queueing and retries can make recovery worse. The numbers illustrate amplification, not a benchmark.

🗺️ High-Level Big Picture

“One load” applies only within the stated coordination scope and failure assumptions. Bounded waiters, refresh deadlines, result policy and safe publication remain necessary.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the copy, authoritative owner, acknowledgment and recovery boundary.

1. Classify the miss amplification

Measure concurrent regeneration by key, distinct cold keys, origin work duration and retry attempts. A single popular expired value benefits from duplicate suppression; many distinct cold values still require aggregate admission. A random-key flood has different cache value/admission economics.

Observe why a key is missing: expiry, eviction, explicit invalidation, unavailable cache, failed fill or oversized rejected value. Repeatedly applying a TTL fix when the cache cannot store the item will not stop the loop. Use capacity and correctness evidence together.

2. Coalesce work within an explicit scope

A per-key in-flight map can let one process share a refresh result with waiters. Go x/sync/singleflight is a concrete reference for per-Group duplicate function suppression; it is not a distributed ownership service. Canonical keys must include safe tenant/representation context so unrelated private requests never share a result.

Bound the refresh duration, waiter count and memory. Decide how a cancelled waiter affects shared work: it may leave without cancelling a refresh still needed by others, but the refresh needs an independent deadline. Do not let one slow origin call hold unlimited waiters indefinitely.

3. Treat refresh leases as fallible coordination

Across processes, a refresh lease can reduce duplicate work if acquisition, expiry and release follow a verified protocol. Release only an ownership token you still hold, with an atomic check/delete or equivalent. A timed-out old owner can continue executing after another starts, so publication needs an appropriate version/lease guard where stale fills matter.

Redis lock documentation explains important failover/ownership limitations; the Memcache paper describes engineered leases for stale sets/load control. Neither implies every basic cache offers the same protocol or that a refresh lease protects irreversible business effects. Duplicate refresh computation can be tolerable while duplicate charging is not.

4. Use expiry spreading and stale responses under policy

Combine mechanisms according to the actual load and freshness contract rather than treating them as substitutes.

Complementary origin-protection mechanisms
MechanismWhat it controlsWhat it does not prove
Per-key coalescingDuplicate overlapping loads in its scopeGlobal coordination or distinct-key capacity
Bounded TTL jitterSynchronized expiry across entriesNo burst for one hot miss
Stale-while-refresh/error policySome wait/origin work when stale data is allowedCurrent authorization or unlimited stale lifetime
Origin admission budgetAggregate active/arrival workFreshness or safe duplicate business effects

Pre-refresh valuable entries before a hard deadline where useful, but bound refresh traffic itself. Keep any jitter maximum within the justified lifetime model. Stale serving needs an explicit age/access policy and a way to stop once its allowance is exhausted.

5. Make recovery and absence bounded

A verified negative entry can reduce repeated loads for nonexistent objects, but an origin timeout is not absence. Bound negative-key cardinality, lifetime and create-after-miss behavior. Expiring a refresh lease must not create an immediate unbounded retry herd.

Protect the origin with aggregate concurrency/rate/queue limits across the relevant fleet, especially after a full cache loss. Stage warm-up and degrade/refuse honestly when capacity is unavailable. Test a slow owner, owner crash, lease expiry, lost publish, cancelled waiters, stale permission changes and many-key cold start. Measure useful recovery, not only a rising hit ratio.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Jitter is called a hot-key lock

Symptom: One popular expiry still starts many loads.

Root Cause: Spreading key deadlines was mistaken for suppressing same-key work.

Fix/Prevention: Use bounded coalescing/refresh ownership and origin admission.

An old owner deletes a new lease

Symptom: Another refresh loses ownership unexpectedly.

Root Cause: Release ignored token ownership after expiry.

Fix/Prevention: Use the verified atomic owner-check release and guard publication where needed.

Stale serving never ends

Symptom: Private or obsolete data is returned indefinitely during failure.

Root Cause: The fallback lost its maximum age/permission conditions.

Fix/Prevention: Enforce bounded allowed stale behavior and fail or use authority when it cannot be met.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Prevent stampedes by separating duplicate regeneration, synchronized expiry and total cold demand; combine bounded coordination, explicit stale policy and origin admission under honest failure assumptions. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

How do one hot missing key and many distinct cold keys differ?

The first contains duplicated regeneration that coalescing can share. The second still needs many independent loads and aggregate capacity control.

What is the scope of the referenced singleflight Group?

It coordinates duplicate in-flight function calls through that Group, normally inside a process. It does not automatically coordinate every application instance.

Why can two refresh owners run despite a lease?

An old worker may continue after its lease expires while a new worker starts. Safe publication/version rules and bounded work must account for that case.

When is stale serving an acceptable response?

Only when the representation’s age, visibility and product policy explicitly permit it. It is not a blanket fallback for current permission or business-invariant decisions.

Tricky & Most-Asked Interview Scenarios

A two-second fill at fifty requests/second creates roughly a hundred loads. What changes?

The Scenario & Constraint

All callers miss the same scoped view and the origin slows under duplicated work. What will you do?

The Direct Answer & Architectural Decision

Coalesce overlapping work per safe key in the needed scope, bound waiters/refresh deadlines and protect aggregate origin capacity. Publish/reuse a result only under its freshness/authorization policy. Measure actual duplicate load count and recovery latency.

Key Trade-Offs & Follow-Up Traps

Waiters add latency/state; a permitted stale view can avoid waiting. A local coalescer still permits work in other processes, and a unique-key flood needs a separate capacity policy.

Thousands of keys expire together. Is one refresh lock enough?

The Scenario & Constraint

A warm-up job gave every entry the same deadline; most arriving requests concern different keys. What will you do?

The Direct Answer & Architectural Decision

Spread allowed expiry/refresh times, warm high-value entries gradually and enforce aggregate origin admission. Use per-key suppression for duplicate work as a complementary measure, not the only protection. Monitor distinct cold keys and oldest useful refresh work.

Key Trade-Offs & Follow-Up Traps

Jitter/early expiry can increase ordinary refresh volume; origin headroom is another cost. One key’s lock cannot cap work for thousands of different keys. Keep jitter within the actual freshness ceiling.

A slow refresh owner outlives its lease and overwrites a newer result. What prevents it?

The Scenario & Constraint

A second worker acquires the expired lease and publishes version 2 before the first returns version 1. What will you implement?

The Direct Answer & Architectural Decision

Use a verified ownership/version publication guard in its actual atomic coherence boundary and retain/recover the metadata it needs. Release only the current token you own. Bound refresh work and accept harmless duplicate computation only where its effects are truly repeatable.

Key Trade-Offs & Follow-Up Traps

Guards add coordination and can reduce availability on unknown state; simpler stale display may fit another requirement. Extending lease time indefinitely hides failures rather than proving safety. A cache refresh lease is not a payment idempotency guarantee.

Serving stale content keeps latency low during an outage. When must it stop?

The Scenario & Constraint

The product allows a limited stale public catalog view, but the current fallback has no age cutoff and also serves private entitlements. What will you change?

The Direct Answer & Architectural Decision

Separate representation policies, enforce the allowed age/visibility boundary and refuse or use a capable authority once it cannot be met. Keep refresh attempts bounded and provide an explicit degraded state. Do not let errors renew the stale allowance forever.

Key Trade-Offs & Follow-Up Traps

Stopping stale reuse reduces availability; longer explicitly accepted public staleness is another product decision. HTTP stale extensions apply under their real implementation/response contract and do not redefine current authorization.

Bots ask for millions of nonexistent keys. Will negative caching solve everything?

The Scenario & Constraint

Each request uses a different ID and the cache fills with low-reuse negatives while origin traffic stays high. What will you do?

The Direct Answer & Architectural Decision

Bound admission/key cardinality, cache only confirmed absence under a useful scoped short policy and enforce origin/resource limits. Filter clearly invalid requests early and measure negative reuse. Preserve creation visibility/invalidation behavior for legitimate objects.

Key Trade-Offs & Follow-Up Traps

Negative caching helps repeated absent keys, not arbitrary unbounded novelty. A separate existence mechanism may help at added cost. Never store timeout-as-absence or allow the negative set to evict all valuable hot data unchecked.

One caller times out and cancels a shared refresh needed by many others. Who owns cancellation?

The Scenario & Constraint

A coalescer ties refresh lifetime to the first request’s context. Other active waiters now fail and immediately restart work. What will you choose?

The Direct Answer & Architectural Decision

Give shared refresh work an explicit bounded lifetime/owner policy, allow departing waiters to stop waiting independently where appropriate and cap remaining work/waiters. Cancel the refresh only under that policy, preserving a useful result for valid active consumers.

Key Trade-Offs & Follow-Up Traps

Independent work can outlive one request and needs strict resource limits; tightly request-bound work may fit simpler cases. Never turn cancellation into unbounded background jobs or assume a local coordination primitive supplies the desired lifecycle automatically.
