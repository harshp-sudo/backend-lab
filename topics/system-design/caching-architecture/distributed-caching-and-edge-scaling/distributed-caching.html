Distributed Caching

🎯 The Hook & ELI5

A city puts popular reference books in several neighborhood libraries. Someone must decide which branch holds each book, what happens when a branch closes and how readers find a replacement without all rushing to the central archive. Distributed caching adds those coordination and capacity questions to the ordinary copy-and-reuse idea.

A distributed caching design spreads reusable data or access across processes/nodes. Key partitioning, replicated copies and local-plus-shared tiers solve different problems and can be combined deliberately. Distribution does not automatically establish a freshness, durability or global-lock guarantee.

Our product views are rebuildable from an authoritative service. We contrast client-routed Memcached item placement with Redis Cluster’s slot/redirection model using their documented contracts, not a universal recommendation. Business records that cannot be lost require a separate authoritative design; the existing Sharding and Distributed System Fundamentals lessons cover broader ownership/failure vocabulary.

🗺️ High-Level Big Picture

Adding capacity changes placement and miss behavior. Losing an ordinary cache partition should be recoverable under the stated product promise, but the refill load still needs an owner.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the copy, authoritative owner, acknowledgment and recovery boundary.

1. Choose partitioning, replication and tiering separately

Partitioning assigns different keys to owners; replication creates more copies of some data; an L1/L2 design places local copies before a shared cache. Name which one solves capacity, throughput, latency or availability in the actual workload. More copies also require freshness and failure policy.

A partitioned database owns durable data differently from a rebuildable cache partition. Do not hide accepted jobs or deduplication state in a “disposable” node and assume losing it is only a hit-rate issue. State what can be reconstructed and from which owner.

2. Make every client understand actual routing

Client-routed caches require compatible key hashing, server membership and normalization across deployments. Redis Cluster uses slot ownership and documented redirections; a compatible client can update its routing view. A Memcached basic item deployment can use its client’s configured distribution policy instead.

Handle topology changes, stale client views and bounded redirect/retry loops. Include deployment generation/compatibility where needed, and test a mixed-client rollout. A new node is not merely extra RAM: some keys can move or be observed as cold, changing origin load.

3. Budget skew and failure domains

Average keys per node can look balanced while one key dominates requests/bytes. Identify hot key/tenant/result-size distributions, expensive misses and concentration after failover. A single key is not automatically divided by adding more key owners.

Consider smaller reusable units, safe replicated/local immutable views, workload isolation or explicit request reduction. Each introduces assembly/coherence or memory costs. Replicas in the same failure domain may not provide the availability benefit assumed by the design.

4. State failover and partition semantics

Redis Cluster’s documented asynchronous replication can lose acknowledged updates under specified failures. For a rebuildable cache, that can be acceptable if values are revalidated/reloaded under bounded capacity. It is a different problem if the lost key was part of a required business guarantee.

During a network partition decide whether a read may use an allowed stale copy, reach another owner, wait or fail. The cache cannot silently promise current authoritative data while serving an isolated old copy. Refresh leases and metadata also need failure semantics; do not infer a safe global lock from cache availability.

5. Coordinate cold-start, local tiers and observation

Node replacement, rebalancing and full fleet restart can create different cold-key patterns. Warm valuable keys gradually, coalesce duplicate regeneration and enforce aggregate origin limits for distinct-key work. Capacity tests should include degraded topology, not only a healthy uniformly distributed benchmark.

For local L1 caches, define invalidation/version and reconnect-gap handling; shared L2 updates do not automatically reach every process. Measure hit/miss cost per tier, redirects, client retry load, lag, evictions and hot partitions. Reconcile authority and cached views after recovery instead of treating connection health as proof of correctness.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

A new node triggers origin overload

Symptom: Hit rate collapses during expansion.

Root Cause: Placement changed without a cold-key budget.

Fix/Prevention: Stage membership and refill under measured origin admission.

A hot key survives every scale-out

Symptom: One owner still dominates latency.

Root Cause: Partitioning keys was mistaken for splitting a single key’s work.

Fix/Prevention: Measure and redesign that access/representation path.

Connected means consistent

Symptom: Recovered clients serve stale local values.

Root Cause: Connection recovery did not repair missed invalidations/version state.

Fix/Prevention: Reconcile or discard uncertain local copies under the required policy.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Distribute cached work with explicit routing, skew, replica and recovery policies; protect the origin and keep rebuildable copies separate from authoritative business promises. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

How do partitioning and replication differ?

Partitioning assigns different keys to owners; replication adds copies. Their capacity, freshness and failure costs differ.

Why test mixed client versions during scaling?

They may disagree about routing/membership/key normalization, producing misses, stale-looking copies or retry storms.

Why can adding owners fail to fix one hot key?

The key may still have one operation owner and the same per-request bytes/work. Change the access pattern or safe replication strategy where justified.

When is a lost cache node more than a performance issue?

When it contains the only accepted/durable business state or coherence metadata required by a stronger guarantee. Rebuildability must be established, not assumed.

Tricky & Most-Asked Interview Scenarios

Adding cache nodes makes origin traffic spike. What is the rollout strategy?

The Scenario & Constraint

Clients change placement at different times and many requests miss the previously warm set. What will you do?

The Direct Answer & Architectural Decision

Stage compatible topology/key changes, bound redirects/retries and plan controlled warm-up/admission for moved keys. Verify each client’s routing contract and monitor per-owner misses. Keep the authoritative source protected while the fleet converges.

Key Trade-Offs & Follow-Up Traps

A routing/control abstraction centralizes policy at another operational cost; careful client rollout can be enough. More cache capacity does not eliminate the transient cost of cold keys. An unbounded fallback can turn a routine scale-out into an origin outage.

One tenant overloads a shard although key counts are balanced. What do you measure?

The Scenario & Constraint

A few giant/hot views dominate requests and bandwidth; other tenants need isolation. What will you choose?

The Direct Answer & Architectural Decision

Measure traffic/bytes/miss cost by key and tenant, then isolate capacity/admission or redesign/split reusable units where semantics permit. Consider safe replicas/local copies for hot read views and keep their freshness policy explicit. Compare degraded-node capacity as well as averages.

Key Trade-Offs & Follow-Up Traps

Isolation can strand spare capacity and replication multiplies memory/update work. Uniform key count is not uniform load. Sharding a single mutable business invariant arbitrarily can introduce correctness problems rather than solve the cache hotspot.

A promoted replica lacks a recently acknowledged cache value. Is this acceptable?

The Scenario & Constraint

Product descriptions are rebuildable, but another team wants to store accepted order identities in the same service. What boundary will you set?

The Direct Answer & Architectural Decision

Use the documented failover model honestly: revalidate/reload rebuildable views under bounded recovery, and keep required operation identity/outcomes in a storage boundary engineered for their durability. Audit which keys are actually disposable before sharing policies.

Key Trade-Offs & Follow-Up Traps

Durable authority costs more coordination/retention; cache reuse can remain best-effort for safe views. Redis Cluster’s asynchronous replication is not a universal no-loss commit protocol. A cache product label cannot decide the business tolerance for loss.

A region is isolated from the owner but has an old cached copy. What can it serve?

The Scenario & Constraint

Public browsing tolerates limited staleness while checkout requires current validation. What will you do?

The Direct Answer & Architectural Decision

Define separate read/action contracts: permit explicitly bounded stale display where justified and refuse/defer or reach a capable authority for strict decisions. Enforce age/version/access policy and recover coherence when connectivity returns. Keep retries bounded.

Key Trade-Offs & Follow-Up Traps

Stricter operations lose availability during some failures; overpromising currentness is not a valid optimization. Regional copies and leases need their own clock/expiry/failure assumptions. A cached display must not silently approve a purchase invariant.

L2 is current but some L1 workers never invalidate. How do you repair them?

The Scenario & Constraint

A notification connection was down during changes, and local entries have long lifetimes. What will you implement?

The Direct Answer & Architectural Decision

Detect the coherence gap and invalidate/reconcile affected local state from trustworthy versions or retained changes. Define supported tracking/reconnect behavior and strict-read bypass. Test worker restarts, lost subscriptions and delayed old fills.

Key Trade-Offs & Follow-Up Traps

Discarding L1 copies increases shared/origin work, so stage recovery; durable replay needs more infrastructure. Updating shared cache alone is not a fleet-wide local purge. Pub/Sub receipt/connection health cannot prove a worker saw every change.

A full cache restart creates many distinct misses. Will single-flight save the origin?

The Scenario & Constraint

Most cold requests concern different keys; the origin can handle only a fraction of them. What will you do?

The Direct Answer & Architectural Decision

Use an aggregate origin concurrency/rate budget, prioritize useful gradual warm-up and provide explicit degraded/refused responses for excess work. Coalesce duplicate keys as a complementary measure, and monitor recovery throughput/backlog across all application instances.

Key Trade-Offs & Follow-Up Traps

Origin overprovisioning is another cost choice. Single-flight removes duplicate work for one key in its scope but cannot eliminate required loads for different keys. Jitter helps synchronized expiry, not every full-cache-loss workload.
