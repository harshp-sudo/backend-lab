Pagination Strategies

🎯 The Hook & ELI5

Reading a changing guest list by “skip the first fifty names” is fragile when new names are inserted at the top. A bookmark that says “continue after this exact ordered name and ticket number” is more stable. But a bookmark is not a photograph: the list can still change while you turn pages.

Pagination divides a collection into bounded responses and defines how a client continues. Offset/page numbers describe a position to skip; keyset pagination seeks after an ordered boundary; an opaque cursor is a public continuation token that may encode keyset state or another server strategy. “Cursor” describes an interface, not a universal physical database algorithm.

Our example browses one tenant’s orders newest first using non-null created_at plus unique order_id as a tie-breaker. The client contract owns traversal, filter binding, permissions and consistency. For the physical composite-key access path, follow the existing Composite Indexes lesson rather than assuming every cursor makes a query fast.

🗺️ High-Level Big Picture

A continuation belongs to a specific query context and ordering. It does not authorize the query, freeze the collection or prove that the storage path is efficient.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; protocol and implementation examples state their scope explicitly. Trace the same client operation through success, uncertainty and recovery.

1. Define a deterministic collection contract

Choose default/max page size, allowed filters and a total order. Sorting only by created_at is incomplete when several orders share a timestamp; add a unique stable tie-breaker and specify direction/null handling. Cap caller page size and work independently of response serialization.

Decide whether the collection is a live view or a consistent export. Explain what updates, insertions and deletions can do during traversal. If a historical snapshot is required, plan that capability explicitly instead of letting a normal browse token imply it.

2. Compare positional skipping with seeking

Offset pagination can support page-number jumps simply, but a deep offset requires skipping preceding results in common relational execution. Concurrent insertion before the offset shifts positions and can repeat a row on a later page. Deletion can shift a row backward so it is missed.

Keyset continuation after (created_at, order_id) uses the entire last boundary under the same order. With descending non-null keys, continue to tuples strictly less than the boundary. This avoids positional drift from newer insertions ahead of it, but updates to sort/filter attributes can still move rows across the boundary. Verify the actual index/plan; opaque tokens do not choose one for you.

3. Make the public token opaque and context-bound

Return a next token clients must treat as uninterpreted. The example uses short illustrative token strings, not an encoding/security implementation:

GET /orders?status=open&pageSize=2 HTTP/1.1
Host: api.example.test

HTTP/1.1 200 OK
Content-Type: application/json

{"items":[{"id":"o-42"},{"id":"o-39"}],
 "nextPageToken":"opaque-continuation-A"}

Internally bind continuation to the ordered boundary, filter/sort contract version and relevant scope; validate it against the authenticated request. Use authenticated token integrity or server-side token state as appropriate. Base64 is encoding, not encryption or tamper prevention. Recheck authorization on every page even for an intact token.

4. Specify continuation, expiry and counts honestly

Document how a caller detects the end. In an AIP-158-style contract, the next token determines continuation; a short or even empty page can still have a token if filtered/backend work was bounded. Do not infer end only because items.length is below pageSize. This is one chosen contract, not a universal rule for every API.

Define changed-filter behavior, invalid/expired tokens and restart guidance. Keep token versioning independent enough to evolve internals. Exact total counts can be expensive or stale relative to independent pages; label approximate counts or omit them when the product only needs next/previous traversal.

5. Provide a separate consistent export when required

Normal independent page requests can read different committed states. A fixed upper bound can exclude later inserts, but it does not prevent updates/deletes of older rows and is not a full snapshot. For an exact reconciliation dataset, use an explicitly consistent snapshot/export workflow or immutable versioned data under a real supported retention model.

A long database snapshot has resource/retention consequences, so an asynchronous materialized export may be more practical. State snapshot timestamp/identity and expiry, protect tenant access, and make export completion/result retrieval durable. Test tied keys, concurrent mutations, token tampering, context changes and deep-page performance.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Timestamp-only pages skip ties

Symptom: Orders with equal timestamps disappear between pages.

Root Cause: The exclusive cursor boundary omitted a unique tie-breaker.

Fix/Prevention: Use the full total-order tuple and matching comparison/order contract.

A token becomes cross-tenant access

Symptom: A caller reuses a token with a different tenant/filter.

Root Cause: Continuation was treated as authorization or unbound query input.

Fix/Prevention: Bind/validate context and enforce current access per page.

A cursor is advertised as a snapshot

Symptom: A reconciliation run misses rows changed during traversal.

Root Cause: Independent live reads were mistaken for one frozen dataset.

Fix/Prevention: Offer an explicit supported snapshot/export contract and label live semantics.

Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Are cursor and keyset exact synonyms?

No. An opaque cursor is the public continuation interface; keyset is one possible ordered-seek implementation behind it.

Why include an ID beside created_at?

It breaks timestamp ties so the continuation can identify a unique ordered boundary. Direction, null handling and mutable-key behavior still matter.

Does a short page always mean the end?

Only if the API contract says so. In a token-driven contract, follow the explicit next token; bounded backend work may yield fewer items before the end.

Does a stable cursor freeze the dataset?

No. Separate page reads can observe changes. A consistent export needs an actual snapshot/version/retention contract.

Tricky & Most-Asked Interview Scenarios

New orders make page two repeat page-one items. How do you redesign navigation?

The Scenario & Constraint

A newest-first feed uses offsets. Inserts arrive while the user reads, and deep pages are slow. What will you do?

The Direct Answer & Architectural Decision

Offer keyset continuation under a total order such as non-null created_at DESC plus unique order_id DESC, backed by a measured suitable access path. Continue after the full last tuple and keep query context fixed. Explain that newly arriving top items appear on refresh rather than inside the already traversed prefix.

Key Trade-Offs & Follow-Up Traps

Random page-number jumps become less natural; offsets remain reasonable for small stable lists. Mutable sort/filter values can still move rows, so document live-view semantics. A cursor interface without a changed query plan does not remove deep offset work by itself.

Several orders share the cursor timestamp and disappear. What must the token contain?

The Scenario & Constraint

The page ends at 12:00:00, but more records have that exact timestamp. The next query uses strictly older timestamps. How will you fix it?

The Direct Answer & Architectural Decision

Define a total order with a unique tie-breaker, include both boundary values and order context in the server continuation and use the matching seek condition. Test ties at and across page boundaries, including the last item. Keep null/order-direction rules explicit.

Key Trade-Offs & Follow-Up Traps

The token grows slightly and backward navigation needs its own direction policy; a surrogate immutable sequence can be another suitable order if it fits the domain. An inclusive timestamp alone can create repeated loops rather than solve the ambiguity.

A client changes status=open to status=closed but reuses its token. What happens?

The Scenario & Constraint

The token was issued for one tenant/status/sort view. Reuse under changed filters would produce confusing or unauthorized traversal. What will you do?

The Direct Answer & Architectural Decision

Validate the token’s bound query context against the new request and reject/restart according to the contract. Reauthorize current caller access for every page and protect token integrity or use server-side continuation state. Do not expose raw trusted query parameters merely because the token is encoded.

Key Trade-Offs & Follow-Up Traps

Binding context reduces flexible token reuse but makes meaning predictable; server-side state offers control at storage/expiry cost. A signed token is still not authorization and base64 alone does not protect integrity or confidentiality.

Finance needs every row from one instant. Is keyset pagination sufficient?

The Scenario & Constraint

An export spans thirty minutes while order state and deletion continue. Missing or mixed-time rows are unacceptable. What will you offer?

The Direct Answer & Architectural Decision

Create an explicit consistent export under a supported database snapshot/version mechanism or materialize the dataset asynchronously. Return durable job status and an authorized result with snapshot identity/expiry. Separate this contract from ordinary live browsing.

Key Trade-Offs & Follow-Up Traps

Snapshot retention or materialization consumes resources; a best-effort live traversal is cheaper when exactness is unnecessary. A maximum timestamp only excludes later inserts and does not freeze older updates/deletes. Choose a mechanism the actual storage engine can sustain.

A page returns zero items and a next token. Should the client stop?

The Scenario & Constraint

A backend scan bounds work before filtering and may produce an empty page with more scan state. The API follows a documented token-driven continuation policy. What should the consumer do?

The Direct Answer & Architectural Decision

Follow the next token under a bounded request/work policy, not items.length alone, until the explicit end marker. Detect repeated/non-progressing tokens as an error and surface a resumable continuation. Consider server-side query/access improvements if many empty pages make normal use inefficient.

Key Trade-Offs & Follow-Up Traps

Additional requests cost latency; a guarantee of filled pages may require more unbounded server work. If the API instead promises short-page termination, its implementation must honor that different contract. Do not silently mix the two conventions.

An order’s updated_at changes while traversing and it appears twice. Is the cursor broken?

The Scenario & Constraint

The live collection sorts by a mutable update timestamp. Clients want efficient browsing, but a billing integration assumes every order appears exactly once. What will you change?

The Direct Answer & Architectural Decision

State the live-view movement behavior and use stable IDs for duplicate-aware browsing. For billing, provide a durable change feed/checkpoint or consistent export contract that matches its processing requirement instead of treating live pages as an exactly-once job queue. Evaluate immutable ordering where it genuinely fits the use case.

Key Trade-Offs & Follow-Up Traps

Immutable order can hide later updates unless another mechanism exposes them; a change feed costs retention/checkpointing. Keyset avoids some positional drift but does not freeze mutable facts. Client-side deduplication alone cannot recover a row moved entirely past the traversal boundary.
