API Documentation (OpenAPI/Swagger)

🎯 The Hook & ELI5

A restaurant menu, a menu-printing tool and the kitchen are different things. A beautiful printed menu can promise a dish the kitchen never cooks. OpenAPI is a machine-readable menu for an HTTP API; Swagger tools help view, edit or generate things from it. Keeping the running kitchen and the published agreement aligned is still engineering work.

OpenAPI describes HTTP API operations, parameters, request/response shapes and declared security requirements. Swagger is a family of tools associated with that ecosystem; the historical Swagger 2.0 format and newer OpenAPI 3.x documents are distinct versions. A documentation UI is a consumer of the description, not the source of runtime enforcement.

The complete small description below explicitly uses OpenAPI 3.1.1 as an example version, not a claim about the latest release. A real project must pin a supported document dialect and compatible validator/UI/generator versions. Its business API can still be v1 independently of OpenAPI’s 3.1.1 document-format version.

🗺️ High-Level Big Picture

Generation creates artifacts from a description. Verification compares those promises with real behavior; no arrow here implies that writing a schema automatically enforces it.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; protocol and implementation examples state their scope explicitly. Trace the same client operation through success, uncertainty and recovery.

1. Choose a contract workflow and owner

In contract-first work, review the public agreement before implementing it. In code-first work, generate the description from deliberate public models/annotations and still review the resulting contract. Either can work if one authoritative workflow and drift checks are clear; two manually maintained sources are likely to disagree.

Assign ownership of operation meaning, examples, security declarations and retirement. Keep internal persistence entities out of the public model. Treat changes to documented defaults, errors and pagination as contract changes even when the UI still renders successfully.

2. Write an explicit minimal description

This complete small OpenAPI 3.1.1 document describes one protected lookup. It is an illustrative description, not a running service or a security configuration. The responses deliberately document distinct failures as well as the successful shape.

{
  "openapi": "3.1.1",
  "info": {"title": "Order Lookup API", "version": "1.0.0"},
  "servers": [{"url": "https://api.example.test"}],
  "security": [{"bearerAuth": []}],
  "paths": {
    "/orders/{orderId}": {
      "get": {
        "operationId": "getOrder",
        "parameters": [{
          "name": "orderId", "in": "path", "required": true,
          "schema": {"type": "string", "minLength": 1}
        }],
        "responses": {
          "200": {
            "description": "An authorized order summary",
            "content": {"application/json": {
              "schema": {
                "type": "object", "required": ["id", "state"],
                "properties": {
                  "id": {"type": "string"},
                  "state": {"type": "string", "enum": ["open", "fulfilled"]}
                }
              },
              "example": {"id": "o-42", "state": "open"}
            }}
          },
          "401": {"description": "Missing or invalid credentials"},
          "403": {"description": "Caller may not read this order"},
          "404": {"description": "Order not found under this access policy"}
        }
      }
    }
  },
  "components": {"securitySchemes": {
    "bearerAuth": {"type": "http", "scheme": "bearer"}
  }}
}

A production contract should document needed error bodies/headers, bounds and examples in the same explicit way. The example service must actually emit a correct authentication challenge where required; the description alone does not cause it to do so.

3. Declare security and schema semantics accurately

A security scheme defines how a mechanism is described; a security requirement applies it at a document/operation scope. Check inherited requirements and deliberate public-operation overrides. Define actual authorization rules in the service, because a bearer declaration cannot express or enforce every object-level permission.

OpenAPI versions differ in schema behavior. Do not mechanically use a 3.0 nullable keyword as if every 3.1 tool interprets it identically; select the correct dialect and test generated clients. Formats and validation keywords can be annotations or assertions depending on the specification/vocabulary and validator configuration. Pin and verify the actual toolchain.

4. Generate artifacts, then test their behavior

Render documentation from the reviewed document, compile representative generated clients and run contract fixtures against the implementation. Check successful and failed responses, examples, serialization, required/optional/null behavior, security paths and content types. A pretty UI proves only that the tool could render something.

Use real fixture tests for meaningful examples without production secrets. A mock generated from the same wrong description cannot independently prove the implementation conforms. Compare old/new contracts and representative old clients before publishing a breaking change; generated source compatibility and semantic compatibility are different.

5. Publish and evolve without hiding drift

Version the description alongside the implementation and publish the artifact that matches the supported deployment. Tie documentation links and client releases to an identifiable contract. Include recovery semantics such as idempotency retention, cursor expiry and error actions in prose where a shape schema cannot express the full agreement.

Observe production mismatches safely and fix either implementation or description according to the intended public behavior. Keep staging and live server choices explicit in interactive tools; avoid inviting users to send secrets or destructive requests to a surprising target. Documentation maintenance is part of supporting the API, not a one-time export.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

The lock icon gives false confidence

Symptom: Documentation says bearer auth but the endpoint allows anonymous access.

Root Cause: A declaration was mistaken for enforcement.

Fix/Prevention: Apply runtime authentication/authorization and test the real protected path.

The example works only in a mock

Symptom: Live calls reject the documented payload.

Root Cause: The mock and example share the same incorrect description.

Fix/Prevention: Run fixtures against the intended implementation and review the source of drift.

A document upgrade breaks clients

Symptom: Nullability or enum handling changes after regeneration.

Root Cause: Format/tooling versions were treated as interchangeable.

Fix/Prevention: Pin compatible versions, compile/test clients and review semantic changes separately.

Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

How do OpenAPI, Swagger UI and the service differ?

OpenAPI describes the contract, Swagger UI renders/explores it, and the service executes it. Each needs alignment; none automatically proves the others behave correctly.

What does openapi: 3.1.1 identify?

The description format version. It is independent of the business API version, HTTP version and client SDK release.

Does declaring bearerAuth enforce permission?

No. It describes a mechanism/requirement; runtime authentication and object/action authorization must actually enforce the intended policy.

Why test generated clients and live fixtures?

Rendering or generation can succeed while serialization, failure behavior, compatibility or runtime enforcement disagrees with the public contract.

Tricky & Most-Asked Interview Scenarios

The documentation says a field is optional, but production rejects requests without it. What is authoritative?

The Scenario & Constraint

Clients generated from the published description fail against the deployed API. Teams each claim their artifact is correct. What will you do?

The Direct Answer & Architectural Decision

Identify the intended supported public contract and actual affected consumers, add a reproducible fixture, then align the implementation/description through a compatibility-aware change. Make one workflow authoritative and run structural plus live contract checks before publishing matching artifacts.

Key Trade-Offs & Follow-Up Traps

Strict contract-first or disciplined code-first can both work; two manually drifting sources impose more reconciliation. Updating docs to match an accidental breaking runtime behavior does not retroactively protect existing clients. Preserve a migration path where the published promise is relied on.

Swagger UI shows authentication, but an anonymous direct request succeeds. What failed?

The Scenario & Constraint

The OpenAPI document declares bearer security, yet no runtime middleware or service check protects the operation. What will you change?

The Direct Answer & Architectural Decision

Enforce authentication and owner authorization in the actual runtime, inspect gateway/direct paths and add real unauthorized/forbidden fixtures. Keep the description’s requirement accurate and test inheritance/overrides. Treat the UI indicator as documentation, not a security control.

Key Trade-Offs & Follow-Up Traps

Runtime enforcement adds configuration and test work; a deliberate public operation may instead need an explicit documented exception. An API key or hidden UI button is not a substitute for access policy. Object-level permissions still matter after a valid bearer token.

A 3.0-to-3.1 document migration changes generated null handling. What is the rollout?

The Scenario & Constraint

The service behavior is meant to stay stable, but regenerated clients reject or omit values differently. What will you do?

The Direct Answer & Architectural Decision

Pin the document dialect and generator versions, inspect supported schema/nullability semantics and test representative old/new client serialization against real fixtures. Correct the description/tool settings without silently changing the business contract; stage client releases and communicate any unavoidable break.

Key Trade-Offs & Follow-Up Traps

Keeping an older supported toolchain can be a temporary alternative; migration adds compatibility fixtures. A format-version upgrade is not a business API version by itself, but generated source and wire behavior can still change. Successful code generation is not compatibility proof.

All mock tests pass while production errors use another shape. How do you close the gap?

The Scenario & Constraint

The mock is generated from the same OpenAPI file as the clients. The actual service returns a different error media type and missing machine codes. What will you test?

The Direct Answer & Architectural Decision

Run contract fixtures against the implementation for known failures as well as success, verify status/content type/body and safe diagnostics, and fix the intended contract at its owner. Keep the mock for consumer development but do not use it as independent conformance evidence.

Key Trade-Offs & Follow-Up Traps

Real fixtures require setup and controlled data; targeted tests for important operations can keep cost bounded. A schema validator may not capture retry meaning or privacy, so review those separately. Avoid copying production secrets into test examples.

The schema documents idempotencyKey as a string. Is that enough for safe retries?

The Scenario & Constraint

A partner needs to recover timed-out order submissions, but retention, key conflicts and in-progress outcomes are absent from the reference. What will you add?

The Direct Answer & Architectural Decision

Document the complete behavioral contract in operation prose/examples: identity scope, meaningful payload equality, duplicate concurrency, outcome replay, retention/expiry and reconciliation. Link relevant error/status examples and verify them against the implementation. Keep schema shape checks as one part of the agreement.

Key Trade-Offs & Follow-Up Traps

Behavioral documentation needs maintained fixtures and review; an explicit operation-status resource can simplify client reasoning. A string schema cannot guarantee duplicate-safe execution. Generated SDKs still need correct retry policy rather than automatically retrying every failure.

A new enum in the description breaks a partner SDK. Can you call it documentation-only?

The Scenario & Constraint

The backend adds a state and regenerated client code becomes incompatible with an old consumer. What will you do before release?

The Direct Answer & Architectural Decision

Review the actual source/wire/semantic compatibility, test representative consumers and unknown-value behavior, and provide a compatible migration/version policy where required. Publish matched description/client artifacts with release notes and preserve supported old behavior during transition.

Key Trade-Offs & Follow-Up Traps

Generated clients reduce handwritten work but couple consumers to tooling choices; tolerant handwritten parsing is an alternative with its own correctness burden. A change in the description can expose or create a real contract break even when the docs page simply gains one line.
