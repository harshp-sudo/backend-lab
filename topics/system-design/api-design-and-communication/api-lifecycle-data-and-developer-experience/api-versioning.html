API Versioning

🎯 The Hook & ELI5

A bus route can add a new stop without changing your existing destination, but renumbering every stop without notice strands people who memorized the old map. API versioning helps old and new clients coexist when the meaning of their agreement changes. Printing “version 2” on the map does not itself keep either bus route working.

An API version identifies a supported contract or compatibility boundary. Compatibility includes source/tooling, wire format and business semantics: a response can still parse while its changed units, ordering or defaults break a consumer. Google AIP-180 is a concrete primary compatibility policy, not a universal requirement that every API must copy its naming scheme.

Our example evolves an order API used by mobile clients that update slowly and partners outside the team’s control. Distinguish the business API version from HTTP version, the version of an OpenAPI description format and a client-library release number. Those can change independently and serve different purposes.

🗺️ High-Level Big Picture

Version labels organize compatibility; running and retiring versions requires evidence about actual consumers, not only a published date or a passing schema parser.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; protocol and implementation examples state their scope explicitly. Trace the same client operation through success, uncertainty and recovery.

1. Inventory the real contract

List request/response fields, requiredness, errors, ordering, pagination, defaults, permissions, side effects and practical resource limits that clients rely on. Include generated-code and strict-reader behavior, not only JSON syntax. Identify supported consumers and how long they can remain on old software.

A change from integer cents to decimal dollars is breaking even if both fit the same broad numeric field. Starting to paginate a formerly complete list can silently lose results for old clients. Compatibility review must ask what the client concludes, not merely whether the payload deserializes.

2. Prefer compatible growth when the meaning holds

Add optional capabilities with defaults that preserve old behavior, and keep established meanings stable. Document unknown response fields and unknown enum handling for intended clients; an additive enum can still break a consumer with an exhaustive switch. Removing or making an input newly required is not additive for existing callers.

Deprecation is a warning and migration signal, not immediate removal. Test both old-client/new-server and new-client/old-server combinations where they are supported. Do not promise a compatible change if a generated client or business interpretation contradicts that claim.

3. Choose explicit selection and cache behavior

Path, header or media-type selection can all be deliberate policies. Choose one coherent consumer-visible scheme and reject unsupported selections clearly. These examples illustrate alternatives rather than requests to combine them:

GET /v2/orders/o-42 HTTP/1.1
Host: api.example.test

GET /orders/o-42 HTTP/1.1
Host: api.example.test
Accept: application/vnd.example.order-v2+json

With negotiated representations, make intermediaries aware of variation and test actual cache keys. A path version is visible in logs/routing but not inherently more compatible. Do not silently serve a different major contract when a requested version is unknown.

4. Separate public versions from implementation duplication

One domain owner can serve several adapters/contracts without maintaining independent copies of every business rule. Keep conversions explicit and test both views against shared invariants. A new external version does not automatically require another database or another independently writable copy of orders.

When a semantic break cannot be represented safely by an adapter, define migration of stored/client state and coexistence behavior carefully. Avoid dual writes whose disagreement becomes a hidden “versioning” problem. Record which team owns old-version support, security fixes and retirement decisions.

5. Migrate using measured adoption and a rollback plan

Publish the change, examples, mapping guidance and support/deprecation timeline. Measure actual traffic by consumer/version without logging secrets. Find clients that appear inactive but run monthly jobs; coordinate partners rather than inferring migration from a short quiet period.

Use staged rollout and compare error/behavior signals. Preserve a viable rollback/old-contract path while clients migrate; new data semantics can make a simple binary rollback unsafe. Retire only under the published policy with evidence and communication. Test unsupported/retired-version responses so callers can act on them.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

A “minor” change breaks checkout

Symptom: Old clients misread amounts after deployment.

Root Cause: A stable field name/type acquired new units.

Fix/Prevention: Treat semantic meaning as contract and migrate with a distinct capability/field/version.

Unknown versions silently succeed

Symptom: A client requests v3 but receives v2 without knowing.

Root Cause: Fallback routing hides unsupported contract selection.

Fix/Prevention: Reject or explicitly negotiate according to a documented policy.

Retirement misses a monthly client

Symptom: A partner’s scheduled job fails after old-version shutdown.

Root Cause: A brief no-traffic window was treated as proof of migration.

Fix/Prevention: Inventory consumers and observe realistic usage cycles with direct migration communication.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Version the client agreement when necessary, preserve meanings where possible and make coexistence, evidence-based migration and retirement part of the implementation. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Can a parsing-compatible response still break a client?

Yes. Changed units, ordering, permissions, errors or defaults can change what the client concludes even when its parser accepts the bytes.

Is OpenAPI 3.1 the same as API v3?

No. One describes the document format version; the other may identify a business contract. HTTP and SDK release versions are separate as well.

Why can an added enum value be risky?

Some consumers have exhaustive switches or generated types without unknown-value handling. Compatibility depends on the supported consumer contract, not only field addition.

What does deprecation accomplish?

It warns and directs migration while support policy remains explicit. It is not proof that all clients migrated or permission to remove immediately.

Tricky & Most-Asked Interview Scenarios

The response number changes from cents to dollars but keeps its field type. Is a version needed?

The Scenario & Constraint

Partner clients parse the number correctly but would charge the wrong amount under the new meaning. What will you do?

The Direct Answer & Architectural Decision

Preserve the old field meaning and add an explicit new representation/field or breaking-contract version with units documented. Migrate consumers with examples and tests for both semantics. Keep the authoritative money rule in one owner and make any conversion deliberate.

Key Trade-Offs & Follow-Up Traps

Parallel fields/adapters add support cost; a coordinated breaking upgrade can fit a fully controlled client fleet. Renaming a library release or claiming the JSON type is unchanged does not protect behavior. Historical stored/client values may also require migration.

A new required fraud field is needed, but old apps update quarterly. How do you ship?

The Scenario & Constraint

The service can improve fraud checks using a new client signal. Existing consumers cannot supply it immediately. What rollout will you choose?

The Direct Answer & Architectural Decision

Determine whether a safe explicit old-client default/fallback exists. If so, introduce an optional field with the old behavior and measure adoption; otherwise provide a new contract boundary and a documented support/risk policy for old clients. Do not silently invent a signal that changes the decision’s meaning.

Key Trade-Offs & Follow-Up Traps

A fallback may reduce protection temporarily; a coordinated minimum-client cutoff may be justified under a different product policy. Newly required input is a break regardless of a “minor” server release label. Communicate migration rather than letting schema rejection discover the policy.

An additive status crashes old clients. What failed in compatibility review?

The Scenario & Constraint

The API adds a new order status, but generated clients use exhaustive cases and reject it. What will you do?

The Direct Answer & Architectural Decision

Review the published consumer unknown-value contract, mitigate the rollout for affected clients and provide a compatible representation or migration path. Add mixed-version fixtures and teach clients a deliberate unknown/fallback state where appropriate. Preserve meaningful distinctions instead of mapping every new status to success.

Key Trade-Offs & Follow-Up Traps

Tolerant clients improve future evolution but require safe product behavior; a new contract version is an alternative when unknown values cannot be handled. A wire-compatible addition does not imply source or semantic compatibility. Avoid losing terminal/error distinctions to a generic fallback.

Header-selected v2 clients receive a cached v1 representation. Where do you fix it?

The Scenario & Constraint

Both versions use /orders/o-42, but a cache keys only on the path. A new client sees the wrong schema. What will you change?

The Direct Answer & Architectural Decision

Make representation negotiation part of the cache contract using the appropriate variation and actual product cache configuration, or bypass reuse until safe. Purge/namespace incompatible entries and test both versions through real cache hits. Keep authorization variation separate and equally protected.

Key Trade-Offs & Follow-Up Traps

More variants reduce cache efficiency; path-based versioning is another deliberate selection policy. A correct origin response is insufficient if the intermediary ignores version inputs. Unsupported versions should not silently fall back to a cached older contract.

Must v1 and v2 write to different databases?

The Scenario & Constraint

A team proposes duplicating the order database to support two API versions, even though both represent the same business order. What will you do?

The Direct Answer & Architectural Decision

Keep one authoritative domain owner where the invariant is the same and implement explicit versioned request/response adapters. Test both contracts against the same ownership rules. If semantics truly diverge, plan a deliberate data/domain migration rather than independent unsynchronized writes.

Key Trade-Offs & Follow-Up Traps

Adapters add translation and regression fixtures; separate ownership can be valid for genuinely distinct domains. Duplicating data merely for a URL version introduces conflict/reconciliation work. Ensure new state can still be represented honestly to supported old clients.

Traffic on v1 is quiet for a week. Can it be removed?

The Scenario & Constraint

A partner runs monthly settlement and has not confirmed migration. The published support window has not ended. What will you do?

The Direct Answer & Architectural Decision

Inventory consumers, observe realistic usage cycles, communicate migration/retirement policy and verify partner readiness. Keep the supported version secure while migration proceeds; stage retirement with actionable unsupported-version behavior and an operational fallback where feasible.

Key Trade-Offs & Follow-Up Traps

Long support windows cost maintenance; a documented enforced cutoff may be appropriate under a different agreed policy. Quiet traffic is not evidence that scheduled clients no longer exist. If a security emergency forces an earlier cutoff, communicate the concrete policy and impact rather than pretending it was a compatible change.
