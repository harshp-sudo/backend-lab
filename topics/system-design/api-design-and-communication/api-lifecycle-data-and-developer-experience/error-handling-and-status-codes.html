Error Handling & Status Codes

🎯 The Hook & ELI5

A delivery notice should tell you whether the address was unreadable, nobody was allowed to accept the parcel, or the courier may already have delivered it before the phone disconnected. “Something went wrong” cannot guide the next step. API errors are instructions for safe recovery, not just numbers for a log dashboard.

An error contract combines protocol status, stable machine-readable meaning, safe human guidance and recovery policy. A client needs to know whether to correct input, authenticate, request permission, refresh state, wait or reconcile an uncertain operation. A status code alone rarely supplies the entire answer.

We will model an HTTP order API with RFC 9110 status semantics and RFC 9457 Problem Details. Other protocols have their own error layers: GraphQL can return execution errors with partial data, gRPC has RPC status, and SOAP has versioned structured faults. An edge adapter must preserve meaning rather than treat every failure as the same HTTP response.

🗺️ High-Level Big Picture

Public recovery guidance and internal diagnostics serve different audiences. Preserve uncertainty when the service cannot prove whether an effect occurred.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; protocol and implementation examples state their scope explicitly. Trace the same client operation through success, uncertainty and recovery.

1. Classify the condition at an ownership boundary

Translate expected domain conditions intentionally: malformed input, missing credentials, denied access, absent resources, current-state conflicts and unexpected failures. Keep error mapping near the API boundary while retaining original internal causes for controlled diagnostics. Avoid every layer independently logging the same exception and flooding alerts.

A 401 response concerns authentication and requires the relevant authentication challenge; 403 represents refusal under the permission policy. A service can deliberately conceal resource existence where appropriate. Distinguish business conflict from a failed explicit conditional request such as If-Match; document the actual recovery flow instead of memorizing a universal code list.

2. Use a stable problem representation

Problem Details offers a standard HTTP error representation. This complete illustrative response uses a stable problem type and custom fieldErrors extension; that extension is an application convention, not a mandatory RFC member.

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json
Cache-Control: no-store

{
  "type": "https://api.example.test/problems/invalid-quantity",
  "title": "Invalid quantity",
  "status": 422,
  "detail": "Quantity must be between 1 and 100.",
  "instance": "/requests/req-7",
  "fieldErrors": [{"pointer":"/quantity","code":"out_of_range"}]
}

The actual HTTP status remains authoritative for HTTP behavior; keep the body status consistent with it. Clients branch on documented stable identifiers, not localized title/detail text. Define safe correlation/instance handling without exposing credentials or storage internals.

3. Separate retryability from outcome certainty

An invalid request normally needs correction before retry. A throttled request may need waiting; a transient dependency failure may permit a bounded retry. A timeout after a mutation can mean an unknown outcome rather than a rejected operation. Reuse a stable operation identity and reconcile before creating a new intent.

Document retry budgets, backoff/jitter and useful Retry-After behavior where supported. Neither a 5xx status nor a library exception universally proves safe repetition. Keep gateway/client retries from multiplying attempts and distinguish service overload from one caller exceeding a quota.

4. Preserve protocol-specific meaning

For GraphQL, distinguish request failures from execution errors and inspect data/errors under the chosen media-type/server contract. Some execution can return useful partial data; non-null propagation can remove a subtree. Do not declare every GraphQL failure either HTTP 200 or HTTP 500 without that context.

For gRPC, inspect the RPC status rather than HTTP 200 alone. For SOAP, use the selected version’s fault and binding semantics. When exposing an HTTP edge, map these to documented domain meanings and preserve partial/uncertain outcomes instead of converting every downstream exception to unconditional success.

5. Keep errors secure, observable and compatible

Return the minimum useful safe detail and stable correlation references; keep stack traces, SQL text, credentials and personal payloads in appropriately controlled diagnostics. Avoid logging secrets merely because an error occurred. Match metrics to error categories and impact, separating expected client refusals from unexpected server faults.

Test known failure cases, intermediary behavior, partial responses, redaction, unknown machine codes and old-client compatibility. Error fields/statuses are part of the contract: changing everything from 200-with-error to meaningful failure may be a needed fix, but it still requires a consumer migration plan. Never claim a successful business outcome solely to keep an HTTP success metric green.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

A success body contains a failure

Symptom: Monitoring and clients treat a rejected operation as completed.

Root Cause: Every exception is wrapped in HTTP 200.

Fix/Prevention: Use truthful protocol/domain outcomes and migrate dependent clients deliberately.

A retry repeats a committed charge

Symptom: A gateway timeout triggers a fresh payment.

Root Cause: Failure status was mistaken for proof of no effect.

Fix/Prevention: Use operation identity and authoritative reconciliation.

An error becomes a data leak

Symptom: Validation returns a token or full SQL stack.

Root Cause: Internal diagnostics were copied into the public response.

Fix/Prevention: Return safe stable detail/correlation and control internal logs separately.

🧠 Active Recall & Mastery Check

Summarize this in your own words: An error response should preserve truth and guide one safe next action, with stable meaning, protocol-aware handling, controlled diagnostics and explicit uncertainty. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Why provide a machine type/code beyond status?

A status groups protocol-level meaning, while a stable documented identifier can distinguish domain causes and recovery. Human wording should not be parsed as the machine contract.

Does a timeout prove the mutation failed?

No. The operation may have committed before the reply was lost. Retry under a safe identity/outcome contract or reconcile authoritative state.

Can HTTP 200 alone establish gRPC or GraphQL business success?

No. Inspect the relevant RPC status or GraphQL result/error contract. Protocol-specific execution and partial-result semantics matter.

Where should a stack trace live?

In appropriately controlled internal diagnostics when needed, referenced by safe correlation. It should not be copied into an ordinary public error response.

Tricky & Most-Asked Interview Scenarios

Every failure returns 200 with success=false. How do you fix the contract safely?

The Scenario & Constraint

Proxies and client SDKs treat invalid requests and service failures as success, but some old clients depend on the current envelope. What will you do?

The Direct Answer & Architectural Decision

Define a consistent status/problem mapping for known conditions, keep stable machine identifiers and introduce it through a measured compatibility/migration path. Test clients and intermediaries, distinguish expected refusals from server faults and preserve truthful business outcome.

Key Trade-Offs & Follow-Up Traps

Migration and parallel support cost effort; a tightly controlled client fleet may allow a coordinated change. Simply flipping statuses without consumer analysis can break retries or error handling. Leaving misleading 200 responses permanently also obscures real failure behavior.

A 504 reaches the client after an order/payment may have committed. What should it do?

The Scenario & Constraint

The gateway lost the downstream reply. The UI wants to show “failed” and submit another fresh purchase. How will you handle recovery?

The Direct Answer & Architectural Decision

Show an unresolved/pending outcome, preserve the original operation identity and query/retry according to the authoritative outcome contract. Use bounded attempts and correlation for support. Distinguish a confirmed domain rejection from a transport path that cannot establish the result.

Key Trade-Offs & Follow-Up Traps

Status reconciliation adds state/UI complexity; an async operation resource can make it explicit. A gateway 504 is not a rollback certificate. Changing to a new key can create another real purchase even though the first reply was an error.

Should an expired credential and a forbidden order use the same response?

The Scenario & Constraint

Clients need to know when reauthentication may help, but the API must avoid revealing private resource existence. What will you choose?

The Direct Answer & Architectural Decision

Use documented authentication challenge behavior for missing/invalid credentials and a deliberate permission/existence policy for authenticated access. Keep public detail safe and enforce the same owner authorization regardless of wording. Teach clients that re-login does not grant missing object permission.

Key Trade-Offs & Follow-Up Traps

Uniform concealment can reduce information leakage but makes debugging harder; safe correlation/support can compensate. Returning 401 for every permission denial can cause endless token refresh, while exposing object details in a 403/404 can defeat the intended privacy policy.

Developers want SQL errors and submitted tokens in Problem Details. What belongs there?

The Scenario & Constraint

Support needs enough context to resolve validation and unexpected failures. The same endpoint accepts credentials and personal information. What will you expose?

The Direct Answer & Architectural Decision

Return stable problem types, safe field categories and an opaque correlation reference. Redact secrets and unnecessary existence/internal details; retain useful diagnostics only in controlled systems with appropriate access. Make error examples show the redacted contract, not production payloads.

Key Trade-Offs & Follow-Up Traps

Reduced public detail requires better support tooling; known non-sensitive validation bounds can still be explained clearly. Problem Details standardizes a representation, not a license to publish internal exceptions. Logging every raw body can simply move the leak to another system.

A response has useful data and a field error. Should the adapter discard it all?

The Scenario & Constraint

A GraphQL order screen has a valid order total but its optional customer lookup failed. The HTTP adapter currently returns either blanket 200 success or blanket 500 with no data. What will you do?

The Direct Answer & Architectural Decision

Define the client’s partial-result contract and preserve field-level error meaning where useful, including nullability behavior. Distinguish request validation from execution errors under the actual transport/media type. If the edge intentionally requires an atomic view, state and enforce that different product contract rather than accidentally discarding data.

Key Trade-Offs & Follow-Up Traps

Partial handling complicates UI states; a simpler all-or-fail read model can fit another requirement. Do not show an untrustworthy total as valid just because another field succeeded. gRPC/SOAP need their own adapters rather than copying GraphQL conventions blindly.

A client retries every 4xx and 5xx until the deadline. What policy would you publish?

The Scenario & Constraint

Validation failures, conflicts, 429s and transient dependency faults are treated identically, creating load and duplicate side effects. What will you change?

The Direct Answer & Architectural Decision

Publish stable error categories and condition-specific actions: correct input, refresh/reconcile state, authenticate, wait or safely retry. Bound total attempts/time and preserve duplicate identity for mutations. Offer truthful retry timing where available and instrument logical operations versus attempts.

Key Trade-Offs & Follow-Up Traps

A detailed taxonomy requires client implementation and compatibility care; a smaller stable set with clear guidance may be enough. Not all 4xx are permanently hopeless and not all 5xx prove safe repetition. Retry-After is guidance, not a guarantee that capacity will be reserved.
