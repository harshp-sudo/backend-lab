Request Validation

🎯 The Hook & ELI5

A school permission slip can have every box filled correctly and still be signed by the wrong person. Checking its shape is useful, but the school must also check who may approve the trip and whether seats are still available. API validation has the same layers: readable input, acceptable meaning, permission and current business rules.

Request validation checks whether incoming data meets an explicit contract. Structural checks cover types, required fields and bounds; semantic checks cover meanings such as a start date preceding an end date. Authentication, authorization and concurrency-safe domain invariants remain separate responsibilities.

Our example creates a shipping request with a bounded quantity and delivery note. JSON Schema examples explicitly use the 2020-12 dialect. Validation behavior depends on dialect and library configuration, including coercion and format handling; state those choices instead of assuming a schema file configures the runtime automatically.

🗺️ High-Level Big Picture

These are logical boundaries, not a requirement to parse unauthenticated huge bodies first. Deploy authentication and cheap rejection early where appropriate, while keeping all layers explicit.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; protocol and implementation examples state their scope explicitly. Trace the same client operation through success, uncertainty and recovery.

1. Bound and parse before trusting a structure

Check supported media type, compressed/decompressed size limits, nesting and collection bounds appropriate to the endpoint. Reject malformed input deliberately and release resources. Choose one interpretation for ambiguous duplicate parameters/JSON members across gateway and service; avoid inconsistent “first wins” versus “last wins” decisions.

Do not deserialize arbitrary privileged application objects. A dedicated request model prevents a caller from assigning fields such as internalRole or approvedBy merely because they exist in the persistence entity. Client-side validation improves feedback but cannot protect a server from a custom caller.

2. Declare a strict contract where it fits

This complete illustrative schema permits only the intended fields. It rejects an unknown property and requires a bounded integer quantity. A server still needs a configured compatible validator and request parser.

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["itemId", "quantity"],
  "additionalProperties": false,
  "properties": {
    "itemId": {"type": "string", "minLength": 1, "maxLength": 80},
    "quantity": {"type": "integer", "minimum": 1, "maximum": 100},
    "deliveryNote": {"type": "string", "maxLength": 500}
  }
}

Strict unknown-field rejection catches typos and unexpected assignments but is a public compatibility policy, not a universal rule. If extension fields are allowed, define where and how they are interpreted. Avoid undocumented string-to-number coercion that makes one layer validate a different value from another.

3. Normalize only by a documented meaning

Choose canonicalization rules for identifiers, dates, Unicode and whitespace based on the actual domain. A display name and a cryptographic identifier do not have the same case/normalization policy. Preserve original values when needed for audit and avoid repeated inconsistent decoding.

Run semantic checks after parsing into the agreed representation: date order, supported currency or mutually exclusive fields. Use parameterized database operations and context-appropriate output encoding independently; an input allowlist is not a universal defense against every injection or rendering problem.

4. Let the owner enforce permission and concurrent rules

A valid itemId does not prove the caller may ship that item. Authorize using trusted identity and the requested object/action. Then enforce stock/credit/uniqueness invariants in an authoritative concurrency boundary; a preflight validation request cannot reserve a fact against another simultaneous writer.

Keep gateway validation for inexpensive boundary checks and service validation for the actual domain operation, with shared versioned contracts where useful. Do not let gateway acceptance become a bypass around service policy or permit untrusted fields to choose privileged execution paths.

5. Return useful safe errors and evolve deliberately

Provide stable machine codes and safe field pointers or validation categories. Explain what a caller can correct without echoing secrets or full sensitive payloads. Choose documented HTTP status/error semantics consistently, separating malformed input, unsupported media, permission failures and current-state conflicts.

Test valid boundaries, missing/null distinctions, unknown fields, duplicate inputs, large/nested inputs and mixed validator versions. Newly required fields, stricter bounds or changed coercion can break existing clients. Plan a compatibility/migration policy rather than silently tightening a published contract after deployment.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

A valid request escalates privileges

Symptom: A caller sets an internal approval field.

Root Cause: The server binds untrusted fields directly into a persistence object.

Fix/Prevention: Use a dedicated request model and explicit allowed assignments plus authorization.

Both validations pass, but stock goes negative

Symptom: Two simultaneous requests each see one item left.

Root Cause: A preflight check was separate from the authoritative decrement.

Fix/Prevention: Enforce the invariant atomically with the change.

A regex blocks the service

Symptom: A short-looking field consumes excessive processing.

Root Cause: An expensive validation expression meets adversarial input without bounds.

Fix/Prevention: Bound input/work and choose safe tested validation mechanisms; observe rejection cost.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Validate bounded interpreted input, authorize the actual action and enforce current invariants at their owner; none of those checks substitutes for the others. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Does a valid UUID authorize reading that object?

No. It establishes a shape property at most. Object/action permission must be checked against trusted identity and ownership policy.

Does adding a schema enforce it automatically?

No. The actual runtime/parser/validator must use the intended dialect and configuration, with tests for coercion and boundaries.

Can a separate availability check protect concurrent inventory writes?

No. Availability can change after the check; enforce the invariant within the authoritative state transition.

Should all APIs reject unknown fields?

It is a documented contract choice. Strict requests catch mistakes but can constrain evolution; allowed extensions still need explicit meaning and resource bounds.

Tricky & Most-Asked Interview Scenarios

A valid JSON body sets approvedBy and bypasses a workflow. Where do you fix it?

The Scenario & Constraint

The service deserializes into its database entity, which contains public and internal fields. A caller adds an internal approval property. What will you do?

The Direct Answer & Architectural Decision

Use an explicit request model/allowlist, map only permitted fields and enforce approval authorization in the owning domain operation. Reject or deliberately ignore unknown fields under a documented policy, and test that direct/backend paths cannot set privileged state.

Key Trade-Offs & Follow-Up Traps

Separate models add mapping work; a carefully configured explicit binder can be another implementation. Schema validity alone does not authorize workflow transitions. Hiding a field from generated documentation is not access control.

The gateway accepts quantity="10", while the service rejects or interprets it differently. What is the contract?

The Scenario & Constraint

Clients rely on implicit numeric-string coercion in one validator, but the service expects an integer. Releases behave differently. How will you resolve it?

The Direct Answer & Architectural Decision

Choose the public input representation and coercion policy explicitly, align dialect/runtime configuration and test the exact boundary values through both layers. If existing clients depend on the old behavior, migrate/version it deliberately rather than silently changing accepted meaning.

Key Trade-Offs & Follow-Up Traps

Coercion can ease legacy clients but adds ambiguity; strict typed input is simpler for new contracts. Consider null, empty strings, fractional numbers and oversized values, not only “10.” A schema file cannot override an independently configured parser automatically.

Two valid requests each buy the last item. Was validation missing a field?

The Scenario & Constraint

Each request passes the quantity schema and a separate stock check, then both decrement. Overselling is forbidden. What will you do?

The Direct Answer & Architectural Decision

Keep structural validation, but move the stock decision and decrement into the authoritative concurrency-safe operation, such as a conditional update/transaction with a defined conflict outcome. Retry or reject under the operation contract and preserve idempotency for repeated intent.

Key Trade-Offs & Follow-Up Traps

Serialization/conditional contention can reduce throughput; a reservation model may fit more complex fulfillment. Raising validation strictness does not close a time-of-check/time-of-use race. If overselling is acceptable for a specific product, document that changed business constraint rather than accidentally relying on it.

A schema-valid payload exhausts CPU and memory. What did the contract omit?

The Scenario & Constraint

A public endpoint accepts very deep nested arrays and a large compressed body. The parser and validator consume excessive resources before returning. What will you change?

The Direct Answer & Architectural Decision

Set limits at byte/decompression, parser depth/collection and semantic work boundaries; use appropriate streaming/resource-limited parsing where available. Bound complex validation and request execution, reject early with safe feedback and test adversarial shapes in the actual stack.

Key Trade-Offs & Follow-Up Traps

Tight bounds can reject legitimate bulk work; a dedicated asynchronous bounded upload workflow may serve it better. Request-count rate limiting alone misses per-request amplification. A valid shape is not a resource budget unless its dimensions are actually bounded.

Gateway and service decode the same path differently. Which value is authorized?

The Scenario & Constraint

An encoded identifier passes one allowlist but resolves to a different backend path after another decoding step. What will you do?

The Direct Answer & Architectural Decision

Define one accepted canonical interpretation across the boundary, reject ambiguous/double-decoded forms and authorize the actual resolved resource using trusted identity. Add fixtures for separators, duplicate parameters, Unicode and normalization appropriate to the domain. Avoid global normalization that changes opaque identifier meaning.

Key Trade-Offs & Follow-Up Traps

Strict canonical forms can require client migration; a versioned compatibility adapter may be necessary. Merely checking a regex on the original bytes is insufficient if later code changes meaning. Parameterized storage access and output encoding remain separate protections.

Validation errors echo tokens and reveal private record existence. How do you keep them useful?

The Scenario & Constraint

Developers want complete payloads and internal constraint names returned for easy debugging. The API handles personal data and credentials. What will you expose?

The Direct Answer & Architectural Decision

Return stable safe error categories and field pointers sufficient for correction, with an opaque correlation reference to controlled internal diagnostics. Redact credentials/sensitive values, preserve permission boundaries and avoid unnecessary object-existence disclosure. Document how clients distinguish malformed input from domain conflicts.

Key Trade-Offs & Follow-Up Traps

Less public detail can slow debugging; secure support tooling is an alternative to returning secrets. Generic 500 for every mistake harms caller recovery and observability. User-visible wording can change without changing the stable machine contract.
