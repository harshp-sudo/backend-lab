Idempotency

🎯 The Hook & ELI5

At a bakery you receive one numbered ticket for one cake order. If the cashier cannot hear your reply, showing the same ticket should recover that order, not buy another cake. A second cake needs a second ticket. Idempotency is about recognizing repeated intent, not deciding that two orders with the same flavor must be the same purchase.

An idempotent operation has the same intended effect when repeated as when applied once. HTTP gives some methods idempotent semantics; a business API can also add an explicit caller-supplied identity for repeat-sensitive operations. A key is useful only when its scope, concurrency, outcome storage and retention rules are implemented correctly.

Our example is order submission with a potentially lost reply. We separate one local authoritative order effect from an external payment effect: a local transaction can protect the former only within its actual database boundary. This lesson covers request/result identity; the linked ACID Properties and Database Transactions lessons explain their different concurrency and durability guarantees.

🗺️ High-Level Big Picture

The diagram describes a contract, not a universal distributed transaction. Commit effect and outcome atomically when they share a boundary; external effects need their own duplicate-safe workflow and reconciliation.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; protocol and implementation examples state their scope explicitly. Trace the same client operation through success, uncertainty and recovery.

1. Define what identifies the same intent

Use a key generated before the initial attempt and reused across transport retries of that intent. Scope it to the authenticated caller/tenant and operation as required by the public contract. A new deliberate order gets a new identity even if its payload is identical.

Bind the key to a canonicalized meaningful request fingerprint or equivalent intent representation. Define how defaults, ordering and omitted fields affect equality. Never identify payments by hashing amount alone: two legitimate purchases can have the same amount, and semantically different requests can share superficial fields.

2. Claim identity atomically, not by checking first

Use a uniqueness/atomic state transition in the authoritative ownership boundary. If two concurrent requests arrive with the same scoped key, only one becomes the owner. Compare intent before returning an existing result; same key with different intent is a documented conflict, not permission to replay an unrelated response.

A separate cache GET followed by SET and business execution lets both callers see “missing.” A simple expiring distributed lock can also lose ownership while an old worker continues. Ownership, fencing/recovery and durable outcome must be designed together; a lock by itself is not the result contract.

3. Commit the local effect and recoverable result together

When order and duplicate identity share one database, one transaction can atomically create the order and persist its operation result. This conceptual state model is implementation-neutral, not executable storage code:

scope + operation_key -> {
  intent_fingerprint,
  state: in_progress | succeeded | rejected,
  result_reference,
  created_at,
  retention_deadline
}

Document which deterministic rejections are recorded, which transient failures allow a retry, how concurrent in-progress callers respond and what a completed replay returns. A stored reference can be safer than copying a sensitive full response, but the client-visible replay/authorization contract must remain coherent.

4. Recover crashes and external effects honestly

If a transaction rolls back before the local effect commits, a new attempt can safely retry within that boundary. If the effect commits with its result and the response is lost, a matching request returns the recorded outcome. A persistent in-progress record needs recovery ownership and inspection; do not leave callers waiting forever.

An external payment cannot be made atomic with your database merely by wrapping local code in BEGIN/COMMIT. Use the provider’s documented idempotency identity, persist workflow state/publication intent and reconcile unknown outcomes. Avoid a new provider key after a timeout until the original attempt is resolved.

5. Make retention and authorization part of the public promise

Choose retention based on realistic retries and late arrivals, and state what happens after expiry. Do not silently promise perpetual duplicate prevention while deleting identity records after a short TTL. A fresh request after expiry may create another effect unless the domain identity or authoritative outcome still prevents it.

Reauthenticate replay access and preserve tenant isolation. Avoid exposing sensitive historic responses after permissions change; document whether replays return an immutable operation receipt or an authorized current resource. Observe key conflicts, duplicate rates, stale in-progress operations and reconciliation failures. Test crashes at each transition, not just sequential happy-path retries.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Check-then-act duplicates

Symptom: Two matching requests both create orders.

Root Cause: The existence test and ownership claim were separate.

Fix/Prevention: Use an atomic unique claim in the effect owner and test concurrent arrivals.

A key changes meaning

Symptom: A retry returns an outcome for a different cart.

Root Cause: The service replayed by key without checking intent.

Fix/Prevention: Scope keys and reject meaningful fingerprint conflicts explicitly.

An expired lock permits a second charge

Symptom: A slow worker continues after another acquires the key.

Root Cause: Lock expiry was mistaken for proof that the first effect never happened.

Fix/Prevention: Use durable ownership/outcome recovery and the external provider’s documented identity contract.

Summarize this in your own words: Recognize one intent in an authoritative boundary, persist a recoverable outcome and define concurrency, external effects, retention and replay access before promising safe retries. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Why are identical payloads not always duplicate intent?

A customer can intentionally buy the same item twice. The operation identity distinguishes those purchases from retransmission of one purchase.

Why must duplicate ownership be atomic?

Concurrent arrivals can both pass a separate existence check. One authoritative claim must decide which execution owns that scoped identity.

What can a local transaction protect?

Only effects/results in its actual atomic boundary. External calls need separate identity and recovery rules; local rollback does not reverse a remote committed charge.

Why is retention part of correctness?

Late retries can arrive after a record expires. The API must define the remaining protection and recovery behavior instead of implying permanent deduplication.

Tricky & Most-Asked Interview Scenarios

Two identical checkout requests arrive simultaneously. What prevents two orders?

The Scenario & Constraint

The service checks a cache, sees no key in both requests and creates two orders. Both use the same caller key. How will you fix it?

The Direct Answer & Architectural Decision

Move ownership to an atomic unique claim scoped to caller/operation and bind it to intent. For local order creation, commit identity, effect and result within one transaction. Make the losing request return the matching completed outcome or documented in-progress state, rather than execute again.

Key Trade-Offs & Follow-Up Traps

This adds state contention and recovery handling; a caller-chosen stable resource identity may naturally fit some creates. A cache lock alone is insufficient if it expires or is lost while work continues. Test a crash between every durable state transition.

The same key is reused for a different amount. Do you return the first result?

The Scenario & Constraint

A buggy client retries a payment key with a changed cart/amount. It expects a new purchase, but the first attempt may already exist. What will you do?

The Direct Answer & Architectural Decision

Compare a defined semantic intent fingerprint and reject conflicting reuse with a clear documented error. Return or expose the original authorized operation separately for reconciliation. Require a new key only for an explicitly new intent, not to escape uncertainty about the old one.

Key Trade-Offs & Follow-Up Traps

Fingerprinting needs stable normalization/default rules; storing a canonical intent reference can be another approach. Blindly replaying the first response hides the client defect, while executing the new payload under the same key breaks identity. Equal amounts alone do not establish equal intent.

A provider charged successfully, then your process crashed before saving success. What now?

The Scenario & Constraint

Order state is local; payment is remote. A transaction wrapper rolls back local changes after the crash, but the remote charge remains. How will recovery work?

The Direct Answer & Architectural Decision

Persist a recoverable workflow and reuse the same provider-supported operation identity. Query/retry according to its outcome contract, then reconcile local state with the authoritative remote result. Keep publication/retry intent durable and distinguish pending/unknown from rejected.

Key Trade-Offs & Follow-Up Traps

Workflow recovery costs operational state; placing all effects in one true transactional owner would be simpler if feasible. A new provider key can double-charge, and a local rollback does not compensate remote effects. Provider retention and lookup capabilities bound the guarantee.

A client retries after your twenty-four-hour key retention expired. What can you promise?

The Scenario & Constraint

A mobile device was offline for three days and resends its original creation intent. Old duplicate records were deleted. How will you handle this honestly?

The Direct Answer & Architectural Decision

Define the public retry/retention window and an explicit late-request recovery policy. Where duplicate harm is high, retain durable business identity or a long-lived receipt/reference that can resolve the original intent; otherwise return an actionable expiry/uncertainty response rather than silently implying old protection.

Key Trade-Offs & Follow-Up Traps

Long retention costs storage/privacy management; narrower supported retry windows can be acceptable if clients can reconcile. TTL expiry does not prove no original effect exists. A client generating a new key is a new intent only after it has resolved the original outcome.

A durable key remains in_progress forever after a worker crash. Can you delete it?

The Scenario & Constraint

A duplicate caller repeatedly gets “still processing.” The worker is gone, but it may have reached an external side effect. What recovery will you implement?

The Direct Answer & Architectural Decision

Use a recovery owner with durable state transitions and inspect the authoritative local/provider outcome before resuming or finalizing. If re-execution is allowed, preserve the same operation identity and prevent stale workers from conflicting. Expose bounded status/retry guidance and alert on aged operations.

Key Trade-Offs & Follow-Up Traps

Recovery adds leases/fencing or other coordination appropriate to the owner; manual reconciliation may be necessary for rare ambiguous external cases. Deleting the key and starting fresh can repeat the effect. A worker heartbeat timeout is suspicion, not proof of business failure.

Two tenants choose the same idempotency key. Can they share a result?

The Scenario & Constraint

Keys are user-generated strings. A global key-only lookup returns one tenant’s order receipt to another caller using the same value. What changes?

The Direct Answer & Architectural Decision

Scope identity and lookup to authenticated caller/tenant and operation, verify intent within that scope and reauthorize access to returned receipts/resources. Purge/contain exposed results and test colliding keys across tenants. Keep identity data separated from untrusted routing headers.

Key Trade-Offs & Follow-Up Traps

More scoped records increase storage but preserve isolation; globally unique random client values reduce collision risk without replacing authorization. Replaying an old sensitive response after permissions change still needs an explicit access policy. A key is an operation identifier, not a bearer credential.
