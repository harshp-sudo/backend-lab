API Gateway

🎯 The Hook & ELI5

A building’s reception desk checks a visitor’s badge, sends them to the right room and can hand out a reusable public brochure. It must never give one visitor another person’s private file or rewrite an instruction so its meaning changes. An API gateway applies similar policies at the API boundary.

This lesson owns API-level routing, authentication boundaries, caching and payload transformation. The gateway receives a client contract and dispatches a controlled downstream request; the domain service still owns business invariants and object-level permission decisions. A verified login is not permission to read every object.

For where a gateway belongs in a system, aggregation, topology and failure-boundary trade-offs, read the existing API Gateway Pattern. This lesson focuses on the API policies executed there.

Our example is a tenant-scoped orders API. General policy examples are implementation-neutral; named product references describe Amazon API Gateway REST APIs, whose cache/mapping features must not be assumed identical to its HTTP or WebSocket API products.

🗺️ High-Level Big Picture

Cache hits and transformed requests must preserve the same access and representation contract as a service call. A shortcut around that contract is a correctness defect, not just a performance choice.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; protocol and implementation examples state their scope explicitly. Trace the same client operation through success, uncertainty and recovery.

1. Make route selection deterministic

Define method/path/host matching and precedence, and test ambiguous cases such as /orders/search versus /orders/{id}. Decide which path normalization/decoding occurs at each hop. Do not allow the gateway and service to interpret encoded separators or duplicate parameters as different operations.

Keep a small reviewed route contract with allowed methods, upstream target, authentication requirement, timeout and transformation version. Reject unmatched or disallowed requests deliberately. A catch-all route that accidentally bypasses a stricter policy can expose a backend intended only for controlled access.

2. Establish identity without widening trust

Verify the selected credentials and token properties at the agreed boundary. Remove or overwrite untrusted identity-forwarding headers and pass authenticated context through a channel the service can trust. Protect the direct backend path so callers cannot impersonate gateway-injected identity.

Keep domain authorization in the owning service: the gateway may verify a token while the service decides whether that caller may view order o-42. An API key used for usage accounting is not automatically authentication/authorization; Amazon REST API usage-plan guidance explicitly warns against that interpretation.

3. Design caching around representation and permission

Cache only responses with a reviewed safety/freshness policy. A key must account for every input that changes the reusable representation, and permission checks must still be valid on a hit. A practical policy worksheet might look like this:

Example policy choices, not executable gateway configuration

For Amazon API Gateway REST APIs, selected parameters can form configured cache keys. Do not assume arbitrary authorization context is automatically part of the key or HTTP cache directives automatically configure every managed method cache. Test the actual product path with different identities and permissions.

4. Transform shape without inventing business meaning

Use explicit versioned mappings for a real compatibility need, such as renaming a field while maintaining the same units and null/missing behavior. Validate the incoming shape and the mapped outgoing contract. Keep money precision, timestamps, enum meanings, unknown fields and error semantics explicit.

A mapping that turns amountCents into amount without a documented units conversion is not harmless formatting. Avoid placing substantive domain decisions in a generic mapping template; they become difficult to test and can diverge from the service. For product examples, use the selected REST API mapping/override feature as documented rather than assuming all integration modes run the same templates.

5. Preserve failure and observability semantics

Budget downstream time within the client operation and propagate correlation safely. Decide whether a timeout means unknown mutation outcome, and avoid adding gateway retries to a non-repeatable operation without duplicate protection. A response mapping must not turn a failed downstream operation into an unconditional success.

Measure route hits, policy rejections, cache hit/miss/isolation, mapping errors and downstream latency. Roll out policy changes with representative fixtures and a staged route/version, and invalidate or namespace cached entries when representation meaning changes. Document operational ownership of policy and domain behavior.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Authentication becomes blanket access

Symptom: A valid user reads another tenant’s order.

Root Cause: The gateway verified a token but no owner checked object permission.

Fix/Prevention: Enforce service authorization and protect trusted identity propagation.

The cache forgets a dimension

Symptom: A French page or private response is reused for the wrong caller.

Root Cause: Cache key/policy ignored representation or visibility inputs.

Fix/Prevention: Bypass until a reviewed safe key/access/freshness contract is implemented and tested.

A mapper manufactures success

Symptom: Client retries and support disagree about whether an order exists.

Root Cause: Response templates replace every upstream status with 200.

Fix/Prevention: Preserve meaningful error/outcome distinctions and test failure mappings.

How does this lesson differ from API Gateway Pattern?

This lesson covers concrete API policy execution: matching, trusted identity, cache eligibility and mappings. The linked pattern lesson covers system placement/composition trade-offs.

Is an API usage key sufficient authorization?

No. Accounting/quota identity and permission to access an object are separate. Verify credentials and enforce the domain owner’s access policy.

What must remain true on a cache hit?

The caller is authorized for the returned representation, its key captures relevant variation, and its freshness/revocation policy remains valid.

When is a payload mapping risky?

When it silently changes units, precision, missing/null meaning, validation or error semantics, or embeds domain decisions that diverge from the owner.

Tricky & Most-Asked Interview Scenarios

A cache keyed by order ID returns another tenant’s fields. What comes first?

The Scenario & Constraint

The gateway caches an authenticated order response using only the path. Different callers see different redacted fields. You must contain exposure and preserve access control. What will you do?

The Direct Answer & Architectural Decision

Bypass unsafe caching, purge affected entries and verify owner authorization on every access. Then either keep caller-dependent responses out of shared reuse or design a reviewed key/permission/freshness policy with the actual gateway capabilities. Test cross-tenant and changed-permission requests through real cache hits.

Key Trade-Offs & Follow-Up Traps

Bypass increases origin load; a public summary or isolated authorized read model may retain useful caching. A key containing tenant alone is insufficient if roles/user permissions change fields within that tenant. TTL limits duration but does not make an unauthorized cached response acceptable.

A client sends X-User-Id and the service trusts it. Where do you close the gap?

The Scenario & Constraint

The gateway verifies tokens but forwards caller-supplied identity headers unchanged. The backend is also reachable directly. What will you change?

The Direct Answer & Architectural Decision

Strip/overwrite untrusted identity inputs, establish a controlled authenticated gateway-to-service context and block or equivalently authenticate bypass routes. The service must authorize the requested object using trusted identity. Test spoofed headers and direct access, not just valid-token happy paths.

Key Trade-Offs & Follow-Up Traps

A trusted internal identity channel needs key/network/service ownership; having the service verify original credentials is an alternative. Merely renaming a header or relying on an API usage key does not establish trust. If several gateways exist, define which identities each may assert.

A new catch-all route bypasses auth for an admin path. How do you prevent it?

The Scenario & Constraint

A route update changes precedence so /orders/admin matches a public fallback instead of its protected handler. What policy and rollout changes will you make?

The Direct Answer & Architectural Decision

Define explicit route precedence and allowed methods, use deny-by-default unmatched handling and validate a route-policy matrix including ambiguous/encoded paths. Deploy the revised routing set in a staged manner and verify gateway/service interpretation agrees. Retain service authorization as a second ownership boundary.

Key Trade-Offs & Follow-Up Traps

More explicit routes cost maintenance; a constrained generated route definition may reduce drift. A catch-all is acceptable only with deliberate equivalent policy. Cache entries from an older route/mapping may need invalidation when path meaning changes.

A gateway rename turns cents into dollars. Who owns the conversion?

The Scenario & Constraint

A legacy client sends amountCents while the backend expects a decimal currency amount. A mapping simply copies the number. Financial correctness is mandatory. What will you do?

The Direct Answer & Architectural Decision

Stop the incorrect mapping, define the exact units/currency/precision contract and implement an explicitly tested conversion or versioned adapter with domain review. Validate bounds, rounding and error behavior for both contracts. Keep the authoritative money rule in a clear owner rather than undocumented templates.

Key Trade-Offs & Follow-Up Traps

An adapter preserves old clients but adds versioned code and fixtures; a coordinated client migration may be simpler. Binary floating-point conversion or missing currency context can still corrupt meaning after a field rename. A syntactically valid mapped payload is not proof of semantic correctness.

The gateway retries a timed-out POST and creates a second order. What is the fix?

The Scenario & Constraint

Downstream creation may commit before the gateway timeout. Gateway and client each retry with no common operation identity. What will you do?

The Direct Answer & Architectural Decision

Disable unsafe blind retries, establish a caller-scoped stable operation identity carried through the boundary and deduplicate at the authoritative effect owner. Return/reconcile durable operation status for uncertain outcomes. Budget any retry layer deliberately within the end-to-end timeout.

Key Trade-Offs & Follow-Up Traps

Retained outcomes and recovery increase state; a naturally idempotent resource operation may fit some APIs. Increasing the gateway timeout only changes the uncertainty window. The gateway cannot infer rollback from a transport error or manufacture an exactly-once business guarantee.

A usage plan is configured, but a customer exceeds its quota. Is the gateway broken?

The Scenario & Constraint

The team treats a managed REST API usage plan as a hard financial spending cap and uses its API key as authorization. What changes?

The Direct Answer & Architectural Decision

Use the documented best-effort quota model honestly, add appropriate authoritative budgeting/admission controls where a hard cap is required, and implement real authentication/object authorization independently of the usage key. Monitor consumption and respond to overshoot under an explicit policy.

Key Trade-Offs & Follow-Up Traps

Strict distributed caps add coordination and can reduce availability; bounded overshoot may be an acceptable cheaper policy if disclosed. Amazon API Gateway REST API usage plans explicitly are not hard limits or an authorization mechanism. Do not generalize one product’s feature label into a universal guarantee.
