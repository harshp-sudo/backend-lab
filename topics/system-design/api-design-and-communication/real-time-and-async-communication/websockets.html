WebSockets

🎯 The Hook & ELI5

A phone call lets either person speak without placing a new call for every sentence. WebSockets give a browser and server a similar two-way conversation. If the call drops, however, neither person automatically knows which instructions were heard, acted on or missed; the application needs its own way to resume the conversation.

WebSocket is a connection-oriented bidirectional message protocol. An opening handshake establishes the conversation, followed by frames carrying application messages. The traditional HTTP/1.1 Upgrade handshake is a common deployment; proxy/transport capabilities must match the actual stack.

Our example is a collaborative support room with chat messages and transient typing indicators. These have different reliability requirements: losing a typing indication may be acceptable, while silently losing an accepted chat message is not. The browser WebSocket API has no built-in receive backpressure, so do not confuse TCP/protocol flow behavior with a bounded application queue.

🗺️ High-Level Big Picture

The socket transports live messages. Durable acceptance, publication and replay are separate responsibilities; the diagram does not promise an atomic database/broker dual write.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; protocol and implementation examples state their scope explicitly. Trace the same client operation through success, uncertainty and recovery.

1. Establish a trusted connection

Use a secure connection and validate the expected browser Origin where relevant; an origin check is not user authentication. Authenticate the session and authorize room access using trusted server-side identity. A browser WebSocket constructor does not expose arbitrary authorization-header configuration like a normal fetch call, so choose a deliberate cookie/session or short-lived ticket flow.

Avoid long-lived credentials in URLs, where infrastructure may log them. Define session expiry, logout/revocation and reconnect behavior. A previously authenticated connection should not retain permission indefinitely after its membership changes.

2. Define application message contracts

The transport gives you messages, not domain commands or deduplication. Give durable chat sends a caller operation identity, validate size/type, and return an explicit acceptance result only after the promised durable boundary.

{"type":"send-message","operationId":"op-31",
 "roomId":"support-7","text":"I need help"}
{"type":"message-accepted","operationId":"op-31",
 "messageId":"m-804","roomCursor":"804"}

These are illustrative application messages, not WebSocket protocol frames or a runnable chat server. Acknowledging queued memory is weaker than acknowledging durable acceptance; document which promise the client sees.

3. Keep ordering, acknowledgment and replay explicit

Within an intact connection, transport order is useful, but reconnecting creates a new conversation. Assign a suitable per-room/event ordering cursor and let the client resume after its last applied position. Deduplicate replayed event IDs and repeated send operation IDs at the appropriate boundaries.

A gateway can crash after persistence but before acknowledgment; a client can apply an event before its saved cursor advances. Design these as recoverable duplicates, not proof of exactly-once delivery. If retained history expired, return an explicit resynchronization path rather than silently skipping the gap.

4. Bound both ends and distinguish message classes

Bound message sizes, outbound queues and allowed work per connection/identity. Coalesce or drop stale typing/presence updates; preserve important messages through a durable log or disconnect a slow consumer with a resume path. Observe the browser’s outgoing bufferedAmount as one signal, while separately controlling received-message processing and application memory.

When server output exceeds browser processing, the classic API cannot ask the transport for built-in receive backpressure. Add application acknowledgments/credits or bounded delivery windows where necessary. Larger queues only postpone memory exhaustion and increase latency.

5. Operate connections across multiple instances

A connection is attached to one gateway at a time. Route room events to the gateways with relevant connections through an explicit publication/fan-out design; load balancing or sticky sessions alone does not share room messages. Keep durable ownership outside an individual connection process.

Plan idle timeout/heartbeat behavior through the actual intermediary path, graceful drain, reconnect backoff with jitter and recovery after deployment. Browser JavaScript does not directly expose protocol ping/pong controls; use application heartbeats if the interaction needs them. Avoid synchronized reconnect storms and measure active connections, queue depth, lag and disconnect reasons.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

A sticky room still misses messages

Symptom: Clients on different gateway instances see different chat histories.

Root Cause: Session affinity was mistaken for cross-instance publication.

Fix/Prevention: Design room fan-out and authoritative durable history explicitly.

A slow tab exhausts memory

Symptom: Queue growth continues despite low network error rates.

Root Cause: The app accepted unlimited received or queued messages.

Fix/Prevention: Bound work/queues, coalesce transient updates and provide resume after disconnect.

A reconnect duplicates a send

Symptom: One click creates two chat messages.

Root Cause: The retry received a new operation identity after the first acknowledgment was lost.

Fix/Prevention: Reuse intent identity and return its durable result; distinguish a new deliberate send.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Choose WebSockets for an actual two-way interaction, then design identity, bounded work and durable reconnect recovery as explicit application responsibilities. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

What does a live socket fail to guarantee?

It does not itself promise durable acceptance, replay across reconnects or exactly-once business effects. Those are application/storage contracts.

Why is a fast server dangerous for a slow browser?

Classic browser WebSocket has no built-in receive backpressure. Unbounded application processing/buffering can consume memory or stall the page.

Is authenticating the handshake enough for every room forever?

No. Room/object authorization, membership changes, expiry and revocation must be enforced during the connection lifecycle.

How do an event cursor and an operation ID differ?

A cursor marks a position for replay; an operation ID recognizes repeated client intent. Replaying an event and resending a command require different duplicate controls.

Tricky & Most-Asked Interview Scenarios

A gateway restarts and a client misses thirty chat events. How does it recover?

The Scenario & Constraint

Chat messages must survive deployments. A browser reconnects to a different instance after a minute offline. What will you do and why?

The Direct Answer & Architectural Decision

Store accepted chat events durably with a room-scoped replay position, reconnect with the last applied cursor and authorize replay against current membership. Send retained events before or consistently with live continuation, deduplicating overlapping IDs. Provide snapshot/resync when the cursor is too old.

Key Trade-Offs & Follow-Up Traps

Retention and replay cost storage and catch-up capacity; best-effort transient updates can simply refresh current state. A sticky route cannot recover a dead instance’s memory. If permissions changed while offline, the old cursor must not authorize historical content the user may no longer see.

One slow tab causes server memory to rise. Should its queue grow?

The Scenario & Constraint

A room produces hundreds of updates per second. One browser processes very slowly; other clients should remain responsive. How will you isolate it?

The Direct Answer & Architectural Decision

Set bounded per-connection queues and work budgets. Coalesce replaceable presence/typing updates, use credit/acknowledgment windows for important delivery if needed, and disconnect lagging clients with a replay/resync path rather than retain unlimited memory. Monitor lag and queue occupancy.

Key Trade-Offs & Follow-Up Traps

Disconnecting costs reconnect/catch-up work; reducing update fidelity may be better for live dashboards. Increasing buffers is a temporary capacity trade, not a solution to sustained overload. An application receipt acknowledgment is distinct from durable business processing.

The server persisted a send, then disconnected before acknowledging. What does retry use?

The Scenario & Constraint

A user sends “please refund” once. After reconnect, the UI cannot tell whether the gateway accepted it. Repeating the text as a new message would confuse support. What will you do?

The Direct Answer & Architectural Decision

Assign the send a stable caller-scoped operation ID before transmission and deduplicate it at durable acceptance. Retry the same intent with that ID and equivalent payload; return the existing message ID/outcome. Persist enough client state to survive the intended retry window.

Key Trade-Offs & Follow-Up Traps

This costs operation retention and payload conflict checks; naturally client-assigned message IDs can fit some designs. Identical text alone is not identity because the user may intentionally repeat it. Expired retention requires explicit uncertainty/reconciliation behavior.

A logged-out user’s socket keeps receiving private messages. Where is the check?

The Scenario & Constraint

A session expires or room membership is revoked while the connection remains open. The handshake was authenticated an hour ago. What will you change?

The Direct Answer & Architectural Decision

Enforce current session/permission lifecycle on message delivery and room actions, using a deliberate revocation/expiry mechanism and closing or reauthorizing connections as needed. Prevent replay and resubscription from bypassing the same policy. Test logout and membership removal across gateway instances.

Key Trade-Offs & Follow-Up Traps

Immediate revocation requires distribution and state checks; short bounded credentials can offer a different documented exposure window. Origin checking helps a browser trust boundary but is not identity or room authorization. Reconnection must not silently restore a revoked subscription.

Users connected to different instances cannot see each other. Will affinity solve it?

The Scenario & Constraint

The load balancer distributes sockets across four gateways. Each gateway broadcasts only to its own memory map. How will you make a room consistent enough for chat?

The Direct Answer & Architectural Decision

Keep an explicit room/event owner and distribute its accepted events to the gateways holding subscribers. Use durable history for recovery, and define per-room ordering and duplicate handling. Scale fan-out separately from ownership instead of assuming connection placement shares state.

Key Trade-Offs & Follow-Up Traps

A pub/sub layer adds operations and can itself lose transient delivery; durable catch-up closes the recovery gap. A single room-owner process is simpler at smaller scale but needs failover and capacity limits. Sticky sessions only attach a client to an instance; they do not publish another client’s events.

A deploy reconnects every browser at once. How do you protect recovery?

The Scenario & Constraint

Tens of thousands of clients reconnect together and all replay full history. The new fleet overloads before it can recover. What will you do?

The Direct Answer & Architectural Decision

Drain gateways gradually, use client reconnect backoff with jitter, bound concurrent handshakes/catch-up and resume from compact saved cursors. Separate snapshot resync from normal replay and enforce tenant/user admission limits. Monitor recovery latency and backlog as deployment signals.

Key Trade-Offs & Follow-Up Traps

Slower staged recovery increases temporary staleness; a product may accept lower update frequency during catch-up. Unlimited retries or restarting the whole fleet repeatedly worsens load. If replay history expired, send a clear resync instruction rather than repeatedly requesting an impossible range.
