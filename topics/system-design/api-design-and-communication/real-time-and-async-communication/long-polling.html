Long Polling

🎯 The Hook & ELI5

Instead of asking a waiter every second whether dinner is ready, you ask once and the waiter waits until there is news or an agreed time runs out. After the reply, you ask again. Long polling uses that pattern with ordinary requests: less empty chatter than rapid polling, but every waiting guest still needs a place in the system.

A long-poll request stays open until relevant data is available or the server ends the wait. The client then issues another request, carrying its last applied position. Unlike SSE, the response normally completes after a batch; unlike a WebSocket, the transport is not a persistent bidirectional message channel.

Our example delivers support notifications when streaming connections are impractical. The API returns bounded event batches with opaque cursors. Example status and JSON choices are an application contract, not a universal long-poll standard; RFC 6202 explains transport and intermediary considerations. Delivery, acknowledgment and durable retention still require explicit design.

🗺️ High-Level Big Picture

The wait is an optimization over a recoverable cursor-based read. Rechecking around waiter registration prevents a notification race from hiding already available events until another wake-up.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; protocol and implementation examples state their scope explicitly. Trace the same client operation through success, uncertainty and recovery.

1. Specify a bounded request/response contract

The client sends its authorized stream position and desired wait budget. The server caps both wait duration and batch size. An empty batch means no event was returned during that completed wait, not that the subscription ended forever.

GET /notifications?after=cursor-803&waitSeconds=20 HTTP/1.1
Host: api.example.test

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{"events":[{"id":"804","kind":"reply-ready"}],
 "nextCursor":"cursor-804"}

This illustrative contract also returns 200 with an empty events array and an unchanged cursor on a normal no-event timeout. Other documented conventions are possible; avoid calling a normal empty wait a server failure.

2. Choose timeout ordering through real intermediaries

Set the server wait below the relevant client/intermediary timeout with room for processing and transit. The example twenty-second wait is a teaching choice, not a recommended universal number. Discover actual load balancer, proxy and client behavior under idle connections.

If a proxy aborts first, the client sees uncertainty instead of a clean empty result. Reuse the same applied cursor on retry and apply bounded backoff/jitter after abnormal failures. A series of normal immediately completed empty responses can also create a tight loop, so define a sensible minimum delay or wait behavior.

3. Wait without losing a wake-up or exhausting workers

Use nonblocking/asynchronous waiting or a capacity-appropriate mechanism; retaining one blocked heavyweight worker per client can exhaust the pool. Register notification interest consistently with checking available data, for example by registering then rechecking the durable log before sleeping.

A wake-up only means data may be available: read the authoritative batch after the cursor. Notification channels can coalesce or lose a wake-up, so a bounded timeout and recheck preserve eventual progress. Keep subscriber cleanup tied to cancellation and connection lifecycle.

4. Advance only after applying data safely

The response cursor marks a server-side traversal position. The client should persist its applied position according to its processing guarantee; advancing before applying can lose work after a crash. A lost response or a crash before checkpoint can cause replay, so make client effects duplicate-aware.

Keep at most the intended number of outstanding polls per logical subscription, or design explicit ordering/deduplication for overlap. Bind cursors to authenticated stream/filter context, cap batches, and provide expired-history resynchronization. An event ID in a URL must not grant access to another user’s notifications.

5. Budget recovery and know when to switch

Even asynchronous waits consume sockets, memory, gateway state and scheduling work. Limit concurrent subscriptions per identity, clean up abandoned waits, and measure active waits, response rate, queue depth, wait duration and reconnect storms. Sticky sessions alone do not provide shared notification history across instances.

For frequent continuous server updates, SSE may avoid repeated request overhead. For true two-way live interaction, WebSockets may be better. Keep the authoritative event/status contract independent enough that changing delivery transport does not change which business outcomes survive a disconnect.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Every poll fails at the proxy

Symptom: The client retries even when no event occurred.

Root Cause: The server wait exceeds an intermediary idle/request timeout.

Fix/Prevention: End the wait cleanly earlier and coordinate real path budgets.

Notifications wait for the next event

Symptom: An existing event is not delivered until another arrives.

Root Cause: Data was checked before subscribing and the event arrived in the gap.

Fix/Prevention: Register/recheck consistently and read durable data after the last applied cursor.

A closed tab consumes a worker

Symptom: Thousands of abandoned waits exhaust capacity.

Root Cause: Wait registrations and blocking work outlive cancellation.

Fix/Prevention: Use capacity-appropriate async waiting and deterministic cancellation/timeout cleanup.

Summarize this in your own words: Long polling is a recoverable bounded read with waiting: coordinate timeouts, prevent lost wake-ups, checkpoint applied data and budget every outstanding request. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

How does long polling differ from short polling?

The server holds the request for bounded time waiting for data, then completes it. The client starts another request after processing the result.

Is an empty normal wait result a failed operation?

Not under the example contract. It means no event was returned during the bounded wait; abnormal transport/server errors are separate.

Does a wake-up notification own the event history?

No. Read authoritative retained data after the cursor; wake-ups are scheduling hints that may be coalesced or missed.

When should the client advance its saved cursor?

According to its actual applied-work guarantee. Saving it before applying can lose work; applying before saving can replay and therefore needs duplicate handling.

Tricky & Most-Asked Interview Scenarios

Every sixty-second poll receives a gateway timeout after thirty seconds. What changes?

The Scenario & Constraint

The server holds requests for sixty seconds, but a production intermediary terminates them at thirty. Clients immediately reconnect and logs fill with errors. What will you do?

The Direct Answer & Architectural Decision

Set an intentional server wait comfortably below the verified path timeout and client budget, then return a documented clean empty response. Retry abnormal transport failures from the same applied cursor with bounded backoff/jitter. Test the full proxy path and distinguish no-event waits from service failure metrics.

Key Trade-Offs & Follow-Up Traps

Shorter waits increase request turnover; a streaming transport may suit frequent updates better. Simply increasing every timeout retains more resources and may hit another limit. A lost response can still contain events, so never advance the cursor on timeout alone.

An event arrives between checking data and registering a waiter. How do you prevent a stall?

The Scenario & Constraint

The server checks an empty log, an event commits, then the server subscribes to notifications and sleeps. Delivery waits until another unrelated event. What will you change?

The Direct Answer & Architectural Decision

Make interest registration and the data check race-safe, such as register then recheck the authoritative log before sleeping. On wake-up or timeout, read after the cursor again. Keep event retention separate from transient notification delivery so a missed wake-up cannot permanently lose the event.

Key Trade-Offs & Follow-Up Traps

Rechecks add reads; a store-provided atomic blocking read may simplify the mechanism where available. Holding a database transaction open for the entire wait can create other resource problems. If a wake-up is duplicated, it should cause at most redundant bounded checking, not duplicate business work.

Two overlapping polls return overlapping events. Which cursor wins?

The Scenario & Constraint

A slow request remains active when a client starts another one. Replies arrive out of order and the saved position moves backward. What will you do?

The Direct Answer & Architectural Decision

Allow only one normal outstanding poll per logical subscription, cancel/track superseded requests and apply events through an ordered duplicate-aware path. Advance the checkpoint monotonically only for applied data under the cursor’s ordering model. Treat transport retries as the same continuation, not new history.

Key Trade-Offs & Follow-Up Traps

Serial polling can reduce throughput; deliberate partitioned subscriptions or bounded pipelining require explicit ordering and deduplication. A numeric max is valid only when cursor ordering actually permits comparison. Opaque tokens should not be sorted lexically by clients.

Ten thousand idle clients consume every application worker. How do you redesign waiting?

The Scenario & Constraint

Each held request blocks a dedicated worker thread. Requests do little CPU work, but ordinary API calls cannot obtain workers. What will you do?

The Direct Answer & Architectural Decision

Use capacity-appropriate asynchronous waiting and bounded subscriptions, isolate wait resources from ordinary request work and clean up on cancellation/timeouts. Load-test memory, sockets and wake-up fan-out. Read batches from durable state rather than keeping all pending data inside individual workers.

Key Trade-Offs & Follow-Up Traps

Async waiting reduces blocked-thread cost but still consumes connection and memory capacity. Coarser short polling may be simpler at smaller scale; SSE does not magically eliminate resource budgets. A single popular event waking every subscriber also needs bounded fan-out/recovery.

A client saved nextCursor before showing a notification, then crashed. Can it recover?

The Scenario & Constraint

The event is considered important to the user. On restart, the client resumes after it and never applies it. How will you change checkpoint handling?

The Direct Answer & Architectural Decision

Separate server traversal from client applied state and persist the checkpoint only according to the required processing guarantee. Design duplicate-safe application of replayed IDs or an explicit acknowledgment/inbox model when important work must survive restart. Reconcile state from an authoritative view where appropriate.

Key Trade-Offs & Follow-Up Traps

More durable client/inbox state costs complexity; replaceable current-state updates may only need a refresh. Applying before checkpoint can cause duplicates after a crash, so “save later” alone is not exactly-once processing. Define what receipt, display and completed action each mean.

A brief outage makes all clients reconnect in a tight loop. What protects the service?

The Scenario & Constraint

Poll failures return instantly during recovery, turning thousands of waiting clients into a request storm. How will you keep useful traffic available?

The Direct Answer & Architectural Decision

Use bounded randomized backoff after abnormal failures, per-identity subscription/admission budgets and server capacity limits. Keep normal long-wait completion separate from outage retry policy. Resume from compact applied cursors and cap catch-up batches so recovery cannot monopolize the service.

Key Trade-Offs & Follow-Up Traps

Backoff adds recovery delay; staged admission or reduced update frequency may better protect critical operations. A delay on every successful full batch can unnecessarily slow catch-up. If traffic is continuously high, evaluate SSE/WebSockets on their actual interaction needs rather than keeping an overloaded retry loop.
