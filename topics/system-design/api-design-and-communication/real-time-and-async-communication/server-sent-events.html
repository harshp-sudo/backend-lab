Server-Sent Events (SSE)

🎯 The Hook & ELI5

A train-station announcement channel keeps telling you when your train changes platform; you do not call the station again for every update. SSE gives a browser that kind of one-way stream. If your radio disconnects, a numbered announcement can help you ask where to resume, but only if the station actually kept the missing announcements.

Server-Sent Events use an HTTP response with text/event-stream content and a defined text framing format. The browser EventSource API parses events and normally reconnects after interruption. Commands can still use ordinary authenticated HTTP requests; one-way updates do not require one-way product interaction.

Our example streams background report progress and completion to a dashboard. A displayed percentage is replaceable current state, whereas a completed report must remain discoverable through an authoritative status resource even if the final event is missed. WHATWG EventSource defines transport behavior; storage, replay, permission checks and job correctness belong to the application.

🗺️ High-Level Big Picture

A reconnecting HTTP stream is useful only when its cursor and retained-history contract are explicit. The authoritative report outcome remains available independently of this connection.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; protocol and implementation examples state their scope explicitly. Trace the same client operation through success, uncertainty and recovery.

1. Choose one-way delivery for the actual task

Use SSE when updates mainly travel server-to-client and normal requests can submit commands. A report job can be created with POST and observed through status GET plus an event stream. Avoid using the stream as the only place where a final result exists.

Authenticate access to both job status and stream. Enforce tenant/object authorization before replay as well as live updates. Choose a cookie/session or other deliberate authentication approach compatible with native EventSource; its constructor does not provide arbitrary request-header configuration.

2. Frame and flush complete text events

The stream is UTF-8 text. A blank line ends an event block; multiple data lines join into the event data. This illustrative response sends one progress event and a comment heartbeat. The ID is a replay position chosen by the application, not a promise of durability.

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

id: 804
event: progress
data: {"jobId":"j-7","percent":60}

: heartbeat

Flush through the application and intermediary path rather than only writing into a framework buffer. JSON is just the chosen data payload; the outer event framing still needs its terminating blank line. Comments can keep traffic active without being dispatched as application events.

3. Connect with the correct listener and lifecycle

Named events use addEventListener for that name; onmessage receives the default message event. Close the EventSource when the view no longer needs it, and define terminal-job behavior to avoid pointless resubscriptions.

const updates = new EventSource("./jobs/j-7/events");
updates.addEventListener("progress", (event) => {
  const progress = JSON.parse(event.data);
  console.log(event.lastEventId, progress.percent);
});
// On view teardown, call updates.close().

This demonstrates the browser listener only; it is not a backend or a production error policy. A disconnect/error notification is not automatically terminal failure of the report job. Fetch authoritative status to resolve uncertainty.

4. Back an event ID with real replay semantics

For automatic reconnect on the same EventSource, the browser tracks event IDs and sends the relevant Last-Event-ID. The server must interpret that position, retain or reconstruct needed events and handle overlap safely. Merely emitting id fields does not build a replay log.

A new page/EventSource instance does not automatically recover a durable application cursor from a previous page. Persist appropriate client position or fetch current status/snapshot on startup. Bind cursor interpretation to the authorized stream and filters; expire history with an explicit reset/resync contract instead of silently skipping missing data.

5. Test the whole path under slow and interrupted connections

Disable inappropriate response buffering for this route using the actual proxy’s supported configuration, and coordinate heartbeat intervals with idle timeouts. A small local write can arrive in a large delayed burst after a CDN/proxy buffer, even while the application believes it is streaming.

Bound per-subscriber queues and reconnect work, coalesce replaceable progress updates and disconnect/resync lagging clients where appropriate. HTTP/1.x connection limits and HTTP/2 stream limits differ by client/intermediary; do not advertise one fixed browser connection count as a universal guarantee. Measure concurrency, flush latency, lag and reconnect rate.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Updates arrive in bursts

Symptom: Percentages appear together every thirty seconds.

Root Cause: A framework or proxy buffered small writes.

Fix/Prevention: Trace timestamps through each hop, flush properly and use route-scoped buffering settings.

IDs exist but missed events vanish

Symptom: A reconnect skips completion.

Root Cause: The server emitted IDs but retained no replay/status information.

Fix/Prevention: Implement the cursor contract and independent authoritative status.

Named events appear missing

Symptom: The stream is active but the callback never runs.

Root Cause: The client uses onmessage for an event named progress.

Fix/Prevention: Register the named listener and verify event framing/blank-line termination.

Can an SSE application still accept user commands?

Yes. Use ordinary authenticated requests for commands while SSE carries server-to-client updates. The transport direction does not dictate the whole product interaction.

What ends an SSE event block?

A blank line. The data payload can contain JSON or another text representation, but it does not replace SSE field framing.

Does setting id automatically retain events?

No. It gives the client a position to communicate. The application must provide replay, deduplication and expired-history behavior.

Does a new page automatically inherit the prior stream position?

No durable cross-page application recovery is implied. Restore an appropriate cursor or fetch current authoritative state when starting a new EventSource.

Tricky & Most-Asked Interview Scenarios

A local SSE demo streams immediately, but production batches updates. What do you inspect?

The Scenario & Constraint

The app logs a flush every second, yet the browser receives thirty events together through the reverse proxy. What will you do?

The Direct Answer & Architectural Decision

Measure emission and arrival times at each hop, inspect content type and buffering/compression behavior, and apply supported route-specific streaming configuration. Verify actual network delivery, heartbeat traffic and idle timeouts using the production-like intermediary path.

Key Trade-Offs & Follow-Up Traps

Disabling buffering changes resource/efficiency trade-offs; periodic status polling may be simpler for coarse progress. Do not globally disable useful caching/buffering without a scoped reason. A framework flush only empties one buffer and does not prove browser receipt.

Last-Event-ID is supplied, but the server no longer has that history. What is the response?

The Scenario & Constraint

A tab resumes after two days while event retention is one hour. Financial task completion must not be silently missed. How will you recover?

The Direct Answer & Architectural Decision

Detect an expired/unknown cursor and trigger a documented snapshot/status resynchronization. Authorize that state request, establish a new continuation boundary and resume live updates consistently with it. Keep task outcomes in durable authoritative state independently of stream retention.

Key Trade-Offs & Follow-Up Traps

Snapshots cost read/catch-up work; retaining more history costs storage and operational capacity. Do not interpret an unrecognized cursor as “start now” without telling the client about the gap. If every historical event is legally required, a durable export/audit contract is separate from this UI stream.

An authenticated EventSource remains open after permissions change. What do you enforce?

The Scenario & Constraint

A user is removed from a private report workspace during a long stream. Reconnect must not restore access. What will you do?

The Direct Answer & Architectural Decision

Define bounded session/revocation behavior and enforce the owning workspace policy for continuing delivery and reconnect/replay. Close or reauthorize expired streams as the policy requires. Use an authentication mechanism supported by the actual browser API and avoid logging long-lived URL tokens.

Key Trade-Offs & Follow-Up Traps

Frequent reauthorization adds lookups or revocation distribution; a documented short credential lifetime can fit a different risk model. A valid last event ID is not proof of access. Existing cached report downloads require the same permission-lifecycle review.

A report finishes while the browser is disconnected. How does the user learn that?

The Scenario & Constraint

The worker deletes its job record after emitting a completion event. A disconnected user sees “running” forever. What will you change?

The Direct Answer & Architectural Decision

Persist a terminal job outcome and result reference with an appropriate retention policy. On reconnect or page startup, read status or replay retained completion; treat events as update notifications rather than the sole owner of truth. Authorize the result download separately.

Key Trade-Offs & Follow-Up Traps

Retained terminal state costs storage and expiry design; a durable notification inbox is another approach for longer-lived obligations. A live transport cannot guarantee an offline user observed an event. Define what happens after result expiry instead of returning a misleading running state.

Many open tabs hit connection limits. Should every widget create its own stream?

The Scenario & Constraint

A dashboard opens one EventSource per widget and users open several tabs. Some streams wait and update latency becomes unpredictable. What will you do?

The Direct Answer & Architectural Decision

Consolidate compatible subscriptions into a bounded per-page stream, inspect actual HTTP version and client/proxy concurrency limits, and close unused streams on teardown. If sharing across tabs is introduced, define ownership and lifecycle deliberately. Measure connections and resource consumption before changing infrastructure.

Key Trade-Offs & Follow-Up Traps

Multiplexing adds event routing and may tie unrelated subscriptions to one failure boundary. A few independent streams can be fine when budgets allow. HTTP/2 changes limits but does not create infinite server capacity or remove slow-consumer queues.

A slow client accumulates thousands of progress events. Must every percentage be replayed?

The Scenario & Constraint

The UI needs current progress and a reliable terminal result, not every intermediate percentage. Slow clients consume too much memory. What will you choose?

The Direct Answer & Architectural Decision

Coalesce replaceable progress to the newest state, bound outbound queues and preserve authoritative terminal outcome/status. Disconnect/resync clients that cannot keep up, with a clear recovery boundary. Retain distinct durable events only when their business semantics require history.

Key Trade-Offs & Follow-Up Traps

Coalescing loses intermediate observations; a full event log is preferable for auditing or per-event obligations. Do not apply that optimization to non-replaceable financial transitions. Receiving an event is still distinct from the client completing its associated work.
