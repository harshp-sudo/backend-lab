gRPC

🎯 The Hook & ELI5

Imagine calling a named kitchen station using a shared order form that both sides understand. The form describes exactly what you may ask and what kind of reply comes back. gRPC turns that idea into generated client/server interfaces, but the cook can still be slow, the reply can be lost and a second call can repeat real work.

gRPC is a remote procedure call framework commonly paired with Protocol Buffers and HTTP/2. A service definition names operations and typed messages; generated stubs encode/decode and invoke them. Network calls remain fallible remote work, even when they look like local functions.

We will use an inventory reservation service shared by backend clients. Proto3 examples are illustrative service contracts, not a deployed server. Runtime language/version, service configuration, browser adaptation and gateway support must be verified for an actual installation.

🗺️ High-Level Big Picture

Typed messages reduce contract ambiguity; they do not turn a network call into an atomic local function. Trace remaining time and durable operation identity with the request.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; protocol and implementation examples state their scope explicitly. Trace the same client operation through success, uncertainty and recovery.

1. Define typed operations and stable field identities

Separate a business reservation ID from a retry identity. The operation identity below lets the domain recognize repeated intent; merely adding the field does not implement deduplication.

syntax = "proto3";
package inventory.v1;
service Inventory {
  rpc Reserve(ReserveRequest) returns (ReserveReply);
}
message ReserveRequest {
  string operation_id = 1;
  string sku = 2;
  int32 quantity = 3;
}
message ReserveReply { string reservation_id = 1; }

Generate client/server interfaces with compatible tooling. Validate quantity, ownership and stock invariants in the implementation; serialization accepts more values than the business allows.

2. Spend one end-to-end budget

Set a realistic caller deadline based on the user operation, then pass the remaining budget downstream. Avoid giving every hop a fresh full timeout. Some languages propagate deadlines automatically and others require configuration; verify yours. Stop spawned work cooperatively when cancellation is observed, where stopping is still safe.

A client DEADLINE_EXCEEDED does not establish that the reservation never committed. If work crossed its durable boundary before the deadline, reconcile the operation identity. Cancellation is a signal, not a transaction rollback protocol.

3. Choose retries deliberately

Configured retries require a bounded policy, appropriate statuses, backoff and a total deadline. Transparent retries cover narrower library-level cases; “retries enabled” does not mean arbitrary business calls are safe to repeat. Retry only under a domain contract that can tolerate duplicates or recognize the same intent.

Put retry responsibility in a clear layer so a gateway, client and handler do not multiply attempts. Separate temporary unavailability from invalid input or failed preconditions. Monitor actual attempts, completion latency and duplicate suppression rather than only successful RPC counts.

4. Treat a stream as a bounded conversation

gRPC supports unary and streaming shapes; choose the shape the interaction needs. Transport flow control can pace sending toward receiver capacity, but your application must also bound queues, handle cancellation and continue reading when using bidirectional streams. A completed write can mean accepted into buffering, not processed by the peer.

If both sides synchronously write large amounts while refusing to read, they can stall. Design concurrent or deliberately interleaved read/write loops with bounded buffers. If messages need durable processing/replay, add application IDs and checkpoints; a live stream does not supply a retained event log.

5. Evolve and expose the service intentionally

Keep protobuf field numbers stable; never reuse a removed field’s number for a different meaning, and reserve removed names/numbers as appropriate. Wire readability does not prove source or business compatibility: enum additions, presence assumptions and changed units can break clients. Test old/new clients against actual generated code.

Native browser clients need an appropriate browser-facing approach such as gRPC-Web with compatible proxy/server support; verify the supported streaming modes for that stack rather than assuming native gRPC parity. A REST or SSE edge can remain useful while internal services use gRPC. Carry authorized identity through the boundary without trusting arbitrary caller metadata.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

A timed-out reservation still exists

Symptom: A retry consumes stock twice.

Root Cause: The client treated deadline expiry as proof of rollback.

Fix/Prevention: Use stable operation identity and inspect the authoritative outcome.

A stream stalls with no CPU pressure

Symptom: Both parties wait forever after filling buffers.

Root Cause: Each side writes synchronously without draining incoming work.

Fix/Prevention: Design bounded, cancellation-aware reading and writing loops.

A harmless field change changes meaning

Symptom: Old clients interpret cents as dollars.

Root Cause: The field number/type remained readable while semantics changed.

Fix/Prevention: Add a new field/contract and migrate callers; protect meanings as well as wire types.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Typed RPC improves contract tooling; correctness still requires propagated budgets, bounded streams, compatible evolution and explicit recovery for uncertain outcomes. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Why is a generated stub still not a local call?

It crosses a failure and latency boundary. A lost response can leave the client uncertain about committed effects even when request/response types are known.

What should a downstream call inherit?

The remaining operation budget, subject to local limits. Giving each hop a fresh full timeout lets downstream work outlive the user operation.

Does a successful streaming write mean peer processing completed?

No. It may mean the framework accepted data into buffering. Application-level acknowledgment is a separate contract.

Why reserve removed protobuf field numbers?

Reusing an old identity can cause older serialized data or clients to interpret a new field under the previous meaning. Compatibility includes semantics and generated-code behavior too.

Tricky & Most-Asked Interview Scenarios

A frontend times out but downstream work runs for another minute. What changes?

The Scenario & Constraint

The user operation has a 500 ms budget. Each of three service hops starts a fresh 500 ms timeout, and cancelled handlers keep spawning queries. What will you do?

The Direct Answer & Architectural Decision

Propagate the remaining deadline, cap each local step within it and make cancellation observable to spawned work. Trace elapsed time by hop and stop avoidable work after cancellation. Preserve or reconcile already committed domain results rather than pretending cancellation reversed them.

Key Trade-Offs & Follow-Up Traps

Shorter budgets can expose slow dependencies earlier; an async operation is preferable if legitimate work cannot fit. Verify language-specific propagation behavior. A deadline does not remove the need for database timeouts or safe cleanup of work already in progress.

A reservation returns DEADLINE_EXCEEDED. Is retrying safe?

The Scenario & Constraint

A stock reservation may commit just before the reply is lost. The caller needs the reservation exactly once for this purchase intent. What will you do?

The Direct Answer & Architectural Decision

Reuse a stable operation ID, enforce duplicate-safe domain execution and recover the stored result. Configure only bounded retry attempts within the total budget and appropriate failure policy. If outcome is uncertain, query/reconcile that operation rather than generate another reservation identity.

Key Trade-Offs & Follow-Up Traps

This requires durable identity/outcome retention; a naturally repeatable set operation is simpler where it fits. A new purchase is a new intent. Neither gRPC retry configuration nor a client error status alone supplies business deduplication.

A bidirectional stream stalls while both sides are writing. How do you debug it?

The Scenario & Constraint

Large messages fill flow-control windows. Both applications synchronously send all output before reading any input, and memory pressure is rising. What will you change?

The Direct Answer & Architectural Decision

Inspect read/write scheduling and buffer metrics, then use bounded concurrent or interleaved reads and writes. Respect framework flow control and cancellation; cap application queues and message sizes. Reproduce with a slow consumer before raising limits.

Key Trade-Offs & Follow-Up Traps

Concurrency introduces ordering/shutdown coordination; a simpler request/response or smaller bounded batches may fit better. Larger windows can delay the stall while increasing memory. If durable receipt matters, add a separate acknowledgment/checkpoint contract.

A deleted protobuf field number is available. Can you reuse it?

The Scenario & Constraint

Old mobile/service clients still send stored messages containing field 4. A new deployment assigns field 4 a different business meaning. How will you avoid corruption?

The Direct Answer & Architectural Decision

Keep field identities stable, reserve the removed number/name and assign a fresh number to the new meaning. Test mixed-version readers/writers and generated clients. Migrate stored messages where semantics require it instead of assuming a successful decode establishes correctness.

Key Trade-Offs & Follow-Up Traps

Keeping obsolete fields increases contract maintenance; a deliberately new major service/message boundary is an alternative for a true break. Numeric wire compatibility can still conceal a units or enum-behavior change, so review meanings and defaults too.

An internal bidirectional RPC must serve browsers. Can you ship the same stub?

The Scenario & Constraint

A dashboard needs live updates and commands. Backend clients use native bidirectional gRPC, but the browser environment and edge proxy have different transport capabilities. What will you do?

The Direct Answer & Architectural Decision

Evaluate the actual gRPC-Web client/proxy/server support and streaming modes, then choose a supported browser contract. If necessary expose commands via ordinary requests and updates via SSE or use WebSockets for a real two-way interaction, while retaining internal gRPC. Test authentication and disconnect recovery across the edge.

Key Trade-Offs & Follow-Up Traps

A separate edge adds translation and lifecycle work; a fully supported browser RPC path can be simpler for the required modes. Do not assume every gRPC-Web implementation matches native streaming. Reconnection and replay remain application concerns whichever browser transport is selected.

An outage turns one RPC into twenty-seven attempts. What is the policy?

The Scenario & Constraint

Three layers independently retry three times while the dependency is overloaded. Error rates and queue times worsen. How will you contain the failure?

The Direct Answer & Architectural Decision

Choose a primary retry owner, enforce one end-to-end attempt/time budget, use bounded backoff with jitter where appropriate and honor overload signals. Stop retrying invalid requests or operations without safe duplicate semantics. Inspect per-logical-operation attempts rather than counting each attempt as independent traffic.

Key Trade-Offs & Follow-Up Traps

Fewer retries may surface transient errors sooner; controlled recovery can be preferable to exhausting the whole fleet. A queued asynchronous operation is another option for delay-tolerant work. Changing status codes to trigger more retries does not create capacity and can repeat committed effects.
