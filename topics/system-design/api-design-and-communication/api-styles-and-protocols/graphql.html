GraphQL

🎯 The Hook & ELI5

At a cafeteria, you can ask for a tray containing just the dishes you need instead of collecting several fixed meal boxes. GraphQL is a typed order form for that tray. The kitchen still has to fetch every ingredient, check what you are allowed to eat and stop an unreasonable order from exhausting the pantry.

GraphQL lets a client select fields from a server-defined type system. A schema describes possible queries and mutations; resolvers obtain the actual values. It changes the API contract and execution model, not the underlying database. One network request can still cause many database or service calls.

Our example is a tenant-scoped order screen with order IDs, totals and customer names. It needs flexible fields without letting one expensive query monopolize the system. The examples use ordinary GraphQL schema/query notation; batching, authorization and demand limits are application/server concerns rather than automatic guarantees from the schema.

🗺️ High-Level Big Picture

Selection flexibility shifts work to field execution. Trace actual resolver/backend calls and authorization context instead of equating one HTTP request with one inexpensive operation.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; protocol and implementation examples state their scope explicitly. Trace the same client operation through success, uncertainty and recovery.

1. Describe the available graph before implementing resolvers

A type is a public contract, not a database table. Expose stable identities and bounded collection arguments; define nullability according to what clients may safely assume. In this illustrative subset, order lookup may return null, but an existing order must have an ID and total.

type Query { order(id: ID!): Order }
type Order {
  id: ID!
  totalCents: Int!
  customer: Customer
}
type Customer { id: ID!, displayName: String! }

query Receipt($id: ID!) {
  order(id: $id) { id totalCents customer { displayName } }
}

Schema validation checks the operation against this contract. It does not prove that the caller owns the order or that fetching customer data is affordable. Keep those checks in the actual execution path.

2. Execute fields with a trusted request context

Authenticate the request and establish tenant/caller context outside untrusted query arguments. Resolve order(id) with object-level authorization, then enforce access to sensitive fields and related objects through the owning policy. Alternative graph paths must not bypass that policy.

Resolvers may run independent read work concurrently. Top-level mutation fields execute serially within one mutation operation, but this is not a database transaction and does not serialize every client or automatically undo earlier side effects. State atomicity in the domain service explicitly.

3. Batch repeated access without leaking identity

A list of twenty orders can make one list query plus twenty separate customer queries. Measure resolver traces, then batch customer IDs into bounded lookups. A request-scoped DataLoader can group loads and memoize matching keys within that request.

Return batch results aligned with requested keys, including missing/error results, and keep tenant/auth context consistent. A process-global loader keyed only by customer ID can leak data across users or serve stale permission-dependent values. Batching removes duplicated trips; it does not eliminate the cost of a huge permitted result.

4. Budget the requested work, not just request count

Bound page sizes and input sizes, and enforce depth/breadth or cost limits appropriate to field fan-out. A shallow query with many aliases can still be expensive. Use timeouts and cancellation, and measure actual backend work to calibrate a cost model.

For controlled clients, an allowlist of reviewed operations can reduce the possible workload. Public flexible clients may need a richer admission policy. Keep authorization separate: a cheap query can still request someone else’s data, and a valid typed query can still be abusive.

5. Treat partial results and evolution as contracts

A field failure can produce errors alongside useful data; non-null failure propagation may null a containing field or larger subtree. Clients must inspect the result structure and their operation’s error policy, not merely assume an HTTP success means every field succeeded. Distinguish request parsing/validation failures from execution errors under the chosen GraphQL-over-HTTP media type and server contract.

Add compatible fields, deprecate old ones with a migration window and inspect actual client operations before removal. Making an input newly required or changing nullability/meaning can break callers. Generated types help detect some changes, but cannot protect a client from changed business semantics.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

One query still makes 101 calls

Symptom: Order screens become slow as list size grows.

Root Cause: Every nested customer field performs its own lookup.

Fix/Prevention: Trace the field path, batch per request and bound collection size.

Typed data leaks across tenants

Symptom: A valid customer query returns another tenant’s name.

Root Cause: A shared loader/cache omitted authorization context or a resolver skipped ownership.

Fix/Prevention: Scope loaders and enforce owner policy at every reachable path.

Success hides missing data

Symptom: The UI displays a total but silently loses a required customer section.

Root Cause: It checked only HTTP status and ignored GraphQL data/errors.

Fix/Prevention: Document nullability and partial-result handling; test actual failure propagation.

🧠 Active Recall & Mastery Check

Summarize this in your own words: A graph is a client contract over real work: authorize every path, batch within safe scope, bound demand and teach clients what partial results mean. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

What does a resolver add beyond a schema?

The schema describes legal fields and types; a resolver supplies values and invokes authorized domain/data operations. Types alone do not fetch or authorize data.

Why can one GraphQL request be slow?

Nested fields may trigger separate backend calls per item. Measure those calls, batch safely and bound the graph; one transport request is not one unit of backend work.

Why prefer a request-scoped loader?

Its memoized results stay within a caller/tenant context and short lifetime. Global caches require a separate explicit authorization, invalidation and keying design.

Can useful data and errors appear together?

Yes. Execution can return partial data and field errors, with non-null propagation affecting the shape. The client must follow its documented result/error policy.

Tricky & Most-Asked Interview Scenarios

One order query creates 101 database calls. What do you change?

The Scenario & Constraint

A query returns 100 orders and a customer name for each. It passes schema validation but p95 latency grows with list size. How will you diagnose and fix it?

The Direct Answer & Architectural Decision

Trace calls by resolver path and confirm repeated customer fetches. Add bounded request-scoped batching with correct key/result alignment and ownership checks, then compare calls, latency and database work on representative pages. Cap list size rather than allowing unlimited batched work.

Key Trade-Offs & Follow-Up Traps

Batching adds scheduling and result-mapping complexity; a tailored joined read can be simpler for one stable view. If customers are remote services, bound batch sizes and failures. A single query that still scans millions of rows needs indexing/workload changes beyond DataLoader.

A global customer loader returns another tenant’s data. What is the boundary?

The Scenario & Constraint

A process-wide loader caches by customer ID. Two tenants can use overlapping external IDs and have different field permissions. What will you do first?

The Direct Answer & Architectural Decision

Remove unsafe cross-request memoization, invalidate affected entries and establish a loader per trusted request context. Fetch through tenant/permission-aware ownership checks. If a shared cache is later justified, explicitly key and invalidate every visibility-relevant dimension instead of copying the short-lived loader design.

Key Trade-Offs & Follow-Up Traps

Per-request caching sacrifices cross-request hits but makes scope easier to reason about. An authorized shared read model is an alternative with more policy work. Even globally unique IDs do not authorize access, and permission changes can invalidate a previously valid cached view.

Depth is limited, but one query still overloads the backend. Why?

The Scenario & Constraint

A client uses many aliases and large sibling lists without exceeding the allowed nesting depth. Backend work exceeds the request budget. What will you do?

The Direct Answer & Architectural Decision

Measure field cardinality and backend cost, bound list arguments and operation size, and introduce breadth/complexity admission plus execution deadlines. For controlled consumers, consider reviewed persisted operations. Keep capacity-aware quotas based on actual expensive dimensions.

Key Trade-Offs & Follow-Up Traps

Cost models require maintenance and may reject legitimate heavy reads; a dedicated asynchronous export may fit that workload better. Rate-limiting only HTTP request count misses this amplification. If one allowed resolver has an unbounded query, fix its access contract as well.

The root query checks ownership, but a nested path exposes a private field. Where does policy live?

The Scenario & Constraint

A private invoice is inaccessible through invoice(id), yet reachable through customer.orders.invoice. Different resolvers were written by different teams. How will you prevent this?

The Direct Answer & Architectural Decision

Centralize object/field permission checks in the owning access layer and ensure each resolver uses trusted request identity. Test alternate graph paths and deny sensitive fields appropriately. Root authentication establishes who the caller is; it cannot substitute for authorization of every returned object.

Key Trade-Offs & Follow-Up Traps

Central policy adds context plumbing and can require bulk permission checks for performance. Separate public/private schema views may simplify some surfaces but do not remove ownership enforcement. If caching is added, verify it preserves the same policy scope.

A customer lookup error nulls an order subtree. Should every field be non-null?

The Scenario & Constraint

A screen could still show order identity and total during a customer-service outage, but a strict nested non-null chain makes the entire view disappear. What will you change?

The Direct Answer & Architectural Decision

Model nullability around actual failure/absence guarantees and document error behavior. Make the optional customer-dependent boundary nullable where appropriate, preserve useful order data and return a safe field error. Update client behavior and compatibility analysis before changing the contract.

Key Trade-Offs & Follow-Up Traps

Nullable fields require explicit UI states; an independently owned denormalized display snapshot may be preferable for a historical receipt. Do not simply hide a failed price calculation behind null when the business requires a trustworthy total. Changed guarantees can break clients even when a query still parses.

Two mutation fields are serial. Is checkout now transactional?

The Scenario & Constraint

A mutation reserves stock and then charges payment. The second field fails after the first succeeded. A proposal relies on GraphQL’s serial execution to roll everything back. What will you do?

The Direct Answer & Architectural Decision

Move checkout orchestration into a domain operation with explicit durable state, idempotency and compensation/reconciliation rules. Use a local transaction only for effects within its actual boundary. Return the truthful operation outcome so retries can recover without creating a second reservation or charge.

Key Trade-Offs & Follow-Up Traps

This costs workflow and recovery state; an atomic local operation is simpler when all invariants share one database. Serial field execution orders these resolver calls but does not create a distributed transaction. If a payment outcome is unknown, do not blindly compensate or charge again.
