REST API Design

🎯 The Hook & ELI5

A library gives every book a stable catalog address. You can read its card, replace a reservation request, or cancel a reservation without knowing which shelf worker handles it. A good API offers similarly predictable addresses and actions, so clients can reason about a request even when its reply is delayed or lost.

REST means Representational State Transfer: an architectural style built around resources, representations and a uniform interface. A resource is the thing identified; a JSON document is one representation of it. HTTP is a common implementation medium, but returning JSON from noun-shaped URLs alone does not establish every REST constraint. Stateless interaction means each request carries the context needed to interpret it; it does not forbid stored orders, authentication records or caches.

We will design an order API for independent mobile and web clients. The important contract includes observable behavior during conflicts, caching and retries, not just endpoint spelling. HTTP examples use RFC 9110/9111 semantics; business rules and idempotency-key behavior must be implemented by the service.

🗺️ High-Level Big Picture

Follow a single order operation from intent to a client-visible result. Resource naming does not remove authorization, concurrency or failure decisions inside the service.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; protocol and implementation examples state their scope explicitly. Trace the same client operation through success, uncertainty and recovery.

1. Identify the resource and its lifecycle

Start with the client task: create an order, inspect its current state, change a delivery note, request cancellation. Give an order a stable identity such as /orders/o-42 and keep internal table names out of the public contract. Model cancellation as an explicit state transition or cancellation resource when it has its own lifecycle; do not disguise an arbitrary command as a safe read.

Define who owns each field, which transitions are allowed, and whether deletion means removal or a recorded cancellation. A resource model should explain business meaning, not mechanically expose every database column.

The full REST style combines client/server separation, stateless requests, cache constraints, a uniform interface and a layered system; downloadable code is an optional constraint. Its uniform interface includes identifying resources, manipulating them through representations, self-describing messages and hypermedia controls. Think of a returned order view as a menu of currently available next actions: links or controls can advertise status and cancellation instead of forcing a client to invent every transition URL. A practical HTTP API may adopt only some constraints; describe that scope honestly rather than calling any JSON CRUD interface fully REST-conformant.

2. Choose methods by intended effects

Use GET to retrieve without asking for a business mutation. PUT supplies a replacement at a known target with idempotent intended effects; POST asks the target to process supplied content, often creating a new member. PATCH is a partial-change method whose idempotency depends on the patch operation. DELETE is idempotent in intended effect even if repeated responses differ.

A proxy, browser or retrying client can act on these semantics. GET /orders/o-42/cancel is dangerous because automated retrieval can trigger cancellation. HTTP idempotence does not promise identical response bytes or prevent incidental logging; it concerns intended effects of repeating the request.

3. Return a result clients can act on

For a completed creation, document a 201 response with a Location pointing to the new order. A 202 response means accepted for processing, not completed: provide a status resource and terminal outcomes. A 204 response has no content. Keep stable machine-readable errors separate from human-facing wording.

POST /orders HTTP/1.1
Host: api.example.test
Content-Type: application/json

{"cartId":"c-7","deliveryNote":"Reception"}

HTTP/1.1 201 Created
Location: /orders/o-42
Content-Type: application/json

{"id":"o-42","state":"confirmed"}

This is an illustrative request/response exchange, not a runnable server. Validate ownership of the cart and allowed state transitions before returning success; the response schema should describe client concepts rather than internal persistence entities.

4. Protect concurrent edits with a condition

Give a retrieved editable representation a strong ETag suitable for comparison, and require If-Match on changes where overwrites would lose another user’s update. Evaluate the condition together with the authoritative write; a separate unchecked read followed by update recreates the race. On a failed precondition, normally return 412 and help the client refresh and reconcile.

For example, two editors read version 8. The first conditional replacement succeeds and advances the version. The second must not silently overwrite it with version 8 data. This protects lost updates; it is distinct from deduplicating two deliveries of the same creation request.

5. Define freshness, traversal and recovery together

For a public catalog, choose a cache policy and validator that fit its accepted staleness. For personalized orders, choose private caching or no-store as appropriate and verify actual intermediary behavior. no-cache permits storage with validation; it does not mean no-store. Representations can vary by negotiated language or other inputs, which must be accounted for in the cache contract.

Bound collection responses and document ordering/cursors from the start. When a mutation times out, treat the outcome as uncertain; query an operation resource or retry under a documented idempotency contract rather than blindly generating a new order. Include correlation information that helps operations staff find the request without leaking internal details.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

A link performs a mutation

Symptom: A preview bot cancels an order.

Root Cause: Cancellation was implemented as GET.

Fix/Prevention: Use an unsafe operation with authorization and documented state transitions; keep retrieval safe.

A successful response hides unfinished work

Symptom: A client displays completion before fulfillment is recorded.

Root Cause: 202 was treated as a final success state.

Fix/Prevention: Expose durable operation status, terminal failure and a recovery path.

A cache leaks a personal order

Symptom: Another user receives the previous user’s response.

Root Cause: A shared cache treated a personalized representation as public.

Fix/Prevention: Disable inappropriate shared storage and verify identity/representation cache boundaries end to end.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Design a resource contract clients can use during concurrency and uncertainty: method effects, representations, conditions, freshness and recovery must agree. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Is an order JSON document the resource itself?

The order is the identified resource; JSON is one representation. Other views or encodings can describe the same resource without exposing the storage layout.

How are safe and idempotent different?

Safe methods do not request business state changes. Idempotent methods can change state, but repeating an identical request has the same intended effect as one such request.

What does If-Match protect?

It prevents applying an update against an obsolete representation version when the service enforces the condition atomically with the write. It does not identify duplicate business intent.

What must accompany a useful 202 contract?

A discoverable way to inspect durable progress and terminal outcomes, plus guidance for retry/cancellation where supported. Acceptance alone is not completion.

Tricky & Most-Asked Interview Scenarios

The order request timed out after the server committed. Will you POST again?

The Scenario & Constraint

A mobile checkout sends POST /orders, loses connectivity, then retries. A second real purchase is possible later, but this attempt must not create two orders. What will you do and why?

The Direct Answer & Architectural Decision

Define caller-supplied operation identity scoped to the authenticated caller. Retry this intent with the same identity and equivalent payload; atomically associate it with the order/outcome and return the stored result or durable in-progress status. Distinguish an unknown outcome from a confirmed rejection before starting another operation.

Key Trade-Offs & Follow-Up Traps

Deduplication costs retained state and recovery work; a client-chosen PUT target can be an alternative when creation naturally has a stable identity. A new intentional purchase needs a new identity. Expired identity retention or external side effects require reconciliation; POST spelling alone neither guarantees nor forbids duplicate protection.

Two agents overwrite each other’s delivery notes. Where is the fix?

The Scenario & Constraint

Two support agents read the same order and submit full updates seconds apart. Both are authorized; silent lost updates are unacceptable. How will you change the API?

The Direct Answer & Architectural Decision

Return a strong representation version and require If-Match on the write. Perform the comparison in the same authoritative concurrency boundary as the state change; reject the stale edit and let its client show a merge/refresh flow. Keep business state-transition checks alongside this condition.

Key Trade-Offs & Follow-Up Traps

Clients must handle conflicts and multiple representations require deliberate validator design. A narrowly scoped atomic field operation may reduce conflicts when changes are independent. If the operation is a non-repeatable increment, conditional replacement and duplicate identity answer different questions and may both be necessary.

A CDN improves speed but returns someone else’s order. What changes first?

The Scenario & Constraint

GET /orders/o-42 is authenticated and personalized. A CDN caches only by URL while authorization changes the visible fields. You must contain the incident before optimizing performance. What will you do?

The Direct Answer & Architectural Decision

Stop unsafe shared reuse, purge affected entries, and apply a reviewed private/no-store policy for the sensitive response as appropriate. Ensure authorization is evaluated for every access and test two identities through the actual cache. Cache a separate truly public representation only under an explicit safe policy.

Key Trade-Offs & Follow-Up Traps

Disabling shared caching increases origin load, so bound and monitor that traffic. Properly partitioned trusted caches can be an alternative but require all visibility-affecting inputs and policy changes to be handled. A Vary header is not a substitute for access control, and browser-private storage still requires its own privacy assessment.

A report takes two minutes but the gateway waits thirty seconds. What is the contract?

The Scenario & Constraint

A report-generation request is legitimate but exceeds the synchronous timeout. Clients must know whether work exists and avoid duplicate jobs after retry. What will you do?

The Direct Answer & Architectural Decision

Create a durable operation resource, return 202 with a documented status link, and let clients poll or receive a notification that refers back to authoritative status. Store terminal success/failure and result access rules. Reuse the same operation identity if the submission outcome is uncertain.

Key Trade-Offs & Follow-Up Traps

This adds durable jobs, expiry and status handling; a synchronous response is simpler for reliably short work. If reports are sensitive, authorize both status and download requests. A completed worker task with a lost notification must remain discoverable, and cancellation needs its own race-aware semantics.

A browser prefetch cancels an order. Is authentication enough?

The Scenario & Constraint

GET /orders/o-42/cancel changes state. Authenticated browsers or link scanners may fetch it without an explicit user action. How will you redesign it?

The Direct Answer & Architectural Decision

Move cancellation behind a documented unsafe operation, such as creating a cancellation request, and validate the caller, object ownership and allowed transition. Keep GET limited to retrieving status. For browser cookie authentication, apply the appropriate CSRF protections rather than assuming method choice alone provides security.

Key Trade-Offs & Follow-Up Traps

A dedicated cancellation resource supports asynchronous approval but adds lifecycle detail; a simple operation can be enough for immediate cancellation. Repeated cancellation should have a defined outcome. If fulfillment already occurred, return the actual domain conflict instead of claiming an earlier cancellation succeeded.

A retried PATCH increments quantity twice. Was PATCH supposed to prevent that?

The Scenario & Constraint

A cart endpoint accepts a partial update meaning “add one.” A client retries after a timeout and quantity rises twice. The user intended only one addition. What will you do?

The Direct Answer & Architectural Decision

Distinguish a set-to-value update from an increment command. For repeated intent, use an operation identity and duplicate-safe execution, or replace an explicitly versioned quantity with If-Match when that matches the interaction. Document the patch format and its effects instead of assuming every PATCH is idempotent.

Key Trade-Offs & Follow-Up Traps

Versioned replacement can conflict with another device’s edit, while operation identity needs retained outcomes. If repeated increments are separate deliberate clicks, give each a separate identity. A transport retry must not invent a new identity or blindly reset another client’s quantity.
