Health Checks

🎯 The Hook & ELI5

A restaurant’s “open” sign, an alarm for a broken oven and a note saying “still warming up” answer different questions. If the vegetable supplier is late, repeatedly demolishing and rebuilding the restaurant will not make vegetables arrive faster. A health check is useful only when its signal leads to the right action.

Health checks are inputs to control decisions: send traffic, allow startup to continue, restart a stuck process or alert an operator. They are not a complete proof that user journeys meet their performance/correctness objectives. Distinguish the question, observer, scope, threshold and action before writing an endpoint.

Other platforms and selected features can differ, so verify the deployed version/configuration. 🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace resource ownership, waiting, useful work and the recovery boundary.

1. Write each probe’s recovery hypothesis

For every signal ask what condition it detects and why the configured action helps. A local deadlock may justify a liveness-triggered restart. A temporary dependency outage may justify withholding some traffic, while restarting every replica can make recovery harder. A model still loading is a startup condition with its own allowed window.

Define the service contract: a catalog path might serve cached reads without its write database, while checkout cannot safely complete. One global readiness bit may be too coarse for every operation; routing and degradation must reflect the actual contract.

2. Separate startup, liveness and readiness

With a configured Kubernetes startup probe, liveness and readiness probes do not run until startup succeeds. Liveness is for a condition where restart is appropriate; readiness controls whether an instance should receive regular traffic without itself implying restart. Check failure/success tolerances and the platform’s actual action.

Avoid a short liveness loop that kills legitimate slow initialization before it can finish. Startup windows should be measured and bounded, not infinite. A process crash can already trigger a restart policy; another expensive liveness endpoint is not automatically required for every application.

3. Choose meaningful low-cost evidence

A successful TCP connection or static 200 response may prove only that a socket or handler is reachable. Conversely, a probe that runs an expensive full dependency transaction on every interval can create load and fail for reasons restarting cannot solve.

Select cheap local progress/resource state for the intended action, and use appropriately bounded dependency evidence only where traffic eligibility genuinely depends on it. Keep details such as credentials, internal topology and stack traces out of a public health response. Synthetic user journeys belong in separate monitoring with their own budget.

4. Use thresholds without building an unstable controller

Probe period, timeout and failure/success thresholds trade detection speed against transient noise and recovery flapping. A simplified three-failure policy with checks every ten seconds detects failure on an order-of-tens-of-seconds scale, but phase, execution time and platform behavior affect exact timing.

A timeout shorter than legitimate handler delay under normal load can cause false failures. Simultaneously withdrawing every overloaded replica can move demand onto fewer instances and amplify stress. Test the feedback loop, not only the endpoint handler in isolation.

5. Coordinate shutdown and dependency treatment

During normal termination, the platform’s terminating endpoint state and the application’s local admission/drain policy cooperate. Propagation is asynchronous; changing readiness does not prove no more work can arrive. Keep health responses meaningful while active work drains, and follow the selected lifecycle semantics.

For a shared database outage, decide whether all paths must stop, some paths can degrade, and which probes should reflect that. Do not wire a remote dependency into liveness merely because it is easy to query. Repeated process restarts do not repair an unavailable external database.

6. Verify control actions and user outcomes

In a controlled environment test slow startup, a recoverable dependency failure, a true local hang, probe timeout, overload, readiness flapping and termination. Observe actual restart counts, traffic eligibility, propagation, surviving capacity and user errors/latency.

Combine probe status with performance monitoring and representative user journeys. A service can pass health checks while p99 or a tenant-specific path is broken. Record limitations: the check samples one signal at particular times and cannot certify all future requests.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Database outage becomes a restart storm

Symptom: Every replica repeatedly restarts while the database remains unavailable.

Root Cause: Liveness includes an external condition that a local restart cannot repair.

Fix/Prevention: Choose local recovery evidence and a separate readiness/degradation policy.

Slow startup never completes

Symptom: New replicas are killed during legitimate warmup.

Root Cause: Steady-state liveness timings are applied before initialization can finish.

Fix/Prevention: Use a measured startup allowance and verify actual probe gating.

Green probes hide broken users

Symptom: The health handler responds but order requests violate objectives.

Root Cause: A narrow reachability check is treated as end-to-end correctness/performance proof.

Fix/Prevention: Monitor actual user outcomes, errors and latency with meaningful cohorts.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Design health signals backward from their actions, test their feedback under failure and use separate user-outcome monitoring to establish performance and correctness. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

What question should precede any probe implementation?

What action will consume this signal, and why would that action improve the named failure condition?

Does failing readiness inherently mean restart?

No. In the Kubernetes example it affects regular traffic eligibility; liveness/startup and restart policy have different actions.

Why avoid remote database reachability as automatic liveness?

Restarting the local process may not repair the database and can create synchronized churn or recovery load.

Does a successful probe establish an SLO?

No. It samples its own condition; actual user paths, tails, errors and correctness need separate monitoring.

Tricky & Most-Asked Interview Scenarios

A model needs ninety seconds to load, but liveness kills it after twenty. What changes?

The Scenario & Constraint

New pods never become useful because initialization restarts repeatedly. What will you configure and measure?

The Direct Answer & Architectural Decision

Use the platform’s startup-specific gating with a bounded measured allowance for initialization, then apply appropriate steady-state liveness/readiness behavior. Confirm startup actually makes progress and test cold as well as warm conditions.

Key Trade-Offs & Follow-Up Traps

An infinite window can hide a genuine startup hang. A longer ordinary liveness interval may delay later recovery unnecessarily. Do not assume a ready pod can serve meaningful traffic before its required model is loaded.

The database fails and every application replica restarts. Is liveness helping?

The Scenario & Constraint

Liveness performs a mandatory database query. The external database outage is unaffected by application restarts. What policy will you choose?

The Direct Answer & Architectural Decision

Separate local progress/restart evidence from external dependency status. Decide readiness or explicit degraded routing according to which operations can still satisfy their contracts, with bounded dependency checks and recovery behavior. Observe remaining capacity and user outcomes during the outage.

Key Trade-Offs & Follow-Up Traps

Withdrawing all traffic may be correct for wholly unusable paths but can also amplify load on surviving capacity. A cached read path might remain useful. Local restart is justified only when evidence shows a local failure it can repair, not every downstream error.

The /health endpoint returns a static 200 while workers are deadlocked. What should it prove?

The Scenario & Constraint

A separate trivial handler remains responsive but the actual execution resource cannot make progress. What signal/action design will you use?

The Direct Answer & Architectural Decision

Define a low-cost local progress or readiness signal that observes the resource necessary for the routed contract, with a liveness action only when restart is a suitable remedy. Validate it using a controlled local-hang scenario and compare actual user behavior.

Key Trade-Offs & Follow-Up Traps

A deep full business transaction on every probe can be expensive and introduce new dependencies. A cheap signal can still have blind spots; separate synthetic monitoring can cover broader behavior without turning every dependency fault into a restart.

All pods oscillate ready/not-ready under bursts. What feedback loop do you inspect?

The Scenario & Constraint

Readiness fails at a low queue threshold; removing replicas concentrates traffic on the rest, causing more failures. What will you change?

The Direct Answer & Architectural Decision

Inspect capacity, routing/admission behavior, probe timing and thresholds together. Prefer bounded overload admission and truthful degradation; tune readiness recovery/failure tolerances against measured conditions instead of a single transient queue sample. Test burst and recovery behavior end to end.

Key Trade-Offs & Follow-Up Traps

Slower detection can send traffic to an unsuitable instance for longer, while faster withdrawal can destabilize the fleet. More replicas may help only if the downstream bottleneck can use them. A health controller needs hysteresis-like stability, not only a fast red/green toggle.

Health checks issue expensive SQL from hundreds of replicas. What is their own cost?

The Scenario & Constraint

Each frequent check performs a deep query, consuming the database during a traffic incident. What will you replace or separate?

The Direct Answer & Architectural Decision

Use cheaper bounded evidence for the specific local/readiness question, and move deep user-journey checks to a separately budgeted monitoring path where appropriate. Measure total check rate, timeout behavior and dependency load across the fleet.

Key Trade-Offs & Follow-Up Traps

A shallower check proves less, so document its scope and keep user-outcome monitoring. Caching dependency status trades freshness for lower cost. Removing all evidence can leave unsuitable instances serving traffic; the choice must preserve the named action’s purpose.

An instance becomes not-ready during deletion but still receives a late request. Was readiness broken?

The Scenario & Constraint

The network path and existing connections take time to observe termination. The process closes its database immediately. What lifecycle behavior is missing?

The Direct Answer & Architectural Decision

Coordinate normal termination state, stopped local admission, bounded in-flight draining and dependency cleanup. Test the actual routing propagation and existing-connection behavior. Treat readiness as one input to traffic decisions, not instantaneous cancellation of every possible arrival.

Key Trade-Offs & Follow-Up Traps

Adding a fixed sleep may help one environment but consumes the same shutdown budget and is not proof of convergence. Abrupt crashes still need separate recovery. Keep the distinction between readiness withdrawal, connection handling and business ownership.
