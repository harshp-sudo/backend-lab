Performance Monitoring

🎯 The Hook & ELI5

A delivery company needs to know whether parcels arrive on time, where each delayed parcel waited and whether trucks are full. A green light on every truck does not answer those questions. Monitoring connects the customer’s result to the route, waiting places and shared capacity, so a mechanic fixes the right problem.

Performance monitoring continuously relates user-visible outcomes to workload and resource evidence. Metrics summarize populations, traces follow related operations, logs record contextual events and profiles describe resource use in code paths. These signals complement one another; correlation is a hypothesis, not proof of cause. Health probes answer narrower control questions.

Our hypothetical orders API has a stated latency/error objective and several tenant/workload classes. OpenTelemetry provides signal/context vocabulary, Prometheus references explain statistical/label constraints, and original SRE guidance supplies operational reasoning. No telemetry backend is added to this static dashboard; all numerical examples are constructed teaching cases.

🗺️ High-Level Big Picture

The loop begins and ends at useful user outcomes. Internal resource signals explain or warn about a failure, but they do not replace the externally meaningful objective.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace resource ownership, waiting, useful work and the recovery boundary.

1. Define the objective and denominator

Name the user transaction, success condition, population and time window. Include meaningful failures/timeouts/rejections rather than counting only successful fast responses. An original illustrative 99.9% success objective over 100,000 eligible operations permits 100 failures under that simple definition; exclusions and eligibility must be explicit.

Choose latency objectives by operation and intended user boundary. A server-only timer excludes client/network waiting; a database timer excludes pool acquisition. Record what each measurement includes before comparing them. Instrumentation and business correctness are separate concerns.

2. Observe symptoms and resource pressure together

Measure traffic, errors, latency and saturation for bounded useful cohorts. Saturation includes queue age, active/available slots, throttling, memory pressure or database waits, not only average CPU. Count offered, admitted, rejected and usefully completed work separately during overload.

Use internal signals to investigate or warn, while paging on conditions that warrant a timely action. A CPU threshold without context may be noisy; a broken critical user path with low CPU still matters. Annotate deployments/configuration changes as potential clues rather than immediate proof of blame.

3. Aggregate distributions instead of averaging percentiles

A percentile summarizes a distribution, not an additive quantity. In an original example, instance A serves 990 requests at 10 ms and B serves ten at 1,000 ms. The combined p95 is 10 ms under the simple nearest-rank definition, while averaging the instance p95 values gives 505 ms, which describes neither the population nor a meaningful typical request.

Use compatible histogram observations/buckets or the backend’s supported distribution aggregation over the correct window/population. Know resolution and low-sample limitations. Inspect instance/tenant cohorts too: an acceptable global percentile can still hide all of one small tenant’s requests being slow.

4. Preserve context without turning it into authority

Propagate supported trace context across HTTP, queues and asynchronous task boundaries so parent/child work can be related. Add bounded operation and deployment context to logs, and use a trace ID to find detailed events. Verify propagation through the actual client/worker libraries; a span without the right parent can make a long wait look unrelated.

OpenTelemetry context/baggage is observability metadata, not an authentication credential. Treat incoming context as untrusted input, avoid secrets/customer payloads in baggage/logs and control what leaves the service boundary. Sampling means a missing trace is not proof that a request never happened.

5. Bound telemetry cardinality, overhead and retention

Use normalized route/operation names and bounded status/environment dimensions. Raw URLs, user IDs and unbounded exception messages as metric labels create a new series for many distinct values. As an illustrative product, 100 routes × five status classes × ten regions already permits 5,000 combinations before instance or other labels.

Put necessary high-detail context in appropriately protected sampled logs/traces rather than every metric identity. Budget exporters, buffers, sampling and retention; telemetry outages must not create unbounded application queues or block every request. Verify actual SDK/exporter support and signal maturity rather than assuming all signals behave identically.

6. Respond with a hypothesis and verify recovery

When an objective worsens, compare the affected operation/time/tenant cohort, resource state, trace path and recent changes. If acquisition waits dominate, investigate connection holders before optimizing a formatter. If CPU dominates, choose representative profiles. State what would disprove the suspected mechanism.

After a bounded fix or rollback, verify latency/errors, useful throughput, saturation and recovery for the same population. Keep enough before/after context to avoid attributing a natural traffic drop to the change. Improve the alert/runbook based on what actually required action, not on the number of graphs produced.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Success latency improves during an outage

Symptom: The dashboard looks faster while many requests are rejected.

Root Cause: Only surviving successful operations enter the displayed distribution.

Fix/Prevention: Show offered/rejected/error counts and the objective’s complete eligible population.

One metric label per customer request

Symptom: Telemetry storage/export cost explodes.

Root Cause: Unbounded IDs/URLs were used as series dimensions.

Fix/Prevention: Normalize labels and put protected high-detail correlation in suitable logs/traces.

A trace ID is trusted as tenant identity

Symptom: Observability context affects access decisions.

Root Cause: Correlation metadata is mistaken for authenticated authority.

Fix/Prevention: Keep authorization on trusted identity/resource policy and sanitize incoming telemetry context.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Define the user outcome, preserve trustworthy bounded telemetry, choose evidence that sees the mechanism and verify recovery against the same workload and population. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

How do metrics, traces, logs and profiles complement one another?

Metrics summarize populations, traces relate work, logs explain events and profiles attribute resource use; choose the signal that sees the suspected mechanism.

Can you average instance p95 values to get service p95?

No. Combine compatible distributions/counts through supported aggregation, then compute the desired population quantile.

Why normalize route labels instead of recording raw URL paths?

An unbounded path/ID dimension creates many time series and expensive telemetry state; operation templates keep the dimension bounded.

What turns a correlation into stronger causal evidence?

A mechanism-backed hypothesis, relevant observations, an appropriate controlled change and comparable outcome verification, with alternative explanations considered.

Tricky & Most-Asked Interview Scenarios

All probes pass, but order p99 and error rate violate the objective. What do you inspect?

The Scenario & Constraint

The health handler is cheap and succeeds while pool acquisition and one tenant’s order requests stall. What evidence and response will you choose?

The Direct Answer & Architectural Decision

Scope the affected user operation/tenant/time window, inspect complete latency/error populations and trace acquisition versus SQL/transfer. Follow the constrained owner/resource, choose a bounded corrective action and verify the same user objective afterward.

Key Trade-Offs & Follow-Up Traps

Probe success only establishes its sampled condition. Restarting healthy processes can worsen capacity; a CPU optimization may miss the waiting bottleneck. Use health checks for their intended control actions and user monitoring for the broader service contract.

Instance p95 values are 10 ms and 1,000 ms. Is global p95 505 ms?

The Scenario & Constraint

The first instance handles 990 observations and the second only ten during the same window. What aggregation and additional view will you use?

The Direct Answer & Architectural Decision

Combine the compatible observations/distributions and compute the population quantile; in the simple stated nearest-rank example, global p95 is 10 ms. Also show per-instance/cohort behavior because the smaller group can be entirely broken despite that global number.

Key Trade-Offs & Follow-Up Traps

Averaging quantiles is not weighted distribution aggregation. Histogram boundaries introduce approximation and must fit the accuracy requirement. Global objectives and fairness/cohort objectives answer different questions; do not hide a small tenant behind a large fast population.

A queue consumer looks unrelated to its originating request. What is missing?

The Scenario & Constraint

HTTP spans are linked, but trace context is lost during asynchronous handoff. What will you verify and propagate?

The Direct Answer & Architectural Decision

Use the selected OpenTelemetry propagator/library conventions to inject/extract appropriate context at the handoff boundary and establish correct parent/link semantics for the processing model. Confirm behavior through retries, batching and sampling with the actual instrumentation.

Key Trade-Offs & Follow-Up Traps

Not every delayed or batched consumer should be forced into one simplistic synchronous parent chain. Context is untrusted correlation metadata and must not carry credentials or grant permission. Missing sampled spans do not prove missing business execution.

A metric labels every raw order URL and user ID. How do you keep diagnosis without the bill?

The Scenario & Constraint

A release creates huge series counts and exporter pressure. Operators still need to investigate individual failures. What will you change?

The Direct Answer & Architectural Decision

Normalize route labels to bounded templates and retain only justified bounded dimensions. Put protected trace/request correlation and detailed events in appropriately sampled/retained logs or traces, and monitor the exporter’s own queue/drop behavior. Compare the new operational questions the metrics can answer.

Key Trade-Offs & Follow-Up Traps

Removing every label loses useful cohorts, while hashing IDs does not bound their count. Sampling and retention limit detail and may miss rare requests; record that coverage. Telemetry must not become an unbounded resource owner inside the application.

CPU pages every night during a healthy batch. What should the alert mean?

The Scenario & Constraint

The batch uses spare CPU without harming interactive objectives, while a low-CPU lock incident was missed. What alert strategy will you design?

The Direct Answer & Architectural Decision

Page on an actionable user-impact/objective condition or well-justified imminent risk, using resource signals to explain and route investigation. Keep batch CPU visible with context, and include latency/errors/saturation relevant to the affected path. Define the operator action and verify it against incidents.

Key Trade-Offs & Follow-Up Traps

Waiting for severe user impact can detect too late, so meaningful predictive capacity alerts still have a role. A single generic CPU threshold is not a substitute for that hypothesis. Avoid replacing useful early warnings with a blanket no-resource-alert rule.

Latency improves just after a deployment rollback and traffic falls too. What can you claim?

The Scenario & Constraint

The team wants to attribute all improvement to the rollback, but workload mix and arrival rate changed. What evidence and wording fit?

The Direct Answer & Architectural Decision

Compare equivalent cohorts/windows, resource/wait mechanisms and the suspected changed path, and reproduce a controlled before/after trial where feasible. State that recovery coincided with both changes unless evidence separates their effects; verify the user objective remains healthy at representative demand.

Key Trade-Offs & Follow-Up Traps

A rollback may still be the right incident action under uncertainty. Correlation supports a hypothesis, not an exact causal percentage. Keep absolute traffic/errors and distribution scope so lower demand or changed rejection does not masquerade as an algorithmic speedup.
