Load Testing

🎯 The Hook & ELI5

A café rehearses the morning rush by sending customers through the real ordering and pickup steps. If each pretend customer waits for the last order before entering, a slow kitchen automatically makes the rehearsal quieter. That may model a small group of regulars, but it does not model a bus unloading people at a fixed rate. A useful load test rehearses the workload you actually expect.

Load testing checks whether a system meets stated behavior and performance objectives under an intended workload, including an expected peak. The workload includes operation mix, arrivals, data, state, dependency behavior and duration. “One thousand users” is incomplete without explaining what they do and how often.

We design a hypothetical tenant API rehearsal with normal and peak demand. Grafana k6 documentation supplies concrete open/closed-model and threshold terminology. No real service has been load-tested as part of this lesson; rates and outcomes below are teaching examples. The dashboard itself only displays the lesson and never generates the example traffic.

🗺️ High-Level Big Picture

A clean latency chart is meaningful only if the test delivered the intended workload and counted failures. Validate the test apparatus before using it to approve a system change.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace resource ownership, waiting, useful work and the recovery boundary.

1. Write an executable meaning for success

Our original illustrative workload is 80% order reads, 15% updates and 5% exports, with validated tenant identities and representative result sizes. Define expected/peak offered demand, successful-response criteria, latency objectives per operation and acceptable resource behavior. Separate a user transaction from the HTTP requests it may contain.

An example objective is that order reads meet p95 under 200 ms with fewer than 1% failed attempts during the relevant stage. Those numbers are an assumed contract, not a universal recommendation. A fast 200 response containing an error payload must not count as useful success.

2. Choose an arrival model that matches the question

A closed model keeps a bounded user population cycling through work; slower iterations reduce the rate at which that population starts new iterations. An open arrival-rate model schedules starts independently of preceding iteration completion, subject to generator limits. Both can be valid if they match the demand question.

For a fixed external request arrival target, closed-model slowdown can underexercise the service when it is slow, the coordinated-omission concern. If the actual product has a truly closed fixed population, that feedback may be part of its real behavior. State the model instead of declaring one universally superior.

3. Make data and state representative

Prepare tenant sizes, page fan-out, payload sizes, cache hit/miss conditions and read/write conflicts that reflect the scenario. A single hot key and empty database can make every access look cheaper than production; randomly generating only nonexistent keys can exercise error paths instead of useful work.

Define setup/reset and unique operation identities so repeated tests neither reuse unrealistic warm state nor create accidental duplicate business effects. Include representative dependency latency/failure behavior, labeling mocks and differences. Never send real customer secrets into a convenient external test target.

4. Budget the generator and distinguish attempts from deliveries

An illustrative open workload starts 500 iterations/s and each iteration occupies a virtual user for 0.4 s on average: roughly 200 active iteration slots are needed before variation/headroom. That is an average occupancy estimate, not a guarantee that 200 slots avoid all dropped starts.

Observe generator CPU/memory/network, actual start/completion rates and dropped/unscheduled work. If the generator cannot produce demand, a low service latency is not a pass at the intended rate. Count retries separately so five attempts do not masquerade as five successful business transactions.

5. Run controlled stages with meaningful thresholds

Begin with a smoke check for correctness, then warmup where appropriate, normal demand and the expected peak, with hold periods long enough to observe the question. Grafana k6 thresholds express pass/fail criteria on metrics; checks and HTTP success alone do not supply every required business criterion.

Inspect latency distributions and errors per operation/stage/tenant class rather than only a run-wide average. Check server queue age, connection waits, CPU, memory and dependency saturation alongside user observations. Keep stop conditions for harmful unexpected behavior even in an authorized test environment.

6. Compare like with like and explain uncertainty

Record build/runtime/configuration, data shape, limits, generator placement/model and time windows. Repeat a before/after trial with equivalent conditions and check correctness plus total resource cost. A single noisy run is weak evidence of a small win.

Report actual delivered load, successful business completions, latency/error outcomes and environment gaps. If the result is inconclusive because the generator saturated or a dependency mock was unrealistically fast, say so and fix the experiment. Use Stress Testing for deliberate beyond-capacity and recovery questions rather than quietly changing the objective mid-report.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

The slow service appears to receive less load

Symptom: Latency looks acceptable while throughput quietly drops.

Root Cause: A closed workload or generator limit reduces offered starts during slowdown.

Fix/Prevention: Report intended and actual arrivals and use the model that matches external demand.

Averages hide a broken export path

Symptom: Overall latency passes while one operation class times out.

Root Cause: Fast high-volume requests dominate a pooled statistic.

Fix/Prevention: Define per-operation objectives and inspect tails/errors with appropriate sample sizes.

The benchmark is all cache hits

Symptom: A change looks excellent until a new tenant or cold start.

Root Cause: Data/state preparation omits costly representative cases.

Fix/Prevention: Control cache/data conditions and disclose the workload mix and limits.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Rehearse a defined workload, prove it was delivered, count correct useful outcomes and compare equivalent conditions before claiming capacity or improvement. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Why is a user count insufficient as a workload description?

Operation mix, arrival pacing, duration, data, dependencies and state determine demand; users alone do not specify them.

What feedback distinguishes closed from open scheduling?

Closed iterations wait for prior work in their population; open starts are scheduled independently, subject to generator capacity.

What must accompany a pass at a target rate?

Evidence that the generator delivered the intended workload, with dropped starts, retries and failures accounted for.

Why split latency by operation and stage?

A mixed or whole-run statistic can hide a slow critical path or an overloaded peak behind many fast samples.

Tricky & Most-Asked Interview Scenarios

The service slows down but the fixed-user test reports fewer errors. Is capacity proven?

The Scenario & Constraint

A fixed set of virtual users waits for each response before sending another. Response time rises and arrivals fall. What will you do for a product with an external fixed arrival stream?

The Direct Answer & Architectural Decision

Use an arrival-rate schedule matching that external stream, budget generator slots for the expected occupancy and variation, and report delivered/dropped starts alongside latency/errors. Keep the closed result only as evidence for its actual population-feedback model.

Key Trade-Offs & Follow-Up Traps

Open scheduling can overwhelm the generator if not provisioned; a failed generator is not a service capacity verdict. If the real workload is genuinely closed, retain that model and explain its feedback instead of calling it inherently wrong.

All HTTP requests return 200, yet some orders are missing. Is the test green?

The Scenario & Constraint

The endpoint embeds validation failures in response bodies and a subset of writes are duplicate/rejected effects. What acceptance criteria will you add?

The Direct Answer & Architectural Decision

Validate the business outcome and operation identity, expected response content and required downstream state. Separate attempted requests, transport successes and useful completed transactions. Define pass/fail thresholds for the actual user contract, not only status codes.

Key Trade-Offs & Follow-Up Traps

End-to-end validation costs test resources and may require cleanup/idempotent setup. Sampling every effect may miss rare defects; state coverage. A lower latency for rejected or invalid work is not equivalent to processing the intended order workload.

The target handles 300 requests/s although you configured 1,000. Who is saturated?

The Scenario & Constraint

Generator CPU is high and scheduled iterations are dropped, while server resources look calm. What conclusion and next action fit?

The Direct Answer & Architectural Decision

Treat the target-rate claim as inconclusive. Profile/budget the generator, reduce local test overhead or use appropriately isolated generator capacity, then verify actual arrivals and latency from the intended client boundary. Keep the failed delivery counts in the report.

Key Trade-Offs & Follow-Up Traps

Adding generators can shift the problem to network limits or synchronized bursts. Do not simply raise configured rate and assume it became real demand. A low target latency at 300/s cannot establish behavior at 1,000/s.

A benchmark hits one cached order and predicts every tenant will meet p99. What changes?

The Scenario & Constraint

Production includes large tenants, cold records and updates, but the test repeatedly reads one small object. What workload will you build?

The Direct Answer & Architectural Decision

Use representative tenant/key distributions, payload/fan-out sizes, state preparation and read/write mix, with separately identified warm/cold cases. Compare the critical operation classes and their error/tail outcomes under the intended peak.

Key Trade-Offs & Follow-Up Traps

A controlled hot-key test is useful for a narrow cache path but cannot support a catalog-wide claim. Fully random keys may mostly generate misses/errors unlike real demand. Record data limitations rather than inventing realism from a larger key count.

Two instances each report p95. Can you average them to approve the rollout?

The Scenario & Constraint

One instance serves far more requests and the latency distributions differ. What test evidence will you aggregate?

The Direct Answer & Architectural Decision

Collect compatible distributions or raw observations with counts and compute the relevant combined quantile using the backend’s supported aggregation. Also inspect per-instance and operation cohorts to find an imbalance. Compare the same stage/window.

Key Trade-Offs & Follow-Up Traps

Averaging quantiles does not produce the population quantile. Histogram resolution and sample count limit precision; a tiny canary’s p99 can be unstable. Preserve error/rejected-work counts so shedding does not make success-only latency misleading.

A new query is 3% faster in one run with a different dataset. Ship the capacity claim?

The Scenario & Constraint

The runs use different tenant sizes and cache states, and variation is comparable to the reported gain. What experiment and report will you produce?

The Direct Answer & Architectural Decision

Repeat equivalent before/after workloads with recorded data/configuration, resource limits and generator behavior. Check correctness and relevant resource costs alongside latency/throughput. Report variability and withhold a strong capacity conclusion until the effect is distinguishable from changed conditions.

Key Trade-Offs & Follow-Up Traps

Perfect production fidelity may be costly; explicitly bounded evidence is still useful. A microbenchmark can explain one mechanism without proving endpoint capacity. Do not turn an uncertain small difference into an unsupported universal percentage.
