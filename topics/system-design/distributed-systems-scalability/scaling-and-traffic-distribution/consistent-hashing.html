Consistent Hashing

🎯 The Hook & ELI5

A library assigns books to shelves using a circular map. When a new shelf is added, it takes a nearby stretch of books instead of forcing every book onto a different shelf. The map reduces disruption, but it does not make a single bestselling book stop attracting a crowd.

Consistent hashing maps keys and ownership tokens into a stable hash space. In a basic ring, a key belongs to the first token encountered clockwise, wrapping at the end. Adding or removing tokens changes particular ownership intervals rather than recomputing every owner with a new modulo divisor.

Use a rebuildable cache as the first example, then ask what changes for authoritative data. Reassigning a cached key can mean a miss and refill; reassigning the only authoritative copy requires an explicit data migration and recovery protocol. The word consistent describes stability of placement under membership change, not strong consistency of reads.

🗺️ High-Level Big Picture

Numbers are positions on a fixed illustrative ring, not current server-count remainders. Inserting token 60 splits the interval formerly owned by token 80.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the actual actor, communication, acknowledgment and recovery boundary.

1. Separate hashing from membership

Choose a deterministic key encoding, hash function and fixed token space, and make every router use the same specification. With tokens 10, 40 and 80 on a circular space, key position 55 goes to token 80 and position 95 wraps to token 10. The tokens identify owners; they are not data versions.

A modulo mapping such as hash(key) % server_count changes its divisor when membership changes. Many keys can then change owner. A ring preserves token positions and changes the intervals next to the edited tokens. Other algorithms, including rendezvous hashing or fixed partition tables, solve related placement problems differently.

2. Work the insertion by hand

Insert token 60. Positions greater than 40 and at most 60 now belong to 60; positions greater than 60 and at most 80 still belong to 80. Keys outside the split interval keep their old owners. Removing a token gives its interval to the next surviving owner under the basic successor rule.

This is a deterministic consequence of this particular map. An expected moved fraction around one equal-capacity node’s share requires distribution assumptions and enough representative keys/tokens. A tiny hand-picked ring need not have equal arcs or equal load; never present an expectation as a bound for every workload.

3. Use virtual nodes for finer assignment

One physical server can own many token positions. This gives the placement controller more, smaller intervals to distribute or move, and can smooth imbalance from a few large random arcs. More tokens require larger routing metadata and more migration bookkeeping; choose using measured bytes, keys and traffic.

For unequal machines, assign capacity-aware token ownership or use a supported weighted design. Count distinct physical owners when choosing replicas: several adjacent virtual tokens can belong to one server. A replicated item must not accidentally have every copy in one physical failure domain.

4. Version and distribute the map

Clients, proxies or a coordinator can compute ownership, but they need a consistent encoding and an explicit membership epoch. During rollout, one router may use the old map and another the new map. Define forwarding, rejection or dual-location lookup behavior, and bound redirects rather than forming a routing loop.

Publishing a map is not a data movement transaction. For cache data, permit controlled misses and protect the origin. For durable data, copy an interval, handle concurrent updates, verify ownership handoff and retire the old copy only after the migration protocol permits it.

5. Treat hot keys and replication separately

Uniform key hashes do not imply uniform request rates or value sizes. A single very popular key still maps to one primary owner in the basic scheme. Measure per-key and per-owner bytes, QPS and latency before increasing the number of virtual tokens.

Replication, read distribution, per-key coalescing, admission or application-level splitting may help, each with freshness/coordination costs. Write-heavy hot objects may need a different data model. The Dynamo paper is a historical example combining ring placement with independent replication, versioning and repair mechanisms; it is not a claim about current DynamoDB routing.

6. Test changes and failure load

Use a stable sample of representative keys and compare owner maps before insertion, removal and unequal-capacity changes. Count moved keys and bytes, then replay the actual request distribution. Validate that an unaffected interval really remains unaffected.

Throttle copy/refill work so membership repair does not overwhelm healthy owners or the authoritative origin. Test a failed server rejoining with stale state. Observability should include map epoch adoption, migration backlog, error/redirect rate, hot-key load and capacity after losing a failure domain. A beautiful ring drawing is not a recovery test.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

A hot key survives every rebalance

Symptom: One owner saturates despite many virtual nodes.

Root Cause: Traffic skew was confused with uneven hash-space arcs.

Fix/Prevention: Measure keys and apply a hot-object strategy with explicit read/write semantics.

Replicas share one machine

Symptom: Several selected tokens disappear together.

Root Cause: Virtual owners were counted as physical failure domains.

Fix/Prevention: Select distinct physical/domain owners under the replication policy.

New map loses durable writes

Symptom: Clients route to a new empty owner before copy completes.

Root Cause: Metadata publication was treated as safe data migration.

Fix/Prevention: Use a versioned handoff protocol with concurrent-write handling and recovery.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Stable placement reduces membership disruption; safe migration, useful load balance, replication and current reads still need separate mechanisms. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Does consistent hashing guarantee current reads?

No. It chooses owners; replication and operation ordering need their own consistency protocol.

Which interval moves when token 60 enters between 40 and 80?

Under clockwise successor ownership, positions greater than 40 through 60 move from 80 to 60.

Why assign several tokens to one physical node?

To manage ownership in smaller pieces and improve placement balance under suitable distributions.

Why distinguish cache and authoritative storage?

A cache can sometimes refill a missing copy; authoritative ownership cannot discard the only valid data during remapping.

Tricky & Most-Asked Interview Scenarios

Adding a cache node overloads the database. What do you change?

The Scenario & Constraint

The new owner begins empty and hot requests refill moved keys simultaneously. What will you do and why?

The Direct Answer & Architectural Decision

Measure moved hot-key demand, pace ownership rollout or prewarm safe data, coalesce concurrent fills and bound origin admission. Keep the fixed map/epoch protocol explicit.

Key Trade-Offs & Follow-Up Traps

Prewarming consumes bandwidth and can copy soon-obsolete values. Lazy refill is simpler for cold keys; neither choice is safe without an origin budget under a cold fleet.

One key receives half the requests. Add more virtual nodes?

The Scenario & Constraint

All reads target the key’s primary owner even though aggregate capacity is spare. What will you do and why?

The Direct Answer & Architectural Decision

Treat it as a hot-object problem: use permitted read replicas/local copies or split the application aggregate where semantics allow, and bound refresh/write work. Measure freshness and update cost.

Key Trade-Offs & Follow-Up Traps

Virtual tokens move ownership pieces but do not divide one key’s request stream. If strong writes dominate, replicas cannot independently accept arbitrary conflicting updates without another contract.

A small server and a large server receive similar bytes. What changes?

The Scenario & Constraint

The small server repeatedly evicts useful data and its capacity is one quarter of the larger server. What will you do and why?

The Direct Answer & Architectural Decision

Use supported capacity-aware token ownership/weights, plan a throttled rebalance and verify byte as well as key distribution against the working set.

Key Trade-Offs & Follow-Up Traps

More tokens add metadata and do not guarantee byte balance for giant values. A controller-managed fixed partition table is an alternative if explicit ownership adjustment is easier to operate.

Two routers disagree about an owner during migration. What is safe?

The Scenario & Constraint

Writes are authoritative and one client has not received the new membership epoch. What will you do and why?

The Direct Answer & Architectural Decision

Use an ownership-epoch/handoff protocol that rejects or safely forwards obsolete-owner writes, copies concurrent changes and bounds rerouting. Keep the old copy until the defined cutover is recoverable.

Key Trade-Offs & Follow-Up Traps

Extra coordination adds latency and temporary duplicate storage. For a rebuildable cache a weaker dual-lookup/refill plan may suffice; authoritative writes require a stronger migration contract.

Three replica tokens reside on one host. Is replication complete?

The Scenario & Constraint

A host failure removes all copies selected by consecutive ring tokens. What will you do and why?

The Direct Answer & Architectural Decision

Select replicas on distinct physical hosts and required racks/zones, accounting for virtual-token ownership, and verify available targets before acknowledging the promised redundancy.

Key Trade-Offs & Follow-Up Traps

Topology constraints can reduce balancing flexibility. If too few independent domains exist, report the reduced guarantee rather than counting virtual positions as separate failures.

A workload needs ordered key ranges. Is a ring the right default?

The Scenario & Constraint

Queries scan adjacent customer IDs while the proposed hash destroys that locality. What will you do and why?

The Direct Answer & Architectural Decision

Compare range partitioning or a suitable ordered secondary access path against point-lookup hashing, including hot ranges, split/merge operations and cross-partition query cost.

Key Trade-Offs & Follow-Up Traps

Ranges preserve locality but may concentrate sequential inserts or busy tenants. If point access becomes dominant, hash placement can regain its advantage; choose from query behavior, not a universal algorithm ranking.
