Load Balancing

🎯 The Hook & ELI5

A host seats arriving groups among restaurant rooms. Sending every group to the next room in turn is simple, but one room may already contain a slow banquet. A good host needs the right measure of work, knows which rooms can accept diners, and stops seating a room before it closes.

A load balancer chooses a target for traffic. The useful unit may be a connection, an HTTP request or another protocol-specific exchange. The choice determines what can actually be balanced: an established long-running connection cannot generally be redistributed by changing the rule for new connections.

Use a reporting API with short status requests and expensive exports as the running example. An equal request count is not necessarily equal CPU, memory or concurrency. Separate selecting a target from discovering targets, enforcing API policy, and adding target capacity. A balancer needs its own capacity and failure plan.

🗺️ High-Level Big Picture

Discovery supplies candidates and health/draining determines eligibility. The selection algorithm then assigns only new work within a bounded resource policy.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the actual actor, communication, acknowledgment and recovery boundary.

1. Choose the protocol boundary

Layer 4 balancing uses transport-level information and commonly assigns a TCP connection. Layer 7 understands an application protocol and can choose based on supported request properties. Decide where TLS terminates and which component can see a path or authenticated identity. Encrypted payload cannot be inspected by a component that does not terminate/decrypt it.

For the reporting API, path-aware routing can isolate exports from quick reads, while an L4 decision cannot infer HTTP path cost. Neither layer is universally faster or safer: protocol support, connection reuse, encryption, observability and operational requirements decide the fit.

2. Pick a signal that approximates actual work

Round-robin distributes selections; weights adjust a target’s intended share. Least connections uses active connection count as a proxy for load. Neither measures every job’s true cost. One persistent HTTP connection may carry many requests, and one export may consume far more resources than many status checks.

Measure per-target in-flight work, queue age, latency and rejection rate. Separate expensive classes where a common algorithm cannot approximate demand. NGINX documentation provides concrete round-robin, least-connected, weighted and IP-hash examples; verify edition/version for additional controls rather than assuming every named feature is available.

3. Discover targets and test readiness

A target list can come from configuration or a discovery control plane. Make freshness, removal and rollout behavior explicit: different balancers may temporarily have different lists. A successful TCP connection proves less than a request that exercises the required serving path.

Use readiness that reflects whether the instance should accept new work, with bounded probe cost and suitable success/failure thresholds. Passive failure observation and active probes are different mechanisms. Do not remove every backend because an optional dependency is degraded; an overbroad health rule can turn partial degradation into a total outage.

4. Handle locality and state honestly

Affinity deliberately sends related traffic to the same target to preserve locality or a protocol/session constraint. It can concentrate busy users and complicate failover. Distinguish an existing WebSocket connection, which is inherently attached to one server for its lifetime, from a separate requirement that reconnections find recoverable session state.

For the reporting API, use durable export identity and shared status so a different target can serve a retry or poll. If local caches justify affinity, describe the performance benefit and the fallback when the target disappears. A balancing hash is not a durable storage replication policy.

5. Drain, fail and retry within bounds

Before removing a backend, stop assigning new work, allow a bounded grace period for existing work, and define cancellation/reconnection after the deadline. Draining behavior depends on the actual protocol and platform. Removing a target from selection does not automatically terminate, migrate or finish its established work.

A timeout leaves an unknown outcome for a side-effecting request. Transparent retries need an explicit safe-operation policy and total deadline. Bound backend concurrency and queueing so failover does not simply move all excess load to the remaining servers. Maintain reduced-capacity headroom or an intentional rejection policy.

6. Make the balancer itself observable and resilient

Avoid introducing a single unprotected process whose failure disconnects the entire fleet. Use a supported redundant topology and understand how clients discover/reach it. A redundant control plane is not useful if every data path still depends on one exhausted socket table or shared network link.

Observe target selection counts together with actual completed work, active connections, errors, health transitions and drain duration. Test a target crash, a bad rollout and an unhealthy dependency. Interpret skew against weights, affinity, connection lifetime and request cost before blaming the random number generator.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Healthy port, broken service

Symptom: Traffic continues to a process unable to serve reports.

Root Cause: The probe only checks that the TCP port opens.

Fix/Prevention: Choose a bounded readiness signal aligned with required serving behavior.

Every server unhealthy together

Symptom: An optional analytics outage removes the whole API fleet.

Root Cause: Health checks fail on a noncritical dependency.

Fix/Prevention: Separate required readiness from optional degraded features.

Shutdown interrupts accepted jobs

Symptom: A rollout kills exports after target removal.

Root Cause: Selection removal was confused with graceful completion.

Fix/Prevention: Drain with a deadline and durable job/reconnection semantics.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Choose the unit, eligibility signal and workload proxy first, then design bounded admission, draining and recovery around the actual protocol. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Why name the balancing unit?

New connections and new requests are different decisions; established work may not move.

What does a successful health probe establish?

Only the behavior and conditions actually exercised by that probe, not universal service correctness.

What does affinity trade away?

Some distribution/failover flexibility in exchange for locality or a scoped session requirement.

Does removing a target finish its current work?

No. Existing connections/jobs need a separate bounded drain, cancellation or recovery policy.

Tricky & Most-Asked Interview Scenarios

Round-robin leaves one backend overloaded. What do you inspect?

The Scenario & Constraint

A few persistent connections carry most reports while connection counts are balanced. What will you do and why?

The Direct Answer & Architectural Decision

Inspect per-connection request/work volume and determine whether selection is per connection or per request. For HTTP workloads consider supported request-aware routing or isolate expensive exports, with bounded target concurrency.

Key Trade-Offs & Follow-Up Traps

Rebalancing new connections may help slowly but cannot instantly move existing protocol state. Least connections is another proxy, not a guarantee of equal CPU. If exports become independent jobs, route them through a separate worker policy.

Health probes succeed while users receive database errors. What changes?

The Scenario & Constraint

The probe hits a static endpoint; reports require a database connection. What will you do and why?

The Direct Answer & Architectural Decision

Add a bounded readiness criterion for critical serving dependencies and inspect resource exhaustion, while retaining separate liveness checks. Use thresholds to avoid flapping and test behavior when only some targets fail.

Key Trade-Offs & Follow-Up Traps

Deep probes add load and can remove the entire fleet if a shared dependency fails. If a report can be served in a documented degraded mode, readiness should reflect that rather than demanding optional functionality.

A deployment drops long-running exports. How do you release safely?

The Scenario & Constraint

Exports last minutes, but the orchestrator terminates a backend seconds after removal. What will you do and why?

The Direct Answer & Architectural Decision

Stop new assignments, align drain and termination deadlines, and persist job progress/output identity so clients can reconnect or recover. Define what happens to jobs exceeding the grace period.

Key Trade-Offs & Follow-Up Traps

Long draining slows rollout and retains capacity. Durable asynchronous jobs can decouple client connections, but add a job lifecycle. If the deadline is fixed, cancellations and partial-output handling must be explicit.

A failed sticky backend logs out its users. What do you fix?

The Scenario & Constraint

Session data exists only in that backend memory. Restoring service matters more than cache locality. What will you do and why?

The Direct Answer & Architectural Decision

Move required session state to a supported shared/reconstructible contract and make backend replacement recover it. Reevaluate whether affinity is needed once correctness no longer depends on local memory.

Key Trade-Offs & Follow-Up Traps

Shared state adds a dependency and latency. Keeping affinity may be a performance choice, but it cannot recover the failed machine’s only copy; a different availability requirement could permit session loss.

May the balancer retry a timed-out payment POST?

The Scenario & Constraint

The first backend might have completed a charge before the connection broke. What will you do and why?

The Direct Answer & Architectural Decision

Do not blanket-retry an uncertain side effect. Require a documented idempotency identity/status-reconciliation mechanism or return an honest pending/error outcome; enforce one total retry/deadline policy.

Key Trade-Offs & Follow-Up Traps

Fewer transparent retries expose uncertainty to callers but avoid accidental duplicate effects. Read-only operations may permit a different policy; a method name alone does not prove the endpoint has safe semantics.

One of three backends fails and the other two collapse. What now?

The Scenario & Constraint

The normal fleet ran near maximum sustainable concurrency. Traffic is now reassigned to survivors. What will you do and why?

The Direct Answer & Architectural Decision

Shed/degrade optional work, cap in-flight requests and scale only within dependency budgets. Establish capacity headroom or a reduced-service objective for one-backend loss and test that state explicitly.

Key Trade-Offs & Follow-Up Traps

Reserve capacity costs money and rejections affect users. A new selection algorithm cannot create missing compute; if workloads can queue, bounded delay may replace some immediate rejection.
