Horizontal vs Vertical Scaling

🎯 The Hook & ELI5

A bakery has one oven and a queue outside. Buying a larger oven is scaling up; opening another kitchen is scaling out. Neither helps if every baker must wait for the same person to approve each order. First find what people are waiting for, then add capacity where it changes that wait.

Horizontal scaling adds instances; vertical scaling changes the resources of an instance. Both can be useful in one design. The decision includes the work distribution, state, failure domain and time needed before new capacity becomes usable. It is not a contest between modern and old-fashioned architecture.

Imagine a receipt service with CPU-heavy rendering and a shared database. At the target request rate, rendering occupies the workers while the database has headroom. Splitting independent render jobs can help. If instead every receipt waits on one contended account row, another renderer can increase the queue without increasing completions. Numbers in this lesson are illustrative workload assumptions, not cloud benchmarks.

🗺️ High-Level Big Picture

Follow the request to its scarce resource. Adding workers is a candidate intervention, not evidence that the shared dependency can absorb their work.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the actual actor, communication, acknowledgment and recovery boundary.

1. Measure demand and the scarce resource

Define a useful unit: completed receipts per second within an end-to-end latency objective. Record arrival rate, queue depth, CPU, memory, I/O, lock waits and dependency latency at the same time. High CPU is informative only if it belongs to the work limiting completions. A rising queue with idle CPU may indicate a blocked dependency.

Compare before/after under the same request mix, including large receipts and slow customers. Separate service time from time waiting for admission. An improvement that raises average throughput but makes tail latency unacceptable has not met the original objective.

2. Consider a larger execution unit

A larger machine can reduce immediate memory pressure or allow more CPU work without distributing state. It is often the smallest operational change for an existing process. Verify whether the runtime, license, storage and algorithm actually use the additional resources; a single serial section does not become parallel because more cores exist.

There is a maximum available shape and a failure-domain cost: losing the large instance removes more capacity at once. Resizing may involve replacement or interruption depending on the platform. Plan a rollback and measure warmup rather than assuming every vertical change is live.

3. Make independent work distributable

To scale rendering out, put enough information in the job to let any eligible worker render it. Store durable job identity and completion outside an individual worker. Assign work through a bounded dispatcher or queue and handle a worker disappearing after producing output but before reporting success.

Request state, uploaded files and session ownership must have an explicit location. Externalizing state can enable interchangeable workers, but the shared state store now needs its own capacity and failure plan. Partitioning authoritative state is a separate design decision, not an automatic side effect of more instances.

4. Price the serial fraction and downstream fan-out

Suppose a hypothetical operation spends 80% of its time in independently parallelizable work and 20% in unavoidable serialized work. Under ideal assumptions the speedup with n workers is 1 / (0.2 + 0.8/n), so even infinitely many workers cannot exceed fivefold speedup. Real communication and contention can make the result worse.

Also count connections: twenty instances opening fifty database connections each request a thousand slots. Bound fleet-wide concurrency and connection demand. Scaling an upstream tier must respect the downstream sustainable rate, including maintenance and failure conditions.

5. Handle elastic capacity as delayed control

A newly requested worker is not immediately useful. Provisioning, process startup, cache warming and target registration all consume time. Choose a scaling signal that anticipates saturation, such as sustained queue age combined with utilization, and cap its range against downstream budgets.

Use hysteresis/cooldowns and a minimum safe capacity rather than making opposite decisions on every short spike. Drain work before scale-in. A queue can absorb a finite burst only if its age, storage and completion deadline remain acceptable; it cannot cure permanent overload.

6. Prove capacity and failure behavior

Load-test the representative mix at steady load, a burst, and one-instance loss. Compare useful completions, percentile latency, error/rejection rate, queue age and cost per useful job. Test a cold start as well as a warm fleet. Document the resource that limits the next growth step.

Roll out gradually with rollback thresholds. Compare scale-up, scale-out and reducing work per request under the same objective. Cloud prices, instance ratios and platform limits change, so use measured contemporary inputs for a real purchase rather than treating an illustrative calculation as a universal recommendation.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

More app instances, fewer completions

Symptom: Database timeouts rise after autoscaling.

Root Cause: Each instance independently grows its connection/work pool.

Fix/Prevention: Set a fleet-aware dependency budget and retest at the maximum instance count.

Scale-in loses work

Symptom: Receipts disappear during a quiet period.

Root Cause: The worker owns the only copy of an accepted job.

Fix/Prevention: Durably register jobs, drain workers and make redelivery duplicate-safe.

Average load hides saturation

Symptom: The service looks idle while one customer waits minutes.

Root Cause: A hot owner or skewed job size is hidden by fleet averages.

Fix/Prevention: Measure per-partition queue age and isolate/repartition the hot work.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Find the scarce resource, choose the smallest effective capacity change, and prove useful throughput, state recovery and downstream safety before scaling the fleet. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

What changes between scaling up and out?

Up changes capacity inside an execution unit; out adds units and requires a way to distribute work and state.

Why might adding workers stop helping?

A serial dependency or saturated shared resource limits completions; more contenders can increase waiting.

Why is a utilization threshold alone insufficient?

Capacity arrives after provisioning and warmup, and different bottlenecks can produce the same utilization signal.

What proves a scaling change helped?

Useful completions and latency meet the objective under representative load and failures, within an explicit cost and dependency budget.

Tricky & Most-Asked Interview Scenarios

CPU is low but database waits dominate. Add ten instances?

The Scenario & Constraint

The API misses its latency objective and lock-wait time is rising. Database rows are shared across callers. What will you do and why?

The Direct Answer & Architectural Decision

Inspect the blocked transactions and ownership/access pattern first, bound admitted concurrency, and reduce the specific contention or expensive access path. Add app instances only after evidence shows app capacity limits useful completions.

Key Trade-Offs & Follow-Up Traps

Admission may reject or defer work, but uncontrolled extra callers worsen the same bottleneck. A larger database can help resource pressure; it does not remove a logically serialized hot-row invariant.

One renderer exceeds the instance memory limit. Scale out?

The Scenario & Constraint

A single legitimate job needs more memory than one worker has; splitting it is not currently supported. What will you do and why?

The Direct Answer & Architectural Decision

Choose an instance size that safely fits the measured peak working set, limit simultaneous large jobs and profile opportunities to stream the input. Keep enough spare capacity for worker loss.

Key Trade-Offs & Follow-Up Traps

Larger units cost more and still have finite limits; more small workers cannot jointly hold one unsplittable job. If streaming becomes feasible, reevaluate smaller independent workers.

A second application instance breaks signed-in sessions. What changes?

The Scenario & Constraint

Sessions and temporary uploads exist only on the first process disk. Requests now alternate between instances. What will you do and why?

The Direct Answer & Architectural Decision

Give sessions and required uploads an explicitly shared/durable home with access and expiry rules, then make requests independent of a particular process. Use affinity only as a scoped transition with documented failure behavior.

Key Trade-Offs & Follow-Up Traps

Shared storage adds latency and another dependency. Affinity can preserve locality but loses state on failure unless another recovery mechanism exists. If sessions are reconstructible tokens, the state contract may be simpler.

Demand triples in seconds but workers take minutes to start. What now?

The Scenario & Constraint

The response deadline cannot tolerate the full startup delay and traffic bursts recur predictably. What will you do and why?

The Direct Answer & Architectural Decision

Keep measured headroom or pre-scale before the known burst, use bounded admission/queues for permissible delay, and shed optional work when capacity is exhausted. Measure cold-start registration and warmup.

Key Trade-Offs & Follow-Up Traps

Idle reserve costs money; a queue trades response time for absorption and must have a deadline. If demand becomes sustained, add permanent capacity rather than repeatedly extending the queue.

Autoscaling exhausts the database connection limit. What will you change?

The Scenario & Constraint

Every replica opens a fifty-connection pool and the fleet can grow to twenty replicas. Existing database clients also need slots. What will you do and why?

The Direct Answer & Architectural Decision

Allocate a dependency concurrency/connection budget across the maximum fleet, use smaller bounded pools and admission, and verify whether a supported pooler fits the transaction/session requirements.

Key Trade-Offs & Follow-Up Traps

Small pools can increase local waiting. A pooler changes connection reuse, not the database work capacity; session-specific features may constrain pooling mode. Revise the budget when other clients or failover topology change.

A larger machine halves latency. Is it the best scaling choice?

The Scenario & Constraint

The workload meets its objective on either two smaller instances or one larger instance. Current measured cost differs and one-instance loss must be tolerated. What will you do and why?

The Direct Answer & Architectural Decision

Compare equal failure capacity, tail latency, operational complexity and current prices under the real request mix. Include spare capacity or replacement time in both options and choose the lowest-risk option that meets the objective.

Key Trade-Offs & Follow-Up Traps

A single large machine may win steady-state cost but fail the outage requirement without redundancy. If that requirement is relaxed or work is restartable batch processing, the preferred option may change.
