CI/CD Pipelines

🎯 The Hook & ELI5

A school kitchen tests a recipe, labels the batch it actually cooked and sends that same batch to the serving counter. Testing one cake and secretly baking a different cake for the children breaks the chain of trust. A delivery pipeline is a visible chain of preparation, checks and handoffs, with somebody responsible when a handoff fails.

Continuous integration combines changes frequently and checks whether they work together. Continuous delivery keeps a verified change ready for release; continuous deployment automates release when the defined conditions pass. These names describe different boundaries, not a promise that every green test should immediately reach every customer.

Our example promotes an orders-service artifact from a reviewed commit through testing and controlled production exposure. GitHub Actions supplies concrete artifact/environment/security references; the process is conceptual and does not install or modify a real workflow. Every illustrative release label and outcome below is invented for teaching.

🗺️ High-Level Big Picture

Each arrow transfers a known artifact or decision, not just a green badge. Deployment completion and successful user exposure are different facts; irreversible state changes require their own recovery plan.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace ownership, state transitions, decision evidence and the failure/recovery boundary.

1. Define the release unit and its owner

Choose what is released together: application image/binary, configuration reference and any compatible schema transition. Record the source commit, dependency/toolchain identities, artifact digest and expected environment contract. Separate the person or service authorizing production exposure from the system merely running a build.

A successful unit test from commit A does not approve artifact B. If configuration is intentionally environment-specific, version and validate it separately rather than pretending every runtime input is identical. Make the linkage auditable without embedding production secrets in the artifact.

2. Build once and make inputs explainable

Build in a controlled environment and retain the produced artifact for later stages. Lock or otherwise identify dependencies and toolchains according to their actual ecosystems, and verify where third-party workflow components came from. A movable tag or a warm dependency cache alone does not establish reproducibility.

GitHub workflow artifacts preserve produced outputs across jobs; dependency caches accelerate regeneration and have a different purpose. Keep cache misses correct and treat cache contents from less-trusted contexts appropriately. Artifact retention must cover the intended investigation/recovery window, not expire before a release needs it.

3. Attach checks to the object you will promote

Run the meaningful unit, integration, contract and security checks for this change against the selected artifact/configuration combination. A gate should expose its evidence and failure meaning, not merely return green. Verify data/API compatibility for mixed-version and recovery paths as part of the release design.

Use a fast deterministic check before a costly environment rehearsal when that answers a real question. Flaky checks need diagnosis and bounded explicit policy; automatically retrying until success can erase a genuine intermittent defect. Do not multiply tests that only repeat implementation details without exercising a requirement.

4. Separate untrusted preparation from deployment authority

Pull-request code, build scripts and third-party actions execute code. Give them only the credentials/resources their trust level requires. A later privileged job must not blindly execute an untrusted artifact or metadata as code. Check action/workflow dependency identities using the provider’s currently supported mechanisms.

GitHub deployment environments can gate a job and scope access to environment secrets. Exact capabilities depend on the repository/provider configuration. Use narrowly scoped short-lived workload credentials where supported, and keep logs/artifacts free of secret values. A gate is useful only if another path cannot bypass it.

5. Serialize conflicting promotion and distinguish partial effects

Suppose two releases target one environment: the newer one completes first, then a slow older job overwrites it. Define deployment concurrency, cancellation and supersession rules around the environment and artifact identity. Cancelling the old job does not necessarily undo work it already started.

Treat deployment steps as owned state transitions, with recorded completion/outcome and a recovery action for each. An application version change, schema migration and external provisioning call are not one atomic transaction just because they appear in one pipeline diagram.

6. Observe exposure and retain a truthful recovery path

After the platform reports deployment success, verify user-facing correctness, latency/errors and the intended cohort before expanding exposure. Use a blue-green, canary or rolling strategy according to the risk/capacity/compatibility contract. Record whether a failed step changed persistent state or left its outcome unknown.

Retain the prior artifact and compatible configuration, but do not promise that redeploying them restores deleted data or reverses external effects. Rehearse recovery under the actual schema contract and keep evidence tied to release identity. The pipeline is complete when its operational promises are verified, not when the last shell command exits zero.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Staging passes but production runs a different build

Symptom: The release differs from the object exercised by tests.

Root Cause: A later stage rebuilt from movable inputs or selected another artifact.

Fix/Prevention: Promote a recorded artifact identity and validate intended configuration differences.

A build log leaks production credentials

Symptom: A routine change obtains secrets it never needed.

Root Cause: Untrusted code or dependencies run with broad deployment authority.

Fix/Prevention: Separate trust domains, scope credentials and validate provider/environment protections.

A cancelled job still changes production

Symptom: The interface says cancelled but a deployment or migration completed.

Root Cause: Cancellation was mistaken for transactional rollback.

Fix/Prevention: Record operation outcomes, serialize conflicting changes and reconcile partial effects.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Keep a verified artifact and its authority chain visible, make gates meaningful, coordinate environment ownership and judge exposure and recovery beyond job completion. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

How do CI, continuous delivery and continuous deployment differ?

CI checks integrated changes; delivery keeps a verified release ready; deployment automates release under defined passing conditions.

Why is a dependency cache not a release artifact?

It speeds regeneration and may be absent or differ; the artifact is the identified output being tested and promoted.

Why inspect a handoff from an untrusted build to a privileged job?

The artifact or metadata can contain executable content; a later job must not grant it deployment authority merely because it came from another stage.

Does a successful deployment establish a successful release?

No. Correct exposure and user outcomes, plus compatibility/recovery behavior, require separate evidence.

Tricky & Most-Asked Interview Scenarios

Staging passes, but production rebuilt a dependency differently. What will you change?

The Scenario & Constraint

Two stages rebuild the same source commit using movable dependencies. The resulting images differ and production fails. What will you do and why?

The Direct Answer & Architectural Decision

Build and identify the release artifact once, test that object and promote it through environments with separately versioned validated configuration. Record dependency/toolchain provenance and compare actual deployed identity during verification.

Key Trade-Offs & Follow-Up Traps

A genuine environment-specific build needs its own identity and checks. Keeping every artifact costs storage and retention planning. A commit SHA alone does not identify all build inputs, and a cache hit is not proof that output is the tested release.

A contribution workflow needs tests, but the proposed job exposes deployment secrets. What boundary fits?

The Scenario & Constraint

An external change can edit build/test code. A reusable workflow currently runs it with production credentials. What will you do?

The Direct Answer & Architectural Decision

Run untrusted preparation with minimal permissions and isolate deployment authority behind validated trusted inputs and environment policy. Review workflow/action dependencies and privileged artifact consumption, then use scoped workload credentials where supported. Test that alternate triggers cannot bypass the boundary.

Key Trade-Offs & Follow-Up Traps

A manual approval does not sanitize malicious code a privileged job later executes. Stronger runner isolation costs resources; broad long-lived secrets increase compromise scope. Keep provider-specific trigger and policy behavior explicit rather than assuming all pull-request events have the same trust model.

A slow older release overwrites a newer one. Which state should own promotion?

The Scenario & Constraint

Release B becomes healthy before release A finishes. A later switches the same environment back to its older version. What will you coordinate?

The Direct Answer & Architectural Decision

Serialize or supersede promotions for the target environment using release/artifact identity and recorded current state. Verify what a cancelled in-flight deployment actually did before allowing another transition, and observe the final serving version rather than only job order.

Key Trade-Offs & Follow-Up Traps

Global serialization can unnecessarily block independent environments. Cancelling a job does not roll back remote effects. If concurrent schema changes share a database, application-job isolation alone does not remove that common state dependency.

An integration test passes after the fifth retry. Should promotion proceed automatically?

The Scenario & Constraint

The test intermittently detects incorrect order totals. Retrying until green masks its failure rate. What policy and investigation will you use?

The Direct Answer & Architectural Decision

Treat the failure as evidence: preserve inputs/artifact/logs, distinguish test-environment instability from a real race, and block or use an explicitly justified bounded exception process rather than silent retry-until-green. Reproduce the suspected concurrency path and define the gate’s decision meaning.

Key Trade-Offs & Follow-Up Traps

Quarantining a known flaky test can unblock work only with visibility and replacement coverage for its risk. More retries may reduce visible failures without improving correctness. A green pipeline does not compensate for unresolved evidence of an actual business invariant defect.

A fast cached build contains unexpected executable output. What do you trust?

The Scenario & Constraint

Less-trusted workflows can populate cache keys consumed by a release build. Tests examine one subset while the later privileged stage executes cached content. What changes?

The Direct Answer & Architectural Decision

Audit the trust and identity of cache inputs, make a correct clean rebuild possible and verify the actual release artifact. Keep privileged stages from treating cached code as inherently trusted, narrow permissions and retain provenance of the producing build and dependencies.

Key Trade-Offs & Follow-Up Traps

Disabling caches can raise cost but is preferable to a hidden authority bridge. A checksum proves equality to a value, not that the producer was trustworthy. Dependency/action verification and artifact checks serve different parts of the chain.

The schema step succeeds and application deployment fails. Is rerunning the old image enough?

The Scenario & Constraint

A pipeline removes a column before all serving versions stop reading it. Application rollout then fails halfway. What recovery and future change will you choose?

The Direct Answer & Architectural Decision

Determine current schema and serving versions, restore a compatible application/data path and reconcile any persistent effects. Use an expand/migrate/contract strategy for future compatible transitions and sequence cleanup only after consumers no longer require the old shape.

Key Trade-Offs & Follow-Up Traps

The old image may be incompatible with the new schema. Backup restoration can lose later writes and has recovery cost; a forward compatible fix may be safer. One pipeline does not make multiple application/database actions atomic or universally reversible.
