OpenTelemetry

🎯 The Hook & ELI5

Different hospitals can use standard forms and a courier system to describe and transport test results. The form-writing tools, processing center and courier are useful, but they are not the long-term medical archive or the doctor’s dashboard. OpenTelemetry similarly helps applications produce and move consistent telemetry to a chosen destination.

OpenTelemetry provides specifications, APIs, SDKs, instrumentation and Collector components for telemetry. Its job is distinct from the backend that retains, queries and visualizes that telemetry. Adoption succeeds when each boundary has an owner: what is measured, how context follows work, which components process data, and what happens during an exporter outage. Follow a service producing traces and metrics through a local agent or gateway to a separate backend.

🗺️ High-Level Big Picture

Instrumentation, collection and backend analysis are separate layers; success at one does not prove end-to-end visibility or durability.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace ownership, state transitions, decision evidence and the failure/recovery boundary.

1. Separate API usage from SDK configuration

An instrumentation API lets code describe telemetry without choosing every runtime/export detail. The SDK implements collection/processing behavior and must be configured with the appropriate provider, resources and exporters for the chosen language/signal. An API call alone does not guarantee exported data. Automatic instrumentation can cover supported framework/library operations; manual spans/metrics add missing business boundaries. Check overlap to avoid counting one operation twice.

2. Make identities and conventions useful

Resource attributes describe the producing service/environment; instrumentation scope describes the instrumentation source, while span/metric attributes describe operations or measurements. Use versioned semantic conventions so shared field meanings and units align across components. Keep service identity bounded and consistent; putting instance or customer identity into the service name fragments queries. Compatibility and stability vary by language, signal and convention, so verify the exact release rather than saying all OpenTelemetry parts have one maturity level.

3. Choose a distribution and verify real component support

A Collector distribution includes selected components listed in its manifest. The upstream component pages checked on 2026-11-22 describe the OTLP receiver as stable for traces/metrics/logs, while the batch and transform processors list beta for those signals. Those checked main-branch statuses illustrate component-specific maturity, not a pinned production compatibility guarantee. Verify your actual release’s manifests, status and migration notes before relying on processor syntax or a signal. A familiar component name in a blog does not prove it exists in your binary.

4. Trace an enabled pipeline and its order

A receiver accepts supported input; ordered processors transform/drop/batch it; an exporter sends it onward. Defining a component is not enough: it must appear in the appropriate service pipeline. Extensions such as persistent storage/authentication also need supported configuration and activation. Apply minimization/redaction before untrusted persistence/export, consider processor error behavior and inspect sensitive diagnostics. OTLP specifies transport/data exchange, not an automatic queryable storage service. Endpoint protocol, TLS and authentication must match on both sides.

5. Bound outage behavior and observe the telemetry system

Exporter queues and retries absorb limited disruption. With hypothetical input of 10,000 spans/s and a truly span-counted capacity of 300,000 spans, an empty queue buys only 30 seconds if no export succeeds. Actual queue sizing can use different units/configurations, plus batching and memory overhead, so inspect the selected implementation. Persistent queue storage can survive selected restarts, not disk loss or infinite outages; retries can duplicate and configured limits can drop data. Monitor queue occupancy/age, accepted/sent/failed/dropped signals and backend ingestion. Shut down/flush within a bounded application lifecycle budget without presenting diagnostics as a durable business ledger.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Configured but disabled

Symptom: A redaction processor has no effect.

Root Cause: It is defined but absent from the active pipeline or runs after exposure.

Fix/Prevention: Inspect enabled pipeline order and verify sanitized output using safe synthetic fields.

Double instrumentation

Symptom: Request metrics double after enabling an agent.

Root Cause: Manual and automatic integrations observe the same operation twice.

Fix/Prevention: Assign instrumentation ownership and test the actual signal count/relationships.

Queue mistaken for archive

Symptom: Spans disappear during a prolonged backend outage.

Root Cause: Finite retry/queue/disk limits are treated as guaranteed storage.

Fix/Prevention: State the loss budget and monitor every queue/export boundary with an explicit fallback.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Explain who creates, relates, processes, exports and stores each signal, then verify enabled components and finite outage behavior at every handoff. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Why can an instrumentation call produce no exported telemetry?

The relevant SDK/provider/exporter may be absent or configured to drop/disable it. API usage and actual collection/export are different boundaries.

Does defining a Collector processor activate it?

No. It must be referenced in the applicable service pipeline, in the intended order, using components supported by that distribution/release.

Does installing a Collector provide a complete observability backend?

No. It receives/processes/exports telemetry; durable retention, query, visualization and their access policies belong to selected backend systems.

What assumption makes 300,000 divided by 10,000 equal 30 seconds of buffering?

The empty queue is actually counted in spans, input is constant and no output succeeds. Batch/request/byte-counted queues and real overhead need different calculations.

Tricky & Most-Asked Interview Scenarios

An auto agent creates the same HTTP spans as manual middleware. What will you keep?

The Scenario & Constraint

The trace tree duplicates request operations and a request counter appears doubled after rollout. What diagnosis fits?

The Direct Answer & Architectural Decision

Inventory instrumentation paths and SDK/provider setup, choose one owner per standard boundary and retain manual business spans where they add distinct meaning. Verify counts and parent relationships using controlled requests.

Key Trade-Offs & Follow-Up Traps

Removing every manual span can lose business context; keeping overlapping counters makes aggregate rates wrong. Similar names alone do not prove duplication, so inspect actual source/scope and events.

A configured redaction transform never removes a sensitive field. Why?

The Scenario & Constraint

The component exists in configuration but does not appear in service.pipelines.traces.processors. What will you change and verify?

The Direct Answer & Architectural Decision

Enable the supported processor in the intended pipeline/order, test with harmless synthetic values and inspect exported output plus error behavior. Minimize sensitive source emission rather than relying only on late cleaning.

Key Trade-Offs & Follow-Up Traps

A configured component is not active automatically. Logs/debug exporters or earlier persistence can leak fields before redaction, and transform syntax/status must match the selected component release.

The backend is unavailable for five minutes. Can a 30-second queue preserve everything?

The Scenario & Constraint

Input is 10,000 spans/s and a hypothetical span-counted queue holds 300,000 with no successful export. What capacity/policy fits?

The Direct Answer & Architectural Decision

Calculate the 30-second raw coverage under those assumptions, then choose an explicit retention/loss budget, bounded storage/retry policy and recovery throughput. Observe drops and protect application availability.

Key Trade-Offs & Follow-Up Traps

A real queue may count requests/bytes instead of spans; persistent storage survives only defined failures. Larger queues cost memory/disk and do not guarantee exactly-once delivery or infinite outages.

A copied configuration references a processor absent from the installed binary. What now?

The Scenario & Constraint

Startup fails although an online example worked for a different distribution/version. What will you verify?

The Direct Answer & Architectural Decision

Check the installed distribution manifest, component support/maturity and release-specific configuration, then choose a supported component or reviewed distribution upgrade. Validate the effective configuration before rollout.

Key Trade-Offs & Follow-Up Traps

Contrib/core/custom distributions and versions can differ. A stable protocol does not make every processor or signal stable, and a status on the current main branch is not a guarantee for an older binary.

Telemetry reaches the backend, but async work is unrelated. Can changing the exporter fix it?

The Scenario & Constraint

Spans arrive successfully under separate roots after a queue handoff. What boundary needs attention?

The Direct Answer & Architectural Decision

Inspect application context injection/extraction/activation and selected messaging instrumentation/semantic conventions. Distinguish relationship creation from successful transport before adjusting exporter endpoints.

Key Trade-Offs & Follow-Up Traps

A Collector normally cannot infer missing application causality from timestamps. Context is not authentication, and joining unrelated work by a reused ID can produce misleading traces.

Each customer gets a different service.name and dashboards fragment. What identity belongs where?

The Scenario & Constraint

A team uses customer IDs as service identity and sends raw personal fields as attributes. What redesign fits?

The Direct Answer & Architectural Decision

Use stable bounded service/resource identity, select appropriate bounded measurement attributes and minimize/redact personal data before export. Establish convention versions and backend access/retention policy across signals.

Key Trade-Offs & Follow-Up Traps

Simply hashing customer values preserves high cardinality and may preserve privacy risk. A central transform helps enforce policy but does not remove already persisted copies or replace source minimization.
