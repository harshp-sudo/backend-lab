Metrics & Monitoring

🎯 The Hook & ELI5

A car dashboard gives a few useful numbers: speed, fuel and warning lights. Those numbers help only if the sensors work and you know their units. A smooth average speed can hide a long breakdown; an empty fuel reading is different from a disconnected sensor. Monitoring turns trustworthy measurements into decisions about user experience and resource health.

Metrics are time-series measurements with defined names, units and labels. This lesson builds the operational pipeline behind them: instrumentation, Prometheus collection/storage/query/rules and Grafana visualization, with RED/USE and SLI/SLO interpretation. The existing Performance Monitoring lesson provides the broader diagnostic investigation; follow its related link after learning how these signals are produced and how a broken telemetry pipeline can mislead that investigation.

🗺️ High-Level Big Picture

A dashboard is the end of a measurement chain. Check the chain and the measurement definition before treating a chart as evidence.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace ownership, state transitions, decision evidence and the failure/recovery boundary.

1. Ask RED and USE questions with the right scope

RED describes request Rate, Errors and Duration for services. USE examines Utilization, Saturation and Errors for resources, following Brendan Gregg’s original method. High request duration is a user symptom; CPU queueing or exhausted worker slots can help explain it. Neither method is a requirement to alert on every collected number. Define which requests and resources are in scope, including client-visible failures that never reach the application.

2. Choose types, units and bounded dimensions

A counter accumulates events and may reset; a gauge can rise/fall; histograms describe observed distributions with counts/sums and buckets or supported native representation. A summary’s precomputed quantiles cannot generally be averaged into a fleet percentile. Label combinations create distinct series: user IDs, raw URLs and trace IDs can explode cardinality. Use bounded route templates, status classes and deliberate dimensions, preserving private/high-cardinality detail in suitable logs/traces instead.

3. Follow collection through visualization

Prometheus discovers targets and scrapes exposed metrics, stores samples and evaluates configured queries/rules. A scrape failure, exporter bug, storage gap and rule evaluation failure are distinct problems. Grafana’s Prometheus data source queries that backend; datasource credentials, query range/step and permissions can fail while collection is healthy. A blank panel is not a measured zero. Inspect target freshness, raw series and query outcomes before modifying the application.

4. Calculate rates and distributions correctly

For a hypothetical counter http_requests_total with bounded service/status labels, take a per-series rate before aggregation so resets are handled at their source. This illustrative PromQL computes the server-error fraction over five minutes; assume a nonzero denominator and a defined meaning for 5xx. Interpret the result as a fraction; absent observations or a zero denominator require an explicit measurement policy.

sum(rate(http_requests_total{service="checkout",status=~"5.."}[5m]))
/
sum(rate(http_requests_total{service="checkout"}[5m]))

For classic histogram buckets, a fleet quantile query must aggregate appropriate bucket rates while retaining the le boundary label before histogram_quantile. Keep units and bucket design aligned with the latency objective. Averaging per-instance p99 values does not yield fleet p99. Missing requests and failed client-side calls cannot be recovered by a clever query over application-only samples.

5. Define the SLI, objective, window and response

An SLI is the measured fraction or distribution representing an outcome; an SLO sets a target over a window. Suppose one million eligible requests have a 99.9% success objective: the request-based error budget is 1,000 bad requests. If 400 were bad, 600 remain under that simplified full-window accounting. Define eligibility, success and measurement location explicitly; request budget is not automatically minutes of downtime. Use burn-rate/operational policy to guide action, and monitor the telemetry system itself through independent evidence where failure would otherwise hide the incident.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Average percentile

Symptom: A fleet p99 looks healthy during serious tail latency.

Root Cause: Per-instance quantiles are averaged.

Fix/Prevention: Aggregate compatible distributions or use correctly defined buckets; state approximation and scope.

Zero from absent data

Symptom: Dashboard is green during a scrape outage.

Root Cause: Missing series were coerced into healthy outcomes.

Fix/Prevention: Monitor freshness/scrapes and use explicit unknown-state handling.

Cardinality incident

Symptom: Metric storage grows with every customer.

Root Cause: Unbounded identities became labels.

Fix/Prevention: Use bounded dimensions and inspect series growth before broad instrumentation rollout.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Define bounded measurements and meaningful user objectives, follow their collection/query chain and combine RED symptoms with USE resource evidence before acting. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

When do RED and USE complement each other?

RED identifies request symptoms; USE investigates resource utilization, saturation and errors that may explain them. They answer different scoped questions.

Why take rate before summing counters?

Reset handling belongs to each original series. Aggregating first can hide individual resets and produce misleading rates.

What budget remains after 400 bad requests against one million eligible requests at 99.9%?

The simplified total allowance is 1,000 bad requests and 600 remain. Eligibility, window and measurement location must be explicit.

What does a Grafana query failure say about application health?

It establishes a visualization/query problem, not a healthy or failed application by itself. Inspect datasource, backend and collection boundaries separately.

Tricky & Most-Asked Interview Scenarios

p99 latency rises while average CPU stays low. Which signals do you inspect?

The Scenario & Constraint

Checkout slows, but host CPU utilization is modest. Thread/connection queues may be saturated. What method fits?

The Direct Answer & Architectural Decision

Start with scoped RED latency/errors/rate and investigate relevant resources with USE, including queues, concurrency and dependency waits. Correlate the same time/workload and test the suspected bottleneck.

Key Trade-Offs & Follow-Up Traps

Low average CPU does not rule out blocking, one saturated core or constrained pools. Collecting every metric without a decision question can increase noise and cost.

A deploy makes an error graph spike negative or huge. What query error is likely?

The Scenario & Constraint

Individual replicas restart and counters reset at different times. The dashboard applies a rate to a pre-aggregated counter. What changes?

The Direct Answer & Architectural Decision

Apply rate to each source counter before aggregating the resulting rates, verify label identity and scrape continuity, and compare raw samples/reset events. Preserve correct request denominators.

Key Trade-Offs & Follow-Up Traps

A gauge should not be treated as a counter. Query changes cannot reconstruct requests that were never observed, and a short window with sparse samples has uncertainty.

Can you average ten instance p99 values to report fleet p99?

The Scenario & Constraint

Traffic differs greatly between instances and the dashboard averages reported quantiles. What measurement do you choose?

The Direct Answer & Architectural Decision

Use mergeable compatible histogram/distribution data with correct query semantics, units and bucket resolution to calculate a fleet quantile, or explicitly report per-instance values without a fleet claim.

Key Trade-Offs & Follow-Up Traps

Even a weighted average of p99s is not generally fleet p99. Histograms trade resolution/cost and classic/native forms need appropriate supported queries; summaries have different aggregation properties.

A user_id label increases series count without bound. What will you preserve?

The Scenario & Constraint

The metric backend slows after per-user diagnostics are added to a request counter. What redesign fits?

The Direct Answer & Architectural Decision

Remove/bound unbounded metric dimensions, keep route/status/service dimensions needed for aggregate decisions and move event-level identity to access-controlled logs/traces. Track series growth and validate queries after the change.

Key Trade-Offs & Follow-Up Traps

Removing labels loses per-user metric slicing but restores a sustainable aggregate model. Hashing IDs does not reduce cardinality, and merely increasing storage postpones the same structural problem.

Grafana is blank while the service receives traffic. Is the SLI zero?

The Scenario & Constraint

One datasource credential expired, and one target has stopped scraping. What boundaries do you test?

The Direct Answer & Architectural Decision

Inspect datasource/query errors, raw backend series, target status and sample freshness separately. Declare unknown where measurement is unavailable and repair the pipeline before asserting a success/error ratio.

Key Trade-Offs & Follow-Up Traps

Filling absent samples with zero can conceal an outage. A working panel does not prove all eligible user outcomes are represented, so measurement location and completeness remain part of the SLI contract.

The service has spent 400 of a 1,000-request error budget. Must every release stop?

The Scenario & Constraint

An objective permits 1,000 bad requests in the defined million-request window. Current use is 400, but errors are accelerating. What decision fits?

The Direct Answer & Architectural Decision

Calculate remaining allowance and current burn in the defined window, then apply an explicit reliability/release policy with owners. Investigate user impact and trend rather than treating the remaining count as unconditional permission to spend it.

Key Trade-Offs & Follow-Up Traps

A budget is a decision mechanism, not a universal release rule. Request-based allowance cannot be converted directly to downtime minutes, and changing eligibility to improve the chart undermines the objective.
