Kubernetes

🎯 The Hook & ELI5

A school coordinator keeps a board saying “three classrooms should be open.” If one room closes, staff find another suitable room and arrange supplies. Writing three on the board does not create space, unlock a cupboard or prove children can enter. Kubernetes similarly keeps trying to make declared workload state real.

Kubernetes is a concrete platform for reconciling containerized workloads and related resources. Its API records intent; controllers, scheduling and node agents carry out different parts of that intent. Understanding those boundaries makes diagnosis faster than memorizing object names. Follow a three-replica API from submission through storage, placement and Service reachability; the same reasoning explains why a resource can exist without a usable application.

🗺️ High-Level Big Picture

Each arrow is a separate boundary to inspect: accepted intent, feasible placement, running process, ready endpoint and successful user request.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace ownership, state transitions, decision evidence and the failure/recovery boundary.

1. Write intent and understand its owner

The API server authenticates/authorizes and validates resource operations; cluster state is persisted through the control-plane storage layer. A Deployment controller manages ReplicaSets, which manage Pods. A Pod is the scheduling unit and may contain cooperating containers. Desired state is not an imperative promise to execute one successful command: reconciliation can retry and observe partial progress. Keep declarative ownership clear so competing controllers do not repeatedly undo each other.

2. Find out whether placement is feasible

The scheduler considers constraints such as resource requests, node eligibility, affinity and storage topology before binding an unscheduled Pod. A Pending Pod can reflect unsatisfied placement or initialization; inspect its conditions and events rather than assuming the process crashed. Requests affect placement, while limits constrain execution behavior differently. Adding replicas cannot overcome a cluster quota or a volume tied to an unavailable zone.

3. Trace node execution and dependencies

A node’s kubelet works with a container runtime to realize assigned Pods. Image pulls, credentials, configuration and volume mounts can fail before application code starts. Separate image/config errors from application crashes. The runtime is not required to be the Docker daemon: modern Kubernetes uses compatible runtimes through its runtime interface. Identify what your actual distribution provides instead of assuming every cluster has identical plugins and defaults.

4. Follow Service selection to real endpoints

A Service supplies stable access to selected workloads; inspect selectors, Pod labels, ports and EndpointSlices/readiness before blaming DNS. Correct name resolution does not establish that endpoints exist or the application listens on the target port. Network policy, implementation-specific data plane and external routing are additional boundaries. A running Pod with failing readiness may deliberately be excluded from normal serving.

5. Treat durable state and the control plane separately

A PVC requests storage and a PV represents provisioned storage. Binding, access mode, topology and reclaim policy have consequences beyond Pod lifetime. ReadWriteOnce generally means single-node read/write attachment, not an application-level single-writer guarantee across all Pods on that node. Control-plane unavailability may leave already running workloads serving while preventing new scheduling or reconciliation; this is neither guaranteed full application availability nor immediate universal process death. Backups and application recovery remain explicit duties.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Replica count mistaken for service

Symptom: The dashboard shows three desired replicas but users cannot connect.

Root Cause: Desired, scheduled, running, ready and reachable were collapsed into one state.

Fix/Prevention: Inspect each boundary with conditions/events and endpoint/application evidence.

Service with no endpoints

Symptom: DNS resolves but every request fails.

Root Cause: A selector or readiness mismatch leaves no usable targets.

Fix/Prevention: Compare labels, selectors, endpoint membership and listening ports before changing DNS.

Storage mistaken for a database contract

Symptom: Two writers corrupt shared files.

Root Cause: Volume access properties are assumed to serialize application writes.

Fix/Prevention: Use the correct data-system concurrency/recovery mechanism and verify storage semantics.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Trace accepted intent through ownership, placement, node execution and endpoints before deciding which component can actually fix the failure. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Why can desired replicas differ from ready replicas?

Scheduling, image access, initialization, mounts and readiness may block intent from becoming serving capacity.

How do scheduler and kubelet responsibilities differ?

The scheduler chooses a feasible node for a Pod; the kubelet and runtime on that node realize assigned container execution.

What does successful Service DNS resolution fail to prove?

It does not prove selected ready endpoints, correct target ports, permitted connectivity or a working application.

Does a bound PVC mean recoverable application data?

No. Binding establishes a storage relationship. Consistent backups, keys, application state and restore procedures are separate responsibilities.

Tricky & Most-Asked Interview Scenarios

New Pods remain Pending despite low average CPU. What next?

The Scenario & Constraint

The API accepts five replicas but only two are scheduled. Nodes show 20% average CPU. What evidence matters?

The Direct Answer & Architectural Decision

Inspect Pod events/conditions and scheduler constraints: requested rather than average resources, affinity, taints, quotas and volume topology. Adjust the actual unmet constraint or provide eligible capacity.

Key Trade-Offs & Follow-Up Traps

Low current CPU does not imply free requested capacity, memory or a feasible zone. Reducing requests blindly may improve placement while causing runtime contention.

Service DNS works but requests fail. Where do you look?

The Scenario & Constraint

Newly deployed Pods run and a Service name resolves, yet there are no successful connections. What order of diagnosis fits?

The Direct Answer & Architectural Decision

Compare Service selectors and Pod labels, inspect ready endpoints and target/listening ports, then check the relevant network/policy path. Test the application boundary rather than treating DNS resolution as end-to-end proof.

Key Trade-Offs & Follow-Up Traps

Changing DNS without endpoint evidence adds noise. A direct Pod request can isolate one boundary but may bypass Service routing and policy, so it is not a complete replacement test.

A Pod never starts after changing image credentials. Is application rollback the first step?

The Scenario & Constraint

Events indicate image access failure before the process starts. The application team is investigating a suspected startup bug. What will you do?

The Direct Answer & Architectural Decision

Separate image-pull/authentication and node connectivity from application execution; verify the selected image identity and scoped pull credential. Restore a valid access path without exposing credentials in logs.

Key Trade-Offs & Follow-Up Traps

A previous image may already be cached and appear to fix the symptom without solving access. Rebuilding code does not repair registry permissions or a wrong platform image.

A replacement cannot mount its data in another zone. What contract blocks recovery?

The Scenario & Constraint

A stateful workload is rescheduled after node loss, but its volume is constrained to one zone. What will you inspect and choose?

The Direct Answer & Architectural Decision

Inspect PV/PVC binding, storage-class/topology/access constraints and the actual storage provider’s recovery capabilities. Restore eligible placement or use an intentionally designed data recovery/replication path.

Key Trade-Offs & Follow-Up Traps

A Pod controller cannot make local data regionally durable. Forcing detach or multiwriter access without provider/application guarantees risks corruption; more replicas do not repair a missing data copy.

The API server is unavailable, but existing requests still succeed. How urgent is it?

The Scenario & Constraint

Serving containers remain on healthy nodes while operations cannot change objects or replace failures. What response fits?

The Direct Answer & Architectural Decision

Treat it as loss of management/reconciliation capacity, assess application dependencies and restore the control plane using the platform’s supported procedure. Monitor serving and replacement risk separately.

Key Trade-Offs & Follow-Up Traps

Existing data-plane operation may continue, but new failures cannot be assumed recoverable and workloads may depend on API access. Claiming either instant total outage or no user risk ignores these boundaries.

Manual replica edits keep reverting. Who owns the value?

The Scenario & Constraint

An operator changes replica count while an autoscaler and deployment configuration also write desired state. The count oscillates. What will you change?

The Direct Answer & Architectural Decision

Identify resource/field ownership and the active controllers, choose one intended scaling authority, and reconcile declarative configuration with that choice. Inspect events and actual metric inputs before editing again.

Key Trade-Offs & Follow-Up Traps

Disabling automation may be a temporary containment action but leaves operational work. Repeated imperative edits do not establish durable intent when another controller legitimately reconciles the same field.
