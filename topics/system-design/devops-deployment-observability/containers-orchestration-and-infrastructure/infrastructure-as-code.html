Infrastructure as Code

🎯 The Hook & ELI5

Imagine a building blueprint, a register linking each room number to a real room, and a contractor who compares the blueprint with the building before making changes. The blueprint is configuration, the register is state, and the proposed work is a plan. If work stops halfway, the rooms already changed do not magically return to yesterday.

Infrastructure as Code makes infrastructure intent reviewable and repeatable through versioned definitions and tool-driven changes. Terraform is the concrete example here: providers interact with remote systems, while state relates declared resource addresses to real objects. The central challenge is coordinated change across systems that are not one transaction. Follow a service network update with two operators, a protected state backend and a partially failing provider action.

🗺️ High-Level Big Picture

Configuration, state, a plan and real infrastructure are distinct. Failure recovery begins by reconciling their actual relationship.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace ownership, state transitions, decision evidence and the failure/recovery boundary.

1. Declare the management boundary

Write which resources this configuration owns and which remain external dependencies. Select provider sources/versions and appropriate runtime credentials; provider behavior and API constraints affect the outcome. Keep dependency selections reviewable with the tool’s supported lock mechanism. Separate environments deliberately, including backend/state identity and access, so an apparently safe command cannot target production through ambient configuration.

2. Protect the state mapping and its secrets

State records relationships between configuration addresses and remote objects and may contain sensitive attributes even when normal output is redacted. Use an access-controlled durable backend, supported encryption/versioning and a recovery procedure. A remote backend does not automatically imply every desired security or locking property; verify the chosen backend. Do not commit state or exported plan files as harmless documentation.

3. Read a plan as a conditional proposal

A plan compares selected configuration, prior state and observed remote information to propose provider actions. Inspect replacements, dependency order and destructive consequences. A speculative plan is not the same workflow as applying a saved plan. Saved plans preserve selected decisions/inputs but are sensitive and do not freeze remote reality indefinitely; changed state, credentials or APIs can invalidate assumptions or cause failure. Reassess stale evidence before applying.

4. Coordinate writers without confusing the lock with universal ownership

Terraform state locking is backend-dependent and protects cooperating operations on that state. Do not disable it merely because another writer is inconvenient. Confirm the active operation and lock ownership before any force-unlock; an interrupted terminal does not prove all remote work stopped. A state lock does not stop a console user or another independently managed state from changing the same real object. Establish one clear owner and an emergency-change reconciliation policy.

5. Recover partial changes and import deliberately

If the network is created but a later permission operation fails, inspect actual resources, diagnostics and recorded state, then produce a fresh reviewed plan. Do not assume automatic global rollback. For an existing object missing from state, use the provider-supported import workflow with correct configuration/resource identity, then review the resulting diff before further changes. Restore validated state history where appropriate; arbitrary state edits or recreation can orphan or destroy live infrastructure. Reconcile intentional console drift into configuration or deliberately reverse it after review.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Lock bypass causes conflict

Symptom: One apply overwrites assumptions of another.

Root Cause: Operators disable coordination to clear a delay.

Fix/Prevention: Identify the active writer; use supported locking and owner-aware recovery.

Redacted output mistaken for safe state

Symptom: A state export exposes credentials.

Root Cause: Sensitive display flags were assumed to remove stored values.

Fix/Prevention: Protect state/plans as sensitive and rotate any exposed credentials.

Partial apply mistaken for no change

Symptom: Rerun attempts duplicate or destructive resources.

Root Cause: Failure is treated as transactional rollback.

Fix/Prevention: Inspect remote/state outcomes and review a fresh plan before recovery.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Explain how reviewed intent, protected state and coordinated provider actions support repeatability while drift and partial failure still require explicit recovery. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

How do configuration, state, plan and reality differ?

Configuration states intent; state maps managed addresses to objects; a plan proposes changes from selected inputs/observations; reality is what remote APIs and resources actually contain.

What does a state lock fail to prevent?

It does not block out-of-band API users or an unrelated state managing the same object. It coordinates cooperating writers within its backend-supported scope.

What is the first recovery step after apply fails halfway?

Inspect actual effects and current state, protect data, then replan and review. Do not assume earlier successful provider operations were rolled back.

What does import establish?

A management mapping for an existing supported remote object. Configuration and resulting differences still need review; importing is not proof the object already matches intent.

Tricky & Most-Asked Interview Scenarios

A lock delays a second operator during an incident. Should it be disabled?

The Scenario & Constraint

Two applies target the same state. One terminal appears idle but a cloud API operation may still run. What will you do?

The Direct Answer & Architectural Decision

Identify the current operation and owner, coordinate its completion/termination and inspect real effects before any supported unlock/recovery. Preserve the backend’s writer coordination rather than running conflicting applies.

Key Trade-Offs & Follow-Up Traps

Waiting has incident cost, but bypassing an active lock can corrupt assumptions or state. Force-unlock requires ownership evidence; losing a terminal is not proof the provider action stopped.

A reviewed plan is three days old after an emergency console edit. Can it be blindly applied?

The Scenario & Constraint

A network rule changed outside IaC after approval. The saved plan was prepared against an earlier environment. What decision fits?

The Direct Answer & Architectural Decision

Inspect current remote/state/configuration relationships, reconcile the emergency intent and regenerate/review evidence where assumptions changed. Verify how the selected Terraform workflow handles saved-plan state consistency.

Key Trade-Offs & Follow-Up Traps

A new plan can delay release, but an old approval does not establish present safety. Versioned source alone does not freeze real resources, APIs, quotas or credentials.

The network exists but a later IAM step failed. Should the entire apply be considered undone?

The Scenario & Constraint

The tool reports failure after several successful provider actions. A retry may encounter existing resources. What recovery fits?

The Direct Answer & Architectural Decision

Inspect diagnostics, remote objects and state recording, then plan the remaining/reconciliation work with correct identities. Preserve accepted changes or deliberately reverse them through a reviewed recovery, accounting for consumers.

Key Trade-Offs & Follow-Up Traps

Provider operations do not form one universal transaction. Deleting everything to start over can destroy data or live dependencies; simply rerunning without understanding state can compound the failure.

The CLI hides a password, but the state file contains it. What controls are needed?

The Scenario & Constraint

A teammate proposes committing state because values marked sensitive are masked in normal output. What response fits?

The Direct Answer & Architectural Decision

Treat state and saved plans as sensitive, use access-controlled storage with appropriate encryption/version recovery and avoid committing exports. Rotate any values already exposed and limit provider/runtime authority.

Key Trade-Offs & Follow-Up Traps

Redaction is a display behavior, not proof of absence. Encryption alone does not restrict authorized readers, and state backup access must be included in the same policy.

State is lost while production resources remain. Is recreating the stack safe?

The Scenario & Constraint

A new local state appears empty and the plan proposes creating objects that already serve traffic. What will you do?

The Direct Answer & Architectural Decision

Stop before destructive/duplicate operations, recover a validated state backup where possible, or deliberately import supported existing objects into correct addresses/configuration. Review all resulting differences before managing them.

Key Trade-Offs & Follow-Up Traps

Import requires correct provider identity and resource support; it does not automatically reconstruct every intended setting. Blind recreation risks name conflicts, orphaned resources and data loss.

Two independent IaC states keep changing the same firewall rule. Which lock fixes it?

The Scenario & Constraint

Each state locks correctly, but one team’s apply reverts the other team’s change. What ownership model fits?

The Direct Answer & Architectural Decision

Assign a single management owner or split truly independent resource boundaries, represent dependencies explicitly and reconcile desired policy in one place. Remove overlapping authority through a reviewed migration.

Key Trade-Offs & Follow-Up Traps

Per-state locks do not coordinate unrelated owners of one remote object. Larger shared state simplifies some coordination but broadens blast radius and access; choose boundaries based on actual lifecycle ownership.
