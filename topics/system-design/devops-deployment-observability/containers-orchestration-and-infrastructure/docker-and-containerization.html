Docker & Containerization

🎯 The Hook & ELI5

Think of an image as a sealed recipe box with ingredients and instructions. A container is one kitchen actually using that box. Two kitchens can start from the same box but spill different things on their worktops. Their reusable pantry belongs somewhere separate, and the kitchens still share the building’s foundations.

Containerization packages an application filesystem and execution configuration so instances can start consistently. Docker provides tools to build, distribute and run these packages. For ordinary Linux containers, namespaces and resource controls isolate processes using the host kernel; a container is not automatically a separate virtual machine or a complete security boundary. Follow an API image from build to replacement, paying attention to what is immutable, persistent and trusted.

🗺️ High-Level Big Picture

The image, each container’s writable layer, persistent storage and host kernel have different ownership and lifetimes.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace ownership, state transitions, decision evidence and the failure/recovery boundary.

1. Build from a bounded, reviewable context

A Dockerfile describes build operations against a context. Exclude unnecessary files before sending that context to the builder, and keep credentials out of it. Layers/cache can speed repeated work, but a cached result is not proof that a dependency is current or trusted. Multi-stage builds can keep compilers and temporary build files out of the final runtime image; the final output still needs verification and patching.

2. Identify the actual artifact rather than a movable nickname

A tag such as latest can be retargeted. Record the image digest, platform and build inputs so staging and production consume the intended verified output. A multi-platform image index can select different platform-specific content, so identify the relevant target when comparing results. Pinning an old image improves identity, not its security freshness: maintain a tested rebuild and update policy.

3. Supply build secrets through the correct boundary

For Docker BuildKit, secret/SSH mounts are intended for sensitive build-time access; ARG/ENV or copying a token into a layer is not a safe replacement. A later deletion does not erase a credential embedded in an earlier layer. Avoid printing the mounted value or copying it into generated output. Build-time identity and runtime service identity should have separate minimal permissions and rotation paths.

4. Separate replaceable writes from durable state

The container’s writable layer is coupled to that container; replacing it can discard those writes. A Docker volume has a separate lifecycle and must be deliberately mounted, owned and backed up. Moving a database directory into a volume does not create consistent backups or replication. Check file permissions, filesystem semantics and the application’s consistency requirements when multiple instances access persistent data.

5. Bound the running process and verify shutdown

Run with only needed user privileges, capabilities, mounts and daemon access. Apply measured CPU/memory limits and monitor throttling or termination; resource isolation does not create infinite capacity. The main process must receive and handle termination appropriately, and logs must be collected beyond the container lifetime. Host kernel exposure, privileged containers and a mounted Docker socket can defeat assumptions about isolation. Test replacement, restart and data recovery separately.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Deleted secret still retrievable

Symptom: A registry image exposes an old token.

Root Cause: A previous layer or build output retained it.

Fix/Prevention: Revoke it, inspect history/output and rebuild with appropriate secret mounts and scoped credentials.

Healthy restart, vanished data

Symptom: Uploaded files disappear after replacement.

Root Cause: The application wrote only to its container layer.

Fix/Prevention: Use deliberate durable storage and verify restoration, not just process restart.

Packaging mistaken for isolation

Symptom: An application gains host control.

Root Cause: Broad capabilities or daemon/socket access crosses the intended boundary.

Fix/Prevention: Reduce authority and select a stronger isolation model where required.

How does an image differ from a container?

An image is packaged filesystem/configuration content; a container is an executing instance with runtime state and a writable layer.

Why record a digest as well as a tag?

A tag can move. An identified digest and target platform help establish which artifact was actually verified and deployed.

Does a volume automatically make data safe?

No. It separates lifetime from a container, but correctness, access, backups and tested recovery remain separate work.

What resource and security assumption survives packaging?

Linux containers still depend on their host kernel and granted capabilities. Namespaces and cgroups do not remove host compromise or capacity risks.

Tricky & Most-Asked Interview Scenarios

Two machines deploy the same tag but behave differently. What do you compare?

The Scenario & Constraint

Production and staging both declare the api:latest tag. Their serving behavior differs after a registry update. What will you do?

The Direct Answer & Architectural Decision

Inspect actual image identities and target platforms, compare configuration and dependencies, then deploy the same verified artifact identity through promotion. Keep a deliberate patch/rebuild policy.

Key Trade-Offs & Follow-Up Traps

A digest proves selected content identity, not that it is safe or correctly configured. Platform-specific variants and runtime secrets can still differ; locking a vulnerable image forever is not a maintenance strategy.

A token was copied then removed in the next build step. Is rotation necessary?

The Scenario & Constraint

The image was pushed to a shared registry and a build log printed the token. What response and prevention fit?

The Direct Answer & Architectural Decision

Treat the credential as exposed, revoke/rotate it and inspect where it propagated. Rebuild using scoped build-secret access and ensure neither output nor logs persist the value; restrict the build context and artifact access.

Key Trade-Offs & Follow-Up Traps

Removing a later file or tag does not erase earlier layers, downloaded copies or logs. Secret mounts reduce accidental persistence but cannot stop a build command intentionally copying or printing the value.

Replacing a container loses customer uploads. What storage contract is missing?

The Scenario & Constraint

The service writes under its local filesystem and deployment recreates containers. Customers expect files to survive. What changes?

The Direct Answer & Architectural Decision

Move durable objects to an explicitly managed volume/object store or database with appropriate ownership, availability and tested backup/restore. Keep transient cache files separate and verify replacement preserves expected state.

Key Trade-Offs & Follow-Up Traps

A mounted volume changes lifetime, not application-level consistency or cross-host portability. Sharing one directory between writers may introduce races; storage access and recovery semantics must match the workload.

The container is repeatedly killed under load although the host has spare memory. What next?

The Scenario & Constraint

A runtime memory limit is below the application’s peak working set and no graceful error appears. What evidence and change fit?

The Direct Answer & Architectural Decision

Inspect termination reason, measured working set and limits, reduce unnecessary retention or tune concurrency and runtime memory settings, then adjust the measured budget where capacity permits.

Key Trade-Offs & Follow-Up Traps

Simply removing limits can move failure to other workloads or the host. Container memory accounting includes more than a language heap; an OOM kill is not equivalent to an application exception with cleanup.

A build helper requests the host Docker socket. Is it an ordinary file mount?

The Scenario & Constraint

Untrusted build code would reach a daemon that can start privileged host containers. What boundary will you choose?

The Direct Answer & Architectural Decision

Treat daemon access as substantial host authority, isolate untrusted build execution and avoid exposing the privileged socket. Use an appropriately restricted builder/host trust model and scoped outputs rather than relying on the helper’s container label.

Key Trade-Offs & Follow-Up Traps

Running as a non-root user inside the helper does not neutralize powerful daemon access. Stronger isolation costs setup and resources; ordinary shared-kernel containers are not interchangeable with VM boundaries.

A fast rebuild still contains an old vulnerable library. What policy is missing?

The Scenario & Constraint

Cached build layers and a stable base identity keep reproducing the same old runtime after a security fix is published. What will you do?

The Direct Answer & Architectural Decision

Update reviewed base/dependency inputs, rebuild and verify a new artifact, then promote it with provenance and compatibility checks. Distinguish reproducible identity from a policy to discover and apply fixes.

Key Trade-Offs & Follow-Up Traps

Disabling all cache can increase time without updating pinned inputs. Automatically taking every latest version reduces control. Reproducibility and deliberate patch freshness need complementary processes.
