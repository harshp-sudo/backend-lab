Relational Database Design

🎯 The Hook & ELI5

A library does not rewrite a reader’s address on every borrowed-book card. It gives each reader and book a dependable number, then records who borrowed which book. Tables work like these organized lists. Relationships connect the lists, and rules stop a loan from pointing to a reader who does not exist. Relational design is deciding what each list means before filling it with data.

A relational schema describes facts, identity and allowed relationships. A row represents one occurrence of the fact named by a table; a column gives one attribute of that occurrence. A primary key identifies a row, a foreign key references another key, and constraints reject specified invalid states.

Our running example is a shop. A customer can place many orders; an order contains many products, and a product can appear in many orders. The design must distinguish a current product price from the price agreed for a particular order. Good design makes those meanings and ownership boundaries explicit rather than copying the shape of the first screen.

🗺️ High-Level Big Picture

OrderLine is the bridge between orders and products. Its quantity and agreed price describe that specific relationship, not the customer or the product’s current catalog state.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; SQL examples target PostgreSQL 18 unless explicitly labeled otherwise.

1. Name the fact and its lifetime

Start with sentences: a customer places an order; an order contains a product in a quantity at an agreed price. Ask what exists independently and what can change independently. Customer contact details can change without rewriting the facts of an old sale.

Define each table’s grain: exactly what one row means. If one row sometimes means an order and sometimes a shipment, joins and totals become unreliable. Use separate relationship rows when one order can be fulfilled in several shipments.

2. Choose identity and real-world uniqueness

A stable internal number can identify a customer even after their email changes. This is a surrogate key. A business identifier that is genuinely unique under the domain’s rules is a candidate key and may deserve a separate uniqueness constraint.

A primary key is not a substitute for every business uniqueness rule. Decide whether an email is optional, case-sensitive, shared or reusable after account closure before declaring it unique. SQL NULL behavior and collation rules matter; document the chosen semantics rather than letting an ORM guess.

3. Model cardinality and put attributes on the right relationship

One customer to many orders means the customer reference belongs on each order. Many orders to many products needs an OrderLine bridge. Quantity belongs on the line, because one product can have different quantities in different orders.

If repeated appearances of the same product in one order must be distinct, give lines their own identity or an order-local line number. A key of order/product intentionally permits only one combined line for that pair; it is a domain choice, not a universal pattern.

4. Make the minimal schema enforce its meaning

This PostgreSQL 18 example uses whole currency minor units and positive quantities. It assumes one line per product in an order and one unique, mandatory contact email per customer. These assumptions must match the real product before using the schema.

CREATE TABLE customer (
  customer_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text NOT NULL UNIQUE
);
CREATE TABLE product (
  product_id bigint PRIMARY KEY,
  name text NOT NULL
);
CREATE TABLE sales_order (
  order_id bigint PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customer(customer_id)
);
CREATE TABLE order_line (
  order_id bigint REFERENCES sales_order(order_id) ON DELETE RESTRICT,
  product_id bigint REFERENCES product(product_id) ON DELETE RESTRICT,
  quantity integer NOT NULL CHECK (quantity > 0),
  unit_price_cents bigint NOT NULL CHECK (unit_price_cents >= 0),
  PRIMARY KEY (order_id, product_id)
);

The composite primary key also makes both key columns non-null. A foreign key prevents a dangling reference; it does not automatically supply every index useful to a join or prevent a semantically incorrect but existing customer from being selected.

5. Separate stored facts from derived answers

Order value can be computed from line quantities and agreed prices. Storing a cached total may be justified, but then a maintained invariant connects the total with its lines. Keep one deliberate update path or a repairable projection.

SQL joins can multiply rows. Joining orders, order lines and multiple payments and then summing line values can count each line once per payment. Aggregate each relationship at the right grain before combining results, and test with one-to-many examples rather than only one-row fixtures.

6. Design changes and concurrency alongside the schema

A diagram does not prevent simultaneous writers from violating a rule that the database does not know. Use unique/foreign-key/check constraints where they express the invariant, and transactions or locking for conditions spanning multiple rows. PostgreSQL CHECK constraints are not a general cross-table assertion mechanism.

Choose deletion, retention and migration policies deliberately. Financial history may require retained snapshots or anonymization instead of cascading deletion. Adding a foreign key to existing data requires orphan checks and a safe validation/locking plan; a schema is a living contract, not a one-time drawing.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

One screen becomes one table

Symptom: Customer details disagree across orders.

Root Cause: The design mixed customer facts with order facts to avoid a join.

Fix/Prevention: Define each row’s grain; store current customer facts once and snapshot only intentionally historical values.

Valid foreign key, wrong tenant

Symptom: An order links to another tenant’s valid customer ID.

Root Cause: Referential existence was mistaken for tenant ownership.

Fix/Prevention: Use tenant-aware keys/foreign keys where appropriate and enforce authorization on every access path.

Totals grow after a join

Symptom: Revenue doubles when an order receives a second payment.

Root Cause: Two one-to-many relationships multiplied each other’s rows.

Fix/Prevention: Aggregate at the intended grain before joining and verify a multi-line, multi-payment example.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Give every stored fact a clear grain, owner and lifetime. Use keys and constraints for the rules they can express, and an explicit concurrency protocol for the rules that span rows. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Why define row grain before columns?

It tells readers and writers exactly what one row represents. Without it, joins, uniqueness and aggregates can combine incomparable facts.

Where should an agreed product price live?

On the order line or equivalent sale fact. It describes the product/order relationship at sale time, not the product’s mutable current price.

What does a foreign key guarantee?

Referenced key existence under the constraint’s timing and rules. It does not establish authorization, choose the correct existing owner or implement every multi-row business invariant.

Why can a table need both a surrogate key and a unique business key?

The surrogate keeps references stable; the business constraint prevents duplicates according to a separately defined real-world identity rule.

Tricky & Most-Asked Interview Scenarios

A student takes many courses and courses have many students. Where does the grade belong?

The Scenario & Constraint

A training platform stores course IDs as a comma-separated student field. It now needs one grade and enrollment date per student/course pair, with duplicate enrollment forbidden. How will you redesign it?

The Direct Answer & Architectural Decision

Create Student and Course entity tables and an Enrollment bridge. Store grade and enrollment date on Enrollment, with foreign keys to both owners and an appropriate unique key on the allowed student/course/attempt identity. Migrate parsed values with validation, reconcile missing courses and switch readers through a compatible transition. This makes each enrollment independently queryable and enforceable.

Key Trade-Offs & Follow-Up Traps

Joins add query work, but the bridge supports constraints and relationship attributes directly. If retakes are valid, a student/course-only key is too strict: add attempt identity or another explicit business discriminator. An array can be suitable for bounded nonrelational data, but a serialized list here hides the relationship’s own lifecycle.

Two requests pass the same uniqueness precheck. How do you prevent duplicate accounts?

The Scenario & Constraint

An API checks whether an email exists and then inserts a customer. Two application instances run simultaneously. The business has defined mandatory normalized contact identifiers as unique. What will you do?

The Direct Answer & Architectural Decision

Represent that normalized identifier explicitly and enforce its uniqueness in the database, with NOT NULL if required. Keep any precheck for user feedback but treat the insert outcome as authoritative. Handle a conflict deterministically, avoiding accidental account disclosure, and use a stable operation identity when retries might otherwise create separate accounts.

Key Trade-Offs & Follow-Up Traps

A unique index adds write and storage costs but protects every writer, not just one API process. A process-local mutex cannot coordinate multiple instances. If shared household emails or reuse after closure are allowed, revise the business key policy instead of treating all duplicate-looking inputs as technical failures.

Every customer ID exists, yet orders cross tenant boundaries. What constraint is missing?

The Scenario & Constraint

Customer and Order rows contain tenant IDs, but Order only references customer_id. A valid customer from another tenant can be attached accidentally. Tenant isolation is mandatory. What will you change?

The Direct Answer & Architectural Decision

Make the intended ownership relationship expressible: enforce a unique referenced customer key on tenant_id/customer_id and a composite foreign key from the corresponding order columns. Keep tenant columns non-null where required, repair existing violations, and use tenant-scoped authorization and queries. The constraint protects relationship integrity even when an application accidentally mixes IDs.

Key Trade-Offs & Follow-Up Traps

Composite keys/indexes consume space and require matching migrations. Separate databases per tenant may offer another isolation boundary but carry operating cost. Neither a composite FK nor separate schemas replaces authorization; a SELECT that omits tenant scope can still disclose rows unless an additional access policy prevents it.

Old invoices change when a product price changes. Should you normalize away the copied price?

The Scenario & Constraint

Order reports join current product prices, so last month’s invoice total changes after today’s catalog update. Auditors require the original commercial agreement. What will you store and why?

The Direct Answer & Architectural Decision

Store the agreed unit price, currency and relevant discount/tax facts on the immutable sale line or a governed pricing snapshot. Keep a product reference for identity, but compute historical sale amounts from historical facts. Treat corrections as an explicit adjustment/versioned business operation rather than silently rewriting finalized records.

Key Trade-Offs & Follow-Up Traps

This duplicates a number that may initially equal the catalog price, but the two fields represent different facts over time. Joining a properly effective-dated price history is an alternative when its interval rules are reliable. Ask whether the report requires original billed revenue or a hypothetical repricing before choosing the query.

Deleting one customer would erase paid orders. Which deletion policy fits?

The Scenario & Constraint

A cascade was added for convenience. Customer closure must remove unnecessary personal data, yet financial records have a mandatory retention period. How will you change the design?

The Direct Answer & Architectural Decision

Separate account/contact lifecycle from retained transaction facts. Use restrictive relationships or an explicit archival policy for finalized orders, minimize retained personal fields, and anonymize or detach contact information according to the actual retention requirements. Make closure an audited workflow that verifies references and deletes only what is permitted.

Key Trade-Offs & Follow-Up Traps

Retention and privacy rules require domain/legal policy, not a universal cascade recommendation. A soft-delete flag alone does not anonymize data or prevent accidental reads. Cascading deletion can still be correct for truly dependent ephemeral rows; distinguish those from records with an independent historical obligation.

Room capacity is exceeded although every individual row is valid. What will enforce the rule?

The Scenario & Constraint

Each booking has valid keys and positive seats, but concurrent inserts make the sum of seats exceed room capacity. The rule spans several bookings. A per-row CHECK was proposed. What will you do?

The Direct Answer & Architectural Decision

Choose an explicit serialization point for the room’s capacity decision: lock its owning row and check/update a maintained reservation quantity in one transaction, or use a suitable serializable design with whole-transaction retries. Ensure every reservation/cancellation path follows the same protocol and define temporary reservation expiry. Keep row-level checks for local value validity.

Key Trade-Offs & Follow-Up Traps

Locking a hot room limits concurrency, while serializable execution may abort transactions that need retrying. A CHECK that looks at unrelated rows is not a safe substitute for a concurrency protocol. If temporary overbooking is acceptable, model compensation and customer promises explicitly rather than accidentally weakening a hard capacity rule.
