Database Denormalization

🎯 The Hook & ELI5

A restaurant keeps the original orders in its order book, but the kitchen also has a board showing how many meals remain to cook. The board saves everyone from recounting every order. It is useful only if someone updates it correctly and can rebuild it when it becomes wrong. Denormalization is creating such convenient copies or precomputed answers on purpose.

Denormalization trades repeated read work for stored duplication or derived values. A customer summary, precomputed daily total or embedded product preview can reduce joins and aggregation. It also introduces a maintenance obligation: who owns the original fact, when copies update, how stale they may be, and how divergence is detected and repaired.

Not every repeated-looking field is redundant. An invoice’s agreed price and the catalog’s current price describe different facts. Decide whether a value is a historical snapshot, a current copy or a derived aggregate before choosing an update policy. The running example is a seller dashboard computed from authoritative order events.

🗺️ High-Level Big Picture

The dashboard is a view of orders, not a second authority for whether an order exists. Normal updates, rebuilds and reconciliation must agree on the same business meaning and event boundaries.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; SQL examples target PostgreSQL 18 unless explicitly labeled otherwise.

1. Measure the read work worth avoiding

A kitchen board helps when cooks repeatedly need the same count. First measure how often the expensive query runs, its latency, rows scanned, available indexes and aggregation cost. Define the target improvement and acceptable freshness lag.

Do not duplicate an entire business entity when a small summary answers the read. Keep scope bounded: a daily seller total, a limited latest-orders list, or a product preview with an explicit version. A one-off report may be better served by a direct indexed query.

2. Declare the source, meaning and consistency contract

Name the authoritative owner of every field. A dashboard total may be the sum of captured orders minus accepted refunds for a particular day/time zone; it is not necessarily the same as cash settled by a payment processor. Decide whether canceled or pending orders count.

Document whether the view is exact at commit, updated shortly afterward, or refreshed on a schedule. “Eventually consistent” without an observable lag, retry policy and repair owner is not an operating plan.

3. Choose synchronous or asynchronous maintenance

Within one database, a transaction can update source facts and a maintained aggregate together. This keeps their commit atomic but adds work, lock contention and coupling to every write. Ensure all writers use the same mechanism; manually edited rows can still break an application-only convention.

For an asynchronous projection, persist durable publication intent with the source transaction, then deliver changes to a worker. The worker must handle retries and failures without losing intent. An in-memory notification after commit alone has a crash window in which no notification is sent.

4. Design for duplicate and out-of-order delivery

For a delta such as “add one captured order,” processing twice is wrong. Keep the processed message identity and projection change in the same atomic boundary. For a full replacement snapshot carrying an entity version, reject an older replacement. These are different algorithms: discarding an old delta merely because a newer delta arrived can lose a legitimate change.

BEGIN projection transaction
  if event_id is already recorded: finish without reapplying
  validate event semantics and any required sequence/gap policy
  apply the order contribution or replace its versioned state
  record event_id as processed
COMMIT projection transaction
acknowledge delivery only after the commit

If the message affects an external system outside that transaction, give that side effect its own idempotency/outcome contract. A processed-ID table does not magically make a remote API call atomic.

5. Build, rebuild and reconcile from known boundaries

An old board can be reconstructed only from a known set of orders. Capture a consistent source snapshot and a corresponding change-stream/log position, build a new projection, then apply changes after that boundary without gaps or duplicates. The exact snapshot/CDC coordination is engine-specific; do not invent a universal timestamp procedure.

Compare meaningful totals, sampled records and per-partition checksums; counts alone can agree while values differ. Keep the old view until the new one catches up and passes checks. Replaying incomplete history cannot recover information that was never retained.

6. Budget updates, retention and deletion

If one product title is copied into a million order-like views, changing it creates a fan-out job. Decide whether the copies represent current catalog text or immutable sale-time text. Bound concurrency and monitor backlog rather than synchronously updating a million rows on one user request.

Propagate deletion/tombstones and prevent an old replay from resurrecting removed personal data. Review caches, read replicas and exported projections as well as the source. Maintain enough state for correctness while respecting the actual data-retention policy.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Fast view becomes an authority

Symptom: A lagging count allows an invalid stock purchase.

Root Cause: A summary designed for browsing was used to enforce a hard write invariant.

Fix/Prevention: Authorize against the inventory owner or maintain an explicit synchronous reservation protocol.

Retries inflate totals

Symptom: Revenue grows after a consumer restart.

Root Cause: A delta was reapplied without an atomic deduplication boundary.

Fix/Prevention: Persist the event identity and projection mutation together and test crash/retry positions.

Rebuild races live changes

Symptom: A new dashboard quietly misses recent orders.

Root Cause: Snapshot and change replay used unrelated boundaries.

Fix/Prevention: Use a documented snapshot/CDC handoff, catch up from its boundary, reconcile, then cut over.

What must accompany every denormalized value?

Its authoritative source, exact meaning, update mechanism, allowed freshness, failure/retry rules, and a way to rebuild or reconcile it.

Why might an invoice retain an old product price correctly?

The agreed sale price is an historical fact. It is not intended to remain equal to today’s catalog price, so changing it would destroy meaning rather than repair a stale copy.

Can an older delta be ignored like an older full-state replacement?

Not generally. Deltas represent separate contributions and may require deduplication and sequencing/gap handling. Version rejection fits a replacement snapshot only when its semantics justify it.

Why are matching row counts insufficient during rebuild verification?

Different rows or values can produce the same count. Verify a common snapshot/change boundary and compare semantic totals, records and checksums where appropriate.

Tricky & Most-Asked Interview Scenarios

A worker retries one captured-order event and doubles revenue. What boundary will you use?

The Scenario & Constraint

A dashboard consumes order-captured events with at-least-once delivery. A crash can occur after changing the total but before acknowledging the message. Each captured order must contribute once. What will you do?

The Direct Answer & Architectural Decision

Use a stable event/contribution identity and atomically write its processed record with the aggregate mutation. On replay, find the existing identity and avoid applying the contribution again. Acknowledge only after commit and exercise crash points on both sides. If refunds or corrections arrive later, model them as distinct operations or versioned order contributions rather than reusing capture identity ambiguously.

Key Trade-Offs & Follow-Up Traps

Deduplication needs retained state and an identity lifetime. Recomputing totals from authoritative orders is an alternative when traffic permits. Putting the dedupe marker in a different store leaves another crash window; a transactional marker does not protect an unrelated external side effect without a second contract.

Version 12 arrives before version 11. Should the consumer overwrite the product preview?

The Scenario & Constraint

A derived catalog preview receives complete product snapshots, and delivery can reorder them. Version 12 contains the newest title. What will you persist, and what changes if messages carry stock deltas instead?

The Direct Answer & Architectural Decision

Persist the last applied entity version and use a conditional atomic replacement so an older full snapshot cannot overwrite a newer one. Define handling for deletes and missing baseline state. If messages are stock deltas, do not discard a distinct earlier delta solely because a later one arrived: use contribution deduplication, ordered application or reconstruct from authoritative versioned state.

Key Trade-Offs & Follow-Up Traps

Conditional version updates add metadata and may expose gaps requiring repair. Ordered delivery can simplify one stream but is not a global transaction guarantee. Ask whether a version denotes full state, an entity-local event sequence or a broker offset; treating these as interchangeable creates silent loss.

The dashboard is allowed ten seconds of lag. Can checkout trust its inventory number?

The Scenario & Constraint

A seller view displays cached available quantity and serves millions of reads. Checkout must never accept an unavailable item. The cache says one unit remains during a lag spike. What will you do?

The Direct Answer & Architectural Decision

Use the view as a browse estimate and perform the authoritative conditional reservation against the inventory owner before confirming purchase. Return a clear unavailable/pending outcome if the owner rejects or cannot establish the reservation. Keep source/view propagation monitored, but do not try to turn a tolerated browse delay into a hidden purchase guarantee.

Key Trade-Offs & Follow-Up Traps

The authoritative check adds latency and can reduce checkout availability during owner failure. Stronger synchronous maintenance is possible within a suitable boundary, at write/coordination cost. If overselling is a deliberate business policy, document compensation and customer promises; do not accidentally introduce that policy through a stale projection.

One shared name is duplicated into a million documents. How will a rename work?

The Scenario & Constraint

Current seller names are embedded in every searchable product. A seller rename must eventually update all search results, while the request path has a short latency budget. What will you choose?

The Direct Answer & Architectural Decision

Keep the seller identity authoritative and either resolve a small current-name lookup at read time or run a durable, bounded versioned fan-out update. Return a known propagation state, track progress/lag, and reconcile missed documents. Ensure newer renames win over older background work. Distinguish this current-name copy from an immutable historical invoice label.

Key Trade-Offs & Follow-Up Traps

Read-time resolution costs another lookup; fan-out costs write amplification and operational tracking. If the fan-out frequency overwhelms its read benefit, remove the duplicated field or redesign the view boundary. A synchronous million-document update on the user request is not required simply because the view was originally convenient.

A backfill and live consumer overlap. How do you avoid missing or double-counting orders?

The Scenario & Constraint

A replacement dashboard is built while new orders continue. A naive snapshot plus “events since the job started” procedure yields inconsistent totals. How will you construct a trustworthy cutover?

The Direct Answer & Architectural Decision

Use an engine-supported consistent snapshot with a corresponding log/stream position, or another proven handoff protocol. Build the replacement projection and apply subsequent changes using idempotent/version-aware semantics. Verify lag reaches the cutover boundary and reconcile semantic totals and sampled records before routing reads to it. Keep the original available while discrepancies are investigated.

Key Trade-Offs & Follow-Up Traps

Coordinated snapshots may retain logs and consume resources; a short write pause is a simpler alternative if permitted. Merely comparing wall-clock timestamps can leave gaps under concurrency or clock differences. A replay cannot repair missing historical events without returning to a suitable authoritative snapshot.

An erased customer reappears after rebuilding a view. What was omitted?

The Scenario & Constraint

Personal data was removed from the source and live search view, but an older replay/backfill restored the name. Deletion must survive rebuilds. What will you change?

The Direct Answer & Architectural Decision

Define deletion as part of the projection contract, with a governed tombstone/version or erasure filtering mechanism that applies to live delivery and rebuild paths. Reconcile all derived copies and stop older snapshots/events from overriding the deletion decision. Coordinate how long deletion metadata and backups are retained with the actual policy rather than retaining personal payloads indefinitely as an easy fix.

Key Trade-Offs & Follow-Up Traps

Tombstone/erasure tracking has lifecycle and storage costs. Reading only current source state can simplify rebuilding, but stale event archives still need a policy. Removing one database row does not prove every cache/export is erased, and a historical business snapshot is not a blanket exemption from data-retention requirements.
