Composite Indexes

🎯 The Hook & ELI5

A school directory sorted by class, then surname, then first name can find one class and a range of surnames efficiently. It is a different directory from one sorted by surname first, even though both contain the same names. A composite index works like one ordered directory with several sorting keys, not several independent directories glued together.

A composite or multicolumn index contains multiple key attributes. For a B-tree, its lexicographic ordering compares the first key, then breaks ties with the next, and continues. That order affects which portion can be located efficiently and which result order is naturally available. Other index access methods have their own rules.

Our example retrieves one tenant’s recent orders in one status. PostgreSQL 18 is the concrete reference; its planner can sometimes use skip scan to exploit later columns even without an equality on an earlier column. Understand the ordinary useful prefix, but verify the actual engine/version and plan instead of claiming an index can never help outside a memorized rule.

🗺️ High-Level Big Picture

Read this as an ordering of tuples, not a rule that every query must constrain every key. Later predicates can still filter entries or support planner-specific strategies; whether they reduce scanned work must be measured.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; SQL examples target PostgreSQL 18 unless explicitly labeled otherwise.

1. Begin with equality, range and ordering requirements

Write the exact access pattern before listing columns: one tenant, one status, recent-first ordering and a bounded page. Consider which predicates are fixed, which vary, and whether results need ordering across several values of a key.

An equality on a leading attribute fixes one group, letting subsequent keys organize the remaining search. A range may span many groups for following attributes. These are useful physical intuitions, not replacements for the chosen engine’s plan.

2. Create one deliberately ordered example

The following self-contained PostgreSQL 18 example fixes tenant and status before ordering by a non-null timestamp and a unique tie-breaker. Choose the key order for this workload, then verify the plan on realistic data.

CREATE TABLE order_feed (
  order_id bigint PRIMARY KEY,
  tenant_id bigint NOT NULL,
  status text NOT NULL,
  created_at timestamptz NOT NULL,
  total_cents bigint NOT NULL
);
CREATE INDEX order_feed_page
  ON order_feed (tenant_id, status, created_at DESC, order_id DESC);
SELECT order_id, created_at, total_cents FROM order_feed
WHERE tenant_id = 42 AND status = 'open'
ORDER BY created_at DESC, order_id DESC LIMIT 50;

An index on status/tenant/time may also serve some all-equality searches, but different prefix-only queries and data distributions can favor another order. “Most selective first” alone does not specify which query families and sort orders must be supported.

3. Distinguish index conditions from scanned extent

A later column can be checked in an index without necessarily narrowing the initial B-tree interval as strongly as a leading equality. PostgreSQL 18 may use skip scan when repeated searches over a manageable set of earlier key values are cheaper.

Inspect actual rows examined, buffers and sort work. An index being mentioned in a plan does not prove its ordering is efficient. A missing leading predicate can be inexpensive for a few groups and expensive for millions; there is no universal row-count threshold.

4. Treat output order as a separate requirement

With tenant fixed but several statuses requested, a status-before-time index groups by status first. It does not automatically yield one global recent-first stream across all statuses. The planner may sort, merge suitable streams or prefer another index.

Sort direction and null positioning also matter. A B-tree can be scanned backward, but reversing all key directions is different from satisfying an arbitrary mixed-direction ordering. Match the complete ORDER BY and tie-breaking policy to the actual index definition.

5. Separate key columns from included payload

An included column can make a returned value available without being a search/sort key. In PostgreSQL, INCLUDE(total_cents) can cover that payload, but it does not turn total_cents into the leading range bound of the existing key order.

Covering entries are wider and visibility checks may still fetch heap pages. Test the read saving against write churn and cache pressure. Two single-column indexes combined with a bitmap path can filter well, yet generally do not preserve the composite index’s useful ordered stream.

6. Use a stable boundary for pagination

An offset page must skip all preceding results, and concurrent inserts can shift page positions. Keyset pagination starts after the last seen ordered tuple. With both timestamp and ID descending and non-null, the next page can add this predicate:

WHERE tenant_id = 42 AND status = 'open'
  AND (created_at, order_id) < ('2026-11-17 12:00:00+00', 9001)
ORDER BY created_at DESC, order_id DESC LIMIT 50;

This is a query fragment using the same SELECT/table as above. Keep tenant/status context in the cursor contract and use bound parameters. If ordering keys can change, define whether movement/duplicates across separate requests is acceptable; pagination alone does not provide a multi-request consistent snapshot.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Same columns, assumed same order

Symptom: A global timeline still sorts despite the new index.

Root Cause: An earlier varying key groups results before the requested timestamp.

Fix/Prevention: Match the complete query/order and verify whether a different leading order is warranted.

A slogan overrides evidence

Symptom: An index is removed because the leading predicate is absent.

Root Cause: An engine/version-specific access path was ignored.

Fix/Prevention: Inspect actual plans, including possible skip scan, without assuming every later-column query is efficient.

Pagination drops ties

Symptom: Orders with identical timestamps disappear between pages.

Root Cause: The cursor used a non-unique timestamp without an agreed tie-breaker.

Fix/Prevention: Order and seek on a stable timestamp/unique-ID tuple with consistent direction and null handling.

Why do composite column permutations matter?

A B-tree orders tuples lexicographically, so each permutation creates different leading groups and natural output orders even though it stores the same attributes.

Is a missing leading equality proof that PostgreSQL 18 cannot use the index?

No. Later filtering and possible skip scan may still help. Inspect the plan and actual work; usefulness depends on data distribution and query semantics.

Does INCLUDE make a payload column a search-order key?

No. It supplies stored payload for covering access. Search/sort ordering follows key columns, and heap visibility checks may still be required.

Why add a unique tie-breaker to a time cursor?

Several rows can share a timestamp. A complete stable order and matching tuple boundary avoid dropping or ambiguously repeating tied rows, subject to the declared mutation/snapshot policy.

Tricky & Most-Asked Interview Scenarios

The index works for one status but sorts heavily for all statuses. What will you change?

The Scenario & Constraint

An index on tenant/status/created_at supports a single-status feed. A new page needs all statuses for one tenant in global recent-first order, with a small LIMIT. What will you do?

The Direct Answer & Architectural Decision

Recognize that a varying status key groups results before time. Test a tenant/time/order-ID index for the global feed and compare its filtering/sort cost with the existing path. Keep or consolidate indexes based on both workloads and write budget. Do not claim the same key set guarantees the same useful output order.

Key Trade-Offs & Follow-Up Traps

A second index adds write/storage cost; reading a few status streams and merging is another possible plan. If status becomes a fixed equality again, the original index may be ideal. Verify actual plan behavior rather than forcing an index that still examines many groups.

A query filters only a later key. Is adding another index always necessary?

The Scenario & Constraint

A PostgreSQL 18 table has an index on region/customer_id. Region has only a few values, and customer lookup omits region. The plan uses the existing index efficiently. How will you evaluate the claimed leftmost-prefix violation?

The Direct Answer & Architectural Decision

Inspect whether the planner uses skip scan or another useful index path and measure work across representative regions. A small number of leading groups can make repeated searches practical. Keep the measured design if it meets targets and avoids unnecessary indexes; add a customer-leading index if real distribution, traffic or query shapes warrant it.

Key Trade-Offs & Follow-Up Traps

This is engine/version- and cost-dependent, not permission to ignore key order everywhere. Millions of leading groups can make the same approach expensive. An index scan that filters most entries is also possible, so check rows/buffers rather than celebrating the node name alone.

Two separate indexes filter correctly but the latest-fifty endpoint remains slow. Why?

The Scenario & Constraint

An endpoint filters by tenant and creation time and sorts newest first. Separate indexes produce a bitmap plan followed by a large sort. How will you test a different design?

The Direct Answer & Architectural Decision

Compare a tenant/created_at/order-ID composite B-tree that can locate the tenant’s ordered interval and stop after a bounded page. Measure scanned pages and sort elimination with actual parameters. Keep the query’s deterministic tie-breaker and compare full-workload costs, not only a synthetic single-tenant lookup.

Key Trade-Offs & Follow-Up Traps

Bitmap intersection can be appropriate for other predicates and is not inherently defective, but it generally does not preserve an ordered B-tree stream for this LIMIT. Another composite index costs maintenance. If the requested page returns most rows, a scan/sort may remain the best measured choice.

Tenant ID has low selectivity globally. Should it be last in every index?

The Scenario & Constraint

Every customer-facing query fixes a tenant, then filters and orders that tenant’s rows. An index review demands putting the globally most selective column first without examining queries. What will you decide?

The Direct Answer & Architectural Decision

Choose order using the query family, leading equality constraints, required ordering and actual tenant skew. A tenant-leading key can support tenant-scoped slices even when tenant is not globally most selective. Benchmark candidate orders for important prefix-only queries and any cross-tenant administrative workload, documenting which access paths are intended.

Key Trade-Offs & Follow-Up Traps

A customer-ID-leading index may be useful for a truly global customer lookup. If one tenant dominates traffic/data, its queries need separate measurement. Selectivity is an input to cost estimation, not a universal sorting algorithm for every composite index.

Price is included in a covering index, yet a price filter scans many entries. Why?

The Scenario & Constraint

An index has tenant/time keys and includes total_cents as payload. A new price-range query examines a large tenant history even though all requested columns are stored. What will you do?

The Direct Answer & Architectural Decision

Distinguish covering from efficient range navigation. The included price is available for evaluation but does not define the B-tree’s price-ordered interval. Test a key order that fits the price-range workload or accept a different path if that query is rare. Measure whether its additional index is worth write/cache overhead.

Key Trade-Offs & Follow-Up Traps

Promoting price to a key changes ordering and may harm the time feed; one index need not optimally serve both. A large price range may still favor a scan. Also inspect heap visibility work before assuming a covering plan has zero table access.

Pagination skips orders sharing the same creation timestamp. What should the cursor encode?

The Scenario & Constraint

A feed orders only by created_at and uses an exclusive timestamp boundary. Several orders share that timestamp. Readers need stable navigation within a tenant/status feed. What will you change?

The Direct Answer & Architectural Decision

Define a total order such as created_at DESC, order_id DESC, use matching composite keys, and put both last-seen values plus the filter context in the cursor. Seek after that tuple with a parameterized predicate. Explain how updated ordering keys or newly inserted rows are handled between requests rather than pretending independent pages share one snapshot.

Key Trade-Offs & Follow-Up Traps

A timestamp/ID cursor improves determinism but makes random page-number jumps less natural. Offset pagination can be adequate for small stable lists. If an export needs an exact frozen dataset, use a separate consistent-snapshot/export contract instead of relying on a normal interactive cursor.
