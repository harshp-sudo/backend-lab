Indexing Strategies

🎯 The Hook & ELI5

An index in a cookbook lets you find recipes mentioning lentils without reading every page. But if you want almost every recipe, repeatedly jumping from the index to the pages may be slower than reading the book in order. Every new recipe also means updating the index. Database indexes make selected reads cheaper by storing extra access paths, and every path has a maintenance cost.

An index is an auxiliary structure the query planner may use to locate or organize data. Its value depends on predicates, ordering, joins, result size and data distribution. An index existing does not require the database to use it, and an index scan is not automatically better than a sequential scan.

For a shop dashboard, assume a tenant needs its latest fifty open orders. We will reason from that query to an index, measure the resulting plan, and account for extra write and storage work. PostgreSQL 18 is the concrete engine here; access methods and planner decisions vary elsewhere.

🗺️ High-Level Big Picture

Measure the full workload, including updates and rollout. The feedback loop prevents “add an index” from becoming an untested prescription for every kind of slowness.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; SQL examples target PostgreSQL 18 unless explicitly labeled otherwise.

1. Measure a query, not a vague slow database

Capture the exact SQL, parameter distribution, frequency and latency target. Separate CPU time, disk work, lock waits and connection waiting. An index cannot remove a network timeout or a lock held by an unrelated long transaction.

Use representative row counts and skew. A tenant with half the rows behaves differently from a typical tenant, and a new empty test database does not exercise the same access path. Establish a baseline before adding several indexes at once.

2. Read estimates and actual work safely

EXPLAIN shows the chosen plan and estimates; EXPLAIN ANALYZE executes the statement and reports actual work. Add BUFFERS in PostgreSQL when examining I/O/cache behavior. Compare estimated and actual row counts, filtering, loop counts, sorts and heap fetches rather than only the top plan-node name.

Executing a modifying query just to inspect its plan can change real data. Use a safe representative environment or a carefully controlled transaction where appropriate, recognizing that sequences and external effects may not roll back. Outdated statistics or correlated predicates can mislead estimates even when an appropriate index exists.

3. Match the access method to the operation

A B-tree is an ordered directory useful for equality/range and compatible ordering. A GIN index is an inverted lookup structure often useful for supported containment/full-text operations; it is not a universal replacement for ordered retrieval. BRIN summarizes block ranges and can be compact when values correlate with physical location, at the cost of rechecking candidates.

Pick the actual operator class and data type semantics supported by the engine. A broad label such as “JSON index” is incomplete without the operators that the query uses. An index must match expressions, collation and relevant predicates sufficiently for the planner to use it.

4. Combine a bounded query with a narrow candidate

For a tenant’s latest open orders, a partial ordered B-tree can exclude closed history and support early termination. This is an illustrative schema/query, not a measured performance claim. The tenant and open-order distribution still determine whether the candidate is worthwhile.

CREATE TABLE app_order (
  order_id bigint PRIMARY KEY,
  tenant_id bigint NOT NULL,
  status text NOT NULL,
  created_at timestamptz NOT NULL
);
CREATE INDEX app_order_open_recent
  ON app_order (tenant_id, created_at DESC, order_id DESC)
  WHERE status = 'open';
EXPLAIN (ANALYZE, BUFFERS)
SELECT order_id, created_at FROM app_order
WHERE tenant_id = 42 AND status = 'open'
ORDER BY created_at DESC, order_id DESC LIMIT 50;

The extra order_id breaks timestamp ties for deterministic pagination. A generic query parameter for status may prevent proving the partial predicate at planning time. Check the actual prepared-plan behavior instead of assuming the index always applies.

5. Pay for what is stored and maintained

Every insert/delete and relevant update must maintain applicable indexes. Wide covering payloads consume space/cache and can make updates more expensive. A covering index stores enough requested columns, but PostgreSQL may still need heap visibility checks; an index-only plan does not promise zero heap access on a write-heavy table.

Review redundant candidates across the real workload before removal. An apparently unused index might support a rare critical report or a uniqueness constraint. Measure over a representative interval and understand resets in monitoring counters.

6. Roll out and revisit with a failure plan

A regular index build can block writers; PostgreSQL CREATE INDEX CONCURRENTLY reduces that kind of blocking but takes extra work and has restrictions, waits and failure states. It cannot run inside an ordinary transaction block. Monitor duration, disk growth, workload impact and index validity.

If a concurrent build fails, inspect and clean up or rebuild the invalid index deliberately. Recheck performance after data growth and distribution changes. An index is an operated piece of data, not a one-time annotation on the schema.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Index count replaces diagnosis

Symptom: Latency stays high after several new indexes.

Root Cause: The bottleneck is locking, result volume or a different predicate than expected.

Fix/Prevention: Capture the real query/wait evidence and compare candidate plans under representative data.

Sequential scan called a bug

Symptom: A report retrieving most rows gets slower after forcing an index.

Root Cause: Many random lookups cost more than reading the table sequentially.

Fix/Prevention: Compare actual work and selectivity; allow the planner a justified scan rather than ranking node names.

Online build treated as free

Symptom: A deployment leaves an invalid index and consumes extra disk.

Root Cause: Concurrent creation restrictions and failure cleanup were ignored.

Fix/Prevention: Monitor validity, resource use and waits, and provide an explicit remediation/rollback procedure.

Summarize this in your own words: An index is a measured access-path investment. Explain the predicate/order it serves, the work it removes, the writes it adds and how its creation and failure states are operated. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

What does every additional index cost?

Storage, cache footprint, write maintenance and operating/rollout work. The benefit must be measured against the complete workload.

Why might a sequential scan be the correct plan?

When much of the table is needed, sequential reading can cost less than using an index and performing many table fetches. Data distribution and estimates matter.

What distinction matters before running EXPLAIN ANALYZE?

It executes the statement. A modifying or externally effectful statement is not a harmless plan-only observation.

What must a query establish to use a partial index?

Its conditions must imply the index predicate in a way the planner can recognize. Prepared/generic parameters and different expressions can prevent that proof.

Tricky & Most-Asked Interview Scenarios

A latest-orders page scans millions of rows for fifty results. What evidence and index will you choose?

The Scenario & Constraint

The dashboard filters by tenant and open status, orders by creation time, and requests fifty rows. Closed history dominates storage. What will you investigate and change?

The Direct Answer & Architectural Decision

Capture the exact plan, parameter skew, filtering and sort work. Test a narrow tenant/time/order-ID B-tree, optionally partial on open status when its predicate matches the actual query. Measure representative hot and ordinary tenants and include deterministic tie-breaking. Verify that fewer rows/pages are examined rather than assuming the CREATE INDEX statement itself proves success.

Key Trade-Offs & Follow-Up Traps

The index adds maintenance and may not help a tenant whose query selects most data. A broader index is more reusable but larger; a partial one is cheaper only for matching workloads. If most time is connection wait or lock contention, fix that cause instead of adding an unrelated access path.

A sequential scan remains after an index is added. Is the planner broken?

The Scenario & Constraint

A nightly export selects 80% of a large table and developers want to force an index used by a small selective API query. How will you assess the export?

The Direct Answer & Architectural Decision

Compare actual elapsed time, buffers, result volume and access patterns for the export rather than borrowing the API’s desired plan. A sequential scan may be efficient for reading most rows. Keep statistics current and investigate transfer/serialization and batching as well as storage reads. Optimize the query’s real objective without treating an index scan as the acceptance criterion.

Key Trade-Offs & Follow-Up Traps

A more selective predicate or a specialized projection can change the answer, but hints/forced plans can become brittle as distributions change. If estimates are wildly wrong, address statistics and correlations before concluding every scan is appropriate. The same table can correctly use different plans for different workloads.

Writes slowed after twelve “helpful” indexes were added. Which ones can go?

The Scenario & Constraint

Read latency improved slightly, but insert latency and storage rose sharply. Some index counters show little use. What will you remove and how?

The Direct Answer & Architectural Decision

Inventory each index’s query and integrity purpose, compare overlapping key prefixes/payloads, and measure usage over a representative window. Preserve uniqueness/primary-key support and rare business-critical paths unless a replacement exists. Remove redundant candidates through a controlled change and compare both read and write behavior, with a recreation plan if a critical workload regresses.

Key Trade-Offs & Follow-Up Traps

Dropping everything with a zero counter is unsafe after a statistics reset or before a monthly job. Consolidating into one huge covering index may retain excessive write/cache cost. If writes saturate one hot key, index cleanup can help overhead but does not eliminate the underlying serialization point.

A partial index works with a literal but not the prepared application query. What changed?

The Scenario & Constraint

An index includes only status = open rows. The application uses a parameter for status and a generic plan, while a hand-written literal query uses the index. What will you do?

The Direct Answer & Architectural Decision

Inspect the actual prepared statement and plan selection. The generic planner may not be able to prove that an unknown parameter implies the partial predicate. Consider a distinct query for the fixed open-order endpoint, a full index that matches all parameter values, or an appropriately measured plan/configuration approach. Preserve parameter safety; do not interpolate untrusted SQL to chase one plan.

Key Trade-Offs & Follow-Up Traps

A dedicated literal predicate is appropriate only when that endpoint really has fixed semantics. A full index costs more storage and updates. If the distribution of statuses changes or the prepared plan becomes custom, remeasure rather than declaring partial indexes universally incompatible with parameters.

An index-only plan still fetches table pages. Should every selected column be added again?

The Scenario & Constraint

A write-heavy table has a covering index, yet the plan reports many heap fetches. The query is correct but slower than expected. What will you investigate?

The Direct Answer & Architectural Decision

Check whether the index supplies the needed values and inspect PostgreSQL visibility-map/heap visibility work, table churn and vacuum behavior. Covering data alone does not establish that every matching heap page is all-visible. Measure maintenance and workload conditions before expanding the index, and compare a narrow index plus heap access against the larger covering version.

Key Trade-Offs & Follow-Up Traps

Wider payloads increase write cost and can reduce cache efficiency without fixing visibility checks. A more stable read model is an alternative if freshness permits. Do not promise zero table access merely because a plan node is named Index Only Scan.

An index build must preserve writes and fails halfway. How will you operate the rollout?

The Scenario & Constraint

A busy PostgreSQL table needs a new access path. A migration framework wraps statements in transactions, and the first concurrent build failed. What will you change before retrying?

The Direct Answer & Architectural Decision

Use a deployment step that supports CREATE INDEX CONCURRENTLY outside an ordinary transaction block. Inspect the failed index’s validity/state, clean up or rebuild it using the documented procedure, and check long-running transactions, disk headroom and load. Monitor progress and actual query benefit after success, keeping an abort/remediation path for excessive impact.

Key Trade-Offs & Follow-Up Traps

Concurrent does not mean instantaneous or lock-free. A regular build in a maintenance window may be simpler if writers may pause. Avoid blindly retrying the same invalid named object or assuming migration-framework atomic rollback covers this operation.
