Sharding

🎯 The Hook & ELI5

A growing library can open several branches and decide which branch owns each set of books. Readers need a directory, moving books needs coordination, and a very popular book can still overwhelm its one branch. Sharding divides data ownership among database nodes. It is more than putting labels on shelves, and it does not mean every branch holds a complete copy.

A shard owns a subset of a dataset. A routing rule maps a shard key, range or directory entry to that owner. Different shards can provide additional storage and work capacity, while replicas within a shard provide copies for availability/read scaling. These are independent dimensions of the design.

Consider a multi-tenant order service. Keeping a tenant’s orders together makes many requests local, but a very large tenant may become a hotspot. Every design must explain routing, skew, transactions, rebalancing, failure and backup semantics. MongoDB is a concrete source for sharded-cluster behavior here; generic patterns are labeled as design choices rather than promises of every product.

🗺️ High-Level Big Picture

Routing arrows distribute requests to owners; replica arrows copy only that shard’s data. Moving ownership must prevent old and new destinations from both accepting conflicting authoritative writes.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; SQL examples target PostgreSQL 18 unless explicitly labeled otherwise.

1. Prove a distributed ownership need

Measure whether the current limit is storage, write throughput, query shape or one hot record. Index/query fixes, more suitable capacity or an analytical read model may be cheaper than introducing distributed ownership. A large row count alone is not a shard-key argument.

Write down operations that must remain atomic and requests that can tolerate partial or stale results. Sharding complicates those boundaries. Define availability and recovery targets per shard and for aggregate queries before spreading data across more machines.

2. Select a shard key from routing and skew

A useful key helps locate the data required by common operations while spreading the limiting work. Evaluate cardinality, frequency/skew, monotonically increasing values and actual query predicates. High cardinality does not guarantee balanced traffic: one value may still dominate.

Tenant affinity can keep a transaction local, but a single large tenant may need a finer subdivision. A time-range key helps time-local queries while concentrating new writes at the latest range. MongoDB’s supported key/refinement/resharding rules are product/version-specific; inspect them before relying on a change being easy.

3. Compare routing schemes and metadata ownership

Hashing can spread many keys but sacrifices natural range locality; a simple modulo change can remap many keys when shard count changes. Range routing supports ordered locality but needs split/hot-range management. A directory can move specific tenants independently but makes metadata consistency and availability important.

Consistent hashing can reduce movement under membership changes for suitable designs, but it does not split a single hot key. Treat stale routing metadata as an expected condition with documented refresh/retry behavior and ownership epochs/fencing, not an excuse to send writes to arbitrary nodes.

4. Keep the common unit of work local where possible

Place records that frequently change atomically in a compatible owner boundary. A tenant-local order and its lines can be simpler than placing each line on an unrelated shard. If a rule spans owners, inspect supported distributed transactions and their failure/latency cost, or redesign the workflow with reservations/compensation and clear intermediate states.

Global unique constraints and joins also need explicit support. An index local to one shard is not proof of cluster-wide uniqueness. A globally generated identifier may avoid accidental collisions probabilistically while still not enforcing a global natural-key rule against bad writers.

5. Move data with one authoritative cutover contract

A resharding procedure must copy a baseline, capture concurrent changes, catch up, verify and transfer ownership at a known boundary. Use the engine’s supported mechanism when available. If building a custom protocol, define routing versions, write fencing, retry identity and treatment of requests already in flight.

Do not just dual-write independently and switch DNS after counts match. Compare meaningful data, handle deletes and test interrupted movement. Keep a clear authoritative owner and rollback/forward-recovery policy throughout; moving an already-active dataset is a protocol, not a bulk copy command.

6. Operate queries, backups and failures across owners

A request with the shard key can often target one owner; a global report may fan out to many shards. Bound fan-out and merge work, propagate deadlines, and distinguish a complete answer from a partial result when one shard is unavailable.

Monitor per-shard load/lag/capacity because averages hide the hottest owner. A cluster backup needs an engine-supported consistent recovery boundary or an explicitly weaker per-shard contract. Restoring each shard to an unrelated point can violate cross-shard business relationships even when every individual backup is readable.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

One hot key survives more shards

Symptom: The largest tenant remains overloaded after adding nodes.

Root Cause: All its work still maps to one indivisible key.

Fix/Prevention: Use a finer workload-compatible key, isolate the tenant or bound that tenant’s concurrency; account for lost locality.

Local uniqueness called global

Symptom: The same business identifier is accepted on different shards.

Root Cause: Independent local indexes lack a shared enforcement boundary.

Fix/Prevention: Use supported shard-key-aware constraints or a deliberately coordinated global identity/ownership design.

Copy mistaken for migration

Symptom: Writes disappear or diverge during cutover.

Root Cause: Concurrent changes and ownership fencing were not included.

Fix/Prevention: Use a supported resharding protocol or prove snapshot/catch-up/ownership transfer and failure recovery explicitly.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Sharding distributes ownership, so its success depends on a workload-aware key and a complete routing, coordination, movement and recovery protocol—not merely on adding nodes. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

What distinguishes a shard from a replica?

A shard owns a subset of data; a replica copies an owner’s data. A sharded deployment may replicate each shard, and neither concept substitutes for the other.

Why is high cardinality insufficient for a good shard key?

A few values or ranges may receive most operations. Distribution of work and query targeting matter in addition to the number of distinct values.

What does making a transaction cross-shard change?

It can require distributed coordination or an explicitly different workflow with partial states and compensation. A local transaction API alone does not cover independent owners.

What must a live ownership move preserve?

A coherent snapshot/change boundary, complete catch-up, correct routing/fencing, duplicate-safe retries, deletion semantics, verification and a known recovery owner.

Tricky & Most-Asked Interview Scenarios

One tenant generates half the writes. Why did tenant-based sharding not balance the cluster?

The Scenario & Constraint

A directory puts each tenant on one shard. One tenant now dominates writes while several shards are idle. Its operations mostly touch independent projects. What will you change?

The Direct Answer & Architectural Decision

Measure that tenant’s actual key/project distribution and evaluate tenant-plus-project or another supported finer ownership boundary. Alternatively isolate the tenant on dedicated capacity and bound its concurrency. Update routing, query and transaction assumptions explicitly; use a supported migration/resharding procedure to move existing data without losing ownership discipline.

Key Trade-Offs & Follow-Up Traps

Finer subdivision spreads independent work but turns tenant-wide reports or invariants into cross-shard work. More replicas do not distribute the primary’s write ownership. If the load is one indivisible record/invariant, no key rearrangement makes that same serialized operation arbitrarily parallel.

Every new insert targets the newest range. Hash the time key?

The Scenario & Constraint

A time-range sharded event store directs all current writes to one owner. Most point reads know an event ID, while rare analytics scans time ranges. What will you choose?

The Direct Answer & Architectural Decision

Compare a hashed independent identifier or a time-plus-bucket scheme with the actual point/range workload, and use supported key/resharding capabilities. Measure distribution and routing impact before committing. Preserve the timestamp as a queryable fact even if it is no longer the sole ownership key. Plan how historical data and live changes reach the new owner boundary.

Key Trade-Offs & Follow-Up Traps

Hashing may spread writes but makes time-only queries fan out. Time buckets plus subkeys add routing and aggregation complexity. If chronological scans are the dominant requirement, managed range splitting or another ingestion design may be preferable; the correct key follows both read and write contracts.

Two shards accept the same email. Does adding local unique indexes fix it?

The Scenario & Constraint

Users are distributed by user ID, but the business requires a globally unique normalized login name. Each shard independently enforces local uniqueness. How will you guarantee the business rule?

The Direct Answer & Architectural Decision

Choose a supported global constraint compatible with the shard key, or make login-name ownership explicit in one coordinated authority/partitioning scheme and coordinate account creation with it. Handle reservations, retries and abandoned attempts deliberately. Validate existing duplicates and define the normalization/reuse policy before claiming the rule is enforced.

Key Trade-Offs & Follow-Up Traps

A central registry adds coordination and can bottleneck; routing by login name affects other access patterns and renames. Random user IDs do not enforce login-name uniqueness. An independent “check every shard then insert” sequence races unless the ownership protocol serializes that decision.

A transfer updates accounts on two owners. Is a local transaction sufficient?

The Scenario & Constraint

Account records were sharded independently. A transfer must not be silently treated as complete after only one side succeeds. What transaction/workflow boundary will you design?

The Direct Answer & Architectural Decision

If the chosen database supports an appropriate distributed transaction within the required failure/performance envelope, use and test that documented boundary. Otherwise redesign around an authoritative ledger/reservation workflow with explicit pending, commit and compensation/reconciliation states. Keep operation identity stable and present completion only after the chosen business protocol establishes it.

Key Trade-Offs & Follow-Up Traps

Distributed transactions add coordination and can reduce availability/throughput during failures. A saga changes the business contract and compensation may not be instantaneous or perfectly reversible. Co-locating frequently coordinated data is another option, but it cannot place every possible account pair together simultaneously.

Data counts match after copying, but writes are still arriving. When can routing switch?

The Scenario & Constraint

A tenant is being moved between shard owners during live traffic. A naive copy job reaches the same row count as the source. How will you decide cutover and handle in-flight retries?

The Direct Answer & Architectural Decision

Use a supported ownership-migration mechanism or a proven snapshot/catch-up protocol. Verify a known change boundary, including updates/deletes, and fence the old owner as the routing epoch changes. Ensure stale routers refresh safely and retries retain operation identity. Compare semantic values, not just counts, and retain a documented recovery direction if cutover is interrupted.

Key Trade-Offs & Follow-Up Traps

Dual-writing can be part of a carefully defined protocol but independent best-effort writes are not enough. A short write pause may simplify the transition if allowed. Switching DNS alone does not resolve cached routes, connections or conflicting old writes.

One shard is down during a global latest-orders query. Can the API return an exact list?

The Scenario & Constraint

A report merges recent orders across all shards with a strict deadline. One owner is unreachable. Product asks the API to return the available results as if they were complete. What will you do?

The Direct Answer & Architectural Decision

Define the report contract: fail/pending when a complete result is required, or return explicitly partial results with coverage/freshness metadata if permitted. For normal execution, use compatible per-shard ordering and bounded merge logic, with deterministic tie-breaking and a declared snapshot/freshness policy. Monitor the missing owner instead of silently treating it as empty.

Key Trade-Offs & Follow-Up Traps

Fan-out increases tail latency and coordination work; a derived global read model can help at propagation/rebuild cost. Fetching ordered slices from shards does not by itself establish one globally consistent transaction snapshot. Never label missing data as zero or globally exact without the required evidence.
