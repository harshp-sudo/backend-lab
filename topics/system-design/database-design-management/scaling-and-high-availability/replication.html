Replication

🎯 The Hook & ELI5

A shop keeps a second notebook of its sales so another clerk can keep working if the first notebook is lost. If the copyist writes a little later, the second notebook may be behind. If the first clerk waits for a durable copy before handing over a receipt, every sale can take longer. Replication is making and maintaining copies, with an explicit rule about when a copy is good enough.

Replication copies database state or changes to other nodes. It can support recovery, availability and appropriate read workloads. It does not automatically provide zero data loss, instant reads everywhere or extra write ownership capacity. Each guarantee depends on the replication mechanism, acknowledgment policy, read routing and failure envelope.

Our running example is a primary accepting orders and a standby used for selected reads/recovery. Recovery point objective (RPO) describes tolerated loss of recent data; recovery time objective (RTO) describes tolerated restoration time. Neither objective is established merely by drawing a replica in an architecture diagram.

🗺️ High-Level Big Picture

This timeline uses a durable-flush acknowledgment, which can precede replay. A remote-apply policy waits for replay before acknowledging, while an asynchronous policy need not wait for a standby acknowledgment before replying. Acknowledgment to one standby does not prove every other reader has replayed the change.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; SQL examples target PostgreSQL 18 unless explicitly labeled otherwise.

1. Identify what is copied and what can fail

Physical replication reproduces storage/log-level changes in an engine-specific format; logical replication sends a more logical representation of selected changes. Their compatibility, object coverage and operational constraints differ. A copy of selected tables is not necessarily a full replacement for the original database.

State the failures being covered: process crash, host loss, availability-zone failure, regional loss, operator error or malicious deletion. Copies in the same failure domain cannot protect against losing that entire domain. Replication also repeats legitimate but destructive application operations.

2. Define the commit acknowledgment point

Asynchronous replication lets the primary respond before a replica has the change, leaving a possible loss/staleness window if the owner fails. Synchronous policies wait for a specified replication milestone and required participants, increasing latency and potentially reducing write availability when those participants cannot respond.

PostgreSQL distinguishes local logging, remote write, remote durable flush and remote apply behavior through configuration. Setting synchronous_commit alone does not configure which standbys must acknowledge. Durability also relies on suitable fsync/storage behavior and the actual topology. Use the documented configuration instead of the label “sync” alone.

3. Separate received, durable and query-visible progress

A replica can receive log bytes before safely persisting them, and persist them before replay makes changes visible to a new query. Monitoring must distinguish those positions. A successful primary commit therefore does not automatically mean a random follower can answer a read-your-write request.

Route correctness-sensitive reads to an appropriate authority or verify the chosen replica has reached the required position under a supported protocol. Long-running snapshots can still intentionally see an older state even after replay advances. Specify what “current” means at the read boundary.

4. Measure lag and resource coupling

Measure bytes/positions behind, replay/receive health, backlog trend and user-visible freshness. Timestamp-based lag can look large on an idle system even with no meaningful work outstanding, so interpret it with actual log progress.

Slow replica I/O, long reads or overloaded apply work can make lag grow. Retention mechanisms such as replication slots can retain WAL needed by a lagging consumer; retained logs can fill primary storage. Alert on the retained volume and time-to-exhaustion, not just whether a replication connection exists.

5. Test recovery against the promised objectives

Choose eligible recovery targets based on their durable/replay progress and the required loss policy. A failure detector cannot infer every remote state from a timeout; promotion also needs a single-writer/fencing protocol described in the topology lesson.

Test a write acknowledged just before failure and confirm which copy retains it. Measure actual application restoration, including routing, stale connections, credentials and warmup. A server becoming healthy is not the same as the application completing requests under its data contract.

6. Keep independent backups and control replica reads

A replica is a live copy, so a bad DELETE or corrupted business update can reach it rapidly. Maintain independent backup/archive recovery with tested restore and point-in-time procedures appropriate to the engine. Ensure retained logs and base backups form a usable recovery chain.

Replicas can isolate some reads but may compete with replay and be stale. Protect the primary’s write authority and avoid assuming read scaling means write scaling. For logical replication, verify selected objects, schema-change compatibility and key requirements rather than treating every subscriber as a transparent physical standby.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Copy mistaken for backup

Symptom: An accidental deletion removes data from primary and standby.

Root Cause: Live replication faithfully copied the bad operation.

Fix/Prevention: Maintain independent retained backups/log archives and practice restoring to a verified point.

One acknowledgment mistaken for all readers

Symptom: A new order is missing on another follower.

Root Cause: Replication policy waited for one milestone/participant but reads used a different state.

Fix/Prevention: Define read-your-write routing or progress validation for the actual reader.

Replication retention fills the primary

Symptom: Primary disk runs out while a subscriber is disconnected.

Root Cause: Required WAL is retained without an operational bound/alert.

Fix/Prevention: Monitor retained bytes and consumer health, define safe limits and plan reinitialization when needed.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Replication provides the guarantees you configure and test at specific acknowledgment, visibility and failure boundaries. Keep read freshness, write ownership and historical recovery separate. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Why distinguish receipt, durable flush and replay?

They are different milestones. Data can have arrived without being crash-durable or query-visible; the configured commit/read contract chooses which milestone matters.

What do RPO and RTO ask?

How much recent data loss is tolerable, and how long recovery may take. A chosen replica topology must be tested against both rather than assumed to meet them.

Do additional single-primary read replicas add independent write capacity?

They copy the primary’s writes and may serve eligible reads. They do not create additional authoritative writers for the same primary-owned workload.

Why keep historical backups if replicas are healthy?

Replicas can copy errors and deletions, share failure domains and fail to retain a usable historical recovery point. Backup/restore solves a separate need.

Tricky & Most-Asked Interview Scenarios

The API confirms an order, but a replica read says it does not exist. How will you fix the user contract?

The Scenario & Constraint

Writes go to a primary and order-detail reads are round-robin among asynchronous replicas. Users immediately reload after checkout. What will you change without promising every follower is current?

The Direct Answer & Architectural Decision

Route the dependent read to an appropriate authoritative primary, or use a supported session/progress mechanism that verifies the selected follower has applied the required change. Keep ordinary browse reads on replicas when their freshness contract permits. Present an explicit pending result if the required read cannot yet be established, and monitor replay lag.

Key Trade-Offs & Follow-Up Traps

Primary reads add owner load and may have higher regional latency. Waiting for one synchronous standby does not update every follower, and a snapshot opened earlier can remain old. If strict current reads are not required, the product may instead expose a bounded delayed-view contract honestly.

An acknowledged order disappears after failover. Which guarantee was missing?

The Scenario & Constraint

The primary acknowledged before its asynchronous standby received the last changes. The primary host was lost and the standby was promoted. The business now requires a stricter loss budget. What will you do?

The Direct Answer & Architectural Decision

Measure the previous acknowledgment/failure envelope and choose a supported durable replication policy that covers the required failures. Configure eligible synchronous participants and commit/storage settings, then test acknowledged writes at crash boundaries. Document what failures remain uncovered and how the application handles commit responses that were lost or delayed.

Key Trade-Offs & Follow-Up Traps

Waiting for remote durability adds latency and may block/reject writes when required replicas are unavailable. A local durable commit alone cannot preserve data if its only host/storage is permanently lost. Promoting whichever replica responds fastest is not a substitute for an eligibility and data-loss policy.

Commit latency jumps when a remote standby slows. How will you trade durability and availability?

The Scenario & Constraint

A write policy waits for a geographically distant durable copy. Network degradation pushes checkout beyond its latency budget. Product asks to disable waiting immediately while keeping the same zero-loss claim. What will you do?

The Direct Answer & Architectural Decision

Show the coupling between the required acknowledgment and the remote path. Investigate network/apply/storage waits, and consider a topology with a suitable lower-latency durable participant plus asynchronous disaster-recovery copies if that meets the actual failure requirement. Any emergency weakening of acknowledgment must explicitly revise the loss contract and be monitored and reversed deliberately.

Key Trade-Offs & Follow-Up Traps

A nearby copy may not cover regional loss. Disabling synchronous waiting can improve availability/latency but cannot honestly preserve the same guarantee. If the strict envelope is mandatory, shed or defer writes rather than silently acknowledging a weaker promise.

A stopped consumer fills primary storage. Delete all retained logs?

The Scenario & Constraint

A replica/subscriber is offline while its retention mechanism keeps required WAL. Disk headroom is shrinking. What will you do to protect production and preserve a recovery plan?

The Direct Answer & Architectural Decision

Identify the retaining consumer, backlog volume, generation rate and time-to-exhaustion. Restore consumption if safe, add controlled headroom or use the documented retention/reinitialization procedure. If required history must be discarded, explicitly mark that consumer for a new base/snapshot rather than pretending it can resume from missing logs. Establish alerts and a bounded policy afterward.

Key Trade-Offs & Follow-Up Traps

Retaining everything protects continuity only until it exhausts the owner. Removing retention can make a replica unusable without reinitialization. A connected process may still be far behind, so monitor positions and retained bytes as well as health pings.

A bad DELETE reaches every replica. Where will recovery come from?

The Scenario & Constraint

An operator deletes valid historical orders and the live standbys faithfully replay the transaction. The deletion is detected an hour later. What recovery options will you evaluate?

The Direct Answer & Architectural Decision

Use independently retained base backups and log archives to restore an appropriate point in an isolated environment, validate the intended data and plan controlled reconciliation/restoration. Protect current legitimate writes and dependent systems while correcting the mistake. Test the restore chain and available recovery points; a healthy live replica is not a historical undo button.

Key Trade-Offs & Follow-Up Traps

Point-in-time restore can take substantial time and may rewind unrelated valid work if applied wholesale. Targeted reconciliation may be safer but needs careful identity/dependency checks. If retention lacks the required history, do not invent a recovery guarantee; document the actual loss and fix the backup policy.

Five read replicas do not improve order-write throughput. Why?

The Scenario & Constraint

A single-primary database is saturated on write logging and index maintenance. The team adds followers and expects linear write scaling. What will you measure and choose instead?

The Direct Answer & Architectural Decision

Confirm the limiting write path and distinguish read offload from authoritative write ownership. Reduce unnecessary index/write work, batch appropriate operations, tune/provision capacity or redesign hot invariants. If independent data ownership truly exceeds one owner’s capacity, evaluate sharding with its transaction/routing costs. Keep replicas for the recovery/read objectives they actually serve.

Key Trade-Offs & Follow-Up Traps

Followers still consume and apply the primary’s writes and can add replication overhead. A multi-writer system is a different coordination/conflict model, not a configuration slogan. If reads were blocking useful primary resources, offloading them can help indirectly, but that is a measured resource effect rather than additional independent primary writers.
