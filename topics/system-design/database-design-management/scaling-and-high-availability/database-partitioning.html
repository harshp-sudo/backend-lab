Database Partitioning

🎯 The Hook & ELI5

A library can put this year’s newspapers in monthly boxes. A reader asking for November can open one box, and staff can retire an old box without removing papers one by one. The boxes still belong to the same library. Table partitioning similarly divides one logical table into manageable pieces; it does not automatically create more database servers.

Partitioning is a broad way of dividing data. This lesson focuses on PostgreSQL 18 declarative table partitioning: a logical parent routes rows into child tables according to a partition key. Range, list and hash schemes organize different access/lifecycle patterns. Sharding is the separate distributed-ownership decision covered in its own lesson.

Partitioning is useful when it makes important operations cheaper: pruning irrelevant data, managing retention, or maintaining a bounded slice. It adds planning, indexing and operational complexity. A single database can still run out of CPU, I/O or connection capacity even if its largest table has many partitions.

🗺️ High-Level Big Picture

Pruning chooses which boxes need opening; indexes choose how to search inside an opened box. Neither operation by itself distributes writes across independent database owners.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; SQL examples target PostgreSQL 18 unless explicitly labeled otherwise.

1. Choose a key from access and lifecycle

Monthly boxes help queries and retention only when date is relevant. For time-bounded event reads and time-based expiry, recorded_at can be a useful range key. List partitioning can separate a small controlled set of categories; hash partitioning spreads rows among a fixed set of hash buckets.

Consider late arrivals, changing key values, skew and all important queries. Partitioning by date does not make a tenant-only history query touch just one month. The newest partition may still receive nearly every write.

2. Define explicit bounds and supported uniqueness

This toy PostgreSQL 18 schema deliberately includes recorded_at in its primary key to satisfy the partitioned uniqueness requirement. It guarantees uniqueness of the pair, not event_id alone across every month. All bounds below use UTC.

CREATE TABLE event_log (
  event_id bigint NOT NULL,
  tenant_id bigint NOT NULL,
  recorded_at timestamptz NOT NULL,
  payload jsonb NOT NULL,
  PRIMARY KEY (event_id, recorded_at)
) PARTITION BY RANGE (recorded_at);
CREATE TABLE event_log_2026_11 PARTITION OF event_log
  FOR VALUES FROM ('2026-11-01 00:00:00+00')
             TO ('2026-12-01 00:00:00+00');
CREATE TABLE event_log_2026_12 PARTITION OF event_log
  FOR VALUES FROM ('2026-12-01 00:00:00+00')
             TO ('2027-01-01 00:00:00+00');
CREATE INDEX event_log_tenant_time
  ON event_log (tenant_id, recorded_at);

Upper range bounds are exclusive, so the first instant of December belongs in December. This miniature example covers only two months; production lifecycle automation must create future partitions before data arrives and implement an explicit policy for uncovered timestamps.

3. Verify pruning with the actual predicate

A request bounded by recorded_at >= the start and recorded_at < the end can allow PostgreSQL to exclude unrelated partitions. Inspect EXPLAIN and actual execution rather than assuming a partitioned parent always means only one child is read.

Wrapping the key in a different expression can prevent useful inference. Prepared parameters can support execution-time pruning in appropriate plans, so do not claim every parameter defeats pruning. Match types, time zones and operators to the real partition definition.

4. Index the work remaining inside each partition

After pruning to November, a query for one tenant may still scan that whole month without an appropriate access path. An index declared on the parent represents corresponding child indexes; the parent index is not one independent global index covering every partition.

Track statistics and data distributions per relevant table/partition, and compare plans for recent and historical ranges. A good partition key does not replace a good query/index design, and too many tiny partitions can add overhead without a useful lifecycle benefit.

5. Maintain partitions as an operated lifecycle

Create future partitions ahead of time, monitor boundary coverage and handle late data deliberately. A default partition can accept otherwise unmatched rows, but it can hide missing lifecycle automation and complicate later attach/validation work.

Attach/detach and index-building operations have engine-specific lock and validation behavior. Test the maintenance procedure with long-running transactions and realistic data. “Metadata operation” is not a promise that no lock is needed or that every concurrent variant can run inside a transaction block.

6. Apply retention without confusing it with disaster recovery

Dropping an eligible old partition can avoid deleting a huge number of rows individually. First verify business retention, legal holds, references, backups and archive readability. Detaching is useful when data must be exported or retained elsewhere before final removal.

Record which bounds were removed, validate counts/semantic samples and monitor consumers that still query old ranges. A deletion policy does not erase older backups automatically, and an archived partition is not a complete database recovery plan without schema, indexes, ownership and restore verification.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Boxes confused with more libraries

Symptom: Write throughput is still bounded by one server.

Root Cause: Local partitions were expected to provide distributed node capacity.

Fix/Prevention: Measure the shared bottleneck; use sharding or another capacity change only if its added ownership complexity is justified.

Calendar automation fails

Symptom: New-month inserts are rejected or pile into a default partition.

Root Cause: Future ranges were not created or monitored.

Fix/Prevention: Create ahead, alert on uncovered/default traffic and define late/out-of-range handling.

Uniqueness quietly weakened

Symptom: The same event ID appears in different months.

Root Cause: A composite key was assumed to enforce event_id alone globally.

Fix/Prevention: Define the intended identity and use an appropriate registry, key design or different partition strategy when a global invariant is required.

Summarize this in your own words: Partition around useful access and lifecycle boundaries. What different jobs do pruning and indexing perform?

Pruning excludes irrelevant partitions; an index locates useful rows within selected partitions. A query can benefit from one, both or neither.

Which month owns a row exactly at an exclusive upper bound?

It belongs to the following matching range, not the range whose upper bound equals that timestamp. Consistent types and time zones matter.

Why does a timestamp-inclusive primary key not guarantee global event_id uniqueness?

It makes the pair unique, allowing one event ID with different timestamps. PostgreSQL partitioned unique constraints must satisfy partition-key requirements.

What must be checked before retiring a partition?

Its actual bounds, retention/hold requirements, references, consumer needs, archive/backup implications and a verified maintenance/restore procedure.

Tricky & Most-Asked Interview Scenarios

Time partitioning permits duplicate IDs in different months. How will you keep global identity?

The Scenario & Constraint

An ingestion API requires event_id to identify exactly one event regardless of timestamp. A partitioned primary key on event_id/recorded_at accepts duplicate IDs in different months. What will you do?

The Direct Answer & Architectural Decision

Make the global invariant explicit. Options include an authoritative unpartitioned ID registry protected by a unique key and coordinated with ingestion, a partition strategy compatible with the identity requirement, or a different physical design. Keep event-time retention separate from claiming the composite key enforces a single-column rule. Repair conflicts before declaring the migration correct.

Key Trade-Offs & Follow-Up Traps

A registry adds writes and a possible contention/lifecycle boundary. Random UUID collision probability may support an application design but is not the same as database enforcement against intentional or buggy duplicates. Any cross-store registry needs an explicit transaction/repair protocol; adding another service does not make uniqueness atomic.

A one-day report scans every monthly partition. What will you inspect?

The Scenario & Constraint

A query applies a function to recorded_at before comparing it to a calendar date. Hundreds of partitions appear in the plan. How will you restore useful pruning without changing the result meaning?

The Direct Answer & Architectural Decision

Compare the predicate with the actual partition key, types and time-zone policy. Test a direct half-open timestamp range representing that day, and verify the changed plan and boundary results. Inspect prepared/execution-time pruning behavior where parameters are involved instead of assuming parameterization itself is the error.

Key Trade-Offs & Follow-Up Traps

A rewritten range can improve pruning but must preserve the intended business time zone and daylight-saving boundaries. If queries genuinely lack a partition-key condition, scanning many partitions may be unavoidable. Indexes inside those partitions solve a different part of the work.

Yesterday’s partition has been archived, but late events still arrive. Where should they go?

The Scenario & Constraint

The ingestion pipeline can deliver events several days late while retention automation detaches old ranges. Operations proposes silently changing old event timestamps to today. What will you do?

The Direct Answer & Architectural Decision

Preserve the event’s semantic timestamp and define a late-arrival policy: retain an adequate writable lateness window, route exceptions to a governed quarantine/reprocessing path, or reopen an eligible range through a controlled procedure. Monitor rates and ensure downstream aggregates reconcile late corrections. Do not falsify time merely to satisfy a routing boundary.

Key Trade-Offs & Follow-Up Traps

A wider writable window costs storage and complicates retirement; quarantining delays visibility and needs an owner. If legal retention forbids reintroduction, reject/handle the event under that policy. Event time and ingestion time can both be stored, but they must not be silently interchanged.

Retiring old data blocks the application. Is detach/drop guaranteed lock-free?

The Scenario & Constraint

A large event table must retire monthly data with minimal disruption. Long transactions exist and an earlier maintenance operation blocked traffic. What will you change?

The Direct Answer & Architectural Decision

Use the documented engine-specific detach/archive/drop procedure, inspecting lock requirements, active transactions and supported concurrent forms. Test the exact operation under realistic load, apply time budgets and schedule/abort safely. Confirm retention/hold eligibility and consumer expectations before removing the range, and keep a verified archive path where required.

Key Trade-Offs & Follow-Up Traps

Partition lifecycle can avoid massive row-by-row deletion, but lock acquisition and validation still matter. A maintenance window may be safer than an unsupported “online” command. Backup/archive retention is a separate policy; dropping a child table neither proves secure erasure everywhere nor supplies a complete restore plan.

A tiny daily partition scheme increases planning cost. Keep splitting?

The Scenario & Constraint

A workload usually reads several years of history and now has many small partitions. Planning/metadata overhead is visible, while retention only needs monthly boundaries. What will you choose?

The Direct Answer & Architectural Decision

Measure planning versus execution and assess whether coarser partitions better fit access and lifecycle. Consolidate through a tested compatible migration if appropriate, and keep suitable indexes for the actual predicates. Choose a partition count/size from observed operations rather than a universal maximum copied from another engine.

Key Trade-Offs & Follow-Up Traps

Coarser ranges make per-range maintenance larger; finer ranges can help selective time reads. If most queries scan all history, a different read/analytical model may be more useful than further splitting. Preserve keys, boundaries and verification throughout any repartitioning migration.

All writes hit the newest partition. Why did monthly partitioning not scale writes across machines?

The Scenario & Constraint

An append-heavy service partitions by month on one PostgreSQL server. The newest child and shared I/O are saturated. More old partitions are added but throughput does not improve. What will you do?

The Direct Answer & Architectural Decision

Identify the actual shared bottleneck and improve batching, indexes, resource provisioning or workload admission where justified. Local range partitioning is primarily an access/lifecycle organization here; it does not distribute ownership to additional servers. If independent node capacity is truly needed, evaluate a shard key and distributed architecture with its routing, transaction and recovery obligations.

Key Trade-Offs & Follow-Up Traps

Hash subpartitioning can change local contention/maintenance but still shares server resources. Sharding adds operating cost and cannot make one indivisible hot invariant arbitrarily parallel. Do not rebuild a distributed data platform before measuring whether simpler physical/query changes meet the load.
