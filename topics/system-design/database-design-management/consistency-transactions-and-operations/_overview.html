Consistency, Transactions & Operations

A shop needs a rule for changing both sides of a record together, a rule for helpers acting at the same time, a policy when distant desks cannot communicate, and a safe way to replace the record format. One reassuring word such as consistent cannot stand in for all these different promises.

These lessons connect formal guarantees with decisions and operating procedures. ACID names transaction properties; CAP analyzes a particular communication-failure trade-off; Database Transactions implements concurrent decision boundaries; migrations evolve the shared live contract. Keep the unit of work, failure model and recovery state visible.

Suggested reading guide

Read ACID Properties for the separate atomicity, invariant, isolation and durability questions. Read CAP Theorem for precise partition-time reasoning and the distinct real-time meaning of consistency. Neither lesson replaces the other.

Use Database Transactions to choose conditional mutations, constraints, locks and whole-operation retry boundaries. Finish with Database Migration Strategies: cover old/new writers, bounded backfills, data verification, cutover and the actual limits of rollback.

Explore this branch

  • ACID Properties

    Separate atomicity, invariant consistency, isolation and durability, including the boundary beyond which local transaction guarantees stop.

  • CAP Theorem

    Trace missing information during a network partition using precise operation, real-time consistency and availability definitions.

  • Database Transactions

    Protect the actual concurrent decision with conditional writes, constraints, locks or isolation, and define whole-operation retries and unknown outcomes.

  • Database Migration Strategies

    Coordinate old/new writers, backfill safely, verify values and cut over through explicit expand–migrate–contract gates.
