ACID Properties

🎯 The Hook & ELI5

Imagine moving three counters from one jar to another. You want both jar records to change together, the rules to remain true, two helpers not to interfere incorrectly, and an announced success to survive the agreed kinds of accident. ACID names these four different promises. It is not one magic switch that makes every program or every distributed operation correct.

ACID stands for Atomicity, Consistency, Isolation and Durability. These properties describe transaction behavior under a defined system model. A transaction groups database work into one unit; its boundary and configured guarantees must match the business operation.

The consistency in ACID concerns preserving declared/data-domain invariants through valid operations. It is not the linearizable single-copy meaning used by CAP. Isolation has levels and engine-specific behavior; ordinary defaults do not imply every transaction is fully serializable. Durability protects committed work against the configured failure envelope, not against every conceivable loss of all copies.

🗺️ High-Level Big Picture

Atomicity groups the changes; consistency asks whether the operation preserves the right rules; isolation controls concurrent interference; durability defines what an acknowledged commit survives.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; SQL examples target PostgreSQL 18 unless explicitly labeled otherwise.

1. Atomicity: one logical change, not a collection of partial commits

The two jar records must not reflect only one half of a transfer. Atomicity means the transaction’s database changes take effect as a unit or not at all. It does not mean the code executes instantly or that another external service shares the same transaction.

Autocommit can make each statement its own transaction. If an application debits one row, commits, then fails before crediting another, each statement can be perfectly atomic while the larger business operation is still split incorrectly. Choose the boundary explicitly.

2. Consistency: identify the rules that need protection

For the jar example, counts stay non-negative and the bookkeeping transfer conserves the total. NOT NULL, key, foreign-key and CHECK constraints enforce the specific rules they express. Correct application/procedure logic must enforce additional invariants, with suitable concurrency control.

A transaction does not infer that a discount is unauthorized or that an omitted credit was intended. “ACID compliant” does not make an arbitrary program invariant-preserving. Define the valid starting state and the rule every accepted operation must maintain.

3. Work through an atomic operation with explicit failure checks

In an isolated scratch PostgreSQL 18 database, this example creates two bins and moves three units in one procedural statement/transaction. It checks both affected owners and rolls the statement back on an exception. The quantities are bookkeeping state; the transaction does not physically move goods.

CREATE TABLE acid_bin (
  bin_id integer PRIMARY KEY,
  quantity integer NOT NULL CHECK (quantity >= 0)
);
INSERT INTO acid_bin VALUES (1, 8), (2, 2);
DO $$
BEGIN
  UPDATE acid_bin SET quantity = quantity - 3
    WHERE bin_id = 1 AND quantity >= 3;
  IF NOT FOUND THEN
    RAISE EXCEPTION 'Source missing or insufficient quantity';
  END IF;
  UPDATE acid_bin SET quantity = quantity + 3 WHERE bin_id = 2;
  IF NOT FOUND THEN
    RAISE EXCEPTION 'Destination missing';
  END IF;
END;
$$;

This illustrates a valid local operation, not a complete concurrent transfer service. A production API also needs stable request identity, all relevant authorization checks, an agreed lock/retry strategy and protection against unrelated writers bypassing the operation.

4. Isolation: overlapping operations need a specified model

Two helpers may make individually reasonable decisions from the same old jar counts. Isolation defines which concurrent effects an operation can observe and which anomalies are prevented. Serializable execution aims for outcomes equivalent to some serial order, but may abort transactions that must then be retried.

PostgreSQL Repeatable Read offers a stable snapshot but can allow write skew across different rows; serializable behavior adds dependency checks. Other engines’ similarly named levels can differ. Explicit conditional updates, constraints or locks can solve particular invariants, but a process-local mutex does not coordinate every database writer.

5. Durability: state the commit and failure policy

A database can acknowledge commit after the required transaction log is safely persisted even before every modified table page is flushed; crash recovery can replay logged changes. That is the idea behind write-ahead logging.

PostgreSQL’s fsync, synchronous_commit and synchronous standby settings affect the guarantee. Disabling reliable flush or acknowledging before required persistence weakens some failure promises. A durable local commit does not preserve data after permanently losing its only storage, and a read replica or backup solves a different part of the failure model.

6. Keep outside effects and uncertain responses separate

An email, payment-provider request or message sent outside the transaction is not rolled back by rolling back database rows. Persist an appropriate intent alongside the authoritative change, then process it with an explicit delivery/idempotency policy.

If the server commits but the response is lost, the client may not know the result. A fresh retry can be a second valid ACID transaction with duplicated business intent. Stable operation identity and authoritative outcome reconciliation address that ambiguity; ACID alone does not distinguish a retry from a genuinely new command.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Each statement atomic, business change partial

Symptom: The debit persists without its matching credit.

Root Cause: The application committed separate statements instead of one operation boundary.

Fix/Prevention: Use the correct transaction scope and check every required write/result before completion.

Consistency confused with knowing business intent

Symptom: A committed record obeys column types but violates a business rule.

Root Cause: No constraint/protocol expressed the missing invariant.

Fix/Prevention: Name the invariant and enforce it across every writer with the necessary concurrency mechanism.

Commit promise left implicit

Symptom: Acknowledged data is missing after an accepted failure.

Root Cause: Flush/replication settings did not match the advertised durability envelope.

Fix/Prevention: Document and test acknowledgment/storage/replica settings and independent recovery procedures.

🧠 Active Recall & Mastery Check

Summarize this in your own words: State the invariant and transaction boundary, choose the needed concurrency and commit policy, and test the promised failure envelope. ACID properties support correct operations; they do not replace business modeling or retry identity. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Can two separately committed updates each be atomic while their combined business operation is wrong?

Yes. Atomicity applies to the chosen transaction boundary. If a business invariant requires both changes together, two separate commits do not provide that unit.

Does ACID consistency automatically enforce every business rule?

No. Constraints and correct operation logic must express the intended invariants, and concurrency control must preserve them across accepted operations.

Does a stable Repeatable Read snapshot imply serializable behavior?

Not in general. PostgreSQL snapshot-based Repeatable Read can allow write skew; other engines differ. Verify the exact isolation semantics and the invariant.

Why can a durable commit still require replicas and backups?

Durability covers a configured failure model. Losing the only storage or copying a destructive operation to live replicas requires other redundancy/historical recovery mechanisms.

Tricky & Most-Asked Interview Scenarios

A failure leaves one side of a transfer committed. Which ACID boundary is wrong?

The Scenario & Constraint

Two inventory-bin updates run in separate autocommit statements. The process crashes after decrementing the source. What will you change and verify?

The Direct Answer & Architectural Decision

Put the logically paired database mutations in one transaction/procedure and check required row counts or errors before success. Enforce local non-negative values and other expressible rules. Test failure between the writes and before commit, verifying that an incomplete operation cannot become a successful committed business transfer.

Key Trade-Offs & Follow-Up Traps

The combined transaction can hold locks longer and must follow a deadlock/retry policy. If the two sides live in different independent services, one local transaction cannot cover both; use a supported distributed boundary or an explicit workflow with intermediate states.

Every insert commits successfully, yet the business rule fails. Is the database inconsistent?

The Scenario & Constraint

An authorization limit spans several records, but the code checks it only before a separate write and there is no constraint/locking protocol. Concurrent requests exceed the limit. What will you do?

The Direct Answer & Architectural Decision

Specify the invariant and choose an enforcement point: a suitable constraint, an authoritative owner row with a transaction/lock or conditional update, or a serializable protocol with full retries. Ensure all writers use it and test concurrent requests. The database cannot infer a business rule absent from its schema/operation protocol.

Key Trade-Offs & Follow-Up Traps

A hot owner serializes work; higher isolation may increase abort/retry rates. Moving the check into one application process is not sufficient when other instances or jobs write too. Some rules require redesigning the data boundary rather than adding a CHECK expression that reads changing external rows.

Two stable-snapshot transactions each preserve their own view but jointly break a rule. What isolation is needed?

The Scenario & Constraint

Two workers each see enough other active capacity and deactivate a different record. Both use PostgreSQL Repeatable Read. At least one record must remain active. What will you do?

The Direct Answer & Architectural Decision

Recognize write skew: a stable snapshot does not necessarily serialize decisions involving multiple rows. Use a shared invariant-owner lock/record, a schema/protocol that makes the conflict explicit, or Serializable with whole-transaction retries. Demonstrate the two-transaction interleaving and verify the chosen fix with the real engine’s semantics.

Key Trade-Offs & Follow-Up Traps

Serializable may abort and requires an application retry boundary; a shared owner can be a contention point. Locking only each worker’s different row leaves the decision uncoordinated. If the business can tolerate temporary absence, that is a different explicit availability policy, not a proof the original hard invariant holds.

A fast acknowledgment disappears after a crash. Which durability assumptions must change?

The Scenario & Constraint

A service reduced commit waiting to improve latency. After a host/power failure, some acknowledged changes are missing. What will you inspect before declaring ACID broken?

The Direct Answer & Architectural Decision

Inspect the actual flush, synchronous_commit, storage and replication settings and the failure that occurred. Reestablish the required persistence/replica acknowledgment policy and test crash boundaries against the promised loss envelope. Distinguish local process recovery from permanent loss of a host or failure domain.

Key Trade-Offs & Follow-Up Traps

Waiting for persistence or a remote durable participant can increase latency and reduce write availability under failures. Faster acknowledgment may be a valid choice for disposable data, but it must carry an honest weaker promise. A healthy application response is not evidence that the data reached every required durable copy.

An email says the order succeeded, but the database transaction rolls back. Can rollback retract the email?

The Scenario & Constraint

Application code sends a confirmation email inside a database transaction before commit. A later constraint error aborts the rows. What will you change?

The Direct Answer & Architectural Decision

Persist a notification/publication intent in the same local transaction as the order’s committed result, then send afterward through a durable retryable worker. Make delivery duplicate-aware and ensure the message truthfully describes the committed business state. Database rollback cannot undo a message already accepted by an independent email service.

Key Trade-Offs & Follow-Up Traps

This adds asynchronous delay, retry state and possible duplicate-delivery concerns. Sending only after commit without durable intent leaves a crash gap that can lose the notification. If exactly-once external action is demanded, inspect the provider’s operation identity/receipt contract instead of claiming local ACID extends over HTTP.

A retried request creates two valid orders. Which guarantee was never provided?

The Scenario & Constraint

The first transaction committed, but the client lost its response and retried with a fresh request ID. Both orders satisfy keys and isolation rules. How will you prevent duplicate intent?

The Direct Answer & Architectural Decision

Define a stable operation identity from the caller’s business intent and durably associate it with the result within the appropriate owner boundary. Replays return or reconcile that existing operation, and reuse with different parameters is handled as a semantic conflict. Keep ordinary transaction guarantees, but add the missing request-level idempotency contract.

Key Trade-Offs & Follow-Up Traps

Idempotency records need retention and outcome semantics. Hashing payloads alone can confuse two intentionally identical purchases with one retry. A timeout is not proof the first transaction failed, and creating a fresh transaction does not inherently mean creating a fresh business operation.
