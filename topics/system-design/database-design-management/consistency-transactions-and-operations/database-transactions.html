Database Transactions

🎯 The Hook & ELI5

At a ticket counter, a clerk checks availability and hands out a ticket as one controlled job. If two clerks both read an old sticky note and act separately, they can promise the same last seat. A database transaction is the work envelope around related actions; correct concurrency rules decide how several envelopes can overlap safely.

A transaction has a beginning, reads/writes, and a commit or rollback outcome. Correct design identifies the invariant, the records/predicates involved, the isolation needed and the full retry boundary. Wrapping arbitrary statements in BEGIN/COMMIT does not automatically protect every decision made from earlier reads.

This lesson uses PostgreSQL 18 for concrete behavior. Read Committed commonly gives a new statement snapshot, while Repeatable Read maintains a transaction snapshot and Serializable adds stronger checks. Locks, conditional writes, uniqueness/exclusion constraints and retries solve different parts of concurrency control; choose them against the actual race.

🗺️ High-Level Big Picture

This PostgreSQL 18 Read Committed timeline protects one row’s conditional decrement when all writers follow the rule. At Repeatable Read or Serializable, a conflicting transaction may instead receive a retryable failure. Adding an order row, external payment or several inventory owners requires defining the larger business boundary explicitly.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; SQL examples target PostgreSQL 18 unless explicitly labeled otherwise.

1. Choose a business boundary before a transaction boundary

Name the invariant: one stock unit cannot be reserved twice; every accepted order has its required reservation; no room has overlapping confirmed bookings. List the rows and predicates that can change that conclusion.

Keep external user/network work outside a short local transaction where possible. If the business requires multiple independent owners, decide on a supported distributed transaction or an explicit reservation/workflow protocol rather than silently stretching a local connection’s transaction over them.

2. Understand the snapshot your decision reads

A snapshot is a coherent view of versions at a chosen point, like looking at one dated photograph. PostgreSQL’s multiversion concurrency control allows readers and writers to overlap without every read locking the live row. That does not mean every decision based on a photograph stays valid until commit.

Read Committed can observe different committed data in separate statements; Repeatable Read uses a stable snapshot but can permit write skew. Serializable emulates a valid serial outcome for committed work and may reject transactions that need retrying. Verify other engines separately; names alone do not define identical anomalies.

3. Use an atomic conditional mutation for a row-local invariant

In a scratch database, this toy example places the quantity test in the same update that consumes it. Treat no returned row as a failed reservation, not as success. A production order transaction must also verify required downstream database writes before committing.

CREATE TABLE transaction_stock (
  sku text PRIMARY KEY,
  quantity integer NOT NULL CHECK (quantity >= 0),
  version bigint NOT NULL DEFAULT 0
);
INSERT INTO transaction_stock (sku, quantity) VALUES ('book', 1);
UPDATE transaction_stock
SET quantity = quantity - 1, version = version + 1
WHERE sku = 'book' AND quantity >= 1
RETURNING sku, quantity, version;

An optimistic version condition can instead reject an update whose expected version changed. A plain SELECT followed later by an unconditional assignment does not provide the same protection. Check the database result; an ORM returning a normal method call is not proof a qualifying row was changed.

4. Lock the decision owner, not just convenient rows

SELECT FOR UPDATE can protect existing rows that all competing operations lock consistently. If a rule is about the absence of matching rows, selecting zero rows does not necessarily lock a future insertion opportunity. PostgreSQL row locks are not a general predicate-locking substitute.

Use a suitable uniqueness/exclusion constraint, a shared owner/sentinel row protocol or Serializable with retries when the invariant requires it. Acquire multiple row locks in a consistent global order, keep the transaction short and expect deadlocks to remain a recoverable error class.

5. Retry the complete decision when the model requires it

A serialization failure means re-executing the operation with a new transaction and fresh reads, including logic that selected values. Retrying only the final statement can replay a decision already invalidated by concurrency. PostgreSQL identifies serialization failures with SQLSTATE 40001; deadlocks use 40P01 and also need a deliberate policy.

Bound retries, add backoff/jitter where appropriate and retain stable business operation identity. Do not repeat irreversible external effects inside a transaction callback that may run again. Not every integrity error is transient: retrying a permanently invalid unique key forever is not error handling.

6. Control errors, savepoints and connection lifetime

Commit establishes the transaction result under its configured policy; rollback abandons its uncommitted database effects. A savepoint can allow partial rollback inside an explicitly designed larger transaction, but it must not hide a failed mandatory business step. PostgreSQL transactions in an error state require the appropriate rollback/recovery before ordinary work resumes.

Return or discard pooled connections only after cleanup. Long-running snapshots can retain old versions and interfere with cleanup; long writers hold locks and increase rollback work. Use deadlines and observe transaction age. A lost commit response is an unknown outcome requiring authoritative reconciliation, not automatic proof that rollback occurred.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

BEGIN mistaken for race prevention

Symptom: Two requests both reserve the last unit.

Root Cause: An earlier SELECT fed an unconditional later write under insufficient protection.

Fix/Prevention: Use a suitable conditional mutation, constraint, lock or serializable protocol and check the result.

Only the last statement retries

Symptom: A transaction repeats a stale allocation decision.

Root Cause: Serialization recovery reused invalidated reads/logic.

Fix/Prevention: Restart the complete transaction decision with a fresh snapshot and bounded retry policy.

Network error called rollback

Symptom: The same business operation is committed twice after reconnect.

Root Cause: The client assumed a missing commit response meant failure.

Fix/Prevention: Retain stable operation identity and reconcile against the authoritative outcome before applying again.

Summarize this in your own words: Protect the actual decision, not merely the statement syntax. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Why is a transaction wrapper alone insufficient for a read-then-write race?

The chosen isolation and operation semantics may still allow two transactions to make decisions from stale/concurrent reads. The invariant needs an actual concurrency protection mechanism.

Does SELECT FOR UPDATE returning no rows always prevent a matching future insert?

No. A row lock protects selected existing rows, not every absent-row predicate. Use an appropriate constraint, owner protocol or documented stronger isolation.

What belongs inside a serialization retry boundary?

The full database decision, including reads and value-selection logic, re-executed in a new transaction. External irreversible effects require a separate idempotent/durable workflow.

Can a savepoint safely hide every failed statement?

Only when partial success is the intended business contract. A failed required reservation/credit cannot be ignored while still claiming the whole operation succeeded.

Tricky & Most-Asked Interview Scenarios

Two buyers read quantity one. What must the database operation decide atomically?

The Scenario & Constraint

A service reads stock, decides it is sufficient, then assigns a reduced quantity in a later statement. Two requests confirm purchases for one unit. How will you fix the race?

The Direct Answer & Architectural Decision

Place the availability predicate in an atomic conditional decrement or another correct locking/constraint protocol. Check that exactly the intended stock row changed before creating/confirming the order, and keep related required database work in one suitable transaction. Test two concurrent requests rather than only a sequential happy path.

Key Trade-Offs & Follow-Up Traps

A row-local update is simple but may serialize a very hot item. Multiple SKUs or external reservation owners require a larger explicit protocol. A zero-row result is a business/concurrency outcome to handle, not a reason to proceed as if the reservation succeeded.

Both transactions find no overlapping booking. Why did locking the query result not help?

The Scenario & Constraint

Two PostgreSQL transactions query an empty overlapping-booking set with FOR UPDATE, then each inserts a conflicting reservation. The room must never be double-booked. What will you do?

The Direct Answer & Architectural Decision

Use an engine-supported constraint that expresses the overlap rule, or serialize the room decision through a shared owner row, or use a documented Serializable protocol with full retries. Check the exact time interval semantics and confirmed/pending states. Locking zero existing rows did not establish ownership of every future row satisfying that predicate.

Key Trade-Offs & Follow-Up Traps

An owner lock reduces concurrency per room; exclusion-constraint designs require suitable types/operators and deployment support. Serializable may abort contenders. If temporary holds expire, integrate their lifecycle so the invariant does not accidentally ignore a still-promised reservation.

Two valid transfers repeatedly deadlock. What should change besides increasing timeout?

The Scenario & Constraint

One transaction locks item A then B; another locks B then A. Both wait for the other. What will you change and how will the application recover?

The Direct Answer & Architectural Decision

Acquire the required owner locks in a consistent order based on stable identifiers, keep the transaction short and inspect deadlock evidence. Roll back/retry the complete safe operation under a bounded policy when the engine chooses a victim. Ensure the retry preserves one business intent and does not repeat irreversible external work.

Key Trade-Offs & Follow-Up Traps

Consistent ordering reduces this pattern but does not prove no deadlocks can ever occur through other locks/triggers. A longer timeout does not break a true wait cycle more safely. Coarser serialization may simplify correctness at a larger contention cost.

The ORM retries only the failed UPDATE after SQLSTATE 40001. Is that sufficient?

The Scenario & Constraint

A transaction computes a new allocation using several reads, then PostgreSQL rejects it for a serialization failure. The retry reuses the old allocation decision. What will you do?

The Direct Answer & Architectural Decision

Restart the whole transaction with fresh reads and re-run all logic that selected the allocation and values. Keep the retry loop bounded and report exhaustion truthfully. Audit callbacks for messages, charges or other non-transactional effects that would repeat; move those to an appropriate durable intent/idempotent workflow.

Key Trade-Offs & Follow-Up Traps

Whole-operation retries consume work and can contend repeatedly, so backoff/admission or a different invariant boundary may be needed. A permanent integrity violation is not automatically a transient serialization failure. Retaining an old snapshot or precomputed values defeats the purpose of retrying under a new concurrent history.

COMMIT was sent but the socket closed. Should the server-side operation be repeated?

The Scenario & Constraint

An API cannot tell whether its transaction committed. A new connection is available, but blindly repeating would risk a duplicate order. What is the recovery contract?

The Direct Answer & Architectural Decision

Use the same stable operation identifier to query/retry against the authoritative result policy. Record the identifier and accepted database effect atomically where possible, reject semantic reuse with different parameters, and reconcile before creating another business operation. Keep pending/unknown visible until evidence establishes the outcome.

Key Trade-Offs & Follow-Up Traps

The idempotency record’s durability and retention must match the operation’s failure model. A replica can be too stale to establish that an identifier is absent. A transport exception and a local rollback attempt do not prove the original server transaction failed.

A consistent export holds a transaction for hours. What costs must be controlled?

The Scenario & Constraint

A report needs a stable dataset and keeps a PostgreSQL snapshot open while slowly sending rows to a remote client. Cleanup falls behind and storage grows. What will you redesign?

The Direct Answer & Architectural Decision

Measure transaction age, retained old versions, output rate and resource use. Separate snapshot acquisition/materialization/export from slow client delivery where appropriate, or use a supported bounded export/replica strategy with an explicit consistency contract. Apply time/resource limits and ensure cancellation closes the transaction and connection correctly.

Key Trade-Offs & Follow-Up Traps

Short independent chunks reduce snapshot lifetime but do not automatically represent one consistent point in time. A materialized export costs storage and creation work; a replica still has retention/replay constraints. Choose the required data consistency rather than silently changing it to solve a streaming bottleneck.
