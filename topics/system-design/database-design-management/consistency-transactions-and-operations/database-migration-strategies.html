Database Migration Strategies

🎯 The Hook & ELI5

A busy shop cannot replace its only doorway while customers are walking through it. Build a second compatible entrance, guide traffic across, check that everyone uses it, and remove the old entrance later. Database migrations similarly change a live contract shared by old code, new code and existing data. The safest sequence is not usually one giant leap.

A migration can change schema, data, indexes or storage ownership. Versioned scripts record intended steps, but safe production evolution also needs compatibility, locking/load budgets, resumability, verification and recovery. “The script ran” does not prove every record has the new meaning or that old workers stopped using the old shape.

Expand–migrate–contract separates adding a compatible shape, moving readers/writers/data, and later removing obsolete structure. Some changes can be transactional in PostgreSQL; others, such as concurrent index creation, have different restrictions. An online technique can reduce disruption without being lock-free, instantaneous or universally reversible.

🗺️ High-Level Big Picture

The arrows are gates rather than one deployment transaction. A passing backfill count or a new app release alone does not establish writer compatibility, value correctness or safe removal of the old shape.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; SQL examples target PostgreSQL 18 unless explicitly labeled otherwise.

1. Inventory the contract and recovery envelope

Find every reader/writer: APIs, jobs, ETL, administrative tools, reports and old application versions. Define how long mixed versions can exist, the load/lock budget and observable success criteria. Review the exact database/version behavior for rewrites, validation and index operations.

Establish a tested backup/recovery path before a destructive change. A rollback script cannot reconstruct information that has been discarded or reinterpret all new writes automatically. Decide which phases can roll back by switching reads and which require forward recovery or data restoration.

2. Expand compatibly without pretending all DDL is free

Add a new nullable column/table or supported access path without immediately removing the shape used by running code. Keep old readers/writers working during rollout. Even a fast catalog change can wait behind long transactions, so configure a bounded lock-acquisition strategy and observe blockers.

Avoid assuming every default/type/constraint operation is metadata-only in every engine/version. Test realistic data and concurrent activity. Separate schema additions from incompatible reader/writer changes so a partial application rollout does not instantly make the database unusable.

3. Coordinate writers before copying live data

For a rename-like transition, decide the authoritative value and how every write keeps the new shape up to date. New application dual-writes are insufficient while old versions still update only the old column. Use a proven trigger/CDC/compatibility protocol or retire old writers before the required final catch-up.

Within one database, update logically coupled old/new representations in a suitable transaction. Across independent stores, independent writes can separate and need durable propagation/reconciliation. Define how concurrent updates, deletes, defaults and transformations are versioned so an old backfill cannot overwrite newer meaning.

4. Backfill in bounded, restartable units

This PostgreSQL 18 scratch example illustrates an additive schema and one bounded copy batch. It is not a complete live-rollout protocol by itself: the preceding writer-compatibility gate must be satisfied. The source is non-null, the new value has the same meaning, and the second predicate avoids overwriting an already populated target.

CREATE TABLE migration_customer (
  customer_id bigint PRIMARY KEY,
  display_name text NOT NULL
);
INSERT INTO migration_customer VALUES (1, 'Asha'), (2, 'Ben');
ALTER TABLE migration_customer ADD COLUMN full_name text;
WITH batch AS (
  SELECT customer_id FROM migration_customer
  WHERE full_name IS NULL
  ORDER BY customer_id LIMIT 500
  FOR UPDATE SKIP LOCKED
)
UPDATE migration_customer AS c
SET full_name = c.display_name
FROM batch AS b
WHERE c.customer_id = b.customer_id AND c.full_name IS NULL;

Track progress and retry safely with a fresh transaction per bounded unit. SKIP LOCKED means some eligible rows may be temporarily skipped; perform a final reconciliation sweep rather than declaring completion from a high-water mark or one empty skipped batch. More complex transformations need version/conditional checks beyond “target is null.” Monitor lock waits, write load, replica lag and retained log volume.

5. Verify meaning before switching reads

Compare transformed values, null/error rates, key/reference invariants and representative old/new query results. Counts/checksums are useful only when their semantics match the transformation and a coherent change boundary. Shadow reads can expose discrepancies without changing the user’s authoritative answer.

Add supported constraints through an appropriate phased validation procedure. In PostgreSQL, a suitable NOT VALID constraint can separate existing-row validation from its addition, but the operations still have lock requirements and transaction lifetimes. Do not keep an earlier strong lock open while performing the long validation in the same outer transaction.

6. Cut over, observe, then contract deliberately

Switch readers using a controlled release/flag or compatible code path, observe correctness and performance, and retain a fallback while it is genuinely valid. Confirm old instances, background jobs and retry queues no longer depend on the old shape. A time delay alone does not prove that inventory.

Remove obsolete columns/tables/indexes in a later governed step. Record the point at which old code/data recovery is no longer available. If a new write cannot be represented in the old schema, an application rollback is not automatically safe. Keep release/migration state auditable and treat multi-database/shard progress as independently verifiable rather than one fictional atomic fleet update.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

New deploy assumed to replace every writer

Symptom: Old jobs keep repopulating only the retired column.

Root Cause: The compatibility inventory omitted workers or mixed-version instances.

Fix/Prevention: Track every producer and establish the writer/catch-up gate before read cutover.

Batch resumes by overwriting newer data

Symptom: A backfill restores an older value over a live edit.

Root Cause: Progress tracking ignored version/ownership semantics.

Fix/Prevention: Use safe conditional/versioned updates and reconciliation, with explicit handling for skipped rows and deletes.

Rollback promised after information loss

Symptom: Old code cannot read new states after a destructive cutover.

Root Cause: A reverse schema command was confused with restoring original data meaning.

Fix/Prevention: Define the reversible window, retain suitable data/backups and choose a tested forward-repair/restore procedure.

What does expand–migrate–contract separate?

Add a compatible shape; coordinate writers, migrate and verify data/read paths; only later remove the obsolete contract after old dependents and recovery needs are accounted for.

Why are new-code dual-writes insufficient during a rolling deployment?

Old instances or jobs may still write only the old representation. A complete compatibility/catch-up protocol must account for every writer.

Does a high-water mark prove a SKIP LOCKED backfill covered all records?

No. Locked or concurrently changed earlier records can remain. Use a safe resumable procedure and a final invariant/value reconciliation sweep.

Why can dropping a new column fail to restore the old application’s world?

New writes may carry states/information the old schema cannot represent, and removed data may be gone. Schema reversal does not automatically reverse data semantics or external effects.

Tricky & Most-Asked Interview Scenarios

Old pods still use the old name during a column rename. What release sequence will you choose?

The Scenario & Constraint

A live service wants display_name renamed to full_name while old and new versions overlap. Immediate rename breaks old readers/writers. What will you do?

The Direct Answer & Architectural Decision

Add a compatible new shape, establish a writer protocol covering old instances/jobs, backfill with concurrency-safe semantics, verify values and switch reads in stages. Retain the old shape while it is needed for compatibility or a valid fallback. Contract only after the full dependent inventory is retired and the rollback boundary is explicit.

Key Trade-Offs & Follow-Up Traps

The transition adds temporary code/storage and may require triggers or another supported compatibility mechanism. A brief downtime rename is simpler if the service can truly stop all dependents. New-code dual-writes alone do not cover old writers that continue editing only the old column.

A phased constraint migration still blocks writes for a long time. Which transaction boundary matters?

The Scenario & Constraint

A PostgreSQL migration adds a NOT VALID constraint and validates it inside one framework-managed transaction. A strong lock from the first operation remains held during the scan. What will you change?

The Direct Answer & Architectural Decision

Inspect the exact constraint and lock requirements, blockers and framework transaction behavior. Where appropriate, separate short addition/commit from later validation in its own supported step, and apply bounded lock waiting and observed rollout. Verify new writes are protected by the intended constraint before claiming old-data validation is complete.

Key Trade-Offs & Follow-Up Traps

Phasing changes error/recovery states and needs an auditable migration record. NOT VALID does not mean lock-free or that new invalid writes are universally accepted. A maintenance window may be safer for a small table; the exact procedure depends on constraint type and engine version.

A restarted backfill overwrites live edits and skips locked rows. How will you make it safe?

The Scenario & Constraint

A large copy job uses batches and a last-ID checkpoint while users keep editing. Some earlier rows were skipped under locks, and unconditional assignments restore old values. What will you do?

The Direct Answer & Architectural Decision

Define the authoritative field/version and the compatibility writer protocol first. Use conditional or version-aware mutations in short transactions, record retryable progress and reconcile all remaining exceptions, including skipped low IDs and deletes. A target-null predicate fits only transformations where populated targets should not be replaced; otherwise compare the actual source/target version semantics.

Key Trade-Offs & Follow-Up Traps

Resumability requires more than remembering a cursor. A final sweep adds work but prevents silent holes. If coordinating concurrent writes is too complex, a bounded pause/catch-up phase may be acceptable; do not call an unverified high-water mark a completed migration.

The migration fails because concurrent index creation runs inside a transaction. How will deployment recover?

The Scenario & Constraint

A release uses a PostgreSQL concurrent index build to reduce write blocking, but its migration runner wraps every step atomically. A failed attempt may also leave an invalid index. What will you change?

The Direct Answer & Architectural Decision

Use a supported non-transactional migration step for CREATE INDEX CONCURRENTLY, inspect existing index validity and remediate the failed object deliberately before retrying. Keep resource/lock budgets, progress observation and a documented recovery state. Verify the finished access path’s query behavior and integrity purpose rather than relying only on a migration version being marked applied.

Key Trade-Offs & Follow-Up Traps

A non-transactional step cannot borrow the framework’s ordinary all-or-nothing rollback assumption. A regular build during a permitted maintenance window is an alternative. Concurrent does not mean zero impact, and a repeated name/existence check is not proof a failed index is usable.

Old and new databases diverge during a migration. Can the request simply retry both writes?

The Scenario & Constraint

A migration writes each business change to two independent databases. A crash after the first commit leaves one copy stale, and deletes/retries can reorder. How will you establish a trustworthy transition?

The Direct Answer & Architectural Decision

Keep one declared authoritative write owner and a durable, idempotent/version-aware propagation and reconciliation path, or use a supported distributed transaction if it fits the required envelope. Coordinate the initial snapshot with ongoing changes and establish a verified catch-up/cutover boundary. Track deletes and uncertain outcomes; do not infer atomicity from the fact both writes came from one handler.

Key Trade-Offs & Follow-Up Traps

Durable propagation costs lag, replay/identity state and operating work. Cross-store atomic coordination can cost availability/latency and product compatibility. If two columns are in one database transaction the problem may be simpler, but even then every old writer must participate in the compatibility protocol.

New data no longer fits the old schema. What does rollback mean now?

The Scenario & Constraint

A migration split/changed a field and removed the old representation. New writes use states the old application cannot represent. A release issue triggers a request to “just roll back the schema.” What will you do?

The Direct Answer & Architectural Decision

Identify the actual reversible boundary and protect current data. Choose a tested forward repair, a compatible application fallback, or a controlled restore/reconciliation process based on retained old data and backups. Validate how legitimate writes since cutover will survive. Communicate that a reverse DDL statement cannot reconstruct discarded information or guarantee semantic compatibility.

Key Trade-Offs & Follow-Up Traps

Retaining dual representations longer costs storage/code but extends some recovery options. Whole-database restore can lose unrelated valid changes and affect dependents. A backup is useful only with a tested recovery point/time and a plan for current writes; do not promise data-preserving reversal after an irreversible transform without evidence.
