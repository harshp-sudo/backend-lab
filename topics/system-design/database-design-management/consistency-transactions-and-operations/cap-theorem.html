CAP Theorem

🎯 The Hook & ELI5

Two shop desks keep the same stock number, but their telephone line breaks. One desk sells the last item. The other cannot learn whether that happened. It can keep answering from its old notebook, or refuse/wait when it cannot establish the current answer. No clever label supplies the missing information. CAP makes this tension precise for a distributed service under a network partition.

CAP concerns a particular combination of guarantees in a distributed read/write model. Its consistency is linearizability: operations behave as if a single up-to-date object executed them in an order respecting real-time completion. Its availability requires requests to non-failing participating nodes to complete with the model’s valid responses; returning an arbitrary error is not a trick that satisfies it. A partition prevents some required communication.

Under such failures, an implementation cannot guarantee both of those properties for every allowed execution. This is narrower than “every database chooses two features forever.” Specify the operation, topology, failure assumptions and client-visible contract. The consistency of ACID invariants is a different concept.

🗺️ High-Level Big Picture

The example uses different clients so the reader does not carry the writer’s new value. A policy that refuses the write earlier may preserve consistency, but it has already sacrificed availability for that request.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; SQL examples target PostgreSQL 18 unless explicitly labeled otherwise.

1. Define the object and its operations

Start with the actual promise: a globally unique reservation, a read/write register, an approximate view or an independently mergeable counter. A database can expose several contracts through different operations. Product-wide CP/AP labels often hide those differences.

Write what a successful operation means and which failures the service claims to tolerate. If a design quietly allows a stale answer, conflict or rejected write, name that concession instead of arguing that a successful HTTP status proves all guarantees.

2. Use the precise meaning of consistency

Linearizability makes a completed write precede a later read in the apparent single-object history. Concurrent operations can be ordered consistently, but a read beginning after an acknowledged update cannot simply return an older value when that violates the object contract.

A transaction that obeys foreign keys may preserve ACID consistency while a remote replica read is stale. Serializable execution and linearizability are also different definitions; strong transaction/real-time combinations need their own explicit guarantee. Do not substitute “the rows look valid” for a real-time read contract.

3. Use the precise meaning of availability

The theorem’s availability is not a monthly uptime percentage, nor merely “some users can reach one healthy region.” It asks whether the required operations at non-failing participants finish with valid modeled responses despite the allowed partition. A timeout, indefinite wait or unavailable error gives up that guarantee for the affected operation.

A practical service may rightly prefer fast failure to a false answer. That is an engineering choice, not a mathematical escape. Define separately the service-level latency/uptime targets used in real operations.

4. Trace the missing information during a split

In the diagram, the isolated reader cannot know whether the remote side completed value one, value two or no update. If both reads and writes must remain available on both sides, there is a history in which a locally returned answer conflicts with a completed write.

Refusing or delaying an operation can preserve the stronger answer contract. Returning a permitted weaker answer can preserve more local service. Additional nodes change which partitions permit useful progress but cannot guarantee all required communication survives every partition allowed by the model.

5. Choose policies per operation and business risk

A final allocation of one globally unique resource may require coordination and refusal/pending behavior during uncertainty. A social view or independently mergeable observation may accept delayed/conflicting information with a defined reconciliation policy.

Majority-based systems can keep the majority side working while refusing the minority. That can be a useful design, but it is not full availability at every non-failing node. Nor does an overlap arithmetic condition such as R + W > N alone specify a complete linearizable protocol: membership, ordering, read/write algorithms and failure handling matter.

6. Plan healthy-network latency and recovery separately

CAP does not by itself quantify normal network latency, rank vendors, or prescribe a universal default. Even without a partition, stronger cross-region coordination can cost latency. Measure that trade-off under the chosen protocol instead of invoking CAP to justify every slow query.

After a partition heals, define conflict resolution, read repair/reconciliation and treatment of decisions already exposed to users. Convergence alone does not prove a hard business invariant was never broken. If an approximate count can merge safely but a seat sale cannot, those operations need different contracts.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Choose-two slogan becomes a proof

Symptom: A design says “CA” and ignores partitions in its claimed distributed failure model.

Root Cause: Failure assumptions were omitted from a feature checklist.

Fix/Prevention: State the allowed partitions and trace which operations cannot safely complete under them.

HTTP success hides a false answer

Symptom: A service returns stale inventory as a globally current fact.

Root Cause: Transport success was confused with the modeled operation’s correctness.

Fix/Prevention: Expose weaker/pending results honestly or preserve the authoritative guarantee through coordination.

Quorum arithmetic replaces protocol

Symptom: Overlapping read/write counts are assumed sufficient for linearizability.

Root Cause: Versioning, concurrent writes, membership and read algorithms were left unspecified.

Fix/Prevention: Use a proven supported protocol and verify its actual consistency guarantee instead of inferring it from R/W/N alone.

Choose honest partition-time semantics and keep real-time consistency, invariant validity and ordinary uptime metrics distinct. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

What does consistency mean in this theorem?

Linearizable single-copy operation behavior that respects real-time completion, not merely row validity or the C in ACID.

Does returning unavailable to every isolated request preserve CAP availability?

No. Refusing or indefinitely waiting gives up the required completion guarantee for those operations, although it can be the right engineering choice.

Why is partition tolerance not simply a feature you toggle off while claiming the same fault model?

A partition is a communication failure in the environment. You may narrow the promised failure model, but that changes the claim rather than eliminating the missing information.

Why is eventual convergence insufficient for a never-oversell guarantee?

Replicas can later agree that two conflicting sales occurred. Reconciliation after exposing both promises does not prove the invariant held at the moment of acceptance.

Tricky & Most-Asked Interview Scenarios

Two isolated regions each see one remaining seat. Can both promise success?

The Scenario & Constraint

A reservation service promises a single globally unique seat and must handle a communication split. Both regions remain reachable to local users. What will you do and why?

The Direct Answer & Architectural Decision

Put final allocation behind a supported authoritative coordination/ownership protocol and allow pending/failure where the required authority cannot be established. Do not confirm two independent sales from stale copies. If using preallocated rights, specify the changed operation boundary and finite local rights rather than claiming an always-available globally current seat object.

Key Trade-Offs & Follow-Up Traps

This sacrifices some partition-time write availability or flexibility. Accepting provisional reservations with explicit compensation is another business contract, but it is not the original never-conflict guarantee. Replicas converging after selling twice do not repair the fact that both users were promised the same seat.

A reaction count may be temporarily stale. Must every click wait for another region?

The Scenario & Constraint

A social application accepts temporary count differences, and independent increments can be merged under a chosen operation-identity/counter design. What partition-time policy will you propose?

The Direct Answer & Architectural Decision

Use an explicitly weaker local/projection contract where appropriate, with duplicate-aware increment identity or a proven mergeable representation and a documented convergence/repair path. Tell the product what a displayed count means during a split. Keep hard authorization or finite-allocation decisions on their separate authoritative protocol.

Key Trade-Offs & Follow-Up Traps

More local availability comes with staleness and merge/retention complexity. A counter that only increments is simpler than arbitrary reset/decrement semantics; adding those operations changes the design. “Eventually consistent” is not an algorithm and does not automatically make repeated deliveries or conflicting updates safe.

The database is labeled CP, but a browse cache can be stale. Is that a contradiction?

The Scenario & Constraint

An architecture review assigns one CP/AP label to the whole product, then treats every endpoint as having identical guarantees. Checkout and product browsing have different requirements. What will you specify?

The Direct Answer & Architectural Decision

Describe each operation’s authority, freshness and partition behavior. An authoritative purchase can require coordination while a derived browse view returns a clearly weaker result. Trace which actual store/protocol each endpoint uses rather than inheriting an unqualified vendor label. Verify that a weak view cannot silently authorize the hard purchase invariant.

Key Trade-Offs & Follow-Up Traps

Operation-specific contracts require careful API/UI boundaries and monitoring. Using one stronger path for everything may be simpler but cost latency/availability. A stale cache remains a weaker read even if its underlying authoritative owner uses a stronger protocol.

R + W is greater than N. Does that alone prove every read is linearizable?

The Scenario & Constraint

A design lists replication factor and overlapping quorum counts but omits concurrent-write ordering, membership changes and what a read returns from multiple versions. How will you review the guarantee?

The Direct Answer & Architectural Decision

Require the actual proven/supported read-write protocol and failure assumptions, including version ordering, authoritative membership, concurrent operations and completion rules. Overlap can be an ingredient but does not specify those algorithms. Test adversarial timelines and cite the database’s explicit guarantee instead of promoting arithmetic into a proof of linearizability.

Key Trade-Offs & Follow-Up Traps

A stronger coordinated protocol can add latency or reject work during partitions. A weaker quorum/versioned system may be perfectly suitable if exposed honestly. Sloppy/fallback replicas or changing membership can undermine naive overlap reasoning, so state exactly which participants and histories the equation describes.

An isolated node returns HTTP 503 immediately. Has it preserved both C and A?

The Scenario & Constraint

A team argues every request receives an HTTP response, so rejecting isolated reads keeps full CAP availability while preserving a current-value guarantee. What will you correct?

The Direct Answer & Architectural Decision

Separate transport response from successful completion of the modeled read/write operation. An unavailable error or indefinite wait is the availability concession in this context; it may be the correct choice to avoid an unjustified current answer. Document client retry/pending behavior and practical service objectives without redefining the theorem’s terms.

Key Trade-Offs & Follow-Up Traps

Failing quickly can improve operational latency and protect resources even though full theorem availability is not achieved. A valid domain rejection is different from making an unavailable read appear successful with an invented value. Review what the operation’s specification actually permits.

Cross-region reads are slow when the network is healthy. Is “CAP requires it” a sufficient diagnosis?

The Scenario & Constraint

No partition is observed, yet a strongly coordinated read path misses latency targets. The team cites CAP instead of examining its protocol and physical placement. What will you investigate?

The Direct Answer & Architectural Decision

Measure round trips, leader/quorum placement, storage work and the actual read contract. Decide whether a lower-latency topology, local weaker view or more selective strong-read requirement fits the business. CAP identifies an impossibility under specified communication failures; it does not by itself produce a normal-case latency budget or identify a query bottleneck.

Key Trade-Offs & Follow-Up Traps

Local weaker reads trade freshness/real-time guarantees for latency; moving authority can shift write/recovery costs. A faster index may help database work but not eliminate inter-region coordination. Explicitly separate healthy-network performance choices from partition-time guarantees.
