Password Hashing (bcrypt / Argon2)

🎯 The Hook & ELI5

Instead of keeping everyone’s locker combination, a club keeps a special difficult-to-make fingerprint of each combination. It can check a submitted combination by making the fingerprint again. Each member gets a different random seasoning so equal passwords do not look identical. A thief can still guess combinations, so checking each guess should be deliberately expensive.

Password hashing protects stored password verifiers against offline guessing after a data leak. It is different from encryption, which is meant to recover plaintext, and from a fast general-purpose digest that lets an attacker test enormous numbers of guesses cheaply. Passwords chosen by people often have limited entropy, so storage design must expect guessing.

Use a managed password-hashing implementation with an appropriate algorithm and encoded parameter/salt metadata. This lesson compares Argon2id and legacy bcrypt using OWASP guidance checked 2026-11-17 and RFC 9106 for Argon2 semantics. It does not execute a hashing library or benchmark production hardware; actual library/version and cost settings must be verified in the deployment.

🗺️ High-Level Big Picture

The stored verifier includes enough nonsecret algorithm/salt/parameter information for verification. A pepper, when used, belongs to a separately protected secret lifecycle and is not a replacement for the salt or cost.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the actor, trusted input, enforcement point and recovery boundary.

1. Choose the right kind of storage protection

Store a password verifier produced by a maintained password-hashing API, not plaintext or reversible password encryption. Salted SHA-256 is still designed to be fast and does not provide the intended adaptive cost. Encryption can protect other recoverable personal data, but recoverability is normally not the goal for a password.

A stolen hash database still exposes users to offline guessing; hashing does not make weak passwords unguessable or protect a compromised live verifier from every attack. Combine appropriate authentication policy, breach response and online abuse controls with strong verifier storage.

2. Use salts and understand what a pepper changes

A unique random salt prevents identical passwords from yielding the same stored verifier under the same profile and defeats shared precomputation. It is normally stored with the hash and need not be secret. Well-designed library APIs usually generate/manage it; verify that behavior rather than reusing one global salt.

An optional pepper is secret material held separately, such as under a controlled secret-management boundary. It can improve a database-only compromise model but adds retrieval, rotation and recovery obligations. Do not log it or assume an environment variable is automatically inaccessible after application compromise.

3. Compare Argon2id and bcrypt under explicit constraints

Argon2id combines the variant properties described by RFC 9106 and supports memory, time/pass and parallelism parameters. Memory cost is total configured memory in its defined units; increasing parallelism is not simply multiplying total memory or a universal security improvement.

OWASP’s checked guidance favors Argon2id for new suitable systems and discusses bcrypt for legacy use. One listed Argon2id minimum profile is 19 MiB, two iterations and one degree of parallelism; it is a dated baseline, not proof of suitable latency/capacity on your hardware. Bcrypt has a 72-byte input boundary under common implementations, with exact truncation/rejection behavior depending on library/version. Preserve byte/Unicode semantics deliberately.

4. Tune cost with a bounded verification budget

Benchmark the chosen supported profile on actual target hardware under expected concurrency, including invalid-login traffic. Balance offline guessing cost against useful authentication latency and service memory/CPU capacity. A setting that is tolerable for one login can exhaust a process when many expensive verifications run at once.

Bound input, admitted verification concurrency and retries; use safe per-account/client/global abuse controls as appropriate. Do not silently downgrade the algorithm during load spikes. Use framework-supported timing/error behavior so unknown accounts or legacy hash paths do not unnecessarily reveal account existence, while keeping the resource budget finite.

5. Migrate only after trustworthy verification

Retain each account’s algorithm/parameter metadata so the correct library verification path can check the submitted password. After a successful legacy verification, rehash with the current profile and replace the verifier under a safe account/version update. Never reinterpret existing bcrypt output as if it were Argon2 output.

Test long and multibyte passwords against legacy semantics before migration; a previously truncated password may create compatibility/security questions that need an explicit reset policy. Accounts that never log in may need a forced reset under the chosen risk policy. Do not retain plaintext passwords to make future migration easier.

6. Plan breach and pepper/key recovery

On verifier/secret compromise, assess the exposed algorithm/cost, affected population and credential reuse risk, then use an explicit reset, session/token revocation and notification/recovery policy. Rehashing a known compromised password without changing it does not make the password unknown to the attacker again.

Pepper rotation behavior depends on the construction and retained data; do not promise that every stored verifier can be updated offline without users’ passwords. Losing an essential secret can make verification impossible. Test backup/restore, controlled recovery, cost upgrades and denial paths using the actual library before production claims.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Salted fast hashes crack cheaply

Symptom: A leaked password database yields many recovered weak passwords.

Root Cause: Salt was mistaken for adaptive guessing cost.

Fix/Prevention: Use an appropriate supported password-hashing profile plus authentication policy.

Long Unicode passwords change meaning

Symptom: Two inputs share a legacy verifier or a library rejects an old account unexpectedly.

Root Cause: Byte limits and version-specific bcrypt behavior were ignored.

Fix/Prevention: Verify exact input semantics and migrate/reset deliberately without silent truncation.

Stronger hashing takes down login

Symptom: Invalid traffic consumes all memory/CPU.

Root Cause: Cost was benchmarked without concurrency/admission limits.

Fix/Prevention: Bound verification work and tune measured capacity without fail-open or silent downgrade.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Use supported password verification designed for offline guessing resistance, keep salt/pepper roles distinct, and tune migration, recovery and admitted work as carefully as the algorithm. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Why can a salt be stored beside the verifier?

Its purpose is unique per-password hashing and prevention of shared precomputation, not secrecy.

What new obligation does a pepper add?

A separately protected secret lifecycle including access, availability, rotation and recovery.

Why are Argon2 parameters not universal constants?

They trade offline guessing expense against the actual system’s memory/CPU/latency and concurrent verification budget.

When can a login support a safe hash upgrade?

After successful verification under the stored legacy profile, use the submitted password to create a new supported verifier without storing plaintext.

Tricky & Most-Asked Interview Scenarios

The database stores SHA-256 with unique salts. Is that enough?

The Scenario & Constraint

Passwords are human-chosen and a database leak permits offline guessing. What will you do and why?

The Direct Answer & Architectural Decision

Migrate to a supported adaptive password-hashing profile with measured cost and unique salts, retaining legacy verification only for a deliberate rehash/reset transition.

Key Trade-Offs & Follow-Up Traps

Higher cost consumes resources. Salts stop shared precomputation but do not make a fast digest appropriately expensive for each guess.

A long multibyte password behaves differently after a library update. What do you inspect?

The Scenario & Constraint

Existing accounts use bcrypt and input may exceed the implementation’s supported byte boundary. What will you do and why?

The Direct Answer & Architectural Decision

Verify the exact library/version’s truncation or rejection behavior and Unicode/byte policy, test existing fixtures and use an explicit migration/reset path instead of silent reinterpretation.

Key Trade-Offs & Follow-Up Traps

Compatibility can require user action. Character count is not byte count, and casually prehashing changes the construction and needs vetted guidance.

Argon2 login workers exhaust memory during an attack. Lower every hash cost?

The Scenario & Constraint

The profile was measured for one request but admitted concurrency is unbounded. What will you do and why?

The Direct Answer & Architectural Decision

Bound verification admission/concurrency and abuse budgets, measure total resource use and tune an appropriate supported profile without silent emergency downgrade.

Key Trade-Offs & Follow-Up Traps

Some users wait or are rejected. More memory/instances may help measured capacity, but unbounded work remains a failure mode.

How do you move active accounts from bcrypt to Argon2id?

The Scenario & Constraint

The service cannot recover stored plaintext and must retain legitimate login continuity. What will you do and why?

The Direct Answer & Architectural Decision

Verify each login with its recorded legacy algorithm/parameters, then rehash the successfully submitted password under the new supported profile and safely update the record.

Key Trade-Offs & Follow-Up Traps

Inactive users may need reset and mixed-profile support adds complexity. Rehashing the old hash as if it were the password is a different construction, not ordinary migration.

The pepper is lost during recovery. Can salts reconstruct it?

The Scenario & Constraint

Stored verifiers require the separately held secret for the chosen construction. What will you do and why?

The Direct Answer & Architectural Decision

Follow the controlled secret recovery/backup plan if available; otherwise use an explicit credential reset/recovery policy without bypassing verification.

Key Trade-Offs & Follow-Up Traps

Recovery material itself needs strong protection. A salt is public uniqueness metadata, not a backup copy of the pepper; bypassing the missing secret grants unverified access.

A breach recovered users’ actual passwords. Does raising cost alone repair it?

The Scenario & Constraint

The attacker already knows the plaintext for affected accounts. What will you do and why?

The Direct Answer & Architectural Decision

Use the incident policy to reset affected credentials, address session/token authority and credential reuse risk, and upgrade verifier protection for future storage.

Key Trade-Offs & Follow-Up Traps

Resets and revocation interrupt users. Stronger hashing makes future guesses more costly but cannot make an already disclosed password secret again.
