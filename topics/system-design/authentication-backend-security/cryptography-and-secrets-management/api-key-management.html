API Key Management

🎯 The Hook & ELI5

A delivery company gives each shop a different restricted loading-dock key. A label identifies which key to revoke, while the secret key opens only the permitted dock. Keeping one permanent master key in every shop makes replacement and accountability almost impossible. A copied key identifies a credential, not necessarily the human who copied it.

An API key is a machine/client credential whose authority depends on the issuing service’s policy. Its lifecycle includes generation, delivery, verification, scope, rotation, revocation, attribution and compromise recovery. A key can identify a caller application or tenant while still being insufficient for sensitive end-user authorization.

Consider partner integrations submitting shipment requests. Each partner/environment receives independently revocable credentials with explicit permissions and budgets. The design uses opaque high-entropy secrets conceptually, not passwords chosen by people, and does not execute a vendor key service. JWT signing keys, human passwords and delegated OAuth access are different credential models with different verification and recovery choices.

🗺️ High-Level Big Picture

The identifier helps locate and audit a credential without exposing its secret. Rotation is a coordinated client/server transition; changing a value in a dashboard does not prove every client stopped using the old authority.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the actor, trusted input, enforcement point and recovery boundary.

1. Define identity, scope and ownership

Give each partner/workload and environment an owner and a limited set of permitted actions/resources. Separate development and production authority. Avoid one shared key for every installation if you need independent attribution, budgets or revocation.

A machine key does not automatically identify the human user behind a request. If the operation needs user consent or per-user permission, use the appropriate delegated identity/policy contract as well. Keep API key acceptance separate from tenant/object/action authorization and high-value operation assurance.

2. Generate and deliver a credential deliberately

Use a supported cryptographically secure generator and an appropriately sized secret for the system’s risk model. A visible key identifier/prefix can support lookup and incident response; it must not be treated as the secret. Do not generate credentials from timestamps, usernames or sequential IDs.

Deliver over a protected authenticated management path and avoid secrets in query strings, ordinary logs, analytics or screenshots. If the product displays a secret only once, explain replacement rather than promising later recovery from a one-way verifier. Protect the administration endpoint that can issue new authority.

3. Choose storage from the actual verification need

If the server only needs to verify a presented high-entropy opaque key, store a suitable one-way verifier rather than a recoverable plaintext copy, under the supported cryptographic/service design. Use safe comparison APIs and access controls. Public lookup metadata and secret verifier have different exposure requirements.

Unlike weak human passwords, uniformly generated high-entropy API secrets do not have the same guessing-cost assumptions; do not copy a password-hashing recipe blindly or claim any hash construction fits every purpose. If a service must recover a third-party outbound credential, controlled encryption/secret management is a different requirement.

4. Check lifecycle and permission on every request

Resolve the intended credential, verify it, enforce active/expiry/revocation state and apply its scoped permissions/budgets. Bind tenant/resource decisions to trusted key ownership plus the actual requested object. A valid key for one tenant must not choose another tenant merely by changing a header.

Caches need a deliberate revocation freshness window. A dependency outage cannot silently allow an unverified key. Bound lookup and comparison costs and return safe errors that do not expose secrets or unnecessary account details. Record useful request/key identifiers for controlled audit without recording full credentials.

5. Rotate with explicit overlap and retirement

Issue an independently identifiable replacement, deploy it to the client, observe successful usage and retire the old credential within a bounded policy. Clients that need zero-downtime migration may use a short planned overlap, but every still-valid key remains usable authority.

For confirmed compromise, incident requirements can demand immediate revocation rather than a convenience overlap. Reconcile failed client deployments, cached verifiers and stale processes. Rotation is not finished just because the new key exists; verify old-key rejection after the promised cutoff and keep a controlled rollback plan that does not reactivate compromised authority.

6. Make leaks and ownership visible

Track owner, environment, creation/expiry, last use, scope and revocation events. Detect unusual usage and make unused/abandoned keys reviewable. Provide clients a supported replacement and incident-reporting path; key loss should not require broad sharing of a master credential.

Test wrong/unknown/expired/revoked keys, cross-tenant resources, rotation overlap, cache expiry, manager outage and accidental log exposure. This is a store-neutral lifecycle trace, not an executed SDK implementation. For a particular service, verify generated entropy, verifier format, delivery and rotation API semantics rather than assuming this diagram establishes them.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

A key ID is accepted as the secret

Symptom: Guessing a visible identifier grants access.

Root Cause: Lookup metadata and credential proof were conflated.

Fix/Prevention: Verify the complete supported secret against protected verifier state.

Rotation never retires old access

Symptom: Several old credentials remain active indefinitely.

Root Cause: Issuance was counted as completed rotation.

Fix/Prevention: Set a bounded overlap, observe rollout and verify old-key rejection.

A production credential appears in client code

Symptom: Anyone downloading the app can use partner authority.

Root Cause: A public execution environment was treated as secret storage.

Fix/Prevention: Move privileged use to a proper trusted boundary or use a suitable public-client identity protocol.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Manage API credentials as scoped, independently identifiable authority from issuance through verified retirement. Keep verification secrets, recoverable outbound credentials and user delegation as distinct needs. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

What is the difference between key identifier and secret?

The identifier locates/audits a credential; the secret proves possession under the verifier’s contract.

When is verification-only storage appropriate?

When the service only needs to validate a presented high-entropy key and does not need to recover its plaintext for another service.

What proves planned rotation is finished?

Required clients use the replacement and the old authority is rejected after the promised cutoff, including caches and stale processes.

Does an API key replace all user/resource authorization?

No. It represents its defined machine/client authority; user delegation, tenant/object policy and sensitive actions can require additional checks.

Tricky & Most-Asked Interview Scenarios

A production partner key appears in a public log. Keep a rotation overlap?

The Scenario & Constraint

There is evidence the credential is compromised. What will you do and why?

The Direct Answer & Architectural Decision

Revoke according to incident urgency, issue a scoped replacement through a protected path, remove/redact exposed copies where possible and investigate usage and effects.

Key Trade-Offs & Follow-Up Traps

Immediate revocation can interrupt clients. A long convenience overlap leaves known stolen authority usable; removing the log alone cannot make copied bytes secret again.

A partner needs planned rotation without failed shipments. What is the sequence?

The Scenario & Constraint

No compromise is suspected and both sides support independently identified keys. What will you do and why?

The Direct Answer & Architectural Decision

Issue a restricted replacement, deploy/observe its use, maintain only the approved bounded overlap and retire/test rejection of the old key with cache freshness accounted for.

Key Trade-Offs & Follow-Up Traps

Overlap temporarily increases valid authority. A single-value hard switch is simpler when downtime is acceptable, but rollback must not revive a compromised key.

Support wants to display a forgotten secret stored only as a verifier. What do you offer?

The Scenario & Constraint

The system deliberately cannot recover the plaintext credential. What will you do and why?

The Direct Answer & Architectural Decision

Offer authorized replacement/revocation and one-time protected delivery rather than pretending the verifier can be decrypted. Preserve audit and owner scope.

Key Trade-Offs & Follow-Up Traps

The client must redeploy. Recoverable encrypted storage serves a different requirement and adds key-access risk; it is not needed merely for verification convenience.

A valid tenant A key submits work for tenant B. Where do you reject it?

The Scenario & Constraint

The request body chooses a tenant independently of trusted key ownership. What will you do and why?

The Direct Answer & Architectural Decision

Resolve the credential’s scoped owner, verify the target resource/action and reject unauthorized tenant selection at the owning service.

Key Trade-Offs & Follow-Up Traps

Explicit delegation can support legitimate multi-tenant clients, but must be modeled. Credential validity alone cannot authorize arbitrary caller-selected scope.

A revoked key still works at one region. What changes?

The Scenario & Constraint

Local credential caches outlive the promised cutoff. What will you do and why?

The Direct Answer & Architectural Decision

Align cache lifetime/invalidation/version checks with revocation requirements, test each region and handle unavailable current state without granting unverified authority.

Key Trade-Offs & Follow-Up Traps

Fresher state costs latency and availability. An advertised bounded window can be an alternative, but an undocumented stale cache violates the immediate-revocation promise.

A mobile/browser bundle contains a privileged partner key. Is obfuscation enough?

The Scenario & Constraint

Every distributed client can be inspected and the key authorizes sensitive server actions. What will you do and why?

The Direct Answer & Architectural Decision

Remove privileged shared authority from the public bundle, revoke exposed credentials and use an appropriate trusted backend or supported per-client/user protocol.

Key Trade-Offs & Follow-Up Traps

The replacement architecture adds identity/operations. Public identifiers and limited nonsecret project keys can have other roles, but naming a privileged secret an API key does not make shipping it safe.
