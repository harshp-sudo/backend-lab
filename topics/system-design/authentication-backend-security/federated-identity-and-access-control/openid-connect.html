OpenID Connect

🎯 The Hook & ELI5

A trusted school sends a signed introduction naming a visitor for your club. You check which school wrote it, whether it was meant for your club and whether it belongs to the visit you just started. You still decide which rooms that visitor may enter. A matching email address on two introductions is not enough to merge two people’s memberships.

OpenID Connect adds an identity layer to OAuth 2.0. A relying party, the client, validates the provider’s authentication result through an ID Token and applicable claims/protocol checks. An OAuth access token instead authorizes access to a resource server under its own profile. Those roles are related but are not interchangeable.

Follow a workspace application offering sign-in through a configured OpenID Provider. We use Core 1.0 incorporating errata set 2, Discovery 1.0 and the separately specified RP-Initiated Logout extension when discussing those features. We choose a maintained SDK conceptually and an authorization-code/PKCE deployment under current OAuth guidance. No provider, SDK or real account linking is executed here.

🗺️ High-Level Big Picture

The relying party consumes the identity assertion intended for it. The resource API validates its own access authority; neither identity assertion nor profile email alone replaces local account and permission policy.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the actor, trusted input, enforcement point and recovery boundary.

1. Establish the provider trust configuration

Begin from a configured allowed issuer and the client registration for that provider. Discovery supplies metadata under its specification, including consistency checks around the issuer and endpoints/keys. Do not choose a trust root by accepting an arbitrary token’s requested metadata URL.

A multi-provider product needs explicit issuer-to-client/key configuration and tenant onboarding policy. Fetch/caching needs bounded network behavior and safe outage handling. A document available over HTTPS is not automatically an identity provider your application has chosen to trust.

2. Bind the login transaction using the actual flow

Start the supported authorization-code/PKCE flow through the SDK, recording per-request transaction context. Validate the returned response against that context and enforce applicable state/issuer protections. Use a nonce as specified for the selected OIDC flow/profile and verify its returned value when used/required.

State, nonce and PKCE are not three spellings of the same check. They address request/response, ID Token and code-exchange binding in their applicable protocol roles. A copied static value or a callback accepted without its initiating transaction undermines those protections. Follow the exact SDK/provider profile rather than inventing a partial callback parser.

3. Validate the ID Token for this relying party

Use the supported signature/key and claim validation required by Core and the chosen profile: trusted issuer, intended audience/client, applicable authorized-party rules, time checks and transaction-bound nonce where applicable. Reject a genuine token meant for another client or a different purpose.

If using UserInfo, validate its subject relationship as required by the specification rather than combining unrelated profile responses. An ID Token is an assertion to its relying party, not an instruction that every backend must accept it as API access. The API’s access-token profile may be JWT or opaque and has a separate audience/policy.

4. Map identity without unsafe account merging

Use the issuer and subject relationship as the external account identity under the provider’s contract. Email is a profile attribute that can change, be unverified or have provider-specific reassignment behavior; equal text is not by itself sufficient proof to merge accounts. Pairwise identifiers also limit assumptions about comparing subjects across clients.

Account linking should require deliberate policy and proof appropriate to both existing and new accounts, such as fresh authentication to the account being linked. Bind the link operation to the current session/action and audit it safely. A convenience feature that grants access based only on a returned email can become an account takeover path.

5. Establish local continuity and authorization deliberately

After accepting the authentication result, create or update a local session under the application’s session policy. Regenerate session identity at the appropriate trust transition and apply tenant membership/action checks separately. Provider authentication does not mean membership in every local organization.

Risk-sensitive actions can require recent authentication or a particular assurance contract, but the client must validate the provider’s actual claim semantics. Do not invent assurance from the name of an identity provider or assume every successful login involved the same factors. Document how disabled local membership takes effect despite a still-active provider session.

6. Scope logout, rotation and recovery

Local logout clears/inactivates local session authority. RP-Initiated Logout is a separate supported request to the provider, with its own registered redirect and validation rules. Other applications’ sessions and issued API access tokens require their own supported logout/revocation propagation.

Test wrong issuer/audience, response swapping, missing transaction context, stale/unknown keys, subject mismatch, email collisions, account-link CSRF and provider outage. Observe safe issuer/subject/decision context without bearer token disclosure. No diagram arrow promises global instant logout or security beyond the verified extension/SDK deployment.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

ID Token accepted as universal API credential

Symptom: Another client’s identity assertion reaches a protected API.

Root Cause: Token purpose/audience and API authorization were conflated.

Fix/Prevention: Use the appropriate token at each relying-party/resource boundary.

Two accounts merge on matching email

Symptom: An external identity gains access to an unrelated local account.

Root Cause: An attribute was treated as proof of control of both accounts.

Fix/Prevention: Use trusted issuer/subject mapping and deliberate linking proof.

Local logout advertised as global logout

Symptom: The provider or another relying party still has an active session.

Root Cause: Separate session/token domains were assumed to share one delete operation.

Fix/Prevention: Use supported logout protocols and state the actual scope and propagation limits.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Validate a trusted provider’s identity assertion for the correct relying party and transaction, map accounts deliberately, and retain local authorization and explicit logout scope. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

What does OIDC add to OAuth?

A defined identity/authentication assertion layer for the relying party, including ID Token and applicable claim/flow validation.

Why retain issuer with subject?

The subject’s meaning belongs to its issuer and applicable client/subject-identifier contract; an isolated string is not a universal identity.

Why is email equality insufficient for linking?

It is a mutable/provider-specific profile attribute and does not by itself prove the current user controls both accounts.

Does closing a local session log out every provider and API?

No. Each session/token domain has its own supported logout/revocation protocol and visibility boundary.

Tricky & Most-Asked Interview Scenarios

A gateway accepts any valid ID Token for API calls. What changes?

The Scenario & Constraint

Tokens may be intended for several relying parties and carry no API-specific authority. What will you do and why?

The Direct Answer & Architectural Decision

Validate the API’s intended access-token profile/audience and resource policy, while the login client separately validates its own ID Tokens.

Key Trade-Offs & Follow-Up Traps

Issuer/client configuration adds work. Shared signing keys do not make tokens for different recipients and purposes interchangeable.

A request supplies a new issuer URL and asks to trust its keys. Is discovery enough?

The Scenario & Constraint

The service has not onboarded or authorized that provider. What will you do and why?

The Direct Answer & Architectural Decision

Restrict discovery to the configured trusted issuer/client relationship and enforce issuer/metadata consistency with bounded retrieval. Reject untrusted authority.

Key Trade-Offs & Follow-Up Traps

Provider onboarding is less automatic. HTTPS transport to an attacker-controlled issuer proves its connection, not the application’s trust in its identities.

A new provider returns the same email as an existing administrator. Merge automatically?

The Scenario & Constraint

The user has not proven control of the existing local account. What will you do and why?

The Direct Answer & Architectural Decision

Keep issuer/subject identity mapping distinct and require explicit appropriately authenticated account-linking proof before joining privileges.

Key Trade-Offs & Follow-Up Traps

More user steps reduce convenience. Even verified email has provider/reassignment semantics; blindly merging on text equality does not establish control of the old account.

All users share one login nonce. What does the client need?

The Scenario & Constraint

Callbacks can be replayed or associated with the wrong in-progress login. What will you do and why?

The Direct Answer & Architectural Decision

Use per-transaction SDK-managed binding and validate the flow-specific nonce/state/issuer and PKCE requirements instead of a static global value.

Key Trade-Offs & Follow-Up Traps

Transaction state needs expiry/cleanup. A nonce check cannot replace audience/signature checks, and PKCE is not a generic substitute for every OIDC response check.

An employee remains logged in at the provider after losing workspace membership. Can they enter?

The Scenario & Constraint

Local organization access has been revoked even though external authentication succeeds. What will you do and why?

The Direct Answer & Architectural Decision

Accept external identity only as identity, then deny absent current local membership/action permission under the workspace’s defined freshness policy.

Key Trade-Offs & Follow-Up Traps

Fresh local checks add dependencies. Provider SSO convenience and local authorization are separate; changing the provider account is not the only way to remove workspace access.

Local logout succeeds but another relying party stays signed in. Is that unexpected?

The Scenario & Constraint

The product claimed global logout without a configured cross-party protocol. What will you do and why?

The Direct Answer & Architectural Decision

Define local/provider/other-party/API token scope, implement supported logout mechanisms where required and test their actual propagation and failure behavior.

Key Trade-Offs & Follow-Up Traps

Federated logout adds protocol/state coordination and may be incomplete during failures. RP-Initiated Logout alone is not proof that every independent API token and session has vanished.
