OAuth 2.0

🎯 The Hook & ELI5

You let a photo-printing shop collect selected pictures from your locker without giving it your locker password. The locker office issues a limited pass for that job. The pass says what the shop may access; it does not automatically tell the shop everything it needs to know about who you are.

OAuth 2.0 is a framework for delegated authorization. A client obtains constrained access to a resource server through an authorization server under a grant, rather than collecting the resource owner’s password. Identity/login needs an appropriate identity protocol such as OpenID Connect; OAuth access alone is not a complete end-user authentication assertion.

Follow a calendar-printing client requesting read access to a user’s calendar. We use authorization code with PKCE under RFC 6749, RFC 7636 and RFC 9700, and consider RFC 10017 for browser architectures. Public versus confidential client capabilities, redirect registration, scope, response binding and token lifecycle must be configured for the actual platform. No live provider or OAuth SDK is executed here.

🗺️ High-Level Big Picture

The code travels through the redirect; the token exchange enforces the supported request/client binding. The API independently validates the resulting token and the actual resource permission.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the actor, trusted input, enforcement point and recovery boundary.

1. Assign roles and narrow the delegated job

The resource owner authorizes access, the client requests it, the authorization server issues authority and the resource server enforces it. One organization can operate several roles, but keeping them conceptually distinct exposes trust and failure boundaries.

Request only necessary scopes/resources and explain them clearly. A calendar read grant should not silently become write access to every user’s data. Scope names are issuer/API contracts, not universal permission semantics; the resource server must still apply tenant/object/action policy.

2. Classify the client before handling credentials

A confidential client can protect suitable credentials in its execution environment, such as an appropriately operated backend. A browser-delivered application cannot keep a shared embedded client secret confidential merely by minifying its code. Client identifiers are normally identifiers, not passwords.

For a browser, compare a server-assisted/BFF design with supported direct browser OAuth using current browser guidance. Keeping tokens server-side changes the exposure boundary but adds session/cookie/CSRF responsibilities. Native, machine and browser clients have different capabilities; do not copy one deployment’s grant settings blindly.

3. Bind the authorization request and redirect

Register and enforce the intended redirect under the protocol/provider contract and avoid open redirectors that forward an authorization response to arbitrary destinations. Bind each response to the initiating client transaction/session, including the appropriate state/issuer checks and flow-specific protection.

PKCE creates a per-request verifier and derived challenge, then requires the verifier at code exchange. Use the supported secure challenge method/profile rather than a static verifier reused across users. PKCE, state and an OIDC nonce address related but distinct protocol checks; configure the actual SDK’s supported protections instead of treating those names as interchangeable.

4. Exchange the code under the actual client contract

The authorization server validates the code, redirect/client binding, PKCE verifier and applicable client authentication before issuing tokens. A stolen code should not simply be redeemable by an unrelated requester. Use TLS and supported SDK handling, avoiding tokens or verifiers in ordinary logs and browser URLs.

Codes are not durable bearer API credentials. Handle one-time/expiry and uncertain exchange outcomes under the provider’s contract rather than retrying captured codes as a general login mechanism. Do not use legacy implicit/password grants as a default shortcut around the modern threat model.

5. Enforce access at the resource server

The API accepts only its intended access-token profile, validating signature/claims or online token state according to the issuer/resource contract. A token may be opaque; OAuth does not require every access token to be a JWT. Verify audience/resource and permissions rather than accepting any genuine issuer token.

An OIDC ID Token intended for the client is not a substitute for API authorization. A user’s grant also does not automatically permit the client to access every tenant’s object. Preserve the delegated actor/scope boundary through gateways and downstream calls.

6. Operate renewal, consent changes and compromise

Define access/refresh lifetime, supported revocation, consent withdrawal, key changes and safe reauthorization behavior. A refresh token needs the client-specific replay/storage protections described by current guidance. Already-issued access tokens can have a different revocation visibility boundary.

Test redirect mismatch, transaction swapping, verifier failure, wrong audience, denied consent, scope changes, stolen credentials and provider outage. Store only necessary metadata and make pending/failed states explicit. The sequence is conceptual; correct deployment still depends on the chosen authorization server, client SDK and resource validation configuration.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

OAuth access becomes an invented login identity

Symptom: A client assumes a token proves a specific person without an identity contract.

Root Cause: Delegation was confused with OIDC authentication.

Fix/Prevention: Use the appropriate identity assertion and its validation profile.

A static secret ships to every browser

Symptom: Anyone can copy the supposed confidential credential.

Root Cause: Public code was treated as a protected secret store.

Fix/Prevention: Use the public-client model or a real confidential backend.

Any issuer token unlocks every API

Symptom: A token for one audience accesses unrelated tenant data.

Root Cause: Resource/token profile and object policy were omitted.

Fix/Prevention: Validate the intended access authority and enforce resource/action scope.

Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Which roles should an OAuth trace identify?

Resource owner, client, authorization server and resource server, even when some share an operator.

What does the PKCE verifier/challenge bind?

The supported authorization-code exchange to the initiating client request holding the verifier; it is not a universal API proof or authorization policy.

Why is a client secret in shipped JavaScript not confidential?

Users and attackers can inspect the distributed program and values; the environment cannot protect that shared secret.

Must OAuth access tokens be JWTs?

No. The issuer/resource contract can use opaque or structured tokens with the corresponding validation mechanism.

Tricky & Most-Asked Interview Scenarios

A calendar access token is used as the app’s user identity. What is missing?

The Scenario & Constraint

The client has delegated resource access but no verified end-user identity assertion contract. What will you do and why?

The Direct Answer & Architectural Decision

Use OIDC or another supported authentication protocol for identity, validate its assertions and keep calendar authorization separately scoped.

Key Trade-Offs & Follow-Up Traps

Another protocol adds configuration. An access token may enable a profile API under a defined contract, but its existence alone is not a universal login statement.

A SPA hides its client secret in a bundled file. Is it confidential?

The Scenario & Constraint

The browser downloads all code and configuration. What will you do and why?

The Direct Answer & Architectural Decision

Treat it as a public client with the current supported code/PKCE protections, or move confidential-client duties to a trusted backend/BFF and protect that session boundary.

Key Trade-Offs & Follow-Up Traps

A BFF adds operations; direct browser OAuth retains browser token risks. Obfuscating a shipped value does not change client capabilities.

An authorization redirect can forward to an arbitrary URL. What do you fix?

The Scenario & Constraint

A registered endpoint acts as an open redirector and can leak authorization responses. What will you do and why?

The Direct Answer & Architectural Decision

Remove unsafe forwarding, enforce the supported exact redirect/client binding and validate transaction/issuer context using maintained SDK/provider controls.

Key Trade-Offs & Follow-Up Traps

Tight redirects can require legitimate client configuration changes. PKCE is valuable but does not excuse arbitrary response routing or missing transaction checks.

Every login shares one PKCE verifier. What changes?

The Scenario & Constraint

The verifier is static configuration rather than a per-authorization secret. What will you do and why?

The Direct Answer & Architectural Decision

Generate/store a fresh verifier for each supported transaction, send its correct challenge, enforce exchange verification and bind the callback to that transaction.

Key Trade-Offs & Follow-Up Traps

Per-request state adds lifecycle cleanup. PKCE is not a password or a replacement for all OAuth state/issuer or OIDC nonce checks.

A read-calendar grant can delete another tenant’s event. Where is the boundary?

The Scenario & Constraint

The API checks only that the token came from a trusted issuer. What will you do and why?

The Direct Answer & Architectural Decision

Validate audience/resource and granted action scope, resolve tenant/object ownership and enforce the application policy at the API owner.

Key Trade-Offs & Follow-Up Traps

Policy checks and metadata add work. A signed token’s scopes are meaningful only under the issuer/API contract and cannot override unrelated tenant rules.

The authorization server is down during renewal. Should expired tokens keep working?

The Scenario & Constraint

Private API access depends on a defined token lifetime and revocation model. What will you do and why?

The Direct Answer & Architectural Decision

Honor the validation/lifetime contract, provide a controlled renewal/reauthorization failure and use only explicitly supported bounded cache behavior for still-valid authority.

Key Trade-Offs & Follow-Up Traps

Users may lose availability. Silently extending expired authority changes the security promise; resilient provider operations and suitable token lifetimes must be designed before the outage.
