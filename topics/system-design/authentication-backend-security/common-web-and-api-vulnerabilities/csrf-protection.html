CSRF Protection

🎯 The Hook & ELI5

A club receptionist recognizes your membership pass whenever your messenger arrives. A stranger tricks the messenger into delivering an instruction while still carrying your pass. The receptionist must check that the instruction belongs to an authorized visit, not merely that the messenger automatically brought a familiar pass.

Cross-Site Request Forgery exploits credentials that a browser attaches automatically when a request is eligible, commonly session cookies. An attacker can cause a victim’s browser to attempt a state-changing request without needing to read the response. The defense must bind the operation to an appropriate trusted request/session context, not merely confirm that the user has a session.

Follow a cookie-authenticated account portal changing a recovery email. We use the framework’s supported CSRF mechanism conceptually, combined with deliberate cookie/origin policy and safe HTTP behavior. Browser and framework semantics must be verified for the real deployment. No live request or active form is embedded in this lesson; the process and cases are explanatory.

🗺️ High-Level Big Picture

A valid session cookie proves neither that this request was intentionally initiated by trusted application interaction nor that the requested account action is authorized. Request-forgery and action checks serve different purposes.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the actor, trusted input, enforcement point and recovery boundary.

1. Identify ambient credentials and state changes

Inventory browser endpoints that change meaningful state, including account settings, logout and login/linking flows. Cookies are often ambient: the browser may send them based on URL/cookie rules rather than a script explicitly proving intent for this particular operation.

An API using a bearer credential explicitly attached by trusted client code has a different classical CSRF model, but token format alone does not decide it. A JWT in an automatically sent cookie can still be part of a CSRF-vulnerable design. Also consider client-side code that an attacker can steer into sending a same-origin request.

2. Keep safe methods free of business mutations

Do not perform consequential state changes through GET or another method intended to be safe. Links, navigation and browser behaviors can trigger such requests without the explicit interaction your business assumes. Moving a mutation to POST is necessary design hygiene, not sufficient proof of CSRF protection.

For the recovery-email change, verify the request under the framework’s supported protection before committing the action, then authorize the target account and any required recent assurance. A CSRF token cannot authorize changing someone else’s account merely because it is valid for the caller’s session.

3. Use supported session-bound token protection

A synchronizer-token pattern associates an unpredictable value with the authenticated context and validates its presentation through the supported request channel. Use the framework’s generation, transmission and verification APIs and protect token exposure in URLs/logs or cross-origin reads.

Where a double-submit pattern is appropriate, use a supported signed/session-bound construction under its verified threat model. Merely comparing an arbitrary cookie to an arbitrary request value can fail if an attacker can plant or influence the cookie. Do not improvise cryptography or assume any matching two strings establish trusted intent.

4. Validate origins and browser metadata deliberately

Origin/Referer checks and Fetch Metadata can provide useful request-context signals under a strict configured policy. Compare the actual expected origin/target using correct parsing and trusted proxy configuration; suffix matching against attacker-controlled host text is insufficient.

Decide how missing headers, privacy clients and legacy/browser integrations are handled according to risk and compatibility. Do not silently treat absent proof as trusted for a sensitive action. Webhooks and machine clients have different authentication needs and should not accidentally inherit a browser-only exception that bypasses their own security contract.

5. Understand SameSite, CORS and sibling origins

SameSite is scoped to browser site rules, not identical origin equality. A sibling subdomain can be cross-origin yet same-site under the applicable scheme/domain model. If untrusted content shares that site, SameSite alone may not block its requests to the application. Cookie defaults and edge behavior must be tested on supported browsers.

CORS primarily governs browser cross-origin access/request permissions under its rules; a simple form-like request can reach a server even when the attacker cannot read the response. Strict custom-header/CORS designs can be part of a verified defense, but arbitrary reflected origins, broad trusted subdomains or safelisted-content fallbacks can break the assumptions. Use the framework/token/origin policy appropriate to the actual endpoint.

6. Test failure, login transitions and interaction with XSS

Test missing/invalid/wrong-session tokens, cross-site requests, sibling-origin requests, safe-method mutations, header absence and reverse-proxy origin configuration. Include login/account-linking flows with their actual OAuth/OIDC state, nonce and PKCE responsibilities; do not indiscriminately disable protection at every callback or confuse the protocol checks.

XSS running in the trusted origin can often obtain request context or issue actions despite conventional CSRF measures. Fix the XSS boundary as well. These are scoped architectural cases, not a live framework implementation or external attack test. Observe safe rejection metadata without leaking session or CSRF credentials and verify legitimate clients still work.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

A forged write succeeds without readable response

Symptom: An attacker cannot read private data but can trigger a change.

Root Cause: Response-read restriction was mistaken for request authorization.

Fix/Prevention: Validate the state-changing request’s required CSRF/origin context.

A sibling host bypasses assumed SameSite isolation

Symptom: Untrusted tenant content shares the registrable site.

Root Cause: Same-site and same-origin were treated as identical.

Fix/Prevention: Model sibling trust explicitly and enforce suitable origin/token boundaries.

Matching cookie/request tokens accept planted values

Symptom: An attacker influences both compared values.

Root Cause: Naive double submit lacked the required authenticity/session binding.

Fix/Prevention: Use the supported signed/session-bound construction or appropriate synchronizer mechanism.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Protect state changes according to actual browser credential and origin behavior. Bind request context with supported mechanisms, keep site/origin distinctions clear and enforce authorization independently. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

Why are automatically attached credentials relevant?

A browser can send them on an attacker-induced eligible request even when the attacker does not know the secret.

Why is inability to read a response insufficient?

A state-changing request can already have caused an effect; classical CSRF does not require response disclosure.

How can two hosts be same-site but cross-origin?

Origin includes scheme/host/port, while site grouping follows browser scheme/domain rules and can include sibling subdomains.

Can a valid CSRF defense make XSS harmless?

No. Malicious code inside the trusted origin can often use the application’s request capabilities; the XSS source/sink needs its own fix.

Tricky & Most-Asked Interview Scenarios

An attacker cannot read the response but changes a victim’s email. Why?

The Scenario & Constraint

The cookie-authenticated endpoint accepts a forged state-changing request. What will you do and why?

The Direct Answer & Architectural Decision

Use the supported framework CSRF/session and appropriate origin checks before the mutation, then authorize the account/action and required assurance.

Key Trade-Offs & Follow-Up Traps

Token/origin integration adds work. Blocking response access via CORS cannot undo an already accepted change.

The team replaces the session ID with a JWT cookie and removes CSRF checks. Is that justified?

The Scenario & Constraint

The browser still attaches the authentication cookie automatically. What will you do and why?

The Direct Answer & Architectural Decision

Retain protection appropriate to the ambient-cookie request model and separately validate the JWT profile/lifecycle. Evaluate transport/client behavior rather than token format alone.

Key Trade-Offs & Follow-Up Traps

A deliberate explicitly attached bearer-header architecture has different classical CSRF assumptions but retains XSS/token risks. A JWT label does not decide browser request intent.

Untrusted tenant content on a sibling host reaches the app despite SameSite. What changes?

The Scenario & Constraint

Those hosts share a browser site but are not the same origin. What will you do and why?

The Direct Answer & Architectural Decision

Treat sibling trust explicitly, enforce strict expected-origin and supported token policy, and consider domain isolation when untrusted content should not share that boundary.

Key Trade-Offs & Follow-Up Traps

Separate domains and stricter checks add operational/client complexity. SameSite alone cannot provide origin-level isolation under this site relationship.

Matching cookie and body tokens are accepted after cookie planting. What is missing?

The Scenario & Constraint

The chosen pattern does not authenticate/bind the token to the intended session. What will you do and why?

The Direct Answer & Architectural Decision

Replace it with the framework’s supported signed/session-bound double-submit or synchronizer mechanism and test the actual cookie scope/injection threat.

Key Trade-Offs & Follow-Up Traps

Binding and key/session lifecycle add work. Random-looking equality alone does not prove the attacker could not choose both values.

A cross-site link performs a state-changing GET. Will SameSite=Lax save it?

The Scenario & Constraint

The endpoint mutates account state through a navigation-compatible request. What will you do and why?

The Direct Answer & Architectural Decision

Remove mutation from safe-method handling, require the proper state-changing operation and its supported CSRF/origin/authorization controls.

Key Trade-Offs & Follow-Up Traps

Clients may need migration. Merely changing GET to POST without the remaining request checks does not finish the defense.

A script injected into the real app sends valid CSRF tokens. Is the token system broken?

The Scenario & Constraint

The attacker’s code runs with trusted-origin browser capabilities. What will you do and why?

The Direct Answer & Architectural Decision

Fix the XSS source/sink, investigate effects and credential exposure, and retain correctly scoped CSRF/session/action controls rather than expecting them to remove same-origin code authority.

Key Trade-Offs & Follow-Up Traps

Layered defenses cost effort. Stronger action assurance can limit some consequences, but CSRF tokens alone are not an XSS isolation mechanism.
