SQL Injection

🎯 The Hook & ELI5

A restaurant order form has a box for a customer’s name. The kitchen must read “Pat” as a name, not as permission to rewrite the recipe book. SQL injection happens when customer-written data becomes part of the database’s instructions. Keeping the instruction and its supplied values separate is the key boundary.

SQL injection occurs when untrusted input changes the structure or meaning of a SQL command rather than remaining a data value. It can expose, modify or destroy data under the database account’s authority. Input validation helps define an application contract, but safe query construction must hold even for names containing quotes or previously stored unusual text.

Follow a tenant-scoped contact search. We use Python 3.10’s sqlite3 parameter binding for a local in-memory example; other drivers use their own APIs/placeholder syntax. The model demonstrates values versus approved structural choices, not network security, real database privilege configuration or complete application authorization.

🗺️ High-Level Big Picture

Parameters bind values, not arbitrary table names, column names or SQL keywords. Structural choices must remain application-owned, and a safely constructed query can still violate authorization if its scope is wrong.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the actor, trusted input, enforcement point and recovery boundary.

1. Find every query-construction boundary

Trace request, file, message and stored values into actual SQL execution APIs. Risk can appear in a raw ORM escape hatch, reporting job, administrative filter or second-order use of data written earlier. “It came from our database” does not make a value safe to concatenate as SQL code.

Distinguish the query’s fixed structure from each variable data value and each requested structural option. A valid-looking identifier can still select a forbidden tenant/resource; query construction and authorization must both be correct. Bound expensive queries and result size separately from injection prevention.

2. Bind data through the actual driver

This executable Python 3.10/SQLite model binds tenant and name as values and maps sort choices to fixed application-owned column names. The tenant argument is assumed already authorized by the caller’s trusted context; the function is not an authorization layer. All data and payload-looking strings stay inside an in-memory database.

import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE people (tenant TEXT, name TEXT, created INTEGER)")
db.executemany("INSERT INTO people VALUES (?, ?, ?)", [
    ("alpha", "O'Reilly", 1),
    ("alpha", "Zoe", 2),
    ("beta", "Hidden", 3),
])

def find(tenant, name, sort="name"):
    column = {"name": "name", "created": "created"}.get(sort)
    if column is None:
        raise ValueError("unsupported sort")
    query = (
        "SELECT name FROM people WHERE tenant = ? AND name = ? "
        + "ORDER BY " + column
    )
    return db.execute(query, (tenant, name)).fetchall()

assert find("alpha", "O'Reilly") == [("O'Reilly",)]
assert find("alpha", "' OR 1=1 --") == []
assert find("alpha", "Hidden") == []
try:
    find("alpha", "Zoe", "name; DROP TABLE people")
except ValueError:
    pass
else:
    raise AssertionError("unapproved structure accepted")
assert db.execute("SELECT count(*) FROM people").fetchone()[0] == 3
print("parameter binding model: passed")

Passing the values separately lets the driver preserve their data meaning. Do not interpolate values into a string before passing it to an API whose name sounds like prepared execution. Verify the actual driver’s placeholder, binding and multi-statement behavior.

3. Keep structural options inside a small trusted map

Parameters ordinarily represent values, not SQL grammar. For a selectable sort column/direction, map the external option to a fixed known identifier/keyword and reject unsupported choices. Prefer a fixed query or separate predefined statements when that is simpler.

Do not concatenate a caller-supplied table name after checking only that it contains letters. Even syntactically valid tables can be unauthorized. Dynamic reporting query builders need a deliberate approved grammar and resource policy, not a generic string sanitizer that promises to make arbitrary SQL safe.

4. Review ORM and stored-procedure escape paths

An ORM can bind values safely through supported APIs, but raw query strings or interpolated fragments can recreate the same code/data confusion. Likewise, a stored procedure that dynamically concatenates untrusted input can still be vulnerable. Review the executed statement construction rather than the product label.

Track second-order paths: a saved filter or customer name may be safe during insertion and unsafe during a later report. Reapply the correct binding/structural-control boundary at every SQL sink. Sanitizing once at the input edge cannot account for all future interpretation contexts.

5. Limit damage and expose safe outcomes

Use database identities with only required permissions and separate administrative/migration authority from ordinary application queries. Restrict unnecessary dangerous operations, schemas and network access under the actual database/deployment model. This contains impact but does not repair an injectable read query.

Return safe errors without raw statements, credentials or internal schema details. Keep controlled diagnostic context and trace attempted misuse. Generic failures do not prove the query is safe: blind/error-free injection can still affect behavior, so test the construction boundary itself.

6. Verify both safe construction and correct access

Test quotes, Unicode, empty/bounded values, payload-looking strings, allowed/forbidden structural choices and every raw/reporting path. Include cross-tenant negative cases using trusted resource scope. The local model’s quote/payload/sort checks are useful but do not establish safety for another driver or the entire application.

Use the named primary guidance and the actual driver documentation, then run representative tests under real database privilege and error configuration before deployment claims. Correct parameterization preserves input meaning; it does not automatically prevent expensive queries, unauthorized data access, XSS in displayed results or business-logic abuse.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Prepared in name only

Symptom: A prepared-query API receives an already interpolated string.

Root Cause: The code/data boundary was lost before the driver saw the values.

Fix/Prevention: Pass values separately through the supported binding interface.

Sort parameter becomes query code

Symptom: A caller inserts SQL through ORDER BY.

Root Cause: Structural identifiers/keywords were treated like bindable data.

Fix/Prevention: Map options to fixed application-owned structure and reject anything else.

Stored text attacks a later report

Symptom: A safe insert is followed by unsafe concatenation in a scheduled job.

Root Cause: Stored data was assumed inherently trusted as SQL.

Fix/Prevention: Trace every sink and bind again at the actual execution boundary.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Keep SQL instructions application-owned, bind data at every execution sink and constrain dynamic structure explicitly. Maintain resource authorization, least privilege and safe diagnostics as separate layers. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

What does parameter binding protect?

It preserves supplied values as data in the driver’s supported query interface instead of letting them alter SQL structure.

Can a parameter safely stand for any table or sort keyword?

Not ordinarily. Keep grammar fixed or map limited choices to approved application-owned identifiers/keywords.

Does using an ORM guarantee no SQL injection?

No. Safe structured APIs can help, while raw/interpolated escape paths can reintroduce the flaw.

Can a safely parameterized query still expose another tenant’s records?

Yes. Query syntax safety and trusted resource/tenant authorization are separate boundaries.

Tricky & Most-Asked Interview Scenarios

A real surname with an apostrophe breaks search. Ban apostrophes?

The Scenario & Constraint

Names must remain meaningful and the code concatenates them into SQL. What will you do and why?

The Direct Answer & Architectural Decision

Use the actual driver’s parameter binding for the value and retain domain-appropriate validation without altering legitimate name semantics.

Key Trade-Offs & Follow-Up Traps

Binding requires code changes and driver knowledge. Removing quotes corrupts valid data and is not a universal defense across query contexts.

Users choose a sort column. Bind the whole ORDER BY expression?

The Scenario & Constraint

The driver treats parameters as values and structural selection is currently arbitrary text. What will you do and why?

The Direct Answer & Architectural Decision

Map the external sort option to fixed approved identifiers/directions or predefined query shapes, rejecting unsupported structure while binding ordinary values.

Key Trade-Offs & Follow-Up Traps

Approved choices limit flexibility. Allowing arbitrary SQL is a different high-risk feature; a letters-only regex cannot establish resource permission.

The app uses an ORM but one endpoint is injectable. Why?

The Scenario & Constraint

Its raw-query helper interpolates a reporting filter before execution. What will you do and why?

The Direct Answer & Architectural Decision

Inspect the real SQL construction, replace unsafe interpolation with supported bound/structured APIs and audit similar raw paths and saved-filter use.

Key Trade-Offs & Follow-Up Traps

Some custom reports need redesign. The ORM’s presence does not confer binding on strings built outside its safe API.

A saved customer value attacks a nightly report. Where is the fix?

The Scenario & Constraint

Insertion was parameterized, but the report later concatenates stored text as SQL. What will you do and why?

The Direct Answer & Architectural Decision

Keep the stored value as data at the report’s execution sink using proper binding/approved query structure and trace other second-order paths.

Key Trade-Offs & Follow-Up Traps

Sink-by-sink review takes effort. Treating all database content as trusted code defeats the earlier safe insertion boundary.

A read endpoint’s database user can drop tables. Is reducing privilege sufficient?

The Scenario & Constraint

The endpoint also has an unsafe query-construction path. What will you do and why?

The Direct Answer & Architectural Decision

Fix injection and restrict the runtime database identity to required operations, separating administrative/migration access and safe diagnostics.

Key Trade-Offs & Follow-Up Traps

Least privilege adds permission maintenance and can contain impact. It does not make an injectable read path safe from data disclosure.

Parameter binding passes tests, but tenant B data is returned to tenant A. What is missing?

The Scenario & Constraint

The caller freely chooses the tenant argument despite a safe SQL statement. What will you do and why?

The Direct Answer & Architectural Decision

Resolve tenant/resource scope from trusted authorized context and enforce permission at the owner, retaining parameter binding for query safety.

Key Trade-Offs & Follow-Up Traps

Additional policy checks are required. Binding protects grammar, not the business meaning or authorization of a valid value.
