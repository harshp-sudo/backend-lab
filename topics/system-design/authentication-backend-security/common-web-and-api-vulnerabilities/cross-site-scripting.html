Cross-Site Scripting (XSS)

🎯 The Hook & ELI5

A noticeboard should display someone’s note as writing. If the board treats the note as instructions to unlock office doors, the writer gains the board’s authority. The same text can be safe on paper and dangerous as a button’s instructions, so protection depends on where the text is interpreted.

Cross-Site Scripting occurs when attacker-influenced content executes in a victim application’s browser origin. Stored, reflected and DOM-based descriptions identify useful data paths, not mutually exclusive guarantees about one defense. The decisive question is how untrusted data reaches an HTML, attribute, URL, script or DOM execution context.

Follow customer notes displayed in a support dashboard. The application needs ordinary text in most places and limited rich formatting in one editor. We use current OWASP XSS/DOM guidance and a small browser DOM demonstration. No payload is activated by loading this lesson; every example is escaped code text, and a real sanitizer/template framework must be selected and verified for its exact version.

🗺️ High-Level Big Picture

The source’s location does not determine safety. Context and sink semantics decide whether bytes are shown as data or interpreted with the application origin’s authority.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the actor, trusted input, enforcement point and recovery boundary.

1. Follow sources through storage and client code

Untrusted content can come from URL parameters/fragments, API results, saved comments, external messages or browser storage. A server may reflect it immediately, persist it for later readers or never see the DOM-only path. Trace transformations and decoding to the actual browser sink.

Do not mark a value safe forever because it was validated on input or came back from your own database. The same note can later appear in an attribute, export preview or client-side template with a different interpretation context. The rendering boundary must remain correct each time.

2. Prefer a text sink when the feature needs text

This complete small JavaScript DOM model constructs a paragraph and puts a payload-looking string into textContent. It does not append a live HTML element from that string or issue a request. It demonstrates text construction only, not a sanitizer for rich HTML, URL validation or a full template framework.

const note = '<img src=x onerror="window.__demoExecuted=true">';
const preview = document.createElement('p');
preview.textContent = note;
if (preview.children.length !== 0 || preview.textContent !== note) {
  throw new Error('Text boundary was not preserved');
}
console.log('safe text sink model: passed');

A template engine’s automatic escaping can serve the intended text context, but verify its exact behavior and escape hatches. Replacing a text assignment with innerHTML for convenience changes the boundary. HTML-looking text is not a reason to parse it as markup when the product only needs a note.

3. Use the defense for the actual context

HTML body text, quoted attributes, URLs, CSS and JavaScript are different contexts. Use supported template/construction APIs with the correct context-aware encoding and validate allowed URL schemes/targets where required. Avoid placing untrusted content into executable script/event-handler contexts.

A string escaped for HTML text is not thereby safe inside a JavaScript string or a URL that can execute script. Do not repeatedly decode/re-encode without knowing which representation reaches the final sink. Safer structural APIs can reduce the number of contexts requiring custom reasoning.

4. Treat intended rich HTML as a separate feature

If users genuinely need markup, use a maintained sanitizer configured for the allowed elements, attributes and URL behavior. Keep it updated and verify the selected library/version and configuration with the actual rendering path. Do not invent a regex that claims to remove every script form.

Do not modify sanitized output afterward in a way that reintroduces unsafe interpretation, or assume it is safe in every other context. Server/client rendering and rich-text editors may transform markup differently. For untrusted content needing stronger separation, consider a deliberately isolated presentation boundary with its own access/capability policy.

5. Understand CSP and cookie limits

A well-designed Content Security Policy can constrain script execution and provide defense in depth, but does not excuse unsafe sink construction. Exact nonce/hash/source/third-party behavior is a browser/deployment configuration problem, not a universal header string to copy blindly.

HttpOnly can stop direct script access to a protected cookie while malicious same-origin code can still send authenticated actions or read exposed page data. XSS can undermine CSRF defenses when it runs inside the trusted origin. Fix the source/sink defect and investigate credentials/actions; do not count one cookie flag as removal of the underlying authority.

6. Test the rendered application without activating lesson payloads

Test reflected/stored/DOM paths, ordinary quotes and markup-looking text, rich-HTML sanitizer cases, attribute/URL contexts and framework escape hatches. Check the actual browser DOM, not only a server string. Verify that unsafe values remain data and that allowed formatting still works.

The lesson’s text-sink model can run in an isolated browser context; its payload-looking string must remain inert. Do not run arbitrary user-submitted snippets or deploy attacks against external sites. Record what the local demonstration proves and verify the actual application/framework/sanitizer configuration before claiming broader protection.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Saved comments execute later

Symptom: A note becomes active code in the staff dashboard.

Root Cause: Stored data was rendered as trusted HTML.

Fix/Prevention: Use text output or a verified rich-HTML boundary according to the feature.

HTML escaping is reused inside script

Symptom: A supposedly escaped value breaks into execution context.

Root Cause: Encoding was selected for a different final interpreter.

Fix/Prevention: Avoid the executable context or use the correct supported construction boundary.

HttpOnly is mistaken for an XSS fix

Symptom: Injected code changes settings without reading the cookie.

Root Cause: Cookie-read protection was confused with origin-action authority.

Fix/Prevention: Fix XSS and retain layered session/action controls.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Trace every untrusted value to its final browser context. Render plain text as text, sanitize intentional HTML with maintained tools, and use CSP/session controls as additional scoped layers. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

What question is more useful than whether data is stored or reflected?

Which interpreter/context receives it at the actual sink, and whether it remains data there.

When is textContent appropriate?

When the intended feature is plain text; it does not interpret the supplied string as HTML markup.

Why is rich HTML a separate rendering contract?

It intentionally permits markup and therefore needs a maintained sanitizer/allowed capability policy rather than ordinary text encoding alone.

Can CSP or HttpOnly replace fixing an unsafe sink?

No. They address scoped consequences or execution paths while the rendering defect can still grant origin authority.

Tricky & Most-Asked Interview Scenarios

A saved customer note runs code for support agents. What do you change?

The Scenario & Constraint

The field only needs plain text, but the dashboard assigns it to innerHTML. What will you do and why?

The Direct Answer & Architectural Decision

Use a safe text/template output path, trace other renderings of the same stored value and investigate affected data/actions. Keep payload fixtures inert in tests.

Key Trade-Offs & Follow-Up Traps

Plain text loses deliberate HTML formatting, which this field does not require. Sanitizing at insertion alone cannot guarantee future rendering contexts remain safe.

Customers need limited formatted notes. Ban all markup or write a regex?

The Scenario & Constraint

The product deliberately allows rich text but not script-capable content. What will you do and why?

The Direct Answer & Architectural Decision

Use a maintained sanitizer with an explicit supported formatting/URL policy and test the actual editor/rendering/mutation path for the selected version.

Key Trade-Offs & Follow-Up Traps

Sanitization adds updates and configuration work. Plain text is a simpler alternative if requirements can change; a homegrown regex is not a general HTML parser/security boundary.

HTML-escaped input becomes an unsafe link. Why?

The Scenario & Constraint

The value is placed into a URL-capable context and its scheme/target is not validated. What will you do and why?

The Direct Answer & Architectural Decision

Use supported safe URL construction and an explicit allowed scheme/target policy appropriate to the feature, alongside context-correct attribute rendering.

Key Trade-Offs & Follow-Up Traps

Restrictions can reject legitimate links. Encoding text for one context does not determine whether the resulting URL is permitted or executable.

The server never reflects the payload, yet the browser executes it. Where do you look?

The Scenario & Constraint

Client code reads a URL fragment and inserts it into a dangerous DOM sink. What will you do and why?

The Direct Answer & Architectural Decision

Trace browser-side sources and transformations to the sink, switch to safe text/structural APIs or a verified required rich-HTML boundary and test the actual DOM result.

Key Trade-Offs & Follow-Up Traps

Client-side review adds paths that server scanners may miss. Server-side input handling cannot fix data the browser interprets independently.

A team leaves unsafe HTML in place because CSP is enabled. Is that complete?

The Scenario & Constraint

The policy and third-party script behavior may change across deployments. What will you do and why?

The Direct Answer & Architectural Decision

Repair the rendering boundary first, then verify a compatible restrictive CSP as defense in depth under actual browser/configuration tests.

Key Trade-Offs & Follow-Up Traps

A stronger policy can break legitimate scripts and needs rollout. CSP configuration does not make arbitrary untrusted markup inherently safe in every context.

Injected script cannot read HttpOnly cookies but performs transfers. What was missed?

The Scenario & Constraint

The script runs in the legitimate origin and can issue authenticated actions. What will you do and why?

The Direct Answer & Architectural Decision

Fix the XSS source/sink, enforce action authorization/assurance, investigate effects and credential/session risk, and retain properly scoped cookie/CSRF controls.

Key Trade-Offs & Follow-Up Traps

Additional protections add friction/operations. Cookie-read restriction does not remove the browser’s authenticated request capability or make same-origin malicious code harmless.
