JWT Authentication

🎯 The Hook & ELI5

A signed school permission slip lets a teacher check who issued it and whether it was changed. Anyone holding an ordinary signed paper can still read its contents. The teacher must also check that it names this trip, is still valid and grants the relevant permission. A signature from the wrong school is not enough.

A JSON Web Token is a claims format that can be signed and/or encrypted under the JOSE specifications. It is not an entire login, storage, authorization or revocation system. A common signed JWT can be verified locally, but base64url decoding only reveals bytes and a valid signature alone does not establish that this API should accept the claims.

Our example is an access-token profile for a billing API with a known issuer, intended audience, accepted token type, configured algorithm/key set and bounded lifetime. Define these requirements explicitly; not every JWT protocol has identical required claims. No custom JWT parser or cryptographic verifier is implemented here. Use a maintained library and its documented validation configuration in a concrete deployment.

🗺️ High-Level Big Picture

The trusted validation profile exists before reading the token. Its header and claims cannot choose an arbitrary trust root or replace the service’s resource-level authorization decision.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the actor, trusted input, enforcement point and recovery boundary.

1. Separate format, protocol and credential transport

A common compact signed JWT has encoded header and payload plus signature, but JWT also supports encrypted representations. Do not generalize one serialization into every JWT possibility. Signed readable claims should contain only information appropriate to exposure; signing is integrity/authenticity protection, not confidentiality.

OAuth access tokens need not all be JWTs, and an OIDC ID Token is not interchangeable with an API access token. Cookie versus Authorization-header transport also changes browser threat handling independently of the token format. Define the client and token purpose before discussing storage or CSRF.

2. Select trusted algorithms and keys by policy

Configure the allowed algorithm and trusted issuer/key relationship independently of untrusted token input. The token’s alg is data to validate against that configuration, not an instruction to accept any algorithm. Keep symmetric/asymmetric key usage and purpose consistent with the library profile.

A key identifier can select from an already trusted, bounded key set. Do not concatenate it into a database query/path or fetch an arbitrary attacker-supplied key URL. Discovery/JWKS retrieval needs a configured trusted issuer origin, caching, timeouts and resource bounds. Treat an unknown key as a verification problem, not permission to disable the check.

3. Validate the claims for this exact use

After cryptographic verification, enforce the expected issuer and audience and the token-type/profile rules for this endpoint. Apply the chosen expiry/not-before and bounded clock-skew policy, and use subject/client/scope claims according to their actual issuer-defined meaning.

An ID Token intended for a web client can be correctly signed yet inappropriate for a billing API. An account ID or role claim does not automatically grant access to every object. The application must authorize the requested action with trusted scope, tenant/resource facts and the required permission freshness.

4. Rotate keys without accepting arbitrary old authority

Plan publication of new verification keys before issuing tokens with them where the platform permits, retain needed old verification material through the supported outstanding-token lifetime and remove compromised authority under the incident policy. Signing-key rotation and normal token expiry are related but different events.

Bound JWKS caches and refresh behavior so unknown-key traffic cannot cause an unbounded fetch storm. Define whether a verified cached key may be used during an issuer outage under the stated freshness/risk policy. An unavailable key endpoint does not justify accepting unverifiable tokens or trusting decoded claims.

5. Choose revocation and storage from the threat model

Local signature/claim checks can avoid a lookup on each request, but they cannot learn an uncommunicated permission removal or credential compromise. Short lifetimes bound some exposure; deny lists, version checks or introspection add state and availability costs when prompt revocation is required.

Browser-readable storage exposes bearer credentials to malicious script in that origin. HttpOnly cookies reduce direct script reading but need appropriate CSRF/cookie policy, and malicious same-origin script can still issue actions. A BFF can keep OAuth tokens server-side under its own session boundary. None is a universal storage answer independent of client architecture.

6. Test the verifier as a rejection boundary

Use the selected library/version to test valid input plus wrong algorithm/key/issuer/audience/type, expired/not-yet-valid tokens, malformed/oversized input, key rotation and outage behavior. Do not call a decode function and label its output authenticated.

Observe rejection categories and safe key/issuer identifiers without logging raw bearer tokens. Preserve bounded parsing/fetch costs and explicit response behavior. This lesson provides architectural traces and source-checked validation requirements; no real signing keys, live issuer or JWT SDK is executed, so it makes no deployed-security claim.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Decoded means authenticated

Symptom: An unsigned/tampered token supplies an administrator role.

Root Cause: The application trusted parsed claims without full verification.

Fix/Prevention: Use a supported verifier and a preconfigured acceptance profile.

Correct signature for the wrong API

Symptom: A token issued to another client is accepted for billing.

Root Cause: Audience/type and purpose were not checked.

Fix/Prevention: Bind accepted tokens to this issuer, audience and intended protocol use.

Logout appears immediate but stolen token works

Symptom: Offline validators continue accepting a valid unexpired token.

Root Cause: Revocation knowledge was never communicated to the verifier.

Fix/Prevention: Match lifetime/stateful revocation to the promised cut-off and risk policy.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Accept a JWT only under a trusted purpose-specific verification profile, then authorize the real action. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

What does decoding a JWT prove?

Only how its bytes are represented; it does not verify authenticity or applicability to this API.

Does signing hide the claims?

No. A signed JWT commonly has readable claims; encryption is a distinct supported representation and key boundary.

Why validate audience and token purpose?

A genuine issuer can sign tokens for different recipients and uses; this endpoint must accept only its intended profile.

Why can offline token checks conflict with instant revocation?

A verifier cannot discover a new revocation event from unchanged signed bytes without another state/update mechanism.

Tricky & Most-Asked Interview Scenarios

A decode helper accepts a forged administrator claim. What changes?

The Scenario & Constraint

The endpoint parses JWT payloads but never establishes cryptographic or profile validity. What will you do and why?

The Direct Answer & Architectural Decision

Replace that path with maintained library verification configured for trusted algorithms/keys, issuer/audience/type/time rules, then perform resource authorization.

Key Trade-Offs & Follow-Up Traps

Verification/configuration and key lifecycle add work. A decode helper remains useful for debugging untrusted data but cannot establish identity.

A genuine ID Token works against the billing API. Is the signature enough?

The Scenario & Constraint

The token was intended for the login client rather than the resource server. What will you do and why?

The Direct Answer & Architectural Decision

Reject the wrong token purpose/audience and validate the API’s documented access-token profile, while keeping OIDC ID Token validation at the client boundary.

Key Trade-Offs & Follow-Up Traps

Explicit profiles need issuer/client coordination. Sharing a signing key across token types must not make every signed token interchangeable.

A token asks the verifier to fetch its own signing key URL. What do you trust?

The Scenario & Constraint

The caller controls the header and the service has broad network access. What will you do and why?

The Direct Answer & Architectural Decision

Select keys only through configured trusted issuer/key metadata and bounded retrieval, reject unsupported header choices and avoid turning key identifiers into executable paths/queries.

Key Trade-Offs & Follow-Up Traps

Controlled metadata refresh adds operations. A key matching an attacker’s signature proves nothing about that attacker being the trusted issuer.

A new key appears while the issuer endpoint is down. Disable verification?

The Scenario & Constraint

Some cached keys remain but the new token cannot be verified under the required policy. What will you do and why?

The Direct Answer & Architectural Decision

Keep trusted bounded cache rules for verifiable tokens and reject or return a controlled failure for unverifiable ones. Restore coordinated key publication/refresh and bound fetch retries.

Key Trade-Offs & Follow-Up Traps

Availability can be reduced. Accepting decoded claims is not a rotation strategy; a compromised cached key may require a stricter invalidation response than routine outage handling.

Logout is promised immediately but offline tokens last an hour. What must change?

The Scenario & Constraint

A copied access token remains valid at independent APIs after local browser cleanup. What will you do and why?

The Direct Answer & Architectural Decision

Define the real revocation cut-off and add a supported state/version/introspection update path where immediate invalidation is required, or explicitly change the promise with appropriately bounded token lifetime.

Key Trade-Offs & Follow-Up Traps

Online checks or propagated revocation add latency/state/availability cost. Deleting a browser token or revoking only refresh does not retroactively alter an already issued access token.

Should every SPA store JWTs in localStorage?

The Scenario & Constraint

The app handles private data and can choose a backend-assisted architecture. What will you do and why?

The Direct Answer & Architectural Decision

Choose the client architecture and threat model first; consider a BFF/server session to keep OAuth tokens server-side, and explicitly handle cookie/CSRF and same-origin script risks.

Key Trade-Offs & Follow-Up Traps

A BFF adds backend/session operations. In-browser tokens may fit another constrained client, but storage choice never eliminates the need to prevent XSS and validate API permissions.
