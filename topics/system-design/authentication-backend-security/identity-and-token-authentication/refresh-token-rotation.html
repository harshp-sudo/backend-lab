Refresh Token Rotation

🎯 The Hook & ELI5

A library gives you a replacement borrowing pass each time you renew. The old pass stops working. If it appears again, the library knows there may be two copies, but cannot tell whether a thief or a confused borrower brought it back. If the replacement envelope gets lost, simply accepting every old pass forever defeats the whole idea.

Refresh tokens let a client obtain new access tokens under an existing authorization grant. Rotation issues a replacement refresh token and invalidates the previous one while retaining their relationship for replay detection. RFC 9700 requires an appropriate replay-protection mechanism for public clients; rotation and sender-constrained refresh tokens are distinct supported approaches.

Our trace chooses a rotating token family with server-maintained state and a client that coordinates refresh. The exact provider/client policy for reuse, overlap, expiration and recovery must be verified. It is not a universal grace-window recipe, and revoking a refresh family does not automatically make every already-issued access token invalid at offline APIs.

🗺️ High-Level Big Picture

The server commit and the client receiving the replacement are separate events. A safe design handles that uncertainty without making all historical refresh tokens valid again.

🔍 Step-by-Step Mechanics

Follow the worked example one decision at a time. Open each step to connect the everyday model to the implementation; examples state their product/runtime scope explicitly. Trace the actor, trusted input, enforcement point and recovery boundary.

1. Separate access, refresh and session responsibilities

An access token is presented to a resource server under its profile. A refresh token is a credential for the authorization server and should not be sent as an API bearer token. Its grant, client binding, scope and resource restrictions must remain intact through refresh.

A refresh lifetime is not permission to keep a browser session forever. Define idle/absolute expiry, risk events, device/session relationships and whether fresh authorization is required. Decide whether the client should receive refresh credentials at all; a BFF can hold OAuth tokens behind a server session in an appropriate browser architecture.

2. Represent the family and atomic transition

Conceptually, retain the grant/client context, a current refresh credential verifier, predecessor/reuse relationship, lifecycle state and expiry. Store secrets under the selected provider’s protected credential model and avoid logging raw refresh tokens. The family ID is useful tracking state, not itself a credential.

Accepting R0, invalidating it and issuing/recording R1 must obey a supported atomic or equivalent serialized transition. Two independent read-then-write checks must not both create unrelated valid successors. Verify the actual authorization server’s persistence, concurrency and recovery contract; a diagram is not an implementation of it.

3. Coordinate clients without treating coordination as server security

Within one client, collapse simultaneous refresh attempts and share the fresh result with waiting requests under a safe client architecture. Multiple browser tabs, processes or devices need clearly scoped coordination; each device may appropriately have its own family. Avoid broadcasting raw secrets more widely than necessary.

Client coordination improves reliability but cannot prevent an attacker with a stolen token from racing. The server must still enforce its transition/replay policy. Do not use a promise cache or browser lock as proof that the refresh credential has only one possible holder.

4. Handle lost replies and legitimate reuse explicitly

The server can commit R1 and lose the reply. The client still holds R0, and a blind retry resembles replay. The server cannot infer from the repeated old credential alone which party is legitimate. A strict replay response can terminate the active family and require fresh authorization.

Some providers have documented narrowly bounded overlap/recovery semantics. Use them only under that exact supported contract and threat model, including which predecessor/result may be reused and how replay is bounded. An arbitrary application rule accepting any old token for several minutes can keep a stolen lineage alive or create multiple successors.

5. Revoke and expire the correct authority

On detected compromise, revoke the affected active refresh authority according to the grant/family policy, notify/re-authenticate appropriately and investigate safe metadata. Define whether other devices/families are affected and what the authorization server can actually invalidate.

Already-issued access tokens have their own validation/revocation lifetime. If immediate access cut-off is required, resource servers need a supported current-state or propagated revocation mechanism. Disabling refresh prevents future renewal but does not rewrite a valid signed token already accepted offline.

6. Test state transitions and recovery rather than only happy refresh

Test simultaneous R0 submissions, lost replacement reply, replay after several rotations, expired family, client mismatch, scope escalation and server restart. Measure replay signals, failure/reauthorization rates and storage/clock behavior without recording credentials.

The lesson uses a protocol/state trace, not a live authorization server or executable token implementation. Security depends on the provider/client combination and the entire token storage/transport chain. Sender-constrained alternatives have their own key/proof lifecycle and must not be confused with ordinary bearer rotation.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Read each failure as a story: diagnose the visible symptom, identify its cause, and change the mechanism that produced it.

Two valid successors escape one predecessor

Symptom: Concurrent R0 requests create separate active lineages.

Root Cause: The accept/rotate state transition was not atomic under the store contract.

Fix/Prevention: Use the supported serialized transition and test concurrent submissions.

A lost response logs out every tab repeatedly

Symptom: The client blindly refreshes with a retired credential after uncertain success.

Root Cause: No coordinated client/provider recovery contract exists.

Fix/Prevention: Coalesce attempts and use the provider’s documented recovery or fresh authorization path.

Refresh revoked but APIs still accept access

Symptom: Incident responders expect global immediate logout from one family update.

Root Cause: Refresh renewal and existing access validity were conflated.

Fix/Prevention: Coordinate the actual resource-server revocation boundary or disclose the bounded exposure.

🧠 Active Recall & Mastery Check

Summarize this in your own words: Treat refresh rotation as an atomic credential-family lifecycle with ambiguous network recovery, verified replay policy and separately scoped access-token revocation. Explain a concrete example, name an assumption that changes the answer, and sketch the relevant diagram without looking.

What changes during rotation?

The server replaces the accepted refresh credential, retires its predecessor and retains the relationship needed for the configured replay response.

Why is a repeated predecessor ambiguous?

It may be a copied credential or a legitimate retry after the replacement response was lost; the credential alone does not identify the legitimate party.

Why must the transition be protected against concurrency?

Otherwise two checks can accept one predecessor and create divergent valid successor state.

Does stopping refresh instantly invalidate all access tokens?

No. Existing access tokens follow the resource server’s separate lifetime and revocation contract.

Tricky & Most-Asked Interview Scenarios

Two tabs refresh R0 at once and the session breaks. What changes?

The Scenario & Constraint

The provider rotates and detects reuse, while the browser has no refresh coordination. What will you do and why?

The Direct Answer & Architectural Decision

Coalesce refresh attempts within the supported client architecture and share the resulting session state safely, while retaining server-side atomic transition/replay enforcement.

Key Trade-Offs & Follow-Up Traps

Cross-tab coordination adds complexity and does not stop a thief. Disabling replay checks globally trades away the intended protection rather than fixing client reliability.

The server committed R1 but its response vanished. Retry R0 forever?

The Scenario & Constraint

The client cannot establish whether rotation succeeded. What will you do and why?

The Direct Answer & Architectural Decision

Use the provider’s verified bounded recovery semantics if available; otherwise require fresh authorization under the strict replay policy instead of inventing unlimited old-token reuse.

Key Trade-Offs & Follow-Up Traps

Reauthorization harms convenience. A supported narrow overlap has a replay trade-off and is not equivalent to making every earlier family token valid.

Two workers each issue a successor for the same predecessor. What is broken?

The Scenario & Constraint

Both read current=R0 before either writes its own result. What will you do and why?

The Direct Answer & Architectural Decision

Replace the racy read/write path with a supported atomic/serialized family transition and reconcile any divergent active authority already created.

Key Trade-Offs & Follow-Up Traps

Concurrency control adds contention and failure handling. Client-side locking alone cannot protect the authorization server from another process or attacker.

An old family token is replayed after later rotations. What do you revoke?

The Scenario & Constraint

The provider retains the lineage and follows a replay-detection policy. What will you do and why?

The Direct Answer & Architectural Decision

Apply the verified active-family/grant replay response, stop further renewal of that compromised authority, investigate and obtain a fresh authorization grant as required.

Key Trade-Offs & Follow-Up Traps

The legitimate client may also lose continuity because the server cannot identify the legitimate holder from the retired token alone. Other device families and existing access tokens need explicit separate scope.

A stolen access token works after refresh-family revocation. Is rotation ineffective?

The Scenario & Constraint

Resource servers validate the signed access token offline until expiry. What will you do and why?

The Direct Answer & Architectural Decision

Treat refresh revocation as blocking renewal and add a supported resource-server current-state/revocation mechanism if the incident policy requires earlier access cut-off.

Key Trade-Offs & Follow-Up Traps

Online checks or propagation cost latency/state. Shorter access lifetimes bound some exposure but cannot honestly be called instant global invalidation.

A browser app embeds a client secret to protect refresh. Is that sufficient?

The Scenario & Constraint

All shipped JavaScript and its embedded values are accessible to users. What will you do and why?

The Direct Answer & Architectural Decision

Use the correct public-client security model with supported replay protection, or move confidential-client responsibilities to an appropriate backend/BFF with its own session/CSRF controls.

Key Trade-Offs & Follow-Up Traps

Backend assistance adds operations. A distributed static secret is not confidential, and rotation or key binding still requires the real provider/platform contract.
