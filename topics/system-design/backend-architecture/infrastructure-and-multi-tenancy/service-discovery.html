Service Discovery

🎯 The Hook & ELI5

ELI5 mental model. You call a company’s help line instead of memorizing the personal phone number of whichever employee is on duty. A directory keeps track of current contacts, and someone chooses an available person. Service discovery gives software a similar way to find a changing set of service locations without baking temporary machine addresses into every caller.

Backend instances start, stop, scale, and move. A hard-coded address can become stale even though the logical service still exists elsewhere. Service discovery maps a stable service identity to usable locations under a defined scope and update policy. Selecting a particular instance and routing traffic to it are related responsibilities, but resolving a name alone does not prove that an instance will successfully handle the next request.

WHY it matters: an order service must reach currently usable stock-service instances during scaling and deployments. Discovery should reduce topology coupling without turning its directory into an unexamined single dependency. Health signals, caches, connection reuse, and graceful shutdown determine how quickly callers stop using an obsolete location.

🗺️ High-Level Big Picture

A Stock instance becomes ready and is reflected in a registry or platform endpoint directory. In a client-side pattern, Orders obtains an endpoint set and a client policy selects a target. In a server-side pattern, Orders calls a stable routing address and a proxy/load-balancing component consults the endpoint set. DNS can participate in either arrangement depending on what the name resolves to.

🔍 Step-by-Step Mechanics

Follow the example one boundary at a time. Open each step to connect the familiar mental model to the internal mechanics.

1. Name the capability separately from its location

A help-line name remains meaningful when staff phone numbers change. Use a logical service identity scoped to the correct environment, tenant context where relevant, namespace, or region. A location is the current address/port/protocol combination that can serve it; that location is not the service’s permanent business identity.

A deployment platform may maintain the mapping, or instances/agents may register with a dedicated registry. Ensure the caller looks in the intended scope: an unqualified name that resolves differently in staging and production can be useful when intentional and dangerous when ambiguous. Discovery does not define the API contract at that address; the caller still needs a compatible protocol, identity/trust context, and operation semantics.

2. Register only endpoints that are actually ready

An employee should not appear as available before they can answer the phone. An instance may need configuration, credentials, caches, or dependent resources before serving real traffic. Separate process existence from readiness to perform its advertised capability.

Registrations can use explicit lifecycle updates, heartbeats/leases, or platform-managed endpoint state. Each mechanism has a detection delay and failure assumptions. A health check may pass while a particular customer request fails, and a temporary missed heartbeat can make a healthy instance look absent. Define useful signals and observe churn. Avoid treating a directory entry as a guarantee of future success; it is current routing information with a known freshness model.

3. Choose where endpoint selection lives

A caller can ask for a staff list and dial a chosen employee, or call reception and let it choose. In client-side discovery, the client receives/caches endpoints and applies a selection policy. This can avoid a separate proxy hop but distributes discovery and load-balancing behavior across client runtimes.

In server-side discovery, the client uses a stable routing address while a router/proxy resolves and selects backend instances. This simplifies clients but introduces a routing subsystem whose capacity and failure behavior matter. In either case, distinguish discovering candidates from selecting one and maintaining a connection. A list of ten addresses does not by itself provide fair load distribution or respect every request’s routing needs.

4. Understand DNS and caches instead of assuming instant updates

A saved phone list is convenient until a number changes. Discovery caches reduce lookup load and permit short interruptions, but they also retain stale endpoints. DNS time-to-live, client resolver behavior, registry watches, application caches, and long-lived connection pools can each influence when a change is observed.

On Kubernetes, ordinary Service DNS can resolve a stable service address, while suitable headless-Service configurations expose endpoint addresses. Those are platform-specific mechanisms, not requirements for service discovery generally. Read the platform’s actual readiness and resolution semantics. Refreshing DNS does not necessarily replace an existing pooled connection, and setting a short TTL is not a universal cure for all stale traffic.

5. Drain old instances and handle lookup/routing failure

An employee ending a shift should stop accepting new calls while finishing the current one. A graceful deployment removes or marks an endpoint as draining, allows updates to propagate, stops new work, and gives in-flight work an appropriate completion window. Abruptly killing an instance while every cache still lists it predictably causes failures.

If discovery is unavailable, a deliberate last-known-good cache can support some traffic, but its staleness and failure implications must be accepted. Do not retry every candidate without a deadline or create a lookup storm on every failed call. Bound retries, refresh appropriately, and distinguish resolution failure, connection refusal, authentication failure, and an application-level rejection. These symptoms point to different owners.

6. Test topology change, not just the first lookup

A directory looks reliable on its quietest day. Validate scale-up, scale-down, rolling deployment, slow health checks, registry partitions, and connection reuse. Measure discovery/update lag, endpoint churn, failed connections, and whether a few stale targets receive disproportionate traffic.

Keep capability meaning and service identity stable while locations evolve. A gateway or mesh may provide discovery integration, but it does not remove the need to understand the resulting data path and cache behavior. Start with the platform mechanism that fits the environment; a separate custom registry is not automatically necessary just because the application uses several services.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Treat a failure as a story: start with what a user observes, trace the boundary that failed, and choose a prevention that addresses the cause.

Traffic keeps reaching retired instances

Symptom: A rolling deployment produces connection failures after an instance is removed.

Root Cause: Cached endpoints or pooled connections outlive the shutdown transition.

Fix/Prevention: Coordinate draining, endpoint updates, refresh and connection lifetimes; test the real propagation delay before killing instances.

Healthy process, unusable capability

Symptom: The directory routes work to an instance that cannot serve requests.

Root Cause: Registration or liveness was confused with readiness for the advertised operation.

Fix/Prevention: Use meaningful readiness signals, remove/drain unusable endpoints, and still handle per-request failures with bounded recovery.

A discovery outage becomes a traffic storm

Symptom: A small registry failure causes repeated lookups and calls to every endpoint.

Root Cause: Clients refresh and retry aggressively without budgets or an accepted stale-cache policy.

Fix/Prevention: Bound attempts, add backoff/jitter, define last-known-good behavior where appropriate, and monitor update/lookup pressure.

🧠 Active Recall & Mastery Check

Summarize this in your own words

Explain the opening analogy, trace the worked example, and name one condition that would change your architectural decision. Try answering before opening the cards.

How does discovery differ from load balancing?

Discovery supplies candidate locations for a service under a scope/freshness contract. Load balancing or routing chooses among candidates for a request/connection. One component can perform both, but knowing several addresses does not by itself specify the selection policy.

Why might traffic still use an old instance after a DNS record changes?

Resolver/application caches may not have refreshed, and an existing pooled connection may remain open independently of DNS. Inspect the full client/platform behavior and drain plan rather than assuming the authoritative DNS update instantly moves all traffic.

Who selects the backend in client-side versus server-side discovery?

In a client-side pattern, client code obtains candidates and chooses a target. In a server-side pattern, a router/proxy behind a stable address performs backend selection. Both need current endpoint information and explicit failure behavior.

Does a successful health lookup guarantee the next request succeeds?

No. Health information is sampled and can be stale or incomplete for a particular operation. The target can fail immediately afterward. Good discovery improves candidate selection; callers still need deadlines, bounded retries where safe, and correct interpretation of failure.

Tricky & Most-Asked Interview Scenarios

Practice making a decision under a concrete production constraint. Open each answer, explain your reasoning aloud, then rate your confidence. The budgets and organizations below are author-created assumptions.

Deployments still send requests to terminating instances. What does service discovery need besides registration?

The Scenario & Constraint

Removing a shop from the directory does not stop a customer already walking through its door. During rolling deployment, requests hit terminating instances and fail. Endpoint updates and existing connections do not disappear instantly. What shutdown and readiness sequence will you verify?

The Direct Answer & Architectural Decision

Inspect the actual endpoint conditions, readiness changes, load-balancer propagation and open connection behavior. Stop accepting new work through the platform's supported readiness/drain mechanism, allow in-flight requests to finish within a bounded grace period, and ensure the process handles termination signals correctly. Tune the sequence from measured propagation rather than assuming deregistration is instantaneous.

For Kubernetes, verify the deployed version's EndpointSlice terminating/ready/serving behavior and the data plane's interpretation. Test long-lived connections, keep-alive clients and termination under load. Make retries safe where they are allowed, because a lost reply during shutdown can still hide a completed effect.

Key Trade-Offs & Follow-Up Traps

Graceful draining reduces rollout errors but takes time and temporarily retains old capacity. Immediate termination is a viable alternative for disposable idempotent work whose interruption/retry semantics are acceptable; it is not a default for every request.

Follow-up trap: passing a liveness check does not mean an instance should receive new traffic. If a hard node failure prevents draining, rely on bounded deadlines, safe retries and recovery rather than claiming the graceful path covers every outage. Registration, readiness and active-connection lifecycle are separate concerns.

A new service is registered, yet clients keep receiving name-not-found. Where will you look?

The Scenario & Constraint

A visitor keeps using yesterday's note saying the shop does not exist. The registry contains a newly deployed service, but some clients still fail DNS resolution. A direct registry query succeeds. What will you inspect before restarting every client?

The Direct Answer & Architectural Decision

Trace the complete resolution path: client/runtime cache, local resolver, forwarding DNS cache and registry answer. Check negative caching as well as positive TTLs, and compare fully qualified queries from the failing environment. A registry update cannot invalidate every downstream cache automatically.

Use the platform's documented DNS behavior and configure suitable cache lifetimes and retry/backoff for transient discovery misses. Observe actual answers and TTLs at each layer. Ensure the service is healthy and in the expected namespace/domain before blaming caching; an answer can be correctly negative for a wrongly qualified name.

Key Trade-Offs & Follow-Up Traps

You avoid unnecessary restarts and make rollout discovery predictable, but manage a trade-off between freshness and DNS load. A controlled readiness gate that waits for expected resolution is a viable alternative for deployment sequencing; it does not replace ongoing failure handling.

Follow-up trap: setting every TTL to zero does not force all client libraries to behave identically and can overload resolvers. If the application maintains long-lived resolved connections, refreshing DNS alone may not rotate them. Verify the client's connection lifecycle as well as the DNS cache.

The discovery control plane is unavailable. May clients keep using cached endpoints?

The Scenario & Constraint

An old address book may be more useful than none, but some shops may have closed. A registry disruption prevents fresh reads while existing service instances still run. Read traffic can tolerate some stale endpoint information; a sensitive writer endpoint cannot be guessed safely. What policy will you choose?

The Direct Answer & Architectural Decision

Separate discovery availability from endpoint authority. Permit bounded last-known-good endpoint use for operations whose risk allows it, with connection deadlines, health observations and a maximum staleness policy. Retain an explicit failure path when no usable target remains. Do not infer that a cached endpoint still holds exclusive write authority.

Check the discovery product's consistency/stale-read settings and caching chain, including how quickly unhealthy or removed instances disappear. Exercise a control-plane outage while data-plane traffic continues. Report degraded freshness so operators can distinguish resilient cached operation from a healthy registry.

Key Trade-Offs & Follow-Up Traps

You keep some traffic working during a control-plane incident but may contact stale or unhealthy targets. Failing closed on fresh discovery is a viable alternative where stale routing threatens correctness or security.

Follow-up trap: successful TCP connection is not proof that the server is the current leader. If an endpoint performs exclusive writes, enforce authority with the service's real leadership/fencing protocol or an authoritative proxy. Service discovery locates candidates; it does not supply the business consistency guarantee.

A headless service returns several addresses. Who chooses one and handles failure?

The Scenario & Constraint

A directory gives you several shop addresses instead of one receptionist. A Kubernetes headless Service resolves to multiple endpoints, and the application repeatedly chooses the first address. Traffic is uneven and a failed endpoint causes repeated errors. What responsibilities moved to the client?

The Direct Answer & Architectural Decision

Treat the returned addresses as candidates rather than a complete load-balancing policy. Use a client or proxy that refreshes discovery, selects endpoints appropriately, bounds connection attempts and handles target failure without unsafe retrying of effects. Verify how the actual protocol/client consumes multiple DNS records and reuses connections.

Choose headless discovery deliberately when direct endpoint identity is needed, such as a stateful protocol. If ordinary service-level balancing is sufficient, a normal virtual service address may provide a simpler abstraction. Check endpoint readiness and topology rather than assuming every returned address is equally suitable.

Key Trade-Offs & Follow-Up Traps

You gain direct instance visibility and protocol-specific control but take on balancing, caching and failure behavior. A standard ClusterIP Service or supported proxy is a viable alternative when clients should not manage individual instances.

Follow-up trap: DNS round-robin is not per-request fair balancing, especially with connection pools. If the protocol requires a specific shard or leader, random selection is wrong; route using that protocol's authoritative membership/role information rather than treating every discovered instance as interchangeable.

The same short service name reaches different backends in two environments. How will you debug it?

The Scenario & Constraint

Two towns can each have a Main Street. A client calling inventory works in one namespace but reaches a different service or fails in another. The application config uses only the short name. What will you inspect and make explicit?

The Direct Answer & Architectural Decision

Inspect the client's namespace, resolver search domains, cluster/domain configuration and the actual fully qualified answer. Compare the intended target with the resolved endpoint set from inside each workload's network context. Use the correct qualified service name for cross-namespace communication instead of assuming a short name has global meaning.

Keep environment-specific names in controlled configuration and validate them during deployment. Verify network policy, ports and service selectors after name resolution succeeds; a correct DNS answer does not prove connectivity or authorization. Add a diagnostic that reports the resolved target safely without leaking credentials.

Key Trade-Offs & Follow-Up Traps

You gain predictable routing and clearer diagnostics, but maintain explicit environment configuration. Short names remain a viable convenient alternative for intentionally local same-namespace dependencies when that scope is documented.

Follow-up trap: hard-coding instance IPs bypasses discovery and breaks when instances change. If the intended boundary is cross-cluster rather than cross-namespace, a local service FQDN is insufficient; use the platform's supported cross-cluster discovery/routing design and its security model.

A VM client needs changing service endpoints without a discovery SDK. Which integration fits?

The Scenario & Constraint

A visitor can use an ordinary phone directory without learning the registry's private filing system. A legacy VM application must call changing service instances, but its release process cannot adopt a discovery SDK. It can use standard DNS and a configured proxy. What will you choose?

The Direct Answer & Architectural Decision

Use a supported discovery-facing DNS interface or a local/server-side proxy that resolves membership for the legacy client. Choose based on the client's DNS refresh, connection reuse and protocol behavior. Keep service identity stable while the discovery/proxy layer tracks changing endpoints, and verify authentication and network access from the VM.

Test endpoint removal, DNS failure and a proxy restart under real connection pooling. Document health filtering and cache staleness rather than assuming a DNS answer is a live-health guarantee. An SDK is one integration option, not the definition of service discovery.

Key Trade-Offs & Follow-Up Traps

You avoid invasive legacy code changes and centralize discovery mechanics, but rely on DNS caching behavior or an additional proxy hop/failure domain. An SDK is a viable alternative when fine-grained metadata, watch semantics or protocol-specific routing justify the client change.

Follow-up trap: a very long-lived connection can keep using a removed instance after a DNS refresh. If the application needs immediate revocation or strict per-instance authorization, use a suitable enforced proxy/security boundary and explicit connection draining rather than relying on TTL alone.

Real-world impact

For an order backend, discovery earns its place by making scaling and replacement routine while preserving a stable capability identity. The hard parts are freshness, readiness, draining, and connection behavior—not merely turning a name into an IP address. Use the platform’s real semantics and test the transitions that deployments create.
