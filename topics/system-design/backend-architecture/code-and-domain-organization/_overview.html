Code & Domain Organization

ELI5 big picture. A workshop needs both a clear rulebook and sensible doors between responsibilities. Different people may use different tools while following the same business promises. These lessons explain how code can preserve those promises without becoming inseparable from a screen, database, or framework.

Code organization determines where a change belongs and which other code must understand it. Domain organization determines what the business concepts mean and who may make particular decisions. Both matter inside a monolith and inside a service; neither automatically requires a different deployment topology.

Why this branch exists. Layers, Clean Architecture, Hexagonal Architecture, and DDD are related perspectives with different emphasis. Do not force them into a winner/loser table. Use them to state responsibility, dependency direction, outside interactions, language, and invariants precisely.

Suggested reading guide

Begin with Layered Architecture for a request-flow vocabulary and the distinction between logical layers and physical tiers. Compare Clean Architecture’s policy/dependency emphasis with Hexagonal Architecture’s inside/outside ports-and-adapters view.

Read Domain-Driven Design to connect structural decisions to business meaning, bounded contexts, and protected invariants. If unclear terminology is the immediate problem, read DDD earlier. In every case, trace one concrete use case and distinguish a source-code dependency from a runtime call or a database transaction.

Explore this branch

  • Layered Architecture

    Separate request translation, workflow coordination, business decisions, and persistence responsibilities. Learn why a layer is not automatically another network service.

  • Clean Architecture

    Protect policies with deliberate inward source dependencies and meaningful contracts. The parcel-pickup example also traces how runtime calls still reach an outer adapter.

  • Hexagonal Architecture

    Give the application purposeful input/output ports and verify that real adapters satisfy their semantic promises. Alternative drivers should not require replacing the core rules.

  • Domain-Driven Design (DDD)

    Learn the business language with experts before selecting tactical structures. Bounded contexts, entities/values, aggregates, and events each answer a different modeling question.
