Layered Architecture

🎯 The Hook & ELI5

ELI5 mental model. At a library, a reader asks the front desk for a book. The librarian applies borrowing rules, and the storage room holds the physical copies. These are different responsibilities even if everyone works in the same building. Layered architecture separates software responsibilities in the same way: receiving a request, making a decision, and accessing infrastructure are not one job.

Without a clear division of responsibility, an HTTP handler can become the place that parses input, decides policy, runs SQL, and sends email. Layered architecture groups related technical responsibilities and defines which layers may depend on which others. It helps people locate behavior and reason about changes; it does not by itself define the business domain or guarantee good boundaries.

WHY it matters: changing the web interface should not require rewriting a loan-eligibility rule, and changing a database query should not redefine who may borrow a book. Distinguish a logical layer from a physical deployment tier: several layers may run inside one process, while multiple tiers communicate across network boundaries.

🗺️ High-Level Big Picture

A library borrowing request enters through a presentation adapter, reaches an application workflow, applies domain rules, and uses persistence to load/save state. This is one illustrative layering arrangement. Some layered systems put persistence at the bottom of a downward dependency stack; dependency-inverted designs let inner rules define an interface that outer infrastructure implements. Be explicit about which arrangement the code actually uses.

🔍 Step-by-Step Mechanics

Follow the example one boundary at a time. Open each step to connect the familiar mental model to the internal mechanics.

1. Separate translation from the business request

The front desk understands a reader’s form without deciding every borrowing rule itself. The presentation layer translates a transport-level request into an application-level operation. It handles concerns such as parsing, authentication integration, input shape, response status, and rendering a useful error.

For borrowBook(readerId, copyId), a missing identifier is a request-format problem. Whether that reader has exceeded the borrowing limit is a business decision. Keeping those distinctions explicit prevents the same rule from being implemented differently in a web handler and a future command-line import. Transport-specific objects should not become the only vocabulary the rest of the system can understand.

2. Put coordination in an application workflow

The librarian coordinates several checks and records without making the desk itself the whole library. An application layer describes a use case: load the reader and copy, ask the domain whether a loan is allowed, save the resulting change, and arrange follow-up work. It owns the sequence and required transaction boundary for that use case.

Coordination is not a reason to copy every rule into a giant service method. A workflow can ask a reader or loan policy to decide eligibility rather than embedding the rule beside database calls. Conversely, a domain object should not need to know how to write an HTTP response. Define a clear success/failure result that the presentation adapter can translate into its own protocol.

3. Keep rules distinguishable from storage mechanics

A borrowing policy still makes sense if the library swaps its filing cabinets for a different catalog system. The domain layer captures concepts and constraints such as available copy, active loan, borrowing limit, or overdue restriction. Those rules should be testable without recreating the entire web request pipeline.

A data-access or persistence layer handles queries, mapping, and storage interaction. Hiding SQL text behind a repository does not automatically hide all coupling: returning database row objects or lazy-loading entities into unrelated layers can leak storage behavior. Decide what representation crosses each boundary. For a small CRUD screen, direct mapping may be sufficient; for an invariant-rich borrowing workflow, explicit domain behavior is often easier to reason about.

4. State the dependency rule rather than guessing it

A building directory is useful only when it tells people which doors they may use. In a strict downward layered arrangement, a layer uses the next permitted lower layer. A relaxed arrangement may permit some layers to skip intermediates. Neither rule can be inferred merely from folders named controllers, services, and repositories.

Write the allowed dependency graph and check it. If the application layer needs persistence, one design depends on a concrete data-access service. A dependency-inverted alternative depends on an interface defined nearer the use case, with infrastructure implementing it. Clean and hexagonal architecture explore such boundary choices. The point is to choose the direction consciously, not to claim that every layered diagram has identical dependency semantics.

5. Understand local transactions and concurrent requests

Two librarians can both see one available copy unless the final lending decision is coordinated. Layers organize code; they do not automatically serialize concurrent requests. The application workflow must combine the rule check and persisted state transition using an appropriate transaction/concurrency mechanism at the authoritative data boundary.

An optimistic version check can reject a stale update; a uniqueness constraint may prevent two active loans for the same copy; a locking strategy has different contention costs. Choose according to the invariant. A transaction that stays open while calling a slow remote notification provider can hold resources unnecessarily. Persist a notification intent with the loan when recovery requires it, then perform remote work according to explicit delivery semantics.

6. Distinguish layers from tiers and test the right boundary

The librarian and front desk can be separate jobs at the same desk, while a remote warehouse is another building. A layer is a logical responsibility boundary; a tier is a separately deployed runtime location. Moving each layer to a different service creates network costs and shared-release risks; it is not a prerequisite for layered architecture.

Test rules directly, test application workflows with their interfaces, and test persistence mappings against the intended storage behavior. Add a small number of boundary-spanning checks for the important user journey. If tests can only verify a policy by starting the whole web/database stack, the responsibilities may be too entangled. If every layer merely passes an unchanged object onward, ask whether the layer provides a useful boundary or only ceremony.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Treat a failure as a story: start with what a user observes, trace the boundary that failed, and choose a prevention that addresses the cause.

The controller becomes the business model

Symptom: A batch import permits loans the web interface rejects.

Root Cause: Business eligibility logic lived only in the HTTP handler.

Fix/Prevention: Move shared decisions into explicit application/domain behavior and let each presentation adapter translate the same result.

Every request makes a tour of empty pass-through methods

Symptom: Changing one field requires editing many nearly identical files.

Root Cause: Layers were added for symmetry rather than a useful responsibility boundary.

Fix/Prevention: Keep layers that isolate meaningful change or policy, and remove needless forwarding while preserving deliberate dependencies.

Three layers are mistaken for three services

Symptom: A simple borrowing request becomes a slow chain of tightly coupled network calls.

Root Cause: Logical responsibility separation was equated with physical deployment separation.

Fix/Prevention: Keep layers in one process unless an operational constraint justifies tiers; measure the added failure and release costs.

🧠 Active Recall & Mastery Check

Summarize this in your own words

Explain the opening analogy, trace the worked example, and name one condition that would change your architectural decision. Try answering before opening the cards.

Can a three-layer application run in one process?

Yes. Layers describe logical responsibilities; tiers describe physical deployment locations. Presentation, application, domain, and persistence responsibilities can share a process. Separate deployment is an additional decision with network and operational costs.

Where does a maximum-active-loans policy belong?

In explicit business behavior that the relevant use case invokes, not solely in an HTTP handler or a database mapper. The exact class arrangement can vary, but every interface that starts a loan must enforce the same policy through the authoritative workflow.

Is a folder structure enough to enforce layering?

No. Define permitted imports/calls and test or review them. Strict, relaxed, and dependency-inverted variants differ. Inspect actual dependencies and representations crossing the boundaries instead of assuming conventional directory names provide enforcement.

Why can correct rules still lend the same copy twice?

Two requests can both read an available copy before either writes. Code layering does not solve concurrent state transitions. Use an authoritative transaction and an appropriate version, lock, or uniqueness mechanism so the invariant survives concurrent access.

Tricky & Most-Asked Interview Scenarios

Practice making a decision under a concrete production constraint. Open each answer, explain your reasoning aloud, then rate your confidence. The budgets and organizations below are author-created assumptions.

Six pass-through layers create six network hops. Which boundaries need to remain physical?

The Scenario & Constraint

Passing a note through six desks is slow when five only forward it unchanged. A CRUD request crosses six deployed tiers with almost no policy between them. Network latency dominates the response budget, while the team calls every tier a required architectural layer. What will you change and why?

The Direct Answer & Architectural Decision

Separate logical responsibilities from physical deployment. Keep presentation, application policy and persistence responsibilities clear in code, but co-locate pass-through layers unless an actual scaling, security or ownership requirement justifies a network boundary. Profile the request path and remove needless serialization and round trips.

Review strict versus relaxed layer access deliberately: an agreed read projection may bypass redundant orchestration, while writes still pass required policy. Test behavior and access controls after consolidation. A layer diagram describes dependency organization; it does not mandate one machine or service per box.

Key Trade-Offs & Follow-Up Traps

You reduce latency and operational overhead while retaining logical separation, but give up independent physical scaling/isolation for co-located components. Keeping tiers separate is a viable alternative when a trust boundary or distinct resource demand requires it.

Follow-up trap: removing every layer can also remove validation and authorization. If compliance mandates a physically isolated data tier, retain that boundary and optimize within its constraints. Measure the necessary hops rather than interpreting fewer boxes as the only performance objective.

A fast endpoint writes directly to the database and bypasses pricing checks. Where should the rule live?

The Scenario & Constraint

A side door avoids the cashier as well as the queue. A new controller writes orders directly to persistence for speed, while batch jobs call an application service that validates discounts. Some API orders now receive invalid prices. What boundary will you repair and why?

The Direct Answer & Architectural Decision

Place the authoritative pricing/ordering rule in the shared domain or application use case, then route both HTTP and batch commands through it. Let controllers translate and validate transport shape; let repositories persist data rather than decide eligibility. Audit other write paths for the same bypass and add behavior tests for an invalid discount through each entry point.

Measure the actual overhead before treating policy execution as expendable. Enforce simple data invariants in the database as defense in depth, but keep policy and its explanation in the responsible business layer. Return a consistent rejection rather than silently correcting prices in only one adapter.

Key Trade-Offs & Follow-Up Traps

You gain consistent business decisions with one implementation, but may need to redesign an overly large application service. Direct read projections are an alternative for read-only views that cannot bypass a write invariant; they do not justify an unguarded write path.

Follow-up trap: duplicating the rule in every controller makes the initial fix appear quick but invites drift. If a future import intentionally bypasses a rule, model that as an explicitly authorized business operation with its own constraints and audit trail, not a secret database shortcut.

A team proposes a server for every layer. Will that improve independent scaling?

The Scenario & Constraint

Separate folders do not require separate office buildings. A layered application runs well in one process, but an architecture review proposes deploying presentation, application and domain code on separate servers simply because they are distinct layers. There is no measured capacity issue. What will you recommend?

The Direct Answer & Architectural Decision

Keep logical layers in one deployable initially and choose physical tiers from measured operational constraints. Identify actual independent scaling units, such as CPU-heavy background work, and trust boundaries before adding remote calls. Ensure source dependencies stay intentional regardless of deployment placement.

Prototype and load-test any proposed split, including serialization, authorization, timeout and partial-failure handling. Document how the split improves a concrete objective. If no benefit outweighs those costs, retain the simpler topology while preserving code boundaries that allow a later move.

Key Trade-Offs & Follow-Up Traps

Co-location preserves fast calls and simpler failure handling but shares deployment and resources. Separate physical tiers are a valid alternative when a protected database network, distinct scaling profile or organizational boundary requires them.

Follow-up trap: multiplying tiers does not automatically create microservices or independent business ownership. If application CPU becomes the bottleneck while storage is healthy, scaling whole stateless application replicas may be enough. If a sensitive adapter requires an isolated network zone, split that physical responsibility instead of distributing every conceptual layer.

Controllers depend on ORM query builders during a storage migration. How do you contain the leak?

The Scenario & Constraint

Customers should order a meal, not operate the kitchen machinery. Controllers compose provider-specific queries and catch database exceptions directly. Switching storage now requires editing presentation code across the application. What contract will you introduce and why?

The Direct Answer & Architectural Decision

Identify the queries and commands the application actually needs, then expose purpose-specific application/repository operations with application-owned inputs and outputs. Translate provider models and exceptions in the data-access boundary, preserving useful distinctions such as not-found, conflict and unavailable. Avoid exporting a generic query builder that lets callers rebuild provider coupling.

Migrate one use case at a time with behavior and adapter integration tests. For reports, an explicit read-query service can return a projection without forcing every result through a rich domain object. Verify pagination, ordering and null semantics rather than assuming two providers behave identically.

Key Trade-Offs & Follow-Up Traps

You reduce storage leakage and localize provider changes, but maintain translation and explicit query operations. Direct ORM use is a viable simpler alternative for a small stable application that consciously accepts that coupling.

Follow-up trap: a universal repository interface can become an untestable imitation of every database feature. If a new use case needs a provider-specific analytical query, isolate that capability explicitly and acknowledge its portability limit instead of pretending the entire application has become database-independent.

Two repository writes partially succeed. Which layer should own their transaction?

The Scenario & Constraint

Writing half an invoice is not a completed sale. An application service saves an order, then its second repository call fails while updating a related local reservation. Both use the same transactional database, but each repository commits independently. What will you change and why?

The Direct Answer & Architectural Decision

Make the application use case own the transaction boundary for the business operation. Configure both repositories to participate in the same actual database transaction/session, and commit only after the required writes succeed. Keep repository methods from silently committing work that the use case expects to be atomic.

Use concurrency constraints as well as rollback: a transaction does not automatically prevent overselling under every isolation level. Test failure between writes, commit failure and concurrent access against the real provider. EF Core transaction behavior is a provider-specific example, not a guarantee supplied by layered architecture itself.

Key Trade-Offs & Follow-Up Traps

You gain one explicit local atomic boundary but couple those writes to a shared transactional resource and transaction lifetime. Moving the invariant into one aggregate/repository operation is another viable design. A durable workflow is an alternative when independent commits are intentional and temporary inconsistency is acceptable.

Follow-up trap: wrapping remote service calls in the same application method does not enlist them automatically. If one write moves to a separate database, redesign the workflow or supported coordination rather than retaining an unsupported local-transaction promise. Keep slow external calls outside short database transactions where possible.

Unit tests pass with fake repositories, but production loses updates. What test is missing?

The Scenario & Constraint

A practice lock that never jams cannot prove the real door is safe. Fake repositories store objects in memory and every layered use-case test passes. Production behaves differently under concurrent writes and database constraints. What verification will you add without abandoning fast unit tests?

The Direct Answer & Architectural Decision

Keep fast tests for application decisions, and add adapter integration tests using the real database engine/configuration for persistence semantics. Exercise unique constraints, concurrency conflicts, transaction rollback, ordering and provider error translation. Run selected end-to-end use cases through the actual repository boundary.

Make the fake honor the contract where practical, but do not expand it into a second database implementation. Include the observed lost-update race as a regression with two concurrent actors. Separate a business-policy failure from an infrastructure-semantics failure so each test layer has a clear purpose.

Key Trade-Offs & Follow-Up Traps

You catch provider-specific behavior and realistic transactions at the cost of slower setup and controlled test data. A lightweight substitute database is an alternative for some feedback, but may differ in precisely the locking or SQL feature under investigation.

Follow-up trap: adding more mock expectations does not validate isolation behavior. If a provider change removes a required transaction feature, either choose a supported design or state the changed guarantee; do not weaken the production invariant just to keep an in-memory fake passing.

Real-world impact

A library backend gains clarity when request translation, use-case coordination, borrowing policy, and persistence have accountable roles. The benefit is safer change and more focused reasoning, not a prescribed number of folders. Separate logical concerns first; introduce physical tiers only when their operational benefit justifies their cost.
