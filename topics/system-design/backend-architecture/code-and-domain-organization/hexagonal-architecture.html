Hexagonal Architecture

🎯 The Hook & ELI5

ELI5 mental model. A music player can receive commands from its buttons or a remote control and send sound to headphones or speakers. The act of playing music should not depend on one brand of remote or speaker. Hexagonal architecture gives an application deliberate connection points so different outside devices can interact with the same core behavior.

An application needs to interact with people, other programs, storage, and external providers. If those details are mixed into business behavior, changing one outside system can require changing the whole application. Hexagonal Architecture, also called Ports and Adapters, separates the application’s inside from the technologies that drive it or that it uses.

WHY it matters: a room-booking system should be testable through a simple programmatic driver, not only by clicking a browser with a real database and email account behind it. Clear ports make expected behavior explicit and adapters translate each external technology. The hexagon is a visual reminder of multiple connections, not a requirement for six ports.

🗺️ High-Level Big Picture

For a room reservation, an HTTP adapter or command-line adapter drives the same ReserveRoom use case through an input port. The application asks for room-state storage and notification through output ports. A SQL adapter and an email adapter implement those needs. Ports are defined around purposeful interactions; adapters speak the language of the outside technology and the inside contract.

🔍 Step-by-Step Mechanics

Follow the example one boundary at a time. Open each step to connect the familiar mental model to the internal mechanics.

1. Decide what belongs inside

The music player’s core job is choosing and playing a track, not interpreting a particular remote-control protocol. The application inside similarly owns use cases and business rules. For room booking, it decides what a valid reservation means, when a conflict occurs, and which outcome to return.

Draw the boundary around behavior you want to preserve while technologies change. Inside code should not require a browser request object, SQL connection, or provider SDK exception just to express a reservation. This does not require every rule to live in a separate service or repository. A monolith can have hexagonal boundaries, and each service in a distributed system can use the same pattern internally.

2. Define the way an outside actor drives a use case

Buttons and a remote can both ask for play without exposing their electrical details to the playback rule. An input port, sometimes called a driving or primary port, expresses an application capability that an outside actor can invoke. For example, ReserveRoom accepts room, time interval, and requester information and returns a defined outcome.

An HTTP adapter maps a route, body, identity, and status code into that contract. A command-line adapter maps arguments and exit messages into the same capability. The port is not necessarily a language interface object; a clearly defined callable API can serve the role. Keep parsing errors separate from business conflicts so each adapter can translate the same use-case meaning appropriately.

3. Define what the application needs from the outside

The player asks a sound output to deliver audio without knowing a speaker’s internal circuitry. An output port, often called a driven or secondary port, expresses a capability the application requires. RoomStore might need to attempt a reservation under an overlap constraint, while Notification might record or send a message according to explicit semantics.

The inner application owns the meaning of those requests. A SQL adapter can implement RoomStore, and an in-memory adapter can support focused tests. Avoid a vague universal repository that returns provider-specific query objects: it makes the outside technology leak back into the inside. Name behavior and guarantees important to the use case, including conflicts, missing records, and failure/uncertainty.

4. Let each adapter translate both data and errors

A headphone plug is useful because it matches the connection’s expectations, not because it is merely called an adapter. The SQL implementation translates the application’s reservation operation into database behavior and maps a detected overlap into the promised conflict result. The email implementation maps a notification request into a provider interaction and its possible outcomes.

A timeout to an external provider may mean unknown outcome, not definitive failure. Hiding that distinction behind a Boolean success flag can violate the application’s recovery needs. Adapters should also carry the correlation and identity information needed for observability and authorization. Translation protects meaning; it must not invent a stronger guarantee than the underlying system can deliver.

5. Compose adapters and test the contracts

A player manufacturer chooses which remote receiver and speaker output to wire in. An outer composition point supplies concrete adapters to the application. Production may use HTTP, SQL, and a message provider; a focused test may drive the input port directly and substitute a controlled output adapter.

Those focused tests verify reservation decisions and use-case coordination without a complete runtime stack. They do not prove the SQL adapter’s overlap handling or a provider’s duplicate behavior. Add contract/integration checks for actual adapters, including a race between two overlapping reservation attempts. A fake that always accepts a reservation can make inner tests pleasant while the production invariant remains broken.

6. Evolve connection points without creating interface clutter

You need a deliberate connector where equipment varies, not a plug between every screw. Define ports around business-relevant interactions and genuine outside dependencies. Adding an interface to every class can bury the use case under forwarding code without improving independence.

When a port changes, review all driving and driven adapters that use it. A new notification provider may require different timing or failure semantics even if its method names look similar. Keep the application’s promises stable where possible, adapt explicitly where not, and retain end-to-end checks for the actual user journey. Replaceability is a consequence of compatible contracts, not a guarantee that swapping an adapter is always cost-free.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Treat a failure as a story: start with what a user observes, trace the boundary that failed, and choose a prevention that addresses the cause.

An adapter has the right name but leaks SQL

Symptom: Use-case code must configure query-builder joins.

Root Cause: The port exposed database implementation concepts instead of application needs.

Fix/Prevention: Express reservation behavior and its guarantees in the inner vocabulary; keep query construction in the SQL adapter.

The fake proves a false guarantee

Symptom: Tests pass while simultaneous users book the same room.

Root Cause: The in-memory adapter did not model the concurrency promise required by RoomStore.

Fix/Prevention: Make overlap semantics explicit and test real database conflict handling; use focused fakes only for claims they can support.

One outside provider dictates all application outcomes

Symptom: Replacing email delivery changes reservation rules and HTTP handlers.

Root Cause: Provider-specific data and exceptions crossed the application boundary.

Fix/Prevention: Translate at the adapter, distinguish durable intent from external delivery, and keep use-case outcomes in the application vocabulary.

🧠 Active Recall & Mastery Check

Summarize this in your own words

Explain the opening analogy, trace the worked example, and name one condition that would change your architectural decision. Try answering before opening the cards.

How do an HTTP adapter and a SQL adapter differ in their relationship to the application?

The HTTP adapter drives an application capability through an input port. The application invokes the storage capability through an output port implemented by the SQL adapter. Both are outside adapters, but their role in the interaction differs.

Why is the shape not a requirement for six interfaces?

The hexagon emphasizes that an application can have multiple purposeful connection points without a privileged top/bottom technology stack. The number of ports follows meaningful interactions, not the number of sides in the drawing.

What must a room-storage port promise beyond a save method?

It should express the reservation behavior the application relies on, including overlap/concurrency rules, missing records, conflicts, and relevant failure semantics. An adapter with a matching method signature but weaker guarantees does not satisfy the same contract.

What can direct input-port tests prove, and what still needs real infrastructure checks?

They can verify policy and use-case coordination independently of a web server or database. Real adapters still need validation for mapping, transactions, concurrency, delivery semantics, and provider errors. Retain a representative user-journey check across the assembled application.

Tricky & Most-Asked Interview Scenarios

Practice making a decision under a concrete production constraint. Open each answer, explain your reasoning aloud, then rate your confidence. The budgets and organizations below are author-created assumptions.

REST and nightly CSV imports disagree on order validation. Which port should they share?

The Scenario & Constraint

Different plugs should power the same appliance behavior. A REST adapter rejects invalid orders, while a CSV importer writes directly to storage and accepts them. The business rule must hold regardless of entry channel. What port and adapters will you define?

The Direct Answer & Architectural Decision

Expose an application operation such as PlaceOrder with application-owned inputs and outcomes. Make REST and CSV separate driving adapters that translate transport data into that operation. Put the authoritative validation and invariant inside the application/domain rather than trusting either adapter's preliminary checks.

Keep HTTP status codes, CSV row errors and file parsing at the edges. Test the operation without either transport, then test each adapter's mapping of valid and invalid input. Give batch rows stable operation identities if retries can repeat a purchase. An adapter should translate entry mechanics, not supply an alternate business implementation.

Key Trade-Offs & Follow-Up Traps

You gain consistent behavior and isolated testing but maintain two translation paths. Separate use cases sharing a smaller domain policy are a viable alternative when bulk import and interactive ordering have different authorized semantics.

Follow-up trap: calling the REST endpoint from the importer adds network and authentication failure without necessarily improving the boundary. If the import must cross a process or trust boundary, a remote API may be appropriate, but keep its contract explicit and handle retries and partial batch completion deliberately.

A payment adapter times out after a possible effect. What should the outbound port return?

The Scenario & Constraint

A courier can lose the reply after delivering the parcel. A payment adapter catches every timeout and returns payment-failed. The application retries with a new charge and customers sometimes pay twice. What should the port's contract express and why?

The Direct Answer & Architectural Decision

Model confirmed success, definitive rejection and unknown outcome separately in the application-owned port. Pass one stable operation key to the adapter and require it to preserve that identity across safe retries. Persist the application's pending intent and use provider lookup or reconciliation to resolve ambiguity rather than treating a transport exception as a business rejection.

Keep provider response codes and SDK exception classes inside the adapter, but do not erase uncertainty during translation. Contract-test a lost reply after a committed charge and verify that retries reuse the same identity. The business use case decides whether to wait, return pending or request manual resolution.

Key Trade-Offs & Follow-Up Traps

You gain honest failure semantics and safer recovery at the cost of more application states and durable reconciliation. A provider with a synchronous, queryable idempotent operation can simplify recovery; it still requires the application to distinguish unknown from rejected.

Follow-up trap: an adapter cannot guarantee exactly-once effects from an external system that offers neither deduplication nor outcome lookup. If that assumption changes, stop blind automatic retries and introduce reconciliation or a different provider contract. Renaming the exception does not remove the original distributed uncertainty.

The in-memory adapter passes, but real storage violates uniqueness and rollback. How do you test the port?

The Scenario & Constraint

A toy socket that always works cannot certify the building's wiring. Unit tests use an in-memory repository whose behavior differs from production under concurrent inserts and transaction failures. The port promises one reservation per seat. What tests will establish that promise?

The Direct Answer & Architectural Decision

Write a shared behavioral contract for the port's required semantics, then run it against the real adapter with the production database engine/configuration. Include duplicate-key races, failed writes, transaction rollback and error mapping. Keep the in-memory adapter for fast policy tests, but make its documented simplifications explicit.

Exercise the invariant with concurrent callers through the application and verify the database constraint or concurrency mechanism actually enforces it. Avoid implementing a second database inside the fake. A passing fake shows how policy reacts to assumed outcomes; it does not prove infrastructure can produce those outcomes correctly.

Key Trade-Offs & Follow-Up Traps

You gain realistic adapter guarantees while paying for integration setup and slower tests. A lightweight substitute provider is a useful alternative for some feedback, but cannot validate locking or SQL semantics it does not share.

Follow-up trap: asserting that Save was called once says nothing about two concurrent requests. If the selected store cannot meet the port's atomic reservation contract, change the implementation or explicitly redesign the guarantee; do not quietly weaken the contract to match the fake.

A vendor SDK upgrade breaks the core. Where should its models and exceptions stop?

The Scenario & Constraint

Replacing a phone charger should not require rewiring every room. An outbound shipping adapter exposes SDK address objects and vendor exceptions through an application port. A provider upgrade now breaks use cases and tests. What will you change and why?

The Direct Answer & Architectural Decision

Make the port accept and return application-owned concepts such as ShipmentRequest, ShipmentReference and explicit outcomes. Translate vendor models, authentication and error details inside the shipping adapter. Preserve useful semantics such as invalid address, temporarily unavailable and unknown outcome without leaking SDK types.

Create focused mapping tests and adapter contract tests for the upgraded provider. Wire the implementation at the composition root so the core need not import or instantiate the SDK. Review serialization and units as well as type names; an address or weight conversion can be syntactically valid and still wrong.

Key Trade-Offs & Follow-Up Traps

You localize provider churn and simplify application tests, but maintain a mapping layer and may expose fewer provider-specific capabilities. A deliberately vendor-specific boundary is a viable alternative when the application depends fundamentally on unique features and accepts that coupling.

Follow-up trap: copying every SDK field into an identically shaped internal object preserves semantic coupling. If a new capability is actually required, add an intentional application contract for it rather than a generic provider escape hatch that bypasses the boundary.

An interface per class produces dozens of meaningless ports. What deserves a real port?

The Scenario & Constraint

A building does not need a new entrance for every cupboard. A team creates a port and adapter for each helper class, so a small feature requires many pass-through files. There is only one external storage dependency and little domain complexity. What will you simplify?

The Direct Answer & Architectural Decision

Define ports at meaningful application conversations or external capability boundaries, not mechanically at every class. Keep internal collaboration ordinary when it does not cross a dependency boundary or need replacement. Consolidate pass-through abstractions while preserving the actual driving use case and outbound storage contract.

Explain each remaining port in business or application terms: what does the application need, and what behavior must an adapter satisfy? Test through those stable conversations. Hexagonal architecture describes inside/outside separation; the drawing's six sides do not prescribe a number of ports or layers.

Key Trade-Offs & Follow-Up Traps

You reduce ceremony and improve navigation while accepting ordinary internal coupling that may later need refactoring. More granular ports are a viable alternative when capabilities vary independently or require distinct failure/security contracts.

Follow-up trap: one enormous generic port can be as harmful as dozens of trivial ones because it exposes unrelated capabilities. If a helper becomes a third-party boundary with its own timeout or authorization behavior, introduce a deliberate port then rather than retaining a simplicity rule after its assumptions change.

Two in-process modules already share a compatible application contract. Is another adapter necessary?

The Scenario & Constraint

Two matching plugs do not need a converter just to look architectural. A reporting module can call an application-owned query interface implemented by Orders in the same process. A reviewer demands an extra pass-through adapter on principle. No translation or policy difference exists. What will you recommend?

The Direct Answer & Architectural Decision

Allow direct collaboration through the explicit compatible contract when dependency direction and ownership are correct. An adapter earns its place by translating a protocol/model, enforcing an edge policy or adapting a real mismatch; it need not exist as an empty forwarding class. Keep private storage and domain internals behind the contract.

Add contract tests for the observable query behavior and document its consistency and authorization expectations. Wire the implementation outside the consuming policy. If the modules later separate physically, introduce a remote adapter that preserves the application-facing contract while making latency and failure behavior explicit.

Key Trade-Offs & Follow-Up Traps

You keep local code simple and avoid meaningless wrappers, but depend on a stable agreed interface. A real anti-corruption adapter is a viable alternative when the modules use different meanings or when isolation from provider change is needed.

Follow-up trap: direct access to another module's tables is not equivalent to direct use of its public port. If a remote move introduces unknown outcomes or partial availability, revisit the contract; retaining a synchronous-looking method name must not conceal a materially different failure model.

Real-world impact

A room-booking service benefits when the browser, batch driver, database, and notification provider can vary around a stable reservation capability. The architecture is successful when the inside remains understandable, the ports tell the truth about behavior, and real adapters are held to those promises.
