Backend Architecture

ELI5 big picture. A restaurant needs a floor plan, clear jobs, ways to pass orders, and shared utilities. Those are different decisions about one business. Backend architecture similarly combines where capabilities run, how code expresses responsibilities, how work travels, and how resources are found or isolated.

This branch organizes 15 concepts into four learning dimensions. A topology describes deployment and coordination boundaries. Code/domain organization describes the ownership and direction of behavior inside those boundaries. Communication and routing describe interactions, while infrastructure and tenancy describe shared operational capabilities and customer isolation.

Why this branch exists. Separating these dimensions prevents false choices. A modular monolith can use domain-driven design and events; a microservice can use clean or hexagonal organization; a gateway, discovery mechanism, and mesh address different concerns. The labels help explain decisions, not rank systems on one maturity ladder.

Suggested reading guide

A balanced starting path is Distributed System Fundamentals, Monolithic Architecture, and Modular Monolith, then a comparison with SOA and Microservices. Next, study the code/domain category to understand the inside of any chosen deployment boundary.

Use Communication & Routing when a client or capability must interact with others, and Infrastructure & Multi-Tenancy when locations, communication policy, or customer isolation become part of the story. It is also reasonable to begin with the category matching a current question. Each topic introduces its own mental model and can be read independently.

Explore this branch

  • Core System Topologies

    Five lessons explain distributed uncertainty and alternative deployment/ownership topologies. Compare the actual freedoms and costs a boundary creates instead of counting services or servers.

  • Code & Domain Organization

    Four lessons explain responsibility layers, dependency direction, interaction ports, and domain models. These ideas can shape a monolith or the inside of independently deployed services.

  • Communication & Routing

    Three lessons explain reacting to facts, presenting a stable entry point, and tailoring backend interactions to frontend experiences. Trace both the happy path and the unresolved outcome.

  • Infrastructure & Multi-Tenancy

    Three lessons explain finding changing service locations, operating communication policy, and isolating customer contexts across resources. Treat infrastructure behavior and failure assumptions as explicit contracts.
