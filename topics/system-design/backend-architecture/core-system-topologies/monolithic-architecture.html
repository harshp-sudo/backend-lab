Monolithic Architecture

🎯 The Hook & ELI5

ELI5 mental model. Picture a restaurant whose kitchen stations share one building and open for service together. The baker and grill cook can have different jobs without becoming separate restaurants. A monolithic backend similarly packages its main business capabilities into one application that is released as a unit. The useful question is whether that shared release boundary helps this team serve customers well.

An application needs a place to receive requests, apply business rules, and coordinate data changes. A monolith puts substantial business functionality behind one application deployment boundary. It can contain many modules, processes such as background workers from the same release, and multiple running replicas; one deployment unit does not mean one source file or exactly one server.

WHY it matters: a small booking team may deliver safer changes with one versioned release and local transactions than with ten independently deployed services. Simplicity is valuable only when the inside remains understandable. A shared release can also become a coordination bottleneck as teams and workloads diverge.

🗺️ High-Level Big Picture

Consider a neighborhood class-booking product. One application owns class schedules, seat reservations, and invoices. A request enters the booking handler, calls internal business capabilities, and commits the necessary local changes in its database. A separate notification worker can process follow-up work without turning every internal call into a network request. The diagram shows a chosen implementation, not a requirement that every monolith use one database.

🔍 Step-by-Step Mechanics

Follow the example one boundary at a time. Open each step to connect the familiar mental model to the internal mechanics.

1. Choose the release boundary deliberately

Like the whole restaurant opening after one safety check, the application is built and released as a coherent version. A handler can call another module using ordinary language interfaces. This reduces remote protocol and version-mismatch problems inside that boundary, though calls to a database, email provider, or payment service still have network failure modes.

Name the business responsibilities before naming folders. Booking, schedule management, billing, and notifications should be recognizable capabilities even when deployed together. A useful boundary is the set of changes the team can understand, test, and release safely. The mere fact that all code is in one repository does not prove it forms one deployment unit, and splitting repositories alone does not create independent services.

2. Trace one request through local calls

A student asks for the last seat in a pottery class. The entry point translates the request into a booking command, validates its shape, and passes it to application logic. That logic checks the class, applies booking rules, and asks persistence code to save the result. Calling an internal schedule module is a local interface call; it need not serialize a request and cross a service network.

Keep responsibilities visible while benefiting from local calls. Authentication and request parsing belong at the edge, the booking rule belongs with booking behavior, and database mechanics stay behind an intentional access boundary. If an invoice method directly reaches into an unrelated handler's mutable data structures, the release remains monolithic but the design has become harder to reason about.

3. Use a local transaction for a local invariant

Think of writing a reservation and its invoice into one ledger before closing the page. A transaction can make a related set of local database changes commit or roll back together. For the last class seat, the database must also enforce an appropriate concurrency rule; counting remaining seats in application memory is not sufficient when several replicas handle requests.

A transaction does not automatically include an email or remote payment. Commit a durable notification intent with the booking when needed, then deliver it with retry-safe processing. Otherwise a successful booking followed by a failed email can confuse the user, and sending email before commit can announce a reservation that never existed. The local boundary simplifies some consistency problems; it does not eliminate all distributed interaction.

4. Scale the application without pretending all work is identical

A busy restaurant can open another identical location. A monolith can also run several application instances behind a traffic distributor. Avoid keeping essential session or booking state only in one instance's memory; a later request may reach another instance. Coordinate shared writes through the chosen database or another authoritative owner.

Replicating the whole application may waste resources if one small capability consumes most CPU while others barely work. Measure before extracting it: query tuning, caching, job queues, and separating web versus background worker capacity can sometimes address the problem while preserving one application design. If a capability truly needs an independent release or scaling boundary, service extraction becomes a candidate with additional operational costs.

5. Make one release small enough to trust

Opening the entire restaurant is easy when the change is one new dish; it is risky when every station changes at once. A shared application release benefits from small changes, fast feedback, automated checks around important behavior, and backwards-compatible database migrations. The ability to roll code back can be limited by data already transformed or external effects already triggered.

Several teams can work in a monolith, but common code ownership and a shared pipeline need explicit coordination. Watch for build times, tangled imports, release queues, and changes that unexpectedly affect many capabilities. Those are signals to improve boundaries or evaluate decomposition, not evidence that every monolith has already failed. A modular monolith is one way to strengthen the inside without changing the deployment boundary.

6. Decide whether an extraction solves a measured problem

If only catering needs a different opening schedule, making it a separate operation may help. First identify the concrete problem: independent team delivery, distinct capacity needs, fault isolation, or a regulatory boundary. Identify the data and invariants that would cross the new boundary and design ownership before moving code.

A staged extraction can route one capability to a new owner while the rest remains in the existing application. That requires protocol compatibility, data migration, recovery, and observation of the new network path. Moving coupled functions onto separate servers without resolving their shared data and release requirements produces distributed coordination costs without the intended independence. Keep a monolith when its shared boundary still fits the product and team.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Treat a failure as a story: start with what a user observes, trace the boundary that failed, and choose a prevention that addresses the cause.

One release becomes one tangled responsibility

Symptom: Changing an invoice breaks unrelated class-scheduling behavior.

Root Cause: Shared deployment was mistaken for permission to share every internal structure.

Fix/Prevention: Separate capability interfaces, hide implementation details, and check dependency directions while keeping local calls.

The second replica loses a reservation

Symptom: A student sees different booking state depending on which instance responds.

Root Cause: Essential state or concurrency decisions lived only in one server process.

Fix/Prevention: Use an authoritative shared state model, concurrency constraints, and retry-safe request identity across replicas.

An architecture rewrite replaces a clear performance fix

Symptom: Delivery slows after a broad service split, while the original slow query remains.

Root Cause: The team chose a topology as a substitute for measuring the bottleneck.

Fix/Prevention: Measure query, CPU, queue, and release constraints, then choose the smallest boundary change that addresses them.

🧠 Active Recall & Mastery Check

Summarize this in your own words

Explain the opening analogy, trace the worked example, and name one condition that would change your architectural decision. Try answering before opening the cards.

Can a monolithic application run on ten machines?

Yes. Monolithic describes the application deployment boundary, not the number of running instances. Ten replicas of the same application remain a monolithic deployment model. Shared state, concurrency, and dependencies still require deliberate design.

Why might a booking and its invoice be easier to coordinate in one application?

If they share an appropriate local database boundary, a transaction can commit their related state changes together. That benefit does not automatically cover remote payment or email, and concurrent seat allocation still needs an enforced invariant.

Does calling a system a monolith imply its code is unmodular?

No. Internal organization and deployment shape are different dimensions. A monolith can have explicit capability modules, inward dependency rules, and well-defined domain models. Conversely, separate services can still be tightly coupled.

What evidence would justify extracting notifications?

Examples include a separate ownership/release need or a capacity/failure-isolation requirement not adequately served by a worker role. Account for event delivery, duplicate handling, monitoring, and interface compatibility before assuming extraction reduces total complexity.

Tricky & Most-Asked Interview Scenarios

Practice making a decision under a concrete production constraint. Open each answer, explain your reasoning aloud, then rate your confidence. The budgets and organizations below are author-created assumptions.

Four engineers have two weeks to launch. Should you begin with independently deployed services?

The Scenario & Constraint

Think of one workshop with labeled benches instead of renting a building for each tool. Four engineers must deliver ordering, billing and support in two weeks, with no dedicated operations team. Load is modest and most changes cross these capabilities. What deployment topology will you choose and why?

The Direct Answer & Architectural Decision

Start with a single deployable application and clear internal responsibility boundaries. Keep order and billing rules in named modules, use explicit interfaces and a transaction-capable data store where needed, and build one repeatable deployment with health checks, backups and rollback. The deadline favors fewer operational moving parts.

Write down the conditions that would justify extraction later: a measured scaling hotspot, a durable independent ownership boundary or a regulatory isolation requirement. Add observability by capability now so future choices have evidence. A single deployment need not mean every class can access every table.

Key Trade-Offs & Follow-Up Traps

You gain fast local development, simpler transactions and one operational path; you accept shared resource and release boundaries. A small number of services is a viable alternative if an existing platform team already makes deployment, tracing and recovery routine.

Follow-up trap: saying a monolith cannot scale confuses deployment topology with capacity. If one capability must run in a separately controlled environment from day one, that isolation requirement outweighs the launch convenience. Keep the remaining cohesive work together rather than automatically splitting every noun into a service.

Request count is flat, yet latency doubled after a write-heavy release. Do you add more application replicas?

The Scenario & Constraint

A restaurant serving the same number of customers can still slow down if every order becomes elaborate. Your monolith handles the same requests per second, but a release replaces cached reads with transactional writes. Database waits and p99 latency jump. The release has a 300ms response target. What will you investigate first and why?

The Direct Answer & Architectural Decision

Compare work per request before scaling the application. Trace changed endpoints, query plans, lock waits, transaction duration and connection-pool queues; segment read and write latency rather than relying on average CPU. Reproduce the new write mix under a realistic load test and roll back the release if its regression is clearly responsible.

Shorten transactions, remove redundant queries and index the actual access path before adding replicas that compete for the same database. Bound database connections across the whole fleet. Recheck correctness after batching or caching changes: neither should bypass the business rule that made the write necessary.

Key Trade-Offs & Follow-Up Traps

You target the constrained resource and avoid buying idle application CPU, but diagnosis takes measurement and a rollback may delay functionality. Additional application replicas are an alternative when profiling shows application CPU is the bottleneck and the data tier has headroom.

Follow-up trap: unchanged request count does not imply unchanged workload. If the database remains healthy while encryption or serialization now dominates CPU, scale or optimize the application instead. Make the decision from resource demand and tail latency, not from the word monolith.

A reporting feature consumes all worker threads and checkout fails. How do you contain it inside a monolith?

The Scenario & Constraint

One noisy room can consume a shared building's electricity. An export endpoint launches long reports in the same process and connection pool as checkout. During business hours, checkout times out even though its own code has not changed. You need a same-day containment fix. What will you do and why?

The Direct Answer & Architectural Decision

Disable or throttle the expensive feature immediately, then assign it bounded concurrency, time limits and a bounded queue separate from latency-sensitive requests. Reserve sufficient database and worker capacity for checkout, cancel abandoned work where supported, and reject additional exports predictably instead of retaining unlimited jobs.

Move truly long reports to a controlled background worker using a durable job identity, and expose job status rather than holding an HTTP request open. Observe queues and database contention separately; thread isolation alone does not isolate a shared disk or database. Load-test export traffic alongside checkout.

Key Trade-Offs & Follow-Up Traps

You restore priority isolation quickly without a system rewrite, but users wait for exports and share some remaining failure domains. Extracting reporting into a separately scaled process is an alternative when sustained demand or crash isolation justifies the operational cost.

Follow-up trap: putting work on an unbounded in-memory queue merely moves the overload. If reports must read a consistent historical snapshot, choose a reporting replica or snapshot pipeline with explicit freshness semantics instead of letting arbitrary analytical queries compete with transactional writes.

Five teams ship one artifact. How do you release and roll back without disabling every team's work?

The Scenario & Constraint

A shared train can still have a timetable and guarded boarding. Five teams change one monolith, and a bad billing release causes a whole-application rollback that also removes a working support feature. You must improve release safety this month without creating five services. What will you change and why?

The Direct Answer & Architectural Decision

Keep a reproducible artifact, require capability ownership and targeted plus integration checks, and deploy incrementally with observable health gates. Use independently controlled feature flags for risky behavior so a feature can be disabled without immediately reverting unrelated code. Exercise the old and new paths before release.

Design database changes with an expand-and-contract sequence: add compatible structures first, transition readers/writers, and remove old structures only after the rollback window closes. Record which artifact and flags are active. Test rollback against the deployed schema rather than assuming reverting application code reverses data migration.

Key Trade-Offs & Follow-Up Traps

You reduce blast radius and coordinate releases without immediate service extraction, but own flag lifecycle, compatibility tests and a shared deployment train. Separate deployables are an alternative when teams have genuinely independent contracts and persistent release contention.

Follow-up trap: a feature flag cannot safely undo a destructive schema change or an external payment effect. If a data migration is irreversible, plan a forward repair and reconciliation path before rollout. If regulatory change control requires independent artifacts, internal flags alone do not satisfy that requirement.

You doubled monolith replicas but throughput stayed flat. Why is the database getting worse?

The Scenario & Constraint

More cashiers do not help when there is only one slow stock ledger. Application replicas grow from four to eight, but the database is saturated, lock waits rise and total connections double. Checkout throughput barely moves. What architecture or capacity change will you make and why?

The Direct Answer & Architectural Decision

Stop increasing callers until you identify the data-tier limit. Measure transaction contention, query cost, I/O and connection waits. Apply a fleet-wide connection/concurrency budget, optimize hot queries and reduce unnecessarily broad transactions. Check whether a single hot row serializes the real business operation.

Separate read and write demand: cache safe reads or route them to replicas only where stale data is acceptable, while authoritative writes still enforce invariants. Consider partitioning data along a real access boundary only after a simpler indexing, vertical-capacity or workload-isolation fix is evaluated. Retest with the expected request mix.

Key Trade-Offs & Follow-Up Traps

You improve useful database capacity and protect recovery, but introduce cache freshness or operational partitioning costs if those measures are selected. Vertical database scaling is a viable near-term alternative when the workload fits its limits and cost is acceptable.

Follow-up trap: turning code into microservices while retaining the same contended tables does not remove the bottleneck. If profiling instead shows a stateless CPU-heavy image transformation, a separately scaled worker may isolate it cleanly. Choose a boundary that owns the constrained work, not a distribution exercise around the same ledger.

Only image processing needs independent scaling. How do you extract it without rewriting the whole monolith?

The Scenario & Constraint

You can open a specialist workshop while the original shop keeps serving customers. Image conversion consumes bursty CPU, while ordering and billing remain cohesive. A full rewrite would take a year and cannot interrupt existing clients. What migration sequence will you choose and why?

The Direct Answer & Architectural Decision

Use an incremental strangler boundary around image processing. Define an explicit request/job contract, place routing or an adapter at the old entry point, and move conversion behind that contract while the monolith continues handling other work. Start with a small traffic slice and compare outputs, latency and failure behavior.

Give jobs stable identities and make duplicate processing safe before retrying across the new network boundary. Decide who owns image metadata and avoid uncontrolled dual writes. Retain a rollback route during the transition, observe both paths and remove the old implementation only when the new path proves operationally independent.

Key Trade-Offs & Follow-Up Traps

You gain independent scaling and incremental risk control at the cost of routing, compatibility and a temporary two-path system. Keeping conversion as a separate worker of the same application is a viable cheaper alternative if independent business ownership is unnecessary.

Follow-up trap: a network wrapper around a function that still writes private shared tables is not full ownership isolation. If the dependency graph reveals that conversion cannot be separated without many synchronous callbacks, first simplify the internal boundary. A measured extraction can pause without forcing a rewrite of the working core.

Real-world impact

For a local class-booking business, a monolith can keep reservation rules, billing coordination, and deployment understandable while the product evolves. Its long-term health depends on disciplined internal boundaries and measured bottlenecks. The decision to distribute should improve a specific delivery or operational constraint, not merely change the architecture label.
