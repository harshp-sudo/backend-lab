Modular Monolith

🎯 The Hook & ELI5

ELI5 mental model. Imagine a school in one building. The library, office, and classrooms share the building, but each has a door and a clear way to ask for help. Students should not rummage through the office filing cabinet to borrow a book. A modular monolith keeps one application release while giving its business capabilities similarly deliberate doors.

A growing application needs internal boundaries before every change becomes a search through everybody else’s code. A modular monolith organizes one deployable application into cohesive capabilities with explicit public interfaces and hidden implementation details. Modules are architectural boundaries inside the application; they are not automatically independent services.

WHY it matters: an online learning business can let Enrollment, Billing, and Catalog evolve behind clear interfaces while retaining fast local calls and simpler deployment. The value comes from enforcing the doors, not drawing a package diagram. A folder named billing is not an effective boundary if every other module reads its private tables and classes.

🗺️ High-Level Big Picture

Our example enrolls a learner in a paid course. Enrollment owns the enrollment decision and asks Catalog for the course’s public availability information. Billing owns invoice behavior. The arrows represent allowed public collaborations. Each module hides its internal records and persistence details, even if all tables happen to live in the same database process. One application release contains the modules and any shared composition code.

🔍 Step-by-Step Mechanics

Follow the example one boundary at a time. Open each step to connect the familiar mental model to the internal mechanics.

1. Group code by a business capability

The school library has a meaningful job, rather than being a cupboard for all paper. A module should similarly gather behavior that changes together for a recognizable business purpose. Enrollment contains its use cases, domain rules, and persistence adapters rather than scattering all enrollment behavior across application-wide controller and database folders.

Start by describing ownership: who decides whether a learner is enrolled, who defines a course, and who issues an invoice? These questions identify responsibilities and their contracts. Layering may still exist inside each module. Avoid treating a shared utility package as the home for business rules that seem inconvenient to place; that turns common code into a hidden dependency joining unrelated capabilities.

2. Define the door and hide the filing cabinet

A caller asks the library desk whether a book is available; it does not edit the librarian’s catalog file. A module’s public interface should express stable capabilities and data it is willing to share. Other modules depend on that interface, not its database entities, implementation classes, or private repositories.

For Catalog, a public operation might return a small course-availability result. Returning the live internal course entity lets callers mutate or depend on fields that Catalog never intended to promise. Choose request/result types that explain the operation and preserve ownership. Visibility rules, package exports, import restrictions, or language modules help enforce the distinction; frameworks such as Spring Modulith are examples of tooling, not requirements of the architectural idea.

3. Draw a dependency graph the team can enforce

A school works poorly if every request must circle through all departments before anyone can answer. Circular module dependencies create similar confusion. Record which public interfaces each module may use and run automated architecture checks against those allowed relationships.

If Enrollment needs Billing and Billing needs Enrollment for a different operation, first examine whether one collaboration is really an event notification, whether responsibilities are misplaced, or whether a third workflow should coordinate them. Do not hide a cycle by introducing a generic service locator. A small shared kernel can be intentional, but changes to that shared contract require coordinated ownership. Tests should detect forbidden imports and cycles, not merely confirm that a diagram was drawn.

4. Keep local consistency explicit

Using the same building makes it easy to walk to another office, but it does not make every filing cabinet everybody’s property. Modules can use local calls and, when appropriate, a shared database transaction. However, reaching directly into another module’s table creates a contract that is usually undocumented and hard to change.

Suppose enrollment and invoice creation need coordinated behavior. Expose the required Billing operation and decide whether the workflow truly needs one local atomic transaction or can tolerate a pending invoice. Avoid assuming that any in-process event is durable: a crash after committing enrollment but before dispatching a notification can lose work unless intent is recorded. Ownership and recovery remain design choices even without network services.

5. Test a module through its promised surface

If the library’s public borrowing process works, tests should not need to impersonate its internal filing system. Exercise module behavior through its public API and verify important invariants with its own storage adapter where needed. Replace other module collaborators with explicit contract-compatible test doubles for focused tests, then add integration checks around real collaborations.

The goal is a failure that points to a capability boundary. If a small Catalog change requires rewriting unrelated Enrollment tests that inspect private Catalog internals, the tests are exposing coupling. At application composition time, wire the real collaborators and validate the dependency graph. A shared deployment still needs cross-module regression coverage; module tests do not prove the whole enrollment workflow behaves correctly.

6. Use boundaries to preserve options, not promise free extraction

Clear department doors make it easier to move a department later, but somebody still has to move the files and change how requests travel. A strong module boundary can reduce the conceptual work of extracting a service. It does not remove network latency, protocol versioning, data migration, retries, or distributed transaction decisions.

Before extracting Billing, list every synchronous caller, shared transaction, shared table access, and implicit assumption about immediate completion. Those are the places where local collaboration must become an explicit remote contract. If independent deployment is unnecessary, leaving Billing in the monolith may remain the better decision. Modularity is useful on its own, even if extraction never happens.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Treat a failure as a story: start with what a user observes, trace the boundary that failed, and choose a prevention that addresses the cause.

A package diagram hides table coupling

Symptom: Renaming a Billing column breaks Enrollment.

Root Cause: Enrollment depended on Billing’s private persistence structure.

Fix/Prevention: Move the required collaboration behind Billing’s public interface; detect forbidden repository/import access and make data ownership visible.

In-process events silently disappear

Symptom: Enrollment commits but the invoice notification is lost during a crash.

Root Cause: An in-memory dispatch was assumed to have the durability of stored intent.

Fix/Prevention: Choose and document delivery guarantees; record pending work transactionally when it must survive a restart and make consumers retry-safe.

Everything moves into common

Symptom: A shared package becomes the place every feature must change.

Root Cause: Code reuse was prioritized over clear capability ownership.

Fix/Prevention: Keep business decisions inside owners; restrict shared contracts to small stable concepts and review dependency growth.

🧠 Active Recall & Mastery Check

Summarize this in your own words

Explain the opening analogy, trace the worked example, and name one condition that would change your architectural decision. Try answering before opening the cards.

What evidence distinguishes a real module boundary from a folder name?

Callers use explicit public contracts, internals and owned data remain hidden, forbidden dependencies are detected, and tests exercise behavior through the public surface. A folder alone cannot prevent another module from reaching into a private repository or table.

Does one database mean every module may read every table?

No. Physical storage placement and logical ownership differ. A shared database can simplify transactions while modules still access one another through public behavior. Direct cross-module table access creates coupling that must be treated as an intentional contract if allowed.

Is an event raised inside a monolith automatically durable?

No. A synchronous or in-memory event can disappear when the process fails. If follow-up work must survive a crash, record durable intent and define retry/duplicate behavior. The word event does not specify its transport or delivery guarantee.

Why is extracting a well-isolated module still significant work?

Local assumptions must become remote contracts. Teams need to address latency, uncertain outcomes, separate data ownership, migration, compatibility, and operation of the new service. Good boundaries reduce entanglement; they do not erase distributed-systems costs.

Tricky & Most-Asked Interview Scenarios

Practice making a decision under a concrete production constraint. Open each answer, explain your reasoning aloud, then rate your confidence. The budgets and organizations below are author-created assumptions.

Developers bypass module APIs to query private internals. How will you make boundaries real?

The Scenario & Constraint

Labeled rooms are not private if every door stays open. A modular monolith has packages named Orders and Billing, but Orders imports Billing's persistence classes and reads its tables directly. Routine billing changes now break checkout. You must regain isolation without separate deployments. What will you do and why?

The Direct Answer & Architectural Decision

Define the small published Billing API in business terms and migrate callers to it, translating data at that boundary. Assign table and rule ownership so a package name is backed by an actual dependency policy. Add build-time architecture checks that reject access to internal packages and disallowed module dependencies; Spring Modulith verification is one implementation-specific option.

Inventory existing violations and reduce them deliberately rather than hiding every internal type behind a permissive shared package. Test the API's business behavior and track new violations in CI. Modules can share one process and database while keeping code and data responsibilities explicit.

Key Trade-Offs & Follow-Up Traps

You reduce accidental coupling and make refactoring safer, at the cost of API design and migration effort. Team conventions alone are a cheaper alternative for a tiny stable codebase, but provide weaker protection as contributors increase.

Follow-up trap: exposing the internal entity through the public method preserves the coupling under a new name. If a hot read truly requires a cross-module projection, agree on an explicit read model or query contract rather than secretly reusing write internals. If existing modules remain inseparable for every change, revisit their responsibility boundaries.

Orders, Billing and Inventory depend on one another in a cycle. Should every call become an event?

The Scenario & Constraint

Three departments each insist the other must approve first. Orders calls Billing, Billing calls Inventory, and Inventory calls Orders for business rules. Tests need the whole application and no module can be understood alone. Immediate stock validation is required during purchase. What dependency shape will you choose and why?

The Direct Answer & Architectural Decision

Draw the responsibilities behind the cycle before changing transports. Put the purchase workflow in an explicit application coordinator that invokes narrow capabilities, while each module owns its own invariant. Remove callbacks that merely ask another module to finish the same orchestration. Keep required immediate checks synchronous within the process.

Use events for facts that can be handled later, such as a notification after an accepted order, with explicit transaction and delivery semantics. Add dependency-cycle checks so the repaired graph stays acyclic. If two modules jointly own every immediate decision, combine or redraw them instead of inventing a broker to disguise that relationship.

Key Trade-Offs & Follow-Up Traps

You gain an understandable dependency graph and smaller tests, but introduce an orchestration owner and explicit contracts. Moving a noncritical reaction to an event is an alternative for that edge; converting all edges changes timing and failure handling unnecessarily.

Follow-up trap: asynchronous delivery does not erase conceptual coupling or guarantee an invariant before acceptance. If a later requirement allows stock confirmation to be pending, then a durable workflow with compensations becomes viable. State that changed promise rather than claiming the original immediate transaction remains intact.

Two modules must enforce one immediate invariant. Can a modular monolith use one transaction?

The Scenario & Constraint

Two counters share one ledger even though their staff have separate responsibilities. Orders must reserve inventory and create an accepted order together; either both changes commit or neither does. Both modules currently use the same transactional database. What consistency boundary will you choose and why?

The Direct Answer & Architectural Decision

Use one local transaction initiated by the application use case when the same database and transaction infrastructure genuinely cover both writes. Invoke each module through its owned API; the order module must not mutate inventory tables directly. Let Inventory perform an atomic conditional reservation or appropriate concurrency check, not a read-then-write race.

Test a failure after each write and concurrent attempts for the final unit. Keep the transaction short and avoid remote calls inside it. Document that this convenience depends on a shared local commit boundary; it is an extraction constraint, not evidence that the modules can already deploy independently.

Key Trade-Offs & Follow-Up Traps

You preserve the immediate invariant with simple recovery but accept transaction and data-tier coupling. Co-locating the tightly related invariant under one owner is another valid design. A saga is an alternative only if temporary partial completion and compensation are acceptable business semantics.

Follow-up trap: a module API does not automatically create a transaction across separate databases. If one module moves to independently committed storage, revisit the invariant: retain a shared owner, preallocate rights, or change the workflow to pending states. Do not retain an atomicity claim after removing the atomic commit mechanism.

An email listener fails after the order commits. How do you recover without rolling back the purchase?

The Scenario & Constraint

A stamped order remains real even when the messenger loses its notification. A noncritical listener sends a receipt after a committed order. The process crashes before the listener finishes, and the customer received no email. Purchases must remain accepted, but notifications need eventual delivery. What will you do and why?

The Direct Answer & Architectural Decision

Record the obligation durably with the order transaction, using a persistent event-publication registry or outbox appropriate to the actual framework. A worker retries outstanding publications and marks completion only after the defined delivery step. Spring Modulith's publication tracking is a concrete example whose configured persistence and resubmission behavior must be verified.

Make the handler idempotent with a stable publication key, observe backlog age and failed attempts, and provide a repair path. Test a crash after the main commit and after the external email is accepted but before local completion is recorded. The latter can still cause duplicate sends unless the provider or workflow deduplicates them.

Key Trade-Offs & Follow-Up Traps

You decouple purchase success from notification availability, but manage durable publication storage, retries and monitoring. Synchronous email is a simpler alternative only when the business accepts its latency and failure coupling; it still cannot undo an already accepted external effect reliably.

Follow-up trap: an in-memory event callback is not durable delivery. If the reaction becomes a required credit authorization before acceptance, move it into the decision workflow rather than treating it as a best-effort after-commit notification. Reassess the business promise when criticality changes.

A common package becomes everyone's business-rule dumping ground. What belongs there?

The Scenario & Constraint

A communal cupboard becomes unusable when every team stores its private tools there. A common library now contains discount policy, invoice state transitions and generic string utilities. Any pricing change forces edits across modules. What will you move or share, and why?

The Direct Answer & Architectural Decision

Move business rules to the module that owns their meaning, then expose a narrow capability or an immutable agreed value where another module needs it. Keep a shared kernel small, deliberate and jointly governed; a utility should not silently decide domain policy. Use dependency checks to stop common code from importing business modules.

Compare apparently identical concepts with the domain owners before unifying them. Billing's settled amount and Catalog's displayed price may need different models. Migrate one rule at a time with characterization tests so the boundary repair does not change behavior accidentally.

Key Trade-Offs & Follow-Up Traps

You restore ownership and reduce coordinated changes, but may accept small, intentional duplication and translation. A jointly maintained shared kernel is a viable alternative for genuinely identical, stable concepts when its change process is explicit.

Follow-up trap: renaming common to platform does not establish ownership, and a remote shared service can worsen coupling if it holds unrelated rules. If two teams truly share one invariant and always change together, reconsider whether the proposed module split reflects reality rather than forcing separate copies of a single responsibility.

A module looks isolated in code but shares writable tables. Is it ready to become a service?

The Scenario & Constraint

A room with its own door may still share plumbing that nobody mapped. A team wants to extract Shipping for independent releases. Its public package is clean, yet nightly jobs and Orders write the same shipment tables. You cannot freeze releases for a rewrite. What will you check and change first?

The Direct Answer & Architectural Decision

Audit data readers/writers, transaction scope, background jobs and operational dependencies, not only imports. Assign Shipping authoritative ownership and route writes through its API while still in the monolith. Replace private-table reads with explicit queries or projections, and test failure and compatibility at the proposed contract.

Measure whether independence solves a real delivery or scaling problem. Once the local boundary behaves independently, introduce a remote adapter and migrate traffic incrementally with observable rollback. Define durable messaging or reconciliation where a former local transaction becomes multiple commits; do not make two owners write the same data as an indefinite transition.

Key Trade-Offs & Follow-Up Traps

You reduce extraction risk and expose hidden coupling early, but postpone the separate deployment and temporarily maintain compatibility paths. Remaining a modular monolith is a valid alternative if independent deployment brings little measurable benefit.

Follow-up trap: replacing a method call with HTTP creates network failure without solving ownership. If Shipping must still share one immediate invariant with Orders, keep that decision under one transactional owner or explicitly change to a pending workflow. Do not call a database-sharing deployment fully autonomous.

Real-world impact

For the learning business, a modular monolith can make course, enrollment, and billing changes easier to localize while keeping releases and local consistency manageable. Measure success through fewer boundary violations and clearer ownership, not the number of folders or a promise that all modules will eventually become services.
