Core System Topologies

ELI5 big picture. One busy workshop can organize several skilled teams inside one building, or those teams can become separate shops that coordinate across town. Each arrangement changes travel, ownership, and opening-time decisions. These lessons explain the software equivalents and the failure assumptions behind them.

A system topology is more than a diagram of boxes. It affects release coordination, data ownership, network interaction, capacity, and recovery. Start by asking which capabilities need to change or operate independently and which invariants benefit from staying together.

Why this branch exists. The same product can reasonably use a monolith, a modular monolith, a small number of services, or a larger service system at different stages or boundaries. Distributed fundamentals apply whenever work crosses a network, even if the main business application is monolithic.

Suggested reading guide

Read Distributed System Fundamentals first if remote timeouts, retries, or consistency are unfamiliar. Then use Monolithic Architecture as a concrete deployment baseline and Modular Monolith to see how strong internal boundaries can coexist with one release.

SOA broadens the discussion to capabilities and contracts across ownership domains. Microservices focuses on intended independence and its operational/data costs. When comparing them, choose one real user journey and ask who owns each decision, which commits are local, and what happens if a reply never arrives.

Explore this branch

  • Distributed System Fundamentals

    Build a mental model for partial failure, uncertain outcomes, time budgets, safe repetition, and authoritative invariants. The ticket-purchase story makes the network boundary concrete.

  • Monolithic Architecture

    Trace a class-booking application released as one unit. Learn why one deployment boundary can still contain modules, replicas, workers, and important concurrency decisions.

  • Modular Monolith

    See how explicit capability APIs and hidden internals keep one application understandable. Boundary enforcement is useful even if no module ever becomes a service.

  • Service-Oriented Architecture (SOA)

    Explore service capabilities, meaningful agreements, policy, and process coordination across owners. Protocol choice and a central integration bus are separate implementation decisions.

  • Microservices Architecture

    Evaluate independently deployed business capabilities through ownership, data, contracts, and operations. Learn to recognize distributed coupling that fails to buy real independence.
