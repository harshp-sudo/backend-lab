Distributed System Fundamentals

🎯 The Hook & ELI5

ELI5 mental model. Imagine three shops taking a dinner order by passing notes. One shop can be open while another is closed. A missing reply might mean the note was lost, the cook is slow, or dinner is already ready. Working together over a network has the same uncertainty: separate computers must coordinate without sharing one perfectly reliable view of events.

A backend becomes distributed when useful work depends on components that communicate across a network. A web application talking to a remote database already crosses such a boundary; a hundred microservices are not required. Distribution can share work and isolate some failures, but it introduces delays and outcomes that one participant cannot immediately observe.

WHY it matters: a checkout can charge a customer even though the browser reports a timeout. Correctness depends on what the system did, not just what the caller heard. Start by naming the business promise: for one confirmed purchase, create at most one order and make its eventual outcome discoverable.

🗺️ High-Level Big Picture

Our worked example is a ticket purchase. The browser asks Orders to reserve a seat; Orders coordinates with Inventory and Payments. Each arrow crosses a boundary where a request, reply, or participant can fail independently. A durable operation record gives the caller a way to learn the result later. 🔍 Step-by-Step Mechanics

Follow the example one boundary at a time. Open each step to connect the familiar mental model to the internal mechanics.

1. Find the boundaries where knowledge stops

Like the shops with separate notebooks, each participant owns only the information it can observe. Orders can know that it sent a payment request without knowing whether Payments committed it. This is partial failure: some participants or network paths work while others do not. A failed function call within one process and an unanswered network call have different meanings.

Write a small failure inventory for each arrow: request never arrives, server fails before committing, server commits then fails before replying, or reply arrives after the caller gives up. Serialization also matters: a request must carry an explicit operation identifier and versioned fields rather than relying on shared memory. The boundary deserves its own timeout, authentication context, and observable correlation ID.

2. Bound waiting without pretending uncertainty disappeared

A person stops waiting outside a shop at closing time even if the cook is still working. A timeout similarly bounds the caller's wait; it does not prove cancellation or failure. Give the complete checkout an end-to-end deadline, then allocate smaller budgets to downstream work. A chain of independent ten-second waits can exceed the user's total budget.

If a deadline expires, store or return a pending operation reference where the business permits it. Distinguish a definitive rejection from an unknown result. Cancellation is best-effort unless the protocol and owner provide a stronger guarantee. Measure latency distributions, queue time, and dependency-specific errors; averages alone hide the slow tail that customers actually encounter.

3. Make a repeated request refer to the same business action

If the browser asks twice about the same dinner, the shop should find the original order rather than cook two dinners. Idempotency means repeating the operation has the same intended effect as doing it once. Use a stable key for a particular purchase attempt, persist it with the operation, and reject reuse with incompatible purchase data.

The duplicate check and the side effect must be coordinated at the owning service. Two concurrent requests that both check an empty table before inserting can still double-book. A unique key plus a transaction around the operation record and local state change is one common building block. Keep the stored response or status long enough for the retry window; a new key on every retry defeats the protection.

4. Retry only when doing so can help

Knocking faster does not reopen a crowded shop. Retries consume capacity and can turn a small slowdown into an outage. Retry eligible transient failures with a limited attempt budget, increasing delay, and randomness so clients do not synchronize. An operation with an uncertain outcome is only safe to retry when its protocol makes repetition safe.

Put retry ownership at a deliberate layer. If a browser, gateway, Orders, and a client library each retry three times, downstream attempts can multiply. Stop when the remaining deadline cannot accommodate another attempt. Bound concurrent work and queues as well: rejecting excess load predictably is often more recoverable than retaining an unlimited pile of requests.

5. Decide which facts must agree now

Two shops can display yesterday's opening hours harmlessly, but two cashiers cannot both sell the last reserved seat. Consistency is the agreement the application needs about observed state. Choose it per invariant, not with one slogan for the entire business.

Keep seat allocation inside an owner that can enforce its local constraint. A replicated read model may show a slightly old availability count, so final reservation must recheck authoritatively. Across owners, a multi-step workflow can use durable progress, retries, and business compensation such as releasing an unpaid reservation. Compensation is another business action that can also fail; it is not a magical rewind. During a partition, some operations may deliberately refuse progress rather than violate a required invariant.

6. Reconstruct the story after the request finishes

A receipt number lets every shop discuss the same dinner later. Correlation IDs, structured events, and traces let engineers connect a distributed operation. They complement, rather than replace, durable business state. Logs showing that a request was sent are not proof that its effect committed.

Record meaningful transitions such as requested, reserved, payment-pending, confirmed, and rejected. Reconciliation compares recorded intent with authoritative outcomes after interruptions. Test failures between each pair of steps, including a lost reply after a successful commit. The aim is not that every dependency always works; the aim is that the system preserves its stated business promise and can explain uncertain outcomes.

⚠️ Common Pitfalls, Bugs & What-If Scenarios

Treat a failure as a story: start with what a user observes, trace the boundary that failed, and choose a prevention that addresses the cause.

Charged twice after a timeout

Symptom: A customer sees two payment effects after pressing retry.

Root Cause: Each retry became a new business action, or duplicate checking was separate from committing the effect.

Fix/Prevention: Carry one operation key through retries, enforce uniqueness at the owner, and expose status lookup for unknown results.

A slow dependency overwhelms everyone

Symptom: Healthy endpoints become slow while retry traffic and queues grow.

Root Cause: Unbounded waiting and retries amplify load instead of limiting it.

Fix/Prevention: Use end-to-end deadlines, bounded queues/concurrency, and one deliberate retry owner with backoff and jitter.

Two buyers get the last seat

Symptom: A cached availability page allowed two reservations to be confirmed.

Root Cause: A stale read model was treated as an authoritative constraint check.

Fix/Prevention: Enforce reservation uniqueness at the authoritative owner and design the user flow to handle a failed final reservation gracefully.

🧠 Active Recall & Mastery Check

Summarize this in your own words

Explain the opening analogy, trace the worked example, and name one condition that would change your architectural decision. Try answering before opening the cards.

A payment call times out. What do you know, and what do you not know?

You know the caller did not receive a usable reply within its budget. You do not know whether the request arrived, whether payment committed, or whether a reply was lost. Query the durable operation or repeat the same safely deduplicated action; do not assume failure and create an unrelated charge.

Why is checking for an existing operation before inserting not enough?

Two concurrent handlers can both observe absence. The owning service needs a uniqueness/concurrency mechanism that coordinates the operation record and its local effect. An atomic local transaction and unique operation key are a typical combination; the exact protocol must also cover failures after external effects.

Which can be stale: a seat-count display or the final seat-allocation decision?

The display may be stale if the interface explains availability can change. The final allocation must enforce the no-double-booking invariant at its authority. Separating read convenience from write correctness avoids forcing every browse operation into expensive coordination.

What changes when four layers all retry independently?

Attempts can multiply and consume the very capacity needed for recovery. Assign retry ownership, carry an overall deadline, bound attempts and concurrency, and retry only when the operation and failure class permit it. More attempts are not automatically more reliability.

Tricky & Most-Asked Interview Scenarios

Practice making a decision under a concrete production constraint. Open each answer, explain your reasoning aloud, then rate your confidence. The budgets and organizations below are author-created assumptions.

A payment times out after a possible charge. How do you retry without charging twice?

The Scenario & Constraint

Think of losing a receipt after paying: no receipt does not mean no payment. A checkout waits two seconds for a charge, times out, and the customer immediately retries. The provider may already have committed. You must avoid a second charge while still letting the customer discover the outcome. What will you do and why?

The Direct Answer & Architectural Decision

Treat the timeout as unknown, not rejected. Persist a purchase operation with one stable idempotency key before contacting the provider, and reuse that key for retries of the same amount, currency and customer. The effect owner must atomically bind the key to the effect; a caller-side check alone cannot prevent concurrent duplicate charges.

Return a pending operation reference when the outcome is uncertain. Query the provider by that identity or reconcile its authoritative callbacks, then publish a confirmed or rejected result. Bound retries and retain deduplication records for the documented retry window; reject reuse of the key with different purchase data.

Key Trade-Offs & Follow-Up Traps

You gain recoverable outcomes and duplicate protection at the cost of durable operation state, reconciliation and delayed confirmation. An alternative is a synchronous-only checkout that stops accepting work on timeout, but it still needs a way to reconcile a charge that already happened.

Follow-up trap: generating a new key on each attempt creates new purchases. If the provider has no idempotency or lookup capability, do not claim exactly-once charging: stop automatic ambiguous retries, retain the unresolved operation and reconcile before allowing a fresh charge. A later genuine purchase needs a new identity.

Three dependency layers retry during overload. How do you stop the recovery traffic becoming an outage?

The Scenario & Constraint

Imagine everyone repeatedly redialing a busy shop. Three layers each permit up to three attempts, so one original call can produce 27 downstream attempts. Latency is rising and callers have a one-second overall deadline. Extra attempts consume the capacity the dependency needs to recover. What will you change first and why?

The Direct Answer & Architectural Decision

Measure downstream attempt volume separately from user traffic, shed excess load and temporarily reduce retries. Choose one deliberate retry owner for the operation rather than multiplying independent policies. Retry only eligible transient failures when the remaining deadline and retry budget permit it; back off with jitter so clients do not wake together.

Propagate the end-to-end deadline, cap concurrency and queues, and require safe repetition for mutating operations. Test a degraded dependency under load, watching successful work, saturation and recovery time rather than celebrating a lower error count produced by more attempts.

Key Trade-Offs & Follow-Up Traps

You preserve recovery capacity and predictable latency, while some requests fail earlier instead of receiving extra chances. A small bounded queue or cached read is a viable alternative for selected workloads; it is not a replacement for controlling overload.

Follow-up trap: increasing every timeout holds scarce connections longer and can worsen saturation. If traffic is an asynchronous job stream with a long completion window, move retries into a durable worker schedule with controlled concurrency rather than applying the interactive one-second policy unchanged. The deadline belongs to the user operation, not independently to each hop.

A region is partitioned. Can cart edits stay available while the final stock unit remains safe?

The Scenario & Constraint

Two disconnected shops may write wish lists, but they cannot both promise the same last item without an allocation rule. A regional network partition interrupts coordination. Customers should still edit carts, yet confirmed purchases must never oversell a unique ticket. What do you allow in each region and why?

The Direct Answer & Architectural Decision

Separate cart intent from authoritative allocation. Accept reversible cart changes locally with version metadata and a defined merge policy. Confirm the ticket only through an owner or coordination mechanism that can enforce the single-unit invariant; a region unable to reach that authority must return pending or temporarily unavailable for purchase.

Make the distinction visible: adding an item is not a reservation. After connectivity returns, merge permitted cart changes, revalidate stock and resolve pending operations using stable identities. If you preallocate disjoint regional stock rights, enforce those rights locally rather than letting both regions sell the full inventory.

Key Trade-Offs & Follow-Up Traps

Cart availability improves while strict purchase availability is deliberately reduced. Preallocated quotas are an alternative that preserves local sales within each region's rights, but can strand unused capacity and complicate rebalancing.

Follow-up trap: eventual reconciliation cannot undo the fact that two customers were promised the same unique seat. If the item becomes replenishable stock and the business explicitly accepts backorders, you may allow provisional orders with compensation and clear customer terms. That is a changed business guarantee, not evidence that a strict invariant was preserved during the partition.

A successful profile update is followed by an old value. Which read guarantee will you add?

The Scenario & Constraint

You change a name at one desk, then ask another desk whose notebook has not caught up. A profile API acknowledges a committed update, but the next read hits a lagging replica and shows the old name. Browsing other people's profiles can be slightly stale; seeing your own edit revert is unacceptable. What will you do and why?

The Direct Answer & Architectural Decision

Provide read-your-writes behavior for the editing session instead of making every read globally synchronous. Return an authoritative version with the update. Route the subsequent session read to a source known to include that version, or wait up to a bounded budget for a replica to reach it before falling back to the authority.

Trace cache versions as well as database replication: a fresh database read can still be hidden by an old response cache. Invalidate or version the relevant cache entry, and test a delayed replica, region failover and session movement. Do not acknowledge a write before its required durability condition is satisfied.

Key Trade-Offs & Follow-Up Traps

You improve the editing experience with less coordination than a universal latest-value guarantee, but carry session/version metadata and may increase authority load or latency. Reading all profile traffic from the writer is a simpler alternative when its capacity is adequate.

Follow-up trap: a fixed sleep only guesses replication delay. If a legal-name decision must be current for every observer, session consistency is insufficient; move that decision to an authoritative, appropriately coordinated read and accept its availability/latency cost. Define what happens when the required version cannot be reached within the budget.

Two offline devices edit the same record. Will last-write-wins preserve what the user intended?

The Scenario & Constraint

Two children alter copies of the same shopping list while apart. One adds milk; the other removes bread. A server later receives both snapshots, and device clocks may be wrong. You must preserve meaningful changes without silently resurrecting a deliberate deletion. What conflict rule will you choose and why?

The Direct Answer & Architectural Decision

Model the operations and their business meaning before choosing a merge. Attach version information so the server can detect concurrent edits rather than pretending arrival order represents causality. For a cart, consider item-level add/remove operations with explicit deletion semantics; for a sensitive address change, surface a conflict or require an authoritative choice.

Persist enough causal or revision information to distinguish a retry from a new edit, and make merges deterministic and testable. Explain any conflict to the user when intent cannot be inferred safely. The original Dynamo design is evidence for application-assisted reconciliation, not a universal recipe for every data type.

Key Trade-Offs & Follow-Up Traps

Semantic merging preserves more intent than overwriting whole snapshots, but increases metadata, testing and domain-specific rules. Last-write-wins is a viable cheaper alternative for replaceable preferences when the business accepts lost concurrent updates and understands clock/ordering limitations.

Follow-up trap: unioning every list makes removals disappear. If the record is a bank balance or exclusive allocation rather than a shopping list, merging arbitrary edits may violate an invariant. Send authoritative commands with concurrency checks or serialize those decisions instead of transferring a cart merge policy to money.

A replica misses heartbeats but may still be alive. When is failover safe?

The Scenario & Constraint

A friend who does not answer may be busy, not gone. A replica stops responding during a network slowdown, while some clients can still reach it. An operator wants to promote another writer immediately. The system must not allow conflicting authoritative writes. What will you check and why?

The Direct Answer & Architectural Decision

Treat timeout-based failure detection as suspicion. Investigate network reachability, process health and replication progress separately, while enforcing a bounded client deadline. If a single-writer design fails over, promotion must follow its authority protocol, such as quorum-backed leadership with fencing tokens that the storage layer checks.

Stop or fence the old writer's authority before relying on the new one; merely removing it from one load balancer is insufficient when old connections remain. Monitor lag and explicitly choose the permitted recovery point. Exercise a partition where the old process is alive, not only a clean process crash.

Key Trade-Offs & Follow-Up Traps

Conservative promotion protects consistency but can lengthen unavailability. A multi-writer, conflict-resolving design is an alternative for data whose operations can be merged; it changes semantics and does not remove coordination requirements for strict invariants.

Follow-up trap: aggressive heartbeats improve detection speed but do not prove death. If the workload is read-only and stale reads are acceptable, you can reroute reads sooner without granting new write authority. If the old writer cannot be fenced and a strict single-writer guarantee is mandatory, stop writes rather than silently create split brain.

Real-world impact

For a ticketing service, the useful outcome is a purchase whose identity, seat claim, payment outcome, and recovery path remain understandable after failures. Distribution is a tool for particular scale and ownership needs. Its fundamental engineering work is drawing boundaries, choosing invariants, limiting uncertainty, and making interrupted work recoverable.
